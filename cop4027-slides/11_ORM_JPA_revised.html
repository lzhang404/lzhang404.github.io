From JDBC to ORM

What JDBC Made Us Write

Our JDBC Repository translates every row into a TaskItem by hand.

private TaskItem mapTask(ResultSet rows) throws SQLException {
    return new TaskItem(
            rows.getLong("id"),
            rows.getString("title"),
            rows.getBoolean("done"));
}

  • Write the SQL for each operation.

  • Bind Java values into a PreparedStatement.

  • Read columns from a ResultSet and build objects.

Answer: the table, every SQL string that lists columns, the binding code, and mapTask.

Mapping TaskItem as an Entity

Why Can't TaskItem Stay a Record?

JPA creates entity objects itself and changes their fields later, so it needs an ordinary class.

// Spring Core lecture
public record TaskItem(long id, String title, boolean done) { }

// JPA version
@Entity
public class TaskItem { /* fields, constructors, methods */ }

  • A record is final, and its fields cannot change.

  • An entity is a class whose objects JPA stores as table rows.

  • The name and meaning of TaskItem stay the same.

Map the Entity

Annotations tell JPA which table the class uses and which field is its identity.

@Entity
@Table(name = "task_items")
public class TaskItem {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private boolean done;
}

  • @Entity marks the class as an entity.

  • @Table names the table; without it, the name comes from the class.

  • By default, each field maps to a column of the same name.

Give JPA a Constructor

When JPA loads a row, it calls a no-argument constructor and then fills in the fields.

protected TaskItem() {
    // JPA uses this constructor.
}

public TaskItem(String title) {
    this.title = title;
    this.done = false;
}

  • The no-argument constructor can be protected, so application code does not use it.

  • The class and its persistent fields cannot be final.

  • Application code creates new tasks with the title constructor.

Identity Comes from the Database

The id links an entity to its row, and the database chooses it when the row is inserted.

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

  • @Id marks the identity field.

  • GenerationType.IDENTITY lets the database generate the key.

  • A new TaskItem has no id until it is saved.

Check: Why is the field Long rather than long?

Answer: before saving, there is no id yet. Long can be null; long cannot.

Map a Column, Keep a Rule

A column setting describes the database; an entity method protects the object.

@Column(nullable = false, length = 100)
private String title;

public void rename(String title) {
    if (title == null || title.isBlank()) {
        throw new IllegalArgumentException("Title required");
    }
    this.title = title.trim();
}

  • @Column describes the column: NOT NULL, at most 100 characters.

  • A NOT NULL column still accepts a blank title such as " ".

  • rename(...) rejects blank titles before they reach the database.

Managed Entities and Transactions

EntityManager

EntityManager is the JPA object that stores, loads, and removes entities.

TaskItem item = new TaskItem("Review ORM");
entityManager.persist(item);                // store a new row

TaskItem found =
        entityManager.find(TaskItem.class, item.getId());   // load by id

entityManager.remove(found);                // delete the row

  • We call methods on objects; JPA writes the SQL.

  • Write operations must run inside a transaction.

The Persistence Context

JPA keeps track of the entities it has loaded or stored. This set is the persistence context.

database row  ↔  managed TaskItem object
                        ↑
                  EntityManager

  • An entity in the persistence context is managed.

  • Each managed object stands for one row.

  • JPA remembers each managed object's loaded values so it can spot changes.

Managed Changes Are Saved at Commit

Inside a transaction, changing a managed entity is enough. JPA writes the UPDATE for us.

// inside a transaction
TaskItem item = entityManager.find(TaskItem.class, id);
item.setDone(true);
// at commit, JPA sees the change and sends an UPDATE

  • Finding changed entities at commit is called dirty checking.

  • Commit makes the change permanent; rollback cancels it if something fails.

  • With JDBC, we wrote the UPDATE ourselves.

Entity States

Only managed entities are tracked. An object moves between four states.

StateMeaning

New

Created with new; JPA does not know it yet.

Managed

In the persistence context; changes are tracked.

Detached

Was managed, but is no longer tracked, for example after the transaction ends.

Removed

Marked for deletion at commit.

A Repository with EntityManager

Our Repository can use JPA instead of JDBC. The rest of the app still calls the same Repository methods.

public List<TaskItem> findAll() {
    return entityManager
            .createQuery("select t from TaskItem t order by t.id", TaskItem.class)
            .getResultList();
}

public void add(String title) {
    entityManager.persist(new TaskItem(title));
}

  • The query is JPQL: it names the entity and its fields, not the table.

  • There is no ResultSet and no mapping method.

  • Spring Data JPA will remove even this code.

Takeaways: Entities and Transactions

  • ORM maps Java objects to table rows. JPA is the Java standard, and Hibernate implements it.

  • TaskItem becomes an entity class with @Entity, an @Id, and a no-argument constructor.

  • Managed entities are tracked in the persistence context.

  • Inside a transaction, changes to managed entities are written at commit.

Spring Boot Starts the Context

Spring Boot replaces the AppConfig and context setup from the Spring Core lecture.

@SpringBootApplication
public class TaskApp {
    public static void main(String[] args) {
        SpringApplication.run(TaskApp.class, args);
    }
}

  • @SpringBootApplication turns on component scanning and auto-configuration.

  • The spring-boot-starter-data-jpa dependency brings Spring Data JPA and Hibernate.

  • Auto-configuration creates the database, JPA, and transaction beans for us.

Tell Boot Where the Database Is

Boot reads the database settings from application.properties.

spring.datasource.url=jdbc:h2:file:./data/tasksdb
spring.datasource.username=sa
spring.datasource.password=

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true

  • The datasource lines say which database to use; H2 runs inside the app.

  • ddl-auto=update lets Hibernate create and update tables during development.

  • show-sql=true prints the SQL that Hibernate generates.

What Spring Data JPA Adds

We declare a Repository interface. Spring creates the class that implements it.

public interface TaskRepository
        extends JpaRepository<TaskItem, Long> {
}

  • TaskItem is the entity type; Long is its id type.

  • Spring creates the implementation when the application starts.

  • Hibernate still does the actual database work.

JpaRepository already declares the operations most Repositories need.

Read One Task Item

findById returns an Optional because the id might not exist.

TaskItem item = repository.findById(id)
        .orElseThrow(() ->
                new IllegalArgumentException("Task item not found"));

  • The Repository performs the lookup.

  • Application code decides what a missing task means.

Queries from Method Names

Spring Data reads a method's name and builds the query from it.

public interface TaskRepository
        extends JpaRepository<TaskItem, Long> {
    List<TaskItem> findByDone(boolean done);

    List<TaskItem> findByTitleContainingIgnoreCase(String text);
}

  • findByDone(false) finds unfinished tasks.

  • findByTitleContainingIgnoreCase("jpa") searches titles.

  • If a name gets too long, write the query with @Query instead.

Service Layer and Transactions

Where Do Task Operations Go?

We move reusable task operations into a TaskService, so a web Controller can use them in the next lecture.

JavaFX Controller → TaskModel → TaskService → TaskRepository
Web Controller ───────────────→ TaskService → TaskRepository

  • TaskModel keeps the JavaFX-facing state: the list the View shows.

  • TaskService owns task rules and transactions.

  • Both belong to the application tier; the Service is not a new tier.

Give the Service a Repository

The Service gets its Repository through constructor injection, as in the Spring Core lecture.

@Service
public class TaskService {
    private final TaskRepository repository;

    public TaskService(TaskRepository repository) {
        this.repository = repository;
    }
}

  • Spring passes the generated TaskRepository to the constructor.

  • The class is not final: Spring subclasses it to add transactions.

Add a Task Item

The Service checks the task rule, then asks the Repository to save.

@Transactional
public TaskItem addTaskItem(String title) {
    if (title == null || title.isBlank()) {
        throw new IllegalArgumentException("Title required");
    }
    return repository.save(new TaskItem(title.trim()));
}

  • @Transactional runs the whole method in one transaction.

  • The returned TaskItem now has a database-generated id.

Change a Managed Task Item

Inside a transaction, loading and changing the entity is enough. There is no save call.

@Transactional
public void setDone(Long id, boolean done) {
    TaskItem item = repository.findById(id)
            .orElseThrow(() -> new IllegalArgumentException("Task item not found"));
    item.setDone(done);
}

  • findById returns a managed entity.

  • At commit, dirty checking writes the UPDATE.

Why Put the Transaction in the Service?

One Service method is one task operation, so it should succeed or fail as a unit.

  • Commit completes the operation; a runtime exception normally rolls it back.

  • The transaction keeps loaded entities managed while the method changes them.

Check: What happens if setDone has no @Transactional?

Answer: findById runs in its own short transaction, so item is already detached when setDone(done) runs. The change is never saved.

Read-Only Operations

An operation that only reads can use a read-only transaction.

@Transactional(readOnly = true)
public List<TaskItem> findAllTaskItems() {
    return repository.findAll(Sort.by("id"));
}

  • readOnly = true says the method writes nothing, so Hibernate can skip change tracking.

  • TaskModel gets one simple method to call.

TaskModel Calls the Service

The JavaFX side barely changes: TaskModel calls the Service instead of the Repository.

public void addTask(String title) {
    service.addTaskItem(title);
    reload();
}

private void reload() {
    tasks = List.copyOf(service.findAllTaskItems());
}

  • The title rule now lives in the Service, not in TaskModel.

  • TaskController still talks only to TaskModel.

Testing and Common Mistakes

Test the Repository

A Repository test checks the mapping against a real database.

@DataJpaTest
class TaskRepositoryTest {
    @Autowired
    TaskRepository repository;

    @Test
    void savesAndFindsTaskItem() {
        TaskItem saved = repository.save(new TaskItem("Review JPA"));
        TaskItem found = repository.findById(saved.getId()).orElseThrow();
        assertEquals("Review JPA", found.getTitle());
    }
}

  • @DataJpaTest starts only the JPA part of the app, with an in-memory database.

  • Each test is rolled back, so tests do not affect each other.

  • Test the title rule through TaskService separately.

Common Mistakes

  • Using a record or a final class as an entity.

  • Forgetting the no-argument constructor.

  • Changing a detached entity and expecting an UPDATE.

  • Making TaskService final, so Spring cannot add transactions.

  • Forgetting that findById returns an Optional.

  • Writing very long derived query names.

  • Putting task rules in the Controller or the Repository.

Summary

Key Takeaways

  • ORM maps objects to rows; JPA is the standard, and Hibernate implements it.

  • An entity needs @Entity, an @Id, and a no-argument constructor.

  • Managed entities are tracked, and their changes are written at commit.

  • Spring Data JPA creates Repository implementations from interfaces.

  • TaskService owns task rules and transaction boundaries.
