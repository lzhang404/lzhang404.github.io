Module 6: Expressions, Assignment, and Control Flow

Precedence vs evaluation order

  • Precedence decides grouping in the parse tree

  • Evaluation order decides what runs first at runtime

  • These are different ideas

  • Evaluation order matters when expressions have side effects

1 + 2 * 3
groups as:
1 + (2 * 3)

Evaluation order across languages

  • TypeScript and Python usually specify evaluation order clearly

  • C often leaves subexpression order unspecified

  • Do not rely on side-effect order unless the spec guarantees it

int y = first() + second();

Short-circuit evaluation

  • A && B: if A is false, B is not evaluated

  • A || B: if A is true, B is not evaluated

    • In many languages, these operators do not always return a boolean (JS/TS, Python)
    • In others, they return boolean-only results (Java, C#, Go, Rust)

  • This is control flow inside expressions

  • Usage:

    • Guarding null checks before field access

    • Default values in JS/TS and Python

      • 
u !== null && u.name.length > 0

    • But avoid hiding important side effects in boolean-looking expressions

Defaults: || vs ??

  • || uses the default for falsey values

  • ?? uses the default only for null or undefined

  • Falsy values: values that behave like false in boolean context
  • Nullish values: only null and undefined

Assignment models

  • Ask: is assignment a statement, an expression, or both?

  • C and JavaScript/TypeScript: assignment can produce a value

  • Python: assignment is normally a statement

  • This affects what code is allowed inside larger expressions

  • Classic assignment bug

    • In C, if (x = 0) assigns 0, then tests false

    • Often the programmer meant x == 0

    • Python avoids this specific bug by not allowing normal assignment there

Chained assignment and aliasing

  • Chained assignment is usually fine for immutable values

  • It is risky for mutable objects

  • Example in Python: a = b = []

  • Then mutating one name affects the same shared object

Selection constructs

  • if / else: general branching

  • switch: branch by discrete cases

  • match / pattern matching: branch by value structure

  • Know that C switch fall-through is the default

Iteration, iterators, generators

  • while, counter-style for, and foreach-style loops are different surface forms

  • Python for is iteration over an iterator

  • TypeScript for...of iterates values

  • Generators use yield to produce one value at a time

Module 7: Subprograms, Parameters, and Closures

Subprograms as contracts

  • A caller needs more than just a signature

  • A contract includes inputs, outputs, effects, errors, and timing

  • Especially important for async code and mutation

  • Signature vs Contract

    • Signature: parameter profile and return type

    • Contract: signature plus behavior the caller can rely on

    • Effects, failure rules, and timing are part of the real contract

Referencing environment

  • The referencing environment is all bindings a subprogram can use while running

  • This includes parameters, locals, and captured nonlocals

  • It answers: what names have meaning here?

Activation records and call stack

  • An activation record (stack frame) represents one active call

  • Typical contents: parameters, locals, temporaries, return info

  • Recursion works because each call gets fresh bindings

Parameter Association Vs Passing

  • Parameter association: how arguments match parameters

  • Passing method: what gets transmitted

  • Parameter association

    • Positional association

    • Keyword association

    • Defaults

    • Varargs / rest parameters

  • Passing Modes

    • in: data flows into the subprogram

    • out: data flows back to the caller

    • in out: bidirectional

    • These describe intent, not always exact implementation

Call-by-sharing

  • Common in Java, Python, JS/TS objects

  • The callee receives a copy of a reference value

  • Mutating the shared object is visible to the caller

  • Reassigning the parameter does not change the caller variable

Two kinds of aliasing

  • Variable aliasing: two names refer to the same variable slot

  • Object aliasing: two names refer to the same heap object

  • Pass-by-reference creates variable aliasing

  • Call-by-sharing creates object aliasing only

Dynamic invocation

  • Dynamic invocation = which subprogram runs is chosen at runtime./p>

  • Common mechanisms:

    • First-class functions: functions can be stored/passed/returned
    • Callback: function passed to run later

Deep vs shallow binding

  • Deep binding: use the environment from function creation time

  • Shallow binding: use the environment from call time

  • Closures normally use deep binding

    • A closure captures variables from surrounding lexical scope
    • This lets returned functions keep access to old bindings

Closures in practice

  • Stale state: A callback may observe an old snapshot rather than the latest intended state
  • Retention: If a closure captures a large object and the closure stays reachable, that object stays alive too
  • Common use patterns: memoization, debounce, dependency injection

Module 8: Object-Oriented Programming and Modules

Objects, classes, invariants, and encapsulation

  • Objest: state behavior at runtime

  • Class: blueprint defining fields and methods

  • Invariant: a condition that should always hold for an object

  • Encapsulation: hide representation details, protect invariants, expose controlled operations

Inheritance vs composition

  • Inheritance:

    • models is-a relationship
    • subtype relationship
    • supports polymorphism
  • Composition:
    • models has-a relationship
    • object contains or delegates to another object
    • often better for combining features like logging/caching/retry

Dynamic dispatch

  • Dynamic dispatch
    • Dynamic dispatch chooses a method body at runtime based on the receiver's actual class

    • This is the core of subtype polymorphism

    • One method call can work across many subclasses

  • Statics vs dynamic type
    • Static type: what compiler sees
    • Dynamic type: what object really is at runtime

    • Compile time decides whether a method call is allowed

    • Runtime decides which override runs

  • C++: runtime dispatch requires virtual keyword

Overridding vs Overloading vs Generics

  • Overriding:

    • subclass replaces inherited method body
    • chosen at runtime

  • Overloading:

    • same method name, different parameter lists
    • chosen at compile time

  • Generics / templates:

    • one implementation works across many types
    • compile-time abstraction over type

Interfaces vs abstract classes

  • Interface:

    • contract only
    • minimal coupling
    • multiple implementations
    • good for extension points and testing
  • Abstract class
    • partial implementation + contract
    • can include shared fields, constructors, helper methods
    • good for closely related family of types

Visibility across languages

  • Java: public, protected, package-private, private

  • TypeScript: access modifiers and exports

  • Python: mostly conventions such as underscore names

  • C++: class access control plus headers/source files and namespaces

Module 9: Functional Programming

Main viewpoint of functional programming

  • Imperative programming emphasizes state changes

  • Functional programming emphasizes

    • computing values from values
    • controlling effects
    • organizing code around transformations

  • The goal is easier reasoning, reuse, and testability

Referential transparency

  • An expression is referentially transparent if it can be replaced by its value without changing behavior

  • This enables local reasoning about code

  • Effects break referential transparency

Pure functions and immutability

  • Pure functions

    • A pure function returns the same result for the same inputs

    • It does not perform observable side effects

    • Its behavior depends only on arguments

  • Immutability

    • Immutable values are not updated in place

    • Programs compute new values instead of changing old ones

    • This reduces hidden interaction through shared mutable state

Core toolkit: map, filter, fold

  • map: transform each element

  • filter: keep elements that satisfy a predicate

  • fold / reduce: combine many values into one

  • These package common recursion patterns

Composition, currying, partial application

  • Composition builds larger behavior from small functions

  • Currying turns a multi-argument function into chained one-argument functions

  • Partial application produces specialized functions from general ones

Recursive data and recursion

  • FP often uses recursive data such as lists and trees

  • Structural recursion follows the shape of the data

  • Base case plus recursive case is the standard pattern

  • fold

    • A fold abstracts a common recursive pattern

    • You provide a base value and a combining rule

    • The library handles the traversal

Algebraic data types and pattern matching

  • ADTs represent structured cases explicitly

    • Product types combine data

    • Sum types represent a choice among cases

    • Examples:
      • Maybe/Option: value present or absent
      • Result/Either: sucess or failure. failure may carry information

  • Pattern matching branches clearly on structure

    • inspect which case of a value you have
    • clearer than manual tag checks with nested conditionals
    • pairs naturally with ADTs

Strict vs lazy evaluation

  • Strict:

    • arguments computed before function body uses them
    • common in JS, TS, Python, Java, C

  • Lazy:

    • computation delayed until needed
    • Laziness can avoid unnecessary work and support infinite structures
    • but can make performance and reasoning less obvious

Generators as a demand-driven idea

  • Even strict languages can simulate laziness with generators/iterators.

  • Python and TypeScript generators produce values only when asked

  • They are not full lazy languages, but they illustrate demand-driven computation

Functional style in mainstream languages

  • Use pure transformations where possible

  • Represent state changes as new values

  • Use map/filter/reduce and reducer-style state transitions

Why Haskell matters

  • It makes FP ideas very visible

  • Purity is the default

  • Immutability, higher-order functions, ADTs, and laziness are central

  • Types make effect boundaries easier to see

  • Haskell participation lab

FP and concurrency preview

  • Immutability reduces shared-state bugs

  • Pure functions are easier to reason about independently

  • This is one reason FP ideas matter beyond Haskell itself
