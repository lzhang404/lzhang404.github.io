Why Reflection?

Normal Calls Are Best When Choices Are Fixed

// Direct code names the class and method at compile time.
Car car = new Car("red");
System.out.println(car.describe("A"));

  • The compiler knows the class, constructor, and method.

  • The compiler can check spelling, parameter types, and return types.

  • This is simpler and safer when the exact class is known in advance.

Reflection should not replace ordinary Java calls without a runtime-discovery reason.

When Direct Calls Become a Problem

Suppose the application supports plugins chosen from configuration.

Plugin plugin;

if (name.equals("email")) {
    plugin = new EmailPlugin();
} else if (name.equals("sms")) {
    plugin = new SmsPlugin();
} else {
    throw new IllegalArgumentException("Unknown plugin");
}

  • Every new plugin requires editing this loader.

  • The main application must know every implementation class.

  • The loader must be recompiled when new choices are added.

The Runtime-Discovery Requirement

A more flexible plugin system separates the fixed contract from the runtime choice.

  • Known when writing the loader
    • Plugin interface, no-argument constructor rule, run() method
  • Chosen while running
    • EmailPlugin, SmsPlugin, a new plugin added later

Reflection is useful when the program knows the rules, but the exact implementation is selected later.

What Reflection Does

Reflection lets a running Java program examine metadata about loaded types and use their existing members.

  • Find a type selected by name at runtime.

  • Inspect its constructors, methods, fields, interfaces, and annotations.

  • Create an object through a discovered constructor.

  • Invoke a discovered method.

Reflection does not remove all knowledge. It fills in the part that is chosen while the program is running.

Reflection Still Needs a Contract

Good reflective design:

runtime class or method
    -> validate known rules
    -> construct or select the allowed member
    -> return to normal Java calls when possible

  • A plugin loader can require a known Plugin interface.

  • A test or command runner can validate which methods are eligible.

  • Invalid runtime metadata should produce a clear error.

What Reflection Is Not

  • It is not a better replacement for every method call.

  • It is not checked as strongly by the compiler.

  • It may fail at runtime because of missing classes, wrong signatures, or access rules.

  • It is not a security boundary by itself.

Use reflection only when runtime discovery is part of the requirement.

Class Metadata

Getting a Class Object

Class<?> represents a Java type, not an ordinary instance of that type.

// Type is already known in the source code.
Class<Car> knownType = Car.class;

Car car = new Car("red");
// Ask an existing object for its actual runtime type.
Class<?> actualType = car.getClass();

// The class name can come from configuration or another runtime source.
Class<?> runtimeType = Class.forName("example.Car");

  • Car.class is checked by the compiler.

  • getClass() starts from an object that already exists.

  • Class.forName(...) is useful when the class name is chosen at runtime.

  • An unknown runtime name causes ClassNotFoundException.

  • Example: reflection/MetadataDemo.java

Example: Car

package example;

public final class Car {
    private final String color;

    public Car(String color) {
        this.color = color;
    }

    public String describe(String prefix) {
        return prefix + " " + color + " car";
    }
}

We will use this small class to see what reflection can discover and use at runtime.

  • Example: reflection/Car.java

The Class object is the starting point for asking questions about a runtime type.

Inspecting Members

Method[] publicMethods = type.getMethods();
Method[] declaredMethods = type.getDeclaredMethods();

Constructor<?>[] constructors = type.getDeclaredConstructors();
Field[] fields = type.getDeclaredFields();
  • getMethods(): Public methods available through the type, including inherited public methods.
  • getDeclaredMethods(): Methods declared directly by this class, including non-public methods.

The same declared idea applies to constructors and fields. Discovery does not automatically grant access.

  • Example: reflection/MetadataDemo.java

Creating an Object at Runtime

Once the program has a runtime Class object, it can select a constructor and create an object.

// Find a public constructor that accepts one String.
Constructor<?> constructor =
    type.getConstructor(String.class);

// Call that constructor at runtime.
Object car = constructor.newInstance("red");

  • The parameter types identify which constructor to use.

  • The new object really has runtime type Car.

  • The reflective result is represented as Object until the program validates and narrows the type.

Finding and Calling One Method

// Name + parameter types identify one overload.
Method method = type.getMethod("describe", String.class);

System.out.println(method.getReturnType().getSimpleName());
for (Class<?> parameterType : method.getParameterTypes()) {
    System.out.println(parameterType.getSimpleName());
}

// First invoke argument is the receiver object.
Object result = method.invoke(car, "A");
System.out.println(result);  // A red car

  • The method name alone is not enough because Java methods can be overloaded.

  • The first argument to invoke is the object receiving the call.

  • The remaining arguments are passed to the method.

  • Example: reflection/RuntimeInvocationDemo.java

Safe Boundary: Return to Normal Java

Class<?> candidate = Class.forName(className);

// Require the runtime class to follow the Plugin contract.
if (!Plugin.class.isAssignableFrom(candidate)) {
    throw new IllegalArgumentException("Not a Plugin: " + className);
}

Class<? extends Plugin> pluginType =
    candidate.asSubclass(Plugin.class);

Plugin plugin = pluginType.getConstructor().newInstance();
plugin.run();  // Normal Java call again.

Reflection selects and validates the implementation. The rest of the program uses the normal Plugin interface.

  • Example: reflection/PluginLoaderDemo.java

Direct calls let the compiler catch more mistakes before execution; reflection moves some checks to runtime.

Annotations as Metadata

Why Mark Methods?

Reflection can discover many methods, but a framework usually needs only selected methods.

public final class CalculatorTests {
    public void helperMethod() {
        // Setup code, not a test.
    }

    @Test
    public void addingTwoNumbersWorks() {
        // The test runner should execute this method.
    }
}

  • Reflection can discover both methods.

  • @Test marks the method that has the special role.

  • The test runner reads the annotation and decides what to execute.

Who Reads Annotations?

AnnotationWho uses it?
@OverrideThe compiler checks that a method really overrides another method.
@DeprecatedThe compiler and tools warn about discouraged APIs.
@SuppressWarningsThe compiler suppresses selected warnings.
Custom runtime annotationYour program or framework can read it through reflection.

Reflection works without annotations. An annotation matters only when a compiler, tool, framework, or program reads it.

Defining a Runtime Annotation

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

//@Rentention answers how long does the annotation remain availble?
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD) //@Target answers where may the annotation appear?
public @interface Command {
    String value();
}

  • @interface declares an annotation type.

  • String value() defines one required metadata property.

  • @Command("start") stores "start" as that value.

  • Example: reflection/Command.java

Retention and Target

Retention policyAvailability
SOURCESource code only.
CLASSStored in the class file but not normally exposed through reflection.
RUNTIMEStored in the class file and available through reflection.

Marking Allowed Commands

public final class CarCommands {
    @Command("start")
    public void startCarEngine() {
        System.out.println("Car started");
    }

    public void resetInternalState() {
        System.out.println("Internal state reset");
    }
}

  • Reflection can discover both methods.

  • Only startCarEngine() is marked as part of this command system.

  • The external command "start" does not have to match the Java method name.

The annotation is an explicit marker for this runner; it is not a security mechanism.

  • Example: reflection/CarCommands.java

Discover and Run Commands

for (Method method : type.getDeclaredMethods()) {
    // returns the annotation or null 
    Command command = method.getAnnotation(Command.class);
    //command.value() reads the external command name.
    if (command != null && command.value().equals(name)) {
        method.invoke(handler); //runs the selected no-argument method.
        return;
    }
}

throw new IllegalArgumentException("Unknown command: " + name);

Validate Before Running

An annotation says that a method is intended to be a command. The runner should still verify the command contract.

int modifiers = method.getModifiers();

if (!Modifier.isPublic(modifiers)
        || method.getParameterCount() != 0
        || method.getReturnType() != void.class) {
    throw new IllegalStateException(
        "Invalid @Command method: " + method);
}

  • Require public methods.

  • Require no parameters and a void return type.

  • Also reject duplicate command names while building the command list.

  • Example: reflection/CommandRunner.java

What Annotations Do Not Do

  • An annotation does not run a method by itself.

  • An annotation is not required for reflection.

  • An annotation does not prevent other Java code from using reflection.

  • An annotation is metadata that another part of the system chooses to interpret.

The runner controls which annotated methods it accepts and how it uses them.

Summary

Key Takeaways

  • Use direct calls when the class and method are known in advance.

  • Use reflection when the program must discover a type or member at runtime.

  • Class<?> is the starting point for runtime information about a Java type.

  • Reflection can inspect members, create objects, and invoke existing methods.

  • Annotations attach structured metadata that compilers, tools, or programs can read.

  • Keep reflection behind a small validated boundary and return to normal Java types when possible.

Final Mental Model

Reflection:
    discovers and uses code structure while the program is running

Annotation:
    attaches a structured label to part of the code

Runner or framework:
    reads the metadata, validates the rules, and decides what to do

Reflection discovers. Annotations describe. The framework decides.
