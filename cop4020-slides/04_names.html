Names

Names, values, and locations

When we write programs, we work with names and not raw addresses.

  • A name is a word in the source program (x, total, print).

  • A value is the data being represented (42, "hello").

  • A location is a place that can hold a value (stack slot, heap object, address).

Programmers mostly see names. Execution ultimately reads/writes locations.

Names: design issues in languages

Languages must decide how identifiers behave.

  • Allowed characters (letters, digits, underscore, dollar sign, Unicode)

  • Case sensitivity (count vs Count)

  • Keyword reservation (if, while, class)

  • What can be named (variables, functions, types, modules)

Name forms in C, Python, and TypeScript

// C++
int total_sum = 0;
double x2 = 3.14;
// int class = 1;   // not allowed: class is a keyword
# Python
student_name = "Ana"
_max_count = 10
// TypeScript / JavaScript
let totalSum = 0;
const $cacheKey = "users";
// let if = 1; // not allowed: if is a keyword

  • All three are case sensitive.

  • Style conventions differ (camelCase vs snake_case).

  • Keywords are reserved.

What kinds of things get names

  • Variables (locals, globals, parameters)

  • Functions and methods

  • Types and classes

  • Modules or namespaces

A compiler must record more than the spelling: what kind of thing it is and where it belongs.

Bindings and Symbol Tables

Bindings and environments

A binding connects parts of the program description to each other.

  • A name bound to a type (x has type int)

  • A name bound to a storage location (x is stored at some stack slot)

  • A storage location bound to a current value (that slot currently contains 42)

  • A function name bound to code (max refers to some function body)

The environment is the set of bindings currently in effect during execution.

Declaration, initialization, assignment

  • Declaration introduces a name (and often a type).

  • Initialization gives a first value at the same time.

  • Assignment changes a value later.

int x;      // declaration
int y = 0;  // declaration + initialization
y = y + 1;  // assignment

When do bindings happen?

Some bindings happen earlier than others.

  • Language design time:keywords and primitive types exist

  • Compile time: many type checks and stack layout decisions

  • Link/load time: addresses of globals and functions

  • Run time: parameter values, heap allocations, dynamic dispatch

Earlier binding enables more checking and optimization. Later binding enables flexibility.

Bindings in C

#include <stdio.h>
int global_counter = 0;

int increment(int x) {
  int local = x + 1;
  global_counter++;
  return local;
}

int main(void) {
  int n = 10;
  int result = increment(n);
  printf("%d %d\n", result, global_counter);
}

  • x and local get fresh stack storage each call.

  • global_counter is allocated once and exists for the full program run.

Symbol tables in a compiler

  • A symbol table tracks bindings discovered from declarations.

  • For each name, it may store kind, type, scope, and storage info.

  • Often there is one table per scope, linked to a parent scope.

Toy symbol table operations

open_scope()
insert(name, info)
lookup(name)
close_scope()

Rules like “already declared” and “not declared” are enforced by these operations.

Symbol tables and nested scopes

int x = 1;
void f() {
  int y = 2;
  {
    int z = 3;
    int x = 4;  // shadows global x
  }
}

Lookup searches the current scope first, then walks to parents.

Scope

What scope means

Scope is the region of program text where a name refers to a particular binding.

  • Static scope: determined by the program’s textual nesting.

  • Dynamic scope: determined by the call chain at runtime.

Most modern languages use static scope.

Static scope example in TypeScript

let x = 1;
function outer() {
  let y = 2;
  function inner() {
    let x = 3;
    console.log("x:", x, "y:", y);
  }
  inner();
}
outer();

The meaning of names inside inner is determined by the surrounding code.

Example: ts_static_scope.ts

Dynamic scope thought experiment

var x = 1;
function f() { print(x); }
function g() {
  var x = 2;
  f();
}
g();

  • Static scope prints 1.

  • Dynamic scope would print 2.

Python LEGB rule

  • L: local

  • E: enclosing

  • G: global

  • B: builtins

Python is still static scope; LEGB describes the search order.

LEGB in a small example

x = "global"
def outer():
  x = "outer"
  def inner():
    print(x)
  inner()
outer()

Search order finds x in the enclosing scope (outer), so it prints outer.

Lifetime

Scope vs. lifetime

  • Scope: where a name can be used in the program text.

  • Lifetime: when storage exists during execution.

    • Static lifetime: exists for the entire program run.

    • Stack (automatic) lifetime: exists during a call or block.

    • Heap (dynamic) lifetime: exists from allocation until freed (or garbage-collected).

C storage duration example

#include <stdlib.h>
int global_var = 0;
void foo(void) {
  static int cached = 0;
  int local = 1;
  int *heap_ptr = malloc(sizeof(int));
  *heap_ptr = local + cached;
  cached++;
  free(heap_ptr);
}

Lifetime bugs in C

#include <stdio.h>
#include <stdlib.h>

int *bad_pointer(void) {
  int local = 42;
  return &local;
}

void leak(void) {
  int *p = malloc(sizeof(int));
  *p = 10; /* forgot free(p); */
}

  • Returning &local creates a dangling pointer.

  • Forgetting free creates a memory leak.

Example: c_dangling.c

Closures and extended lifetime in TypeScript

function makeAdder(n: number) {
  return function (x: number) {
    return x + n;
  };
}
const add10 = makeAdder(10);
console.log(add10(5));

The function returned from makeAdder keeps n alive after makeAdder returns.

Expressions and Side Effects

Expressions and Side Effects

An expression is code that evaluates to a value.

  • 3 + 4 evaluates to 7

  • square(5) evaluates to 25

A side effect is a change that happens in addition to producing a value.

  • assignment to a variable

  • mutating an array/object

  • printing, file I/O

Referential transparency

An expression is referentially transparent if you can replace it with its value without changing program behavior.

  • 3 + 4 is referentially transparent

  • a function that updates a global counter is not

Pure and impure functions in Python

def square(x):
  return x * x

acc = 0
def add_to_acc(x):
  global acc
  acc += x
  return acc

Common Pitfalls

Shadowing pitfall in C

int total = 0;
void add(int values[], int n) {
  for (int i = 0; i < n; i++) {
    int total = values[i];  // shadows global total
    // intended: total += values[i];
  }
}

Shadowing in TypeScript and Python

Shadowing happens when an inner scope introduces a new name that hides an outer one.

// TypeScript
let total = 0;
function add(values: number[]): void {
  for (let i = 0; i < values.length; i++) {
    let total = values[i];   // shadows outer total
    // intended: total += values[i];
  }
}
# Python
total = 0
def add(values):
  for v in values:
    total = v   # creates a new local name "total"
    # intended: total += v

  • TypeScript example: the loop declares a new total, so the outer total is never updated.

  • Python example: assigning to total inside add makes it a local variable, so this does not update the global total.

  • Many linters warn about shadowing because it often matches “I didn’t mean to create a new variable.”

Wrap-up

Summary

  • Names, bindings, scope, and lifetime explain how programs connect text to runtime behavior.

  • Symbol tables model how implementations track bindings across nested scopes.

  • Static scope is predictable because it follows program structure.

  • Lifetime issues explain bugs in manual memory management and why closures matter.

  • Side effects complicate reasoning; shadowing and hoisting create common bugs.
