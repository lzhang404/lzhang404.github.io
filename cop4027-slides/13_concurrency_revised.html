Java Concurrency

Advanced Programming

Liting Zhang

Learning Goals

  • Distinguish concurrency from parallel execution.

  • Separate a task from the thread that runs it.

  • Explain why a shared update can fail.

  • Choose a coordination or execution tool for the problem.

  • Handle completion, failure, and cancellation.

Concurrency and Threads

Why Use Concurrency?

  • Keep an application responsive during slow work.

  • Handle several independent requests.

  • Use multiple CPU cores for suitable calculations.

  • Example: load a file while the user keeps working.

Processes, Threads, and Tasks

  • A process is a running program.

  • A thread is one path of execution inside a process.

    • Threads share the process heap but keep separate call stacks.

  • A task is work that a thread can execute.

    • One thread can execute several tasks over time.

Concurrency and Parallelism

  • Concurrency: tasks make progress during overlapping periods.

    • One CPU core can switch between concurrent tasks.

  • Parallelism: tasks execute at the same time.

    • Multiple CPU cores can run tasks in parallel.

CPU-Bound and I/O-Bound Work

  • CPU-bound work spends most of its time calculating.

  • I/O-bound work spends most of its time waiting.

  • While one task waits for I/O, another can use the CPU.

  • Parallel CPU work needs independent tasks and available cores.

  • Thread creation, switching, and coordination add overhead.

  • More threads do not guarantee faster execution.

Representing a Task with Runnable

  • A functional interface has one abstract method.

  • Runnable declares run().

  • A lambda provides the method implementation.

  • A named class is useful when a task needs reuse or extra structure.

class GreetingTask implements Runnable {
    @Override
    public void run() {
        System.out.println("Hello");
    }
}

Runnable named = new GreetingTask();
Runnable lambda = () -> System.out.println("Hello");

Creating and Starting a Thread

  • The main thread begins by executing main().

  • Runnable defines the worker's task.

  • new Thread(task) creates a thread object.

    • Creating the object does not run the task.

  • start() starts the new thread, which executes the task.

    • The current thread can continue while the worker runs.

  • Each Thread object can be started only once.

Runnable task = () -> System.out.println("Hello");
Thread worker = new Thread(task, "Thread A");
worker.start();

start() and run()

  • run() is an ordinary method call on the current thread.

  • start() starts a new thread, which calls run().

Runnable task = () ->
        System.out.println(Thread.currentThread().getName());
Thread worker = new Thread(task, "Thread A");

worker.run();   // main
worker.start(); // Thread A

Thread Scheduling

  • The scheduler decides which runnable thread executes.

  • Starting first does not guarantee finishing first.

  • The output order may change across runs.

  • A correct program must tolerate valid scheduling changes.

Waiting for Completion with join()

  • Both workers can make progress after their start() calls.

  • worker.join() waits until that worker terminates.

  • The final message appears after both join() calls return.

  • join() can throw InterruptedException.

static void runWorkers() throws InterruptedException {
    Thread first = new Thread(() -> System.out.println("Hello"));
    Thread second = new Thread(() -> System.out.println("Bye"));
    first.start();
    second.start();
    first.join();
    second.join();
    System.out.println("Both finished");
}

  • Example: threads/ThreadBasicsDemo.java

join() and sleep() Solve Different Problems

join()

  • Waits for another thread to finish.

  • Expresses a real completion dependency.

  • A timed join may return before completion.

static void startAndWait(Thread worker) throws InterruptedException {
    worker.start();
    worker.join();
}

sleep()

  • Pauses the current thread.

  • Does not know whether another task finished.

static void pause() throws InterruptedException {
    Thread.sleep(100);
}

Blocking and Non-Blocking Calls

  • A blocking call makes the calling thread wait.

  • worker.join() waits for completion.

  • Thread.sleep(100) waits for time to pass.

  • A non-blocking call lets the caller continue.

  • worker.start() does not wait for the worker to finish.

  • Asynchronous work proceeds separately from the caller.

  • Asynchronous work can still make blocking calls.

Interruption Requests Cooperation

  • worker.interrupt() requests interruption.

    • It does not forcibly kill the worker.

    • Interruptible waits can throw InterruptedException.

  • Task code decides how to respond to the request.

Interruption During a Wait

  • Interrupt status records an interruption request.

  • sleep() responds to interruption by throwing InterruptedException and clearing that status.

  • Restore the status when higher-level code should observe the interruption.

Runnable task = () -> {
    try {
        Thread.sleep(1000);
        System.out.println("Work finished");
    } catch (InterruptedException exception) {
        Thread.currentThread().interrupt();
        return;
    }
};
Thread worker = new Thread(task, "Thread A");
worker.start();
worker.interrupt();

  • Example: threads/InterruptionDemo.java

Interruption During Active Work

  • A calculation does not automatically throw InterruptedException when interrupted.

  • isInterrupted() checks the current interrupt status without clearing it.

  • Check between small units of work so the task can stop promptly.

Runnable task = () -> {
    long total = 0;
    for (long n = 1; n <= 1_000_000_000L; n++) {
        if (Thread.currentThread().isInterrupted()) {
            return;
        }
        total += n;
    }
    System.out.println(total);
};

Quick Check: Starting and Waiting

  • To run a task concurrently with the current thread, call worker.run() or worker.start()?

  • Answer: worker.start(). Calling run() directly stays on the current thread.

  • Is Thread.sleep(100) a reliable way to wait for a worker to finish?

  • Answer: No. Use worker.join().

  • If the main thread calls worker.interrupt(), must the worker terminate immediately?

  • Answer: No. The worker must handle the request cooperatively.

Shared State and Synchronization

Shared Object References

  • Shared mutable state can be changed by multiple threads.

  • Two threads can reference the same object.

  • A local reference may still point to shared state.

class Counter {
    private int value;

    public void increment() {
        value++;
    }
}

Nonatomic Counter Updates

  • An atomic operation behaves as one indivisible action.

  • value++ performs a read, an addition, and a write.

  • Another thread can run between those steps.

Counter counter = new Counter();
Thread first = new Thread(counter::increment, "Thread A");
Thread second = new Thread(counter::increment, "Thread B");
first.start();
second.start();

Race Condition: A Lost Update

  • Both threads read 0, compute 1, and write 1.

  • A race condition makes correctness depend on thread timing.

  • Thread-safe code remains correct under concurrent execution.

  • One successful run does not prove thread safety.

  • Example: shared/LostUpdateDemo.java

Mutual Exclusion Protects a Critical Section

  • A critical section accesses shared state.

  • Mutual exclusion allows one thread at a time.

  • Java objects have a monitor used by synchronized.

  • Lock the complete read-change-write sequence.

  • Use the same lock for every conflicting access.

synchronized Methods

  • An instance synchronized method locks this.

  • Calls on the same object therefore use the same monitor.

  • Two different objects have different monitors.

  • A static synchronized method locks the class object.

  • The JVM releases the monitor automatically when the method exits.

class SafeCounter {
    private int value;
    public synchronized void increment() {
        value++;
    }
    public synchronized int value() {
        return value;
    }
}

synchronized Blocks

  • A block can protect only the operation that needs the lock.

  • Use a stable lock object.

  • Use that same lock for every conflicting access to the protected state.

class BlockCounter {
    private final Object lock = new Object();
    private int value;

    public void increment() {
        synchronized (lock) {
            value++;
        }
    }
}

  • Example: shared/CounterDemo.java

The Update with Synchronization

  • Thread B waits while Thread A holds the lock.

  • Thread B then reads the updated value.

  • Two increments now produce 2.

Compound Operations and Invariants

  • A critical section can protect several steps as one operation.

  • The balance check and subtraction form a compound operation.

  • Two 80 withdrawals cannot succeed from a balance of 100.

  • An invariant is a rule every operation must preserve.

  • For positive withdrawals, the balance stays nonnegative.

class Account {
    private int balance = 100;
    public synchronized boolean tryWithdraw(int amount) {
        if (balance < amount) {
            return false;
        }
        balance -= amount;
        return true;
    }
}

Java Thread States

  • NEW: created but not started.

  • RUNNABLE: executing or ready to execute.

  • BLOCKED: waiting to acquire a monitor used by synchronized.

  • WAITING: waiting without a timeout, as in join().

  • TIMED_WAITING: waiting with a time limit, as in sleep().

  • TERMINATED: execution has ended.

Java uses RUNNABLE, not a separate RUNNING state. BLOCKED specifically means waiting for a monitor.

Safety and Liveness

  • Safety: an incorrect state or result does not occur.

  • Liveness: useful work can eventually make progress.

  • Deadlock: threads wait permanently for resources held by one another.

  • Starvation: one thread repeatedly fails to obtain a needed resource.

  • Prevent deadlock by acquiring locks in a consistent order.

Atomicity and Visibility

  • Atomicity: an operation behaves as one indivisible update.

  • Visibility: other threads can reliably observe a write.

  • synchronized provides both mutual exclusion and visibility.

  • Releasing a monitor happens-before a later acquisition of the same monitor.

    • The acquiring thread observes earlier protected writes.

  • A successful join() also makes the completed worker's writes visible to the caller.

Visibility for a Stop Flag

  • Use volatile for a shared stop flag.

  • volatile makes flag updates visible across threads.

  • It does not make value++ atomic.

  • A flag change does not wake a sleeping thread.

  • Interruption can wake an interruptible wait.

class StopFlag {
    private volatile boolean stopRequested;
    public void requestStop() {
        stopRequested = true;
    }
    public boolean shouldStop() {
        return stopRequested;
    }
}

  • Example: shared/VolatileStopDemo.java

AtomicInteger Updates

  • incrementAndGet() performs one atomic update.

  • get() reads the current value.

  • Separate atomic calls do not automatically form one atomic transaction.

  • Use a lock when correctness depends on several fields or several steps.

AtomicInteger count = new AtomicInteger();

count.incrementAndGet();
System.out.println(count.get());

  • Example: shared/AtomicCounterDemo.java

Shared Counts by Job Type

  • A map can track a separate count for each job type.

  • Separate get() and put() calls can lose updates.

  • ConcurrentHashMap supports concurrent access.

  • merge() performs one atomic update for a key.

ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();

counts.merge("reports", 1, Integer::sum);
counts.merge("emails", 1, Integer::sum);

  • Example: shared/ConcurrentMapDemo.java

Reduce Shared Mutable State

  • Task confinement: keep mutable data owned by one task.

  • Each task builds its own report text.

  • Return an immutable String that other tasks cannot change.

  • final prevents reference reassignment.

  • final does not make an object immutable.

static String buildReport(String name) {
    StringBuilder text = new StringBuilder();
    text.append("Report for ").append(name);
    return text.toString();
}

Quick Check: Fix the Counter

  • Two threads share a counter. Each increments its int field value once using value++.

  • Would Thread.sleep(100) before each increment prevent a lost update?

  • Answer: No. Sleep provides no protection.

  • Would volatile int value make value++ atomic?

  • Answer: No. Volatile provides visibility, not an atomic increment.

  • Would making the shared counter's increment() method synchronized protect both updates?

  • Answer: Yes. Both calls acquire the same counter's monitor.

Waiting and Thread Coordination

Lock Availability and Account Balance

  • A withdrawal can wait until enough funds are available.

  • Waiting for a lock: another thread owns the account's monitor.

  • Waiting for state: the balance is too low.

  • Release the monitor while waiting so another thread can deposit.

    • Thread.sleep(100) keeps any locks the current thread holds.

Waiting for Sufficient Funds

  • A synchronized method owns the account's monitor.

  • wait() releases the monitor while waiting.

  • wait() reacquires the monitor before returning.

  • Recheck the balance in while after every wakeup.

    • Another withdrawal may use the funds first.

    • A spurious wakeup may occur without notification.

class MonitorBankAccount {
    private int balance = 20;
    public synchronized void withdraw(int amount)
            throws InterruptedException {
        while (balance < amount) {
            wait();
        }
        balance -= amount;
    }
}

Deposits and Monitor Notification

  • notifyAll() wakes all threads waiting on that account.

    • notify() wakes one waiter instead.

  • Notification does not release the monitor.

  • Each awakened thread must reacquire the monitor and recheck the balance.

public synchronized void deposit(int amount) {
    balance += amount;
    notifyAll();
}

The deposit raises the balance to 60. Thread A can then withdraw 50.

  • Example: coordination/MonitorBankAccountDemo.java

Explicit Locking with ReentrantLock

  • ReentrantLock adds timed and interruptible acquisition to mutual exclusion.

  • lock() waits for ownership.

  • A reentrant lock may be acquired again by its owner.

  • Release with unlock() in finally, even if an exception occurs.

class LockingBankAccount {
    private int balance = 20;
    private final ReentrantLock lock = new ReentrantLock();
    public void deposit(int amount) {
        lock.lock();
        try {
            balance += amount;
        } finally {
            lock.unlock();
        }
    }
}

Timed and Interruptible Lock Acquisition

  • tryLock() returns immediately: true if acquired, otherwise false.

  • Timed tryLock() waits only for the specified duration.

  • Interruption can end the timed wait.

  • lockInterruptibly() waits for ownership but allows interruption to end the wait.

  • Unlock only after successful acquisition.

public boolean tryDeposit(int amount) throws InterruptedException {
    if (!lock.tryLock(100, TimeUnit.MILLISECONDS)) {
        return false;
    }
    try {
        balance += amount;
        return true;
    } finally {
        lock.unlock();
    }
}

  • Example: coordination/LockingBankAccount.java

Waiting for State to Change with Condition

  • A Condition belongs to a specific lock.

  • The condition holds threads waiting for sufficient funds.

  • A withdrawal can proceed only when balance >= amount.

  • await() releases the lock while waiting.

  • await() reacquires the lock before returning.

  • Use while to recheck the balance after every wakeup.

private final ReentrantLock lock = new ReentrantLock();
private final Condition funds = lock.newCondition();

public void withdraw(int amount) throws InterruptedException {
    lock.lock();
    try {
        while (balance < amount) {
            funds.await();
        }
        balance -= amount;
    } finally {
        lock.unlock();
    }
}

Deposits and Condition Signalling

  • Update the balance and signal under the same lock.

  • signalAll() wakes all waiters on funds.

    • signal() wakes one waiter instead.

  • Signalling does not release the lock.

  • Waiters reacquire the lock before rechecking the balance.

  • Every method that adds funds must signal.

public void deposit(int amount) {
    lock.lock();
    try {
        balance += amount;
        funds.signalAll();
    } finally {
        lock.unlock();
    }
}

  • Example: coordination/LockingBankAccountDemo.java

Monitor and Condition APIs

Operation Object monitor Lock + Condition
Wait and release the associated lock wait() await()
Wake one waiter notify() signal()
Wake all waiters notifyAll() signalAll()

  • Own the matching monitor or lock when calling these methods.

  • Keep monitor waiters and Condition waiters separate. Use the matching notification methods.

synchronized or ReentrantLock?

  • For straightforward mutual exclusion, synchronized handles locking and unlocking automatically.

  • For timed or interruptible acquisition, use ReentrantLock.

  • For separate wait sets on one lock, create multiple Condition objects.

  • Both approaches support waiting for state to change. Waiting alone does not require ReentrantLock.

Quick Check: Which Waiter Can Proceed?

The balance is 0. Thread A is waiting to withdraw 100. Thread B is waiting to withdraw 20.

A deposit adds 20 and calls notify() once.

Could Thread B remain waiting even though enough funds are available for it?

Answer: Yes. notify() may wake Thread A, which must wait again. notifyAll() lets both recheck, allowing Thread B to withdraw.

Producer–Consumer Handoff

  • A producer creates file-processing jobs. A consumer takes and processes them.

  • The producer waits while the queue is full.

  • The consumer waits while the queue is empty.

  • BlockingQueue handles the locking and signalling for these conditions.

  • put() blocks while the queue is full.

  • take() blocks while the queue is empty.

static void produce(BlockingQueue<String> jobs) {
    try {
        jobs.put("report.csv");
    } catch (InterruptedException exception) {
        Thread.currentThread().interrupt();
    }
}

Running the Producer and Consumer

  • The producer and consumer share one queue.

  • take() waits until a job is available.

  • Both take() and join() can be interrupted.

static void handoff() throws InterruptedException {
    BlockingQueue<String> jobs = new ArrayBlockingQueue<>(10);
    Thread producer = new Thread(() -> produce(jobs), "Thread A");
    producer.start();
    String job = jobs.take();
    System.out.println("Processing " + job);
    producer.join();
}

  • Example: coordination/BlockingQueueDemo.java

Task Execution and Asynchronous Results

ExecutorService and Worker Threads

  • Thread pool: managed workers that reuse threads for successive tasks.

  • ExecutorService assigns submitted tasks to workers.

  • A fixed pool limits the number of active workers.

  • Additional tasks wait in the executor's queue.

Task Results: Runnable and Callable

  • Runnable.run() performs work but returns no result.

  • Callable<T>.call() performs work and returns a value of type T.

    • call() may declare checked exceptions. run() cannot.

Runnable message = () -> System.out.println("Done");
Callable<Integer> calculation = () -> 6 * 7;

Future: A Result That May Arrive Later

  • Future<T> represents a result that may arrive later.

  • submit() returns a Future.

  • get() blocks the calling thread if the result is not ready.

  • Submit independent tasks before waiting for their values.

  • Try-with-resources closes the executor, waiting for its tasks to finish.

static void totalResults()
        throws InterruptedException, ExecutionException {
    try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
        Future<Integer> first = pool.submit(() -> 6 * 7);
        Future<Integer> second = pool.submit(() -> 5 * 5);
        int total = first.get() + second.get();
        System.out.println(total); // 67
    }
}

  • Example: executors/ExecutorFutureDemo.java

Executor Resource Limits

  • A fixed thread pool limits active workers.

  • newFixedThreadPool() uses an unbounded task queue.

  • Pending work can exhaust memory if submissions outpace processing.

  • A bounded queue limits pending work.

  • A full queue requires a rejection or backpressure policy.

  • The component that owns the executor must close it when finished.

  • close() rejects new submissions.

  • close() waits for submitted tasks to finish.

What Can Happen to a Future?

  • Success: get() returns the result.

  • Task failure: ExecutionException wraps the task's exception.

  • getCause() retrieves the original exception.

  • Interrupted caller: InterruptedException concerns the waiting thread.

static void printResult(Future<Integer> future)
        throws InterruptedException {
    try {
        System.out.println(future.get());
    } catch (ExecutionException exception) {
        System.out.println("Task failed: " + exception.getCause());
    }
}

Future Timeouts and Cancellation

  • A timed get() can throw TimeoutException.

  • A timeout ends this wait. It does not stop the task.

  • cancel(true) requests cancellation.

  • Cancellation may interrupt the worker.

  • The task must cooperate with cancellation.

  • After successful cancellation, get() throws CancellationException.

static void printWithinDeadline(Future<Integer> future)
        throws InterruptedException, ExecutionException {
    try {
        System.out.println(future.get(100, TimeUnit.MILLISECONDS));
    } catch (TimeoutException exception) {
        future.cancel(true);
        System.out.println("Task took too long");
    }
}

  • Example: executors/FutureTimeoutDemo.java

Results and Stages with CompletableFuture

  • Future.get() retrieves a result.

  • CompletableFuture can attach the next computation.

  • A stage is one step in that computation.

  • supplyAsync() submits work that produces a value to the given executor.

  • CompletableFuture.join() returns the stage result.

  • join() blocks while the result is unavailable.

try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
    CompletableFuture<String> message = CompletableFuture
            .supplyAsync(() -> "Report ready", pool);

    System.out.println(message.join());
}

Dependent Work: One Result Feeds the Next

  • Some work cannot start until an earlier result is ready.

  • thenApply() transforms a successful result.

  • The transformation runs after its input becomes ready.

try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
    CompletableFuture<Integer> length = CompletableFuture
            .supplyAsync(() -> "Concurrency", pool)
            .thenApply(String::length);

    System.out.println(length.join()); // 11
}

Independent Work: Start Both, Combine Later

  • Submit independent tasks before waiting for either result.

  • thenCombine() waits for two successful results.

  • The combining function receives both results.

try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
    CompletableFuture<String> user = CompletableFuture
            .supplyAsync(() -> "Alice", pool);
    CompletableFuture<Integer> orders = CompletableFuture
            .supplyAsync(() -> 3, pool);

    CompletableFuture<String> summary = user.thenCombine(orders,
            (name, count) -> name + " has " + count + " orders");
    System.out.println(summary.join()); // Alice has 3 orders
}

  • Example: executors/CompletableFutureDemo.java

Stage Failure and Cancellation

  • If an earlier stage fails, its normal transformation steps are skipped.

  • join() reports failure with CompletionException.

  • get() reports failure with ExecutionException.

  • CompletableFuture.cancel(true) marks the result as cancelled.

  • It does not interrupt the underlying computation.

JavaFX: Keep Slow Work Off the UI Thread

  • A file can load in the background while the interface stays responsive.

  • JavaFX UI updates run on the JavaFX Application Thread.

  • Submit slow work to an executor.

  • Do not block the UI thread with get() or join().

  • Use Platform.runLater() for the UI update.

Virtual Threads

Why Virtual Threads?

  • A platform thread is tied to an OS thread.

  • A virtual thread is a lightweight thread managed by the JVM.

  • When a virtual thread waits, its platform thread can run other work.

  • This makes virtual threads useful when many tasks spend time waiting on I/O.

One Virtual Thread per Task

  • Each submitted task receives a virtual thread.

  • Tasks can use ordinary blocking code.

  • get() waits when we need the result.

static void runVirtualTask()
        throws InterruptedException, ExecutionException {
    try (ExecutorService executor =
            Executors.newVirtualThreadPerTaskExecutor()) {
        Future<String> report = executor.submit(() -> {
            Thread.sleep(100);  // simulate waiting for I/O
            return "Report ready";
        });
        System.out.println(report.get());
    }
}

What Virtual Threads Do Not Solve

  • Shared mutable state still needs synchronization.

  • Virtual threads do not speed up CPU-heavy work.

  • Scarce resources still need limits, such as database connections.

  • Blocking inside synchronized can reduce Java 21 scalability.

  • Example: executors/VirtualThreadDemo.java

Summary

Choose a Tool for the Job

  • Simple shared state: synchronized.

  • Waiting on an object: wait() and notifyAll() under synchronized.

  • One shared counter: AtomicInteger.

  • Extra lock control and separate wait sets: ReentrantLock and Condition.

  • Producer-consumer handoff: BlockingQueue.

  • Task execution and results: ExecutorService and Future.

  • Dependent result stages: CompletableFuture.

  • Many blocking tasks: virtual threads.

Key Takeaways

  • A task describes work. A thread executes work.

  • start() starts a new thread. Calling run() directly does not.

  • Shared mutable state may require both atomicity and visibility.

  • Mutual exclusion prevents conflicting critical sections from overlapping.

  • Correctness requires both safety and liveness.

  • wait() and await() reacquire their lock before returning. Recheck shared state in a while loop.

  • Completion, failure, interruption, timeout, and cancellation are part of task design.
