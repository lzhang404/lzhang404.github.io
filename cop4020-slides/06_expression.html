Introduction

Learning goals

  • Separate parse-time grouping (precedence) from run-time behavior (evaluation order).

  • Explain how side effects interact with expressions and control flow.

  • Compare how languages design assignment, scope, and common control-flow forms.

  • Connect mainstream constructs to a reasoning-first model (guarded commands).

Spec vocabulary you will see (especially in C)

  • Specified / defined: the language guarantees the behavior.

  • Unspecified: the implementation may choose (still a valid program).

  • Undefined behavior: the program has no defined meaning (anything can happen).

  • Design tradeoff: allowing more freedom can enable more optimization, but increases programmer responsibility.

Expressions: grouping vs runtime execution

Operator precedence vs evaluation order

  • Precedence decides grouping (parse tree).

  • Evaluation order decides what runs first at runtime.

  • Order matters when evaluation has side effects (mutation / I/O).

  • Example grouping: \(1 + 2 * 3\) groups as \(1 + (2 * 3)\).

Evaluation order: TypeScript is left-to-right

TypeScript evaluates function arguments from left to right:

function log(label: string, value: number): number {
  console.log(label, value);
  return value;
}
let x = 1;
let y = log("first", x++)
      + log("second", x++);
// Output:
// first 1
// second 2
// After expression: x is 3, y is 3

  • The output order matches the evaluation order.

ts_eval_order.ts

Evaluation order: C often does not specify it

In C, subexpression evaluation order is often not specified:

#include <stdio.h>

int first(void)  { puts("first");  return 1; }
int second(void) { puts("second"); return 2; }

int main(void) {
  int y = first() + second();
  printf("y = %d\n", y);
}

  • The value y is 3 either way, but the printed order may vary.

  • Do not write code that relies on “first runs before second” unless the spec guarantees it.

c_eval_order.c

Definedness: what does the language guarantee?

  • Some languages specify evaluation order (TypeScript, Python).

  • Some leave freedom to implementations (C), which can change behavior across compilers/flags.

  • Rule of thumb: if side effects matter, prefer code whose meaning does not depend on evaluation order.

Short-circuit and truthy/falsey

Short-circuit boolean evaluation

  • Many languages support short-circuit:

    • A && B: if A is false, B is not evaluated.

    • A || B: if A is true, B is not evaluated.

ts_sideeffect.ts

Short-circuit as “desugaring”

  • You can think of short-circuiting as if-like control flow:

A && B   ~   if A then B else false
A || B   ~   if A then true else B

  • Not exact in every language because return values may not be boolean.

Short-circuit as a safety guard (TypeScript)

type User = { name: string } | null;

function greet(u: User) {
  if (u !== null && u.name.length > 0) {
    console.log("hello", u.name);
  } else {
    console.log("no user");
  }
}

  • Second condition only runs when u !== null.

ts_short_circuit.ts

Short-circuit as a safety guard (Python)

def greet(u):
    # u is either None or a dict with "name"
    if u is not None and len(u["name"]) > 0:
        print("hello", u["name"])
    else:
        print("no user")

  • and short-circuits like &&.

Do these operators return a boolean?

  • Returns one operand (value-selecting):

    • JavaScript/TypeScript: &&, ||

    • Python: and, or

    • Ruby: &&, || (also and, or)

    • Lua: and, or

    • PHP: &&, || (also and, or)

    • Perl: &&, ||

  • Returns a boolean (boolean-only logical operators):

    • Java, C#, Go, Rust, Swift, Kotlin

    • C/C++: result is 0/1 (boolean-ish), not an operand value

  • Takeaway: in many dynamic languages, “boolean operators” are also value selectors.

Defaults: || vs ?? (TypeScript)

function label(name: string | undefined) {
  const shown1 = name || "anonymous";
  const shown2 = name ?? "anonymous"; // only null/undefined
  console.log({ shown1, shown2 });
}
label(undefined);
label("");

  • || treats "", 0, false as “use default”.

  • ?? only replaces null or undefined.

ts_default_val.ts

Defaults with or (Python)

def label(name):
    shown = name or "anonymous"
    print(shown)

label(None)
label("")

  • This returns one operand, not a boolean.

  • If empty string is valid, use an explicit check (or distinguish None).

Short-circuit + side effects: readability pitfall

Works, but intent is easy to miss:

let connected = false;
function connect(): boolean {
  console.log("connecting...");
  connected = true;
  return connected;
}
connected || connect();

  • Prefer explicit if when the right side has side effects.

  • avoid hiding actions inside “boolean-looking” expressions.

Assignment and State

Assignment and state: design questions

  • Is assignment a statement, an expression, or both?

  • Does it copy values or copy references?

  • What implicit conversions can occur?

  • What “shorthand” forms exist: compound, destructuring, chained assignment?

Assignment as an expression (C, JavaScript/TypeScript)

In C and JavaScript, assignment produces a value.

#include <stdio.h>

int main(void) {
  int x = 0;
  int y = (x = 5);  // assignment yields 5
  printf("x=%d y=%d\n", x, y);
  return 0;
}

  • Compact, but can enable bugs when = is confused with ==.

c_assign_expr.c

Assignment is a statement (Python)

x = 5
# y = (x = 5)   # syntax error
y = x
print(x, y)

  • Fewer accidental assignments inside conditions.

  • Python has := for limited assignment-expression cases.

Compound assignment

let x = 10;
x += 5;   // x = x + 5
x *= 2;   // x = x * 2
console.log(x);

  • With objects, “update” may mutate or allocate depending on language/type.

Destructuring and multiple assignment

TypeScript destructuring:

let pair: [number, string] = [7, "seven"];
let [n, s] = pair;

let obj = { x: 1, y: 2 };
let { x, y } = obj;

console.log(n, s, x, y);

Python tuple unpacking:

n, s = (7, "seven")
x, y = [1, 2]
print(n, s, x, y)

Chained assignment: readability vs aliasing risk

let a: number, b: number, c: number;
a = b = c = 0;
console.log(a, b, c);
a = b = c = 0
print(a, b, c)

  • Usually fine for immutable values; risky for mutable objects.

Aliasing example (Python)

a = b = []
a.append(1)
print(a)  # [1]
print(b)  # [1]

  • a and b refer to the same list object.

  • Safer pattern: a = [] ; b = [].

Assignment in conditions: classic bug (C)

int x = 5;
if (x = 0) {
  printf("x is zero\n");
} else {
  printf("x is nonzero\n");
}

  • x = 0 changes x and evaluates to 0, so the else branch runs.

  • Often intended: x == 0.

  • Contrast: Python does not allow assignment in an if condition expression.

Block and Scope

Sequences and blocks

  • A sequence expresses multiple computations in order.

  • A block groups statements into a unit.

  • PL question: does a block introduce a new scope?

  • C/TypeScript use braces; Python uses indentation.

Blocks and scope across languages

let x = 1;
{
  let x = 2;        // inner x shadows outer x
  console.log(x);   // prints 2
}
console.log(x);     // prints 1
x = 1
if True:
  x = 2          # modifies same x
print(x)         # prints 2

  • TypeScript: let/const are block-scoped.

  • Python: if/while blocks do not create a new local scope.

Selection

Selection constructs

  • if / else: general-purpose branching.

  • switch: discrete cases (watch fall-through).

  • match / pattern matching: branch by structure, often exhaustiveness-checked.

If / else encodes priority (TypeScript)

function category(score: number): string {
  if (score >= 90) {
    return "A";
  } else if (score >= 80) {
    return "B";
  } else if (score >= 70) {
    return "C";
  } else {
    return "F";
  }
}

  • Order matters: you are encoding a ranking of conditions.

Switch in C: fall-through is the default

int day = 3;
switch (day) {
  case 1:
    printf("Monday\n");
    break;
  case 2:
    printf("Tuesday\n");
    break;
  case 3:
  case 4:
    printf("Midweek\n");
    break;
  default:
    printf("Other day\n");
    break;
}

  • Without break, control continues into the next case.

c_switch.c

Switch in TypeScript: common “return per case” pattern

function httpMessage(code: number): string {
  switch (code) {
    case 200: return "OK";
    case 404: return "Not Found";
    case 500: return "Server Error";
    default:  return "Unknown";
  }
}

  • Returning directly avoids forgetting break.

Pattern matching: why PL people like it

  • Branch by structure, not only by booleans.

  • Encourages explicit case coverage; some languages check exhaustiveness.

  • Often pairs naturally with destructuring.

  • Rust: match is central and exhaustiveness-checked.

  • Python: match/case supports structural patterns (3.10+).

Rust match as an expression

fn classify_score(score: i32) -> &'static str {
    match score {
        0..=59 => "fail",
        60..=79 => "pass",
        80..=89 => "good",
        90..=100 => "excellent",
        _ => "invalid",
    }
}

  • match returns a value and is typically exhaustive.

Python match/case: structural patterns

def handle(m):
    match m:
        case ("move", x, y):
            return x + y
        case ("write", s):
            return len(s)
        case ("quit",):
            return 0
        case _:
            return -1

Iteration, Iterator, and Generators

Iteration constructs

  • while: repeat while a condition holds.

  • for: counting loop (init/condition/update bundled).

  • foreach: iterate over elements of a collection.

  • Iterators/generators: “produce next element” as an abstraction.

while loop: basic form (TypeScript)

let n = 5;
let acc = 1;

while (n > 1) {
  acc *= n;
  n--;
}

console.log(acc);

  • Make progress toward termination.

  • Keep mutation localized and visible.

for loops with counters

C style:

int sum = 0;

for (int i = 1; i <= 10; i++) {
  sum += i;
}

TypeScript style:

let sum = 0;

for (let i = 1; i <= 10; i++) {
  sum += i;
}

foreach: Python

nums = [1, 2, 3, 4]
total = 0

for x in nums:
    total += x

print(total)

  • Python for is a foreach over an iterator.

  • Loop variable remains in scope after the loop.

foreach: TypeScript

let nums = [1, 2, 3, 4];
let total = 0;

for (const x of nums) {
  total += x;
}

console.log(total);

  • for..of iterates values; for..in iterates property names.

  • Example: ts_of_vs_for_in.ts

Iterators conceptually

  • An iterator produces a sequence of values over time.

  • It has internal state; each next() advances.

  • Iterator protocols let loops work with many data sources uniformly.

foreach as “desugaring” to iter/next

  • a surface construct can be defined in terms of a simpler core model.

  • Python: for x in xs uses iter(xs) and repeated next().

  • JavaScript: for..of uses Symbol.iterator and repeated next().

Iterator protocol in TypeScript

JavaScript defines an iterator protocol using Symbol.iterator.

function range(n: number) {
  return {
    [Symbol.iterator]() {
      let i = 0;
      return {
        next() {
          if (i < n) return { value: i++, done: false };
          return { value: undefined, done: true };
        }
      };
    }
  };
}
for (const x of range(4)) {
  console.log(x);
}

Generators in TypeScript

Generators provide a compact way to write iterators.

function* range(n: number) {
  for (let i = 0; i < n; i++) {
    yield i;
  }
}
for (const x of range(4)) {
  console.log(x);
}

  • yield produces one value at a time.

Iterators in Python

Python uses iter() and next() under the hood for for-loops.

it = iter([10, 20, 30])
print(next(it))
print(next(it))
print(next(it))

  • When exhausted, next raises StopIteration.

Guarded Commands

Guarded commands (Dijkstra): why they matter

  • Replace single-condition branching with a set of guarded alternatives.

  • If multiple guards are true, any may be chosen.

  • If no guard is true, the command is blocked (or fails).

  • PL angle: forces thinking about completeness and invariants.

Guarded commands: syntax (pseudo-code)

Selection (if-like):

  • if

    • G1 \(\rightarrow\) S1

    • G2 \(\rightarrow\) S2

    • ...

    • Gn \(\rightarrow\) Sn

  • fi

Iteration (while-like):

  • do

    • G1 \(\rightarrow\) S1

    • G2 \(\rightarrow\) S2

    • ...

    • Gn \(\rightarrow\) Sn

  • od

Guarded selection: semantics

  • Evaluate which guards are true.

  • If at least one is true, choose one true guard and execute its statement.

  • If none are true, there is no enabled action.

  • Reasoning benefit: you must think “did we cover all cases?”

Guarded commands example: absolute value

Pseudo code:

if x < 0  -> x := -x
[] x == 0 -> skip
[] x > 0  -> x := x
fi

  • Exactly one guard is true for any integer x.

Guarded iteration: semantics

  • While at least one guard is true, choose one true guard and execute its statement.

  • Stop when all guards are false.

  • Reasoning style: invariants + termination arguments.

Guarded commands vs mainstream control flow

  • Guarded commands emphasize reasoning and correctness arguments.

  • Mainstream languages use deterministic if/switch/while/for.

  • Guarded commands can be compiled into standard control flow.

Wrap Up

Industry angle: controlling side effects

  • Hidden mutation inside complex expressions hurts readability and reviewability.

  • Prefer explicit control flow when side effects occur.

  • Limit scope of mutable state; avoid subtle aliasing.

  • Use tests, linters, and compiler warnings to catch suspicious constructs.

Summary

  • Precedence groups expressions; evaluation order runs them.

  • Short-circuit is control flow inside expressions.

  • Assignment differs across languages; aliasing is a major source of bugs.

  • Blocks, scope, selection, and iteration shape imperative programs.

  • Iterators and generators unify looping across data sources.

  • Guarded commands provide a reasoning-first model of control flow.
