Language design in practice

Language decisions are product decisions

In industry, language decisions are rarely academic:

  • You optimize for an organization, not just a compiler

  • Stakeholders: engineers, security, SRE, PM, compliance, hiring

  • Most "language design" happens in APIs, DSLs, and conventions

A helpful reframing:

  • What mistakes do we want to make impossible?

  • What do we want to make easy and frequent?

  • What do we want to make hard or forbidden?

Constraint checklist engineers actually use

Typical constraints:

  • Runtime: latency (p99), throughput, memory footprint

  • Safety: untrusted input, sandboxing, compliance, auditability

  • Operational: observability, debugging, incident response

  • Delivery: CI/CD, build time, deployment model

  • Team: hiring pool, onboarding time, code review norms

  • Migration: existing codebase, interop, incremental rollout

Language features are valuable only when they reduce risk or cost under these constraints.

Applying the Module 1 rubric to engineering decisions

Module 1 goals (readability, writability, reliability), reframed for industry:

  • Readability: reviewers understand intent quickly

  • Writability: authors express common tasks with low friction

  • Reliability: system prevents or contains mistakes

  • Cost: training, tooling, runtime, maintenance

Design implies choosing defaults:

  • Defaults become culture (lint rules, style guides, idioms)

  • Defaults also become failure modes

A common pattern: constrain the dangerous parts

Organizations often prefer:

  • a small set of safe primitives

  • explicit escape hatches (rare, reviewed)

  • tooling that catches mistakes early

Examples:

  • restricted query languages instead of embedding arbitrary code

  • typed APIs to prevent misuse

  • safe-by-default concurrency patterns

DSLs: when and why

DSL definition

Domain-Specific Language (DSL):

  • A language for a narrow domain with constrained expressiveness

  • Goal: make the common case easy, the dangerous case hard

Two forms:

  • External DSL: its own syntax (SQL, regex, policy languages)

  • Embedded DSL: fluent API inside a host language

You have seen both. Now the new question: how do you design and ship one?

Decision tree: config vs DSL vs code

Three levels of expressiveness:

  • Config (JSON, YAML, TOML): pure data, no logic

    • Use when: simple schema, values differ by environment

    • Example: feature flags, DB URLs, log levels

  • DSL (SQL, regex, Terraform HCL): restricted language for one domain

    • Use when: rules need structure and safety; non-engineers may edit

    • Example: access policies, routing rules, discount rules

  • Code (TypeScript, Python, Go): general-purpose language

    • Use when: arbitrary computation needed, engineers own it

    • Example: business logic, data pipelines, services

Common DSL success patterns

DSLs succeed when they:

  • have a stable, well-defined domain model

  • benefit from static validation (types, schemas, constraints)

  • benefit from optimization or caching (queries, rules)

  • are authored by people who are not runtime engineers

  • need audit trails and explicit semantics

Common DSL failure patterns

DSLs fail when:

  • error messages are poor (users cannot debug)

  • versioning is neglected (breaking changes accumulate)

  • feature creep turns it into a weak general-purpose language

  • tooling is missing (no formatter, no lint, no tests)

  • security boundaries are unclear (untrusted inputs, injection)

A DSL without tooling is often worse than a small library API.

External DSL example: policy rules


policy "admin_access" when user.role == "admin" and resource.sensitivity <= 2 {
  allow;
  }

policy "readonly_guest" when user.role == "guest" {
  allow read;
  deny write;
  }

Benefits:

  • reviewers can read intent

  • constrained operators reduce surprises

Embedded DSL example: builder pattern (host tooling)

Embedded DSL style (TypeScript):


rule("free_shipping")
  .when(and(eq(varOf("tier"), str("gold")), gte(varOf("total"), num(50))))
  .do(setVar("shipping", num(0)))
  .do(emit("free shipping applied"));

Benefits and costs:

  • gains TypeScript tooling and types

  • loses plain-text readability for non-engineers

DSL productization

A DSL is a contract, not just syntax

A usable DSL needs a spec:

  • Syntax: what programs look like

  • Semantics: what programs mean (evaluation order, types, effects)

  • Errors: what happens on invalid input and how it is reported

  • Compatibility: how changes are rolled out over time

Teams adopt DSLs when the contract is stable and debuggable.

Why DSLs Need Non-Goals

A good DSL is not "small code." It is a language with a narrow purpose.

  • Good design includes explicit non-goals:

    • what users are not allowed to express

    • what the DSL will not try to automate

    • what must stay in host code instead

  • Non-goals prevent feature creep and keep semantics teachable

  • They also make tooling, testing, and versioning manageable

Core Semantic Questions

Questions your DSL must answer:

  • Determinism: are results stable across runs

  • Evaluation order: do rules run top-to-bottom, all-match, first-match

  • Effects: can a rule update state that later rules observe

  • Types/coercions: do you allow implicit conversions (usually avoid)

  • Error behavior: fail-fast, collect errors, partial results

These decisions shape correctness more than the grammar does.

Rule engine semantics: three common models

Module 10 introduced rule engines and their use cases (pricing, fraud, access control, alerting).

Now the design question: what execution model do you commit to?

  • All-match:

    • evaluate every rule, apply all actions

  • First-match:

    • stop after first matching rule (priority semantics)

  • Phased:

    • compute derived facts, then apply actions (reduces order bugs)

Picking one is a design choice with real bug consequences.

Mini spec example: rule order is explicit

A tiny spec excerpt:


Rules execute top-to-bottom.

A rule condition reads from the current environment.

Actions apply immediately:
- set updates the environment
- emit appends to the output log

If a condition evaluates to non-boolean, that is a runtime error.

This prevents ambiguity like "does set affect later rules?"

Sandboxing and Resource Limits

If DSL input is untrusted:

  • no file/network access

  • no host eval or dynamic imports

  • bounded computation (no unbounded loops)

  • resource budgets:

    • max program size, max rules, max actions, max recursion depth

Reliability boundary:

  • fail closed for policy/security DSLs

  • record audit logs of evaluation and decisions

Tooling that makes a DSL viable

Minimum viable tooling:

  • helpful error messages with line/column and context

  • tests: golden files (input \(\rightarrow\) output/errors)

  • formatting / consistent style (even a simple pretty-printer)

  • docs: examples and common patterns

Nice-to-have:

  • editor integration (syntax highlighting)

  • static checks (unknown vars, unreachable rules, type errors)

DSL Evolution and Compatibility

DSLs evolve. Plan for:

  • feature flags / opt-in syntax

  • deprecation warnings before removal

  • strict mode vs legacy mode

  • migration tools (even simple search-and-rewrite scripts)

Organizational reality:

  • you will have many DSL programs across repos

  • changes must be rolled out safely

Bridge: from design to implementation

Once the DSL contract is clear, implementation choices follow from it:

  • Chosen semantics determine evaluator architecture

  • Safety boundaries determine what the runtime must forbid

  • Error UX requirements determine parser/type-checker diagnostics

The key idea: implementation exists to preserve the language decisions you already made.

Implementing a DSL

Implementation architecture (high level)

We assume parsing and AST construction already exist:

  • source text \(\rightarrow\) tokens \(\rightarrow\) AST

Today we focus on the design work that still matters after syntax is handled:

  • semantic checks (unknown variables, type mismatch)

  • evaluation model and outputs

  • errors designed for DSL authors

  • test harness and fixtures

Applying the Modules 3 and 5 pipeline to a DSL

Same mechanism as earlier modules:

  • Module 3: tagged union AST nodes represent syntax structurally

  • Module 5: a type checker walks the AST and rejects mismatches

What changes for a DSL:

  • AST contains only constructs your domain needs

  • Type checker enforces your DSL's rules, not a general-purpose type system

  • Error messages written for DSL authors, not engineers

Takeaway: DSL implementation is not a new skill. It is the same pipeline applied to a smaller, constrained language.

Tree-walking evaluator (TypeScript)

After parsing and type-checking, evaluation walks the AST:

type Env = Record<string, string | number | boolean>;

type Expr =
  | { kind: "var";  name: string }
  | { kind: "lit";  value: string | number | boolean }
  | { kind: "gte";  left: Expr; right: Expr }
  | { kind: "eq";   left: Expr; right: Expr }
  | { kind: "and";  left: Expr; right: Expr };

function evaluate(expr: Expr, env: Env): string | number | boolean {
  switch (expr.kind) {
    case "var":  return env[expr.name];
    case "lit":  return expr.value;
    case "gte":  return (evaluate(expr.left, env) as number) >= (evaluate(expr.right, env) as number);
    case "eq":   return evaluate(expr.left, env) === evaluate(expr.right, env);
    case "and":  return (evaluate(expr.left, env) as boolean)
    && (evaluate(expr.right, env) as boolean);
    }
  }

  • each kind maps to one branch: no hidden control flow

  • type-checker runs first, so casts here are safe

  • to add a new operator, add a variant to Expr and one case to the switch

Semantic checks: catch mistakes before runtime

Examples of static checks:

  • unknown variable names (typos)

  • type mismatch in operators (string < number)

  • rule condition must be boolean

  • unreachable rules (if conditions are contradictory)

Why this matters:

  • DSL authors may not have a debugger

  • production evaluation should be predictable and safe

Industry case studies

How companies pick languages

Beyond technical constraints, organizations weigh:

  • Hiring pool: engineer availability and salary band

  • Onboarding time: weeks to productivity for a new hire

  • Ecosystem lock-in: vendor and framework dependency accepted

  • Incremental adoption: migrate one service at a time, or all-or-nothing

  • Long-term governance: who owns the toolchain if it stalls

Name both the technical and organizational constraints, and most "language debates" resolve cleanly. The next four case studies show this in action.

Case study: Go at Google

Situation:

  • Massive C++ and Java monorepos

  • C++ compile times destroying developer velocity

  • Network services needed safe concurrency

  • Large rotating teams needed fast onboarding

Key constraints:

  • Build speed and iteration time

  • Safe, built-in concurrency for network services

  • Simple enough for large teams to review and onboard

  • Single-binary deployment, no runtime dependency

Decisions made:

  • Garbage collected (accept GC pauses, remove memory burden)

  • Goroutines and channels built into the language

  • No inheritance, no operator overloading (composition only)

  • One enforced style via gofmt; no code-review debates

  • No generics until 1.18 (simplicity first, expressiveness later)

Outcome:

  • Docker, Kubernetes, Terraform, most cloud-native tooling written in Go

Lesson: simplicity has organizational multipliers that technical benchmarks do not measure.

Case study: TypeScript at Microsoft

Situation:

  • Building VS Code, Office 365 web apps, TypeScript compiler itself

  • All large JavaScript codebases

  • Unsafe to refactor, hard to navigate

Key constraints:

  • Cannot break the JS ecosystem or require rewrites

  • IDE tooling (autocomplete, safe rename) must pay off immediately

  • Must support gradual, file-by-file adoption

Decisions made:

  • Structural typing (matches JS duck-typing; no nominal class tags)

  • any escape hatch lowers cost of starting

  • Types fully erased at runtime (no overhead, runs wherever JS does)

  • Compiles to plain JS (100% npm compatibility from day one)

Outcome:

  • Most top npm packages now ship TypeScript types

Lesson: migration path and tooling payoff drove adoption more than correctness arguments did.

Case study: Rust in systems software

Situation:

  • Many severe vulnerabilities in memory-unsafe codebases come from memory safety bugs

  • Use-after-free and buffer overflow remain common risks in C and C++

  • Garbage collection is not always acceptable in low-level or latency-sensitive systems

Key constraints:

  • No GC: latency predictability and embedded targets may require it

  • Memory safety must be statically guaranteed, not just audited

  • Performance must stay close to C/C++

Decisions made:

  • Ownership and borrow checker at compile time, zero runtime cost

  • No null by default; errors modeled as Result

  • Steep learning curve accepted as a trade-off

Outcome:

  • Rust support merged into the Linux kernel in 6.1

  • Adoption is strongest where teams will pay training cost for stronger safety guarantees

Lesson: high training cost can be worth paying when the alternative is security vulnerabilities at scale.

Case study: Java in enterprise systems

Situation:

  • Large organizations needed portable server software across many operating systems

  • Teams were building long-lived systems that had to survive staff turnover and platform changes

  • They needed libraries, frameworks, and tooling that could scale with many teams

Key constraints:

  • Cross-platform deployment mattered more than squeezing out every last bit of performance

  • Backward compatibility and maintainability mattered for systems expected to live for years

  • Organizations wanted standardized tooling and a deep hiring pool

Decisions made:

  • Compile to JVM bytecode so the same program can run across platforms

  • Use garbage collection to reduce manual memory-management burden

  • Invest in strong tooling, libraries, and compatibility over time

Outcome:

  • Java became a long-term default for enterprise backends and large business systems

  • The JVM ecosystem became a major adoption advantage, not just the language syntax

Lesson: portability, tooling, and compatibility can outweigh language elegance when organizations optimize for longevity.

Comparing Case Studies

  • Go: optimize for simplicity, onboarding, build speed, and operational clarity

  • TypeScript: optimize for migration path, IDE support, and ecosystem compatibility

  • Rust: optimize for safety and performance, even with higher training cost

  • Java: optimize for portability, tooling maturity, backward compatibility, and long-lived maintenance

General lesson: language choice is rarely about a single "best" language; it is about the best fit under real constraints.

  • Rust: safety can justify complexity
