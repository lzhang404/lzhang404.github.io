Core idea: subprograms are contracts

A subprogram is not just code. It is an interface promise.

  • Inputs: parameter types + meaning

  • Outputs: return type + meaning

  • Effects: mutation, I/O, global state, logging

  • Errors: throw, return codes, callbacks, promise rejection

  • Timing: sync vs async, may run later, may run multiple times

Contract checklist example

// What must a caller know?

type User = { id: string; name: string };

async function fetchUser(id: string): Promise<User> {
  const r = await fetch("/api/users/" + id);
  if (!r.ok) throw new Error("http " + r.status);
  return (await r.json()) as User;
}

  • Inputs: id is a string user id

  • Output: resolves to User

  • Effects: network I/O

  • Errors: throws (promise rejection)

  • Timing: async (later)

Procedures and Functions

Procedures vs functions

Procedure-like intent

  • Do an action, often returns void / None

  • Common for logging, I/O, mutation

Function-like intent

  • Compute and return a value

  • Easier to test when pure

function logLogin(userId: string): void {
  console.log("login", userId);
}

function discount(price: number, rate: number): number {
  return price * (1 - rate);
}

Design guideline: query vs command

  • Query: returns information, no state change

  • Command: changes state, return value is often not the point

class Cart {
  private total = 0;

  add(priceCents: number): void {  // command
    this.total += priceCents;
  }

  getTotal(): number {            // query
    return this.total;
  }
}

Mixing the two makes code harder to reason about.

Practice: query or command?

Classify each function by intent.

function nowMs(): number {
  return Date.now();
}

function pushAndReturn(xs: number[], x: number): number {
  xs.push(x);
  return xs.length;
}

function sum(xs: number[]): number {
  return xs.reduce((a, b) => a + b, 0);
}

  • Which ones have side effects?

  • Which ones are easiest to unit test?

Practice answers

  • sum is function-like (no effects if reduce is pure)

  • pushAndReturn is command-like (mutates xs)

  • nowMs looks function-like but depends on external time (not pure)

First-Class Functions

First-class functions

  • Assign to variables

  • Pass as arguments

  • Return from functions

  • Store in data structures

This enables callbacks and higher-order APIs.

TypeScript: function types

type Predicate<T> = (x: T) => boolean;

function countWhere<T>(xs: T[], p: Predicate<T>): number {
  let c = 0;
  for (const x of xs) if (p(x)) c++;
  return c;
}

console.log(countWhere([1, 2, 3, 4], x => x % 2 === 0));

Higher-order functions: map, filter, reduce

const nums = [1, 2, 3, 4, 5];

const squares = nums.map(x => x * x);
const evens = nums.filter(x => x % 2 === 0);
const sum = nums.reduce((acc, x) => acc + x, 0);

console.log(squares);
console.log(evens);
console.log(sum);

The callback provides behavior; the library provides control flow.

Callbacks and inversion of control

  • You do not call your callback; the library calls it

  • Callers need to know when it runs and how errors are reported

  • Async callbacks run later (after your function returns)

Practice: what runs, and when?

function register(handler: () => void): void {
  setTimeout(handler, 0);
}

console.log("A");
register(() => console.log("B"));
console.log("C");

  • What prints first: A, B, C?

  • Which line demonstrates async timing?

Practice answers

  • Print order: A, C, then B

  • setTimeout schedules the callback to run later

Java contrast: function values via interfaces

Java uses lambdas targeting functional interfaces.

import java.util.function.IntBinaryOperator;

class Demo {
  static int apply(int a, int b, IntBinaryOperator op) {
    return op.applyAsInt(a, b);
  }
  public static void main(String[] args) {
    System.out.println(apply(2, 3, (x, y) -> x + y));
  }
}

Parameters and Argument Passing

Parameter passing models (conceptual)

  • Pass-by-value: parameter gets a copy of a value

  • Pass-by-reference: parameter aliases caller variable

  • Pass-by-result / value-result: copy out on return

Real languages pick a concrete runtime behavior.

TypeScript: reassignment vs mutation

  • Arguments evaluate to values

  • The value is assigned to a local parameter variable

  • Reassigning the parameter does not change caller variable

  • Mutating a shared object changes what both can observe

function bump(n: number): void { n = n + 1; }
function mutate(u: { name: string }): void { u.name = "new"; }

let x = 10; bump(x); console.log(x);
let a = { name: "old" }; mutate(a); console.log(a.name);

Example: npx ts-node ts_param.ts

Pass-by-reference (what would be different?)

  • If parameters alias caller variables, reassignment updates caller

  • Many mainstream languages restrict this for safety

// C++ example idea (reference parameter)
void reassign(int& x) { x = 99; }  // caller changes

Practice: predict the output

function change(n: number, obj: { v: number }): void {
  n = n + 100;
  obj.v = obj.v + 100;
}

let a = 1;
let b = { v: 1 };

change(a, b);

console.log(a);
console.log(b.v);

Practice answer

  • a stays 1 (parameter reassignment is local)

  • b.v becomes 101 (mutation of shared object)

Python analogy: reassignment is local, mutation is shared

def reassign(lst):
    lst = [99]     # local name now points elsewhere

def mutate(lst):
    lst.append(99) # mutates shared object

a = [1, 2]
reassign(a)
print(a)           # [1, 2]
mutate(a)
print(a)           # [1, 2, 99]

Defaults and API Readability

Default parameters in TypeScript

Defaults apply when the argument is missing or undefined.

function greet(name: string, punctuation: string = "!"): string {
  return "Hello, " + name + punctuation;
}

console.log(greet("Ada"));
console.log(greet("Ada", "!!"));

Why options objects

  • Many parameters become unreadable at call sites

  • Booleans are especially ambiguous

  • Options objects are easier to extend later

TypeScript: named arguments via options object

type RequestOptions = { timeoutMs?: number; retries?: number; cache?: boolean; };

function request(url: string, opts: RequestOptions = {}): void {
  const timeoutMs = opts.timeoutMs ?? 2000;
  const retries = opts.retries ?? 2;
  const cache = opts.cache ?? true;
  console.log(url, timeoutMs, retries, cache);
}

request("/api/users");
request("/api/users", { retries: 3, cache: false });
request("/api/users", { timeoutMs: 5000 });

Example: npx ts-node ts_options_object.ts

Practice: redesign a confusing signature

function connect(host: string, port: number, timeoutS: number, useTls: boolean): void {
  console.log(host, port, timeoutS, useTls);
}

// What does this mean without looking up docs?
connect("db.local", 5432, 2.0, true);

  • Rewrite with an options object and sensible defaults

  • Show 2 clearer call sites

Practice answer

type ConnectOpts = { port?: number; timeoutS?: number; useTls?: boolean };

function connect(host: string, opts: ConnectOpts = {}): void {
  const port = opts.port ?? 5432;
  const timeoutS = opts.timeoutS ?? 2.0;
  const useTls = opts.useTls ?? true;
  console.log(host, port, timeoutS, useTls);
}

connect("db.local");
connect("db.local", { useTls: false, timeoutS: 5.0 });

Variadic parameters (rest args)

function sum(...xs: number[]): number {
  return xs.reduce((acc, x) => acc + x, 0);
}

console.log(sum(1, 2, 3));
console.log(sum(10));

Python: default and keyword arguments

def connect(host, port=5432, timeout_s=2.0):
    return (host, port, timeout_s)

print(connect("db.local"))
print(connect("db.local", timeout_s=5.0))
print(connect(host="db.local", port=6000))

Python pitfall: mutable default arguments

Default values are evaluated once at function definition.

def add_item(x, xs=[]):
    xs.append(x)
    return xs

print(add_item(1))  # [1]
print(add_item(2))  # [1, 2] surprising

Safe pattern uses None.

def add_item_safe(x, xs=None):
    if xs is None:
        xs = []
    xs.append(x)
    return xs

Java: defaults via overloading

class Connector {
  static String connect(String host) {
    return connect(host, 5432, 2.0);
  }
  static String connect(String host, int port) {
    return connect(host, port, 2.0);
  }
  static String connect(String host, int port, double timeoutS) {
    return host + ":" + port + " timeout=" + timeoutS;
  }
}

Callbacks and Async Control Flow

Closure recap (already covered in Module 4)

  • Closures: function + captured bindings

  • Callbacks often run later, so timing matters

  • Module 4 showed classic loop-capture bugs and fixes

This module focuses on async contracts: errors, composition, cancellation.

Error signaling patterns

  • Throw (sync): try/catch

  • Error-first callback: (err, value)

  • Promise rejection: catch or try/catch with await

  • Result object: { ok, value, error }

Result object pattern (TypeScript)

type ParseResult =
  | { ok: true; value: number }
  | { ok: false; error: string };

function parseIntSafe(s: string): ParseResult {
  const n = Number.parseInt(s, 10);
  if (Number.isNaN(n)) return { ok: false, error: "not an int" };
  return { ok: true, value: n };
}

const r = parseIntSafe("123x");
if (r.ok) console.log(r.value);
else console.log("error", r.error);

Callback-based async style

type Callback<T> = (err: Error | null, value?: T) => void;

function readUser(id: string, cb: Callback<{ id: string; name: string }>): void {
  setTimeout(() => cb(null, { id, name: "Ada" }), 10);
}
function readOrders(userId: string, cb: Callback<string[]>): void {
  setTimeout(() => cb(null, ["A1", "B2"]), 10);
}

readUser("u1", (err, user) => {
  if (err || !user) return console.log("error", err);
  readOrders(user.id, (err2, orders) => {
    if (err2 || !orders) return console.log("error", err2);
    console.log(user.name, orders);
  });
});

  • Harder to add retries, timeouts, cleanup

  • Error handling duplicated at each nesting level

Promises reduce nesting

function readUserP(id: string): Promise<{ id: string; name: string }> {
  return new Promise(resolve => setTimeout(() => resolve({ id, name: "Ada" }), 10));
}
function readOrdersP(userId: string): Promise<string[]> {
  return new Promise(resolve => setTimeout(() => resolve(["A1", "B2"]), 10));
}

readUserP("u1")
  .then(user => readOrdersP(user.id).then(orders => [user, orders] as const))
  .then(([user, orders]) => console.log(user.name, orders))
  .catch(err => console.log("error", err));

async/await for sequential readability

async function workflow(): Promise<void> {
  try {
    const user = await readUserP("u1");
    const orders = await readOrdersP(user.id);
    console.log(user.name, orders);
  } catch (err) {
    console.log("error", err);
  }
}
workflow();

try/catch works for awaited promise rejections.

Async composition: sequential vs parallel

Sometimes independent tasks should run concurrently.

async function loadTwo(): Promise<void> {
  const p1 = readUserP("u1");
  const p2 = readUserP("u2");
  const [u1, u2] = await Promise.all([p1, p2]);
  console.log(u1.name, u2.name);
}

Cancellation (contract detail)

  • Long-running async work often needs cancellation

  • Common pattern in JS: AbortController / AbortSignal

  • APIs should document what gets canceled and what cleanup happens

// Conceptual: fetch supports AbortSignal
const c = new AbortController();
fetch("/api/users", { signal: c.signal }).catch(e => console.log("err", e));
c.abort();

Practice: refactor callbacks to async/await

type Callback<T> = (err: Error | null, value?: T) => void;

function step1(cb: Callback<number>): void { setTimeout(() => cb(null, 10), 10); }
function step2(x: number, cb: Callback<number>): void { setTimeout(() => cb(null, x + 5), 10); }
function step3(x: number, cb: Callback<number>): void { setTimeout(() => cb(null, x * 2), 10); }

step1((e1, a) => {
  if (e1 || a === undefined) return console.log("error", e1);
  step2(a, (e2, b) => {
    if (e2 || b === undefined) return console.log("error", e2);
    step3(b, (e3, c) => {
      if (e3 || c === undefined) return console.log("error", e3);
      console.log("result", c);
    });
  });
});

  • Wrap each step in a Promise

  • Use async/await

  • One try/catch for errors

Practice answer (sketch)

function step1P(): Promise<number> {
  return new Promise((resolve, reject) => {
    step1((e, v) => (e || v === undefined) ? reject(e ?? new Error("missing")) : resolve(v));
  });
}
function step2P(x: number): Promise<number> {
  return new Promise((resolve, reject) => {
    step2(x, (e, v) => (e || v === undefined) ? reject(e ?? new Error("missing")) : resolve(v));
  });
}
function step3P(x: number): Promise<number> {
  return new Promise((resolve, reject) => {
    step3(x, (e, v) => (e || v === undefined) ? reject(e ?? new Error("missing")) : resolve(v));
  });
}

async function run(): Promise<void> {
  try {
    const a = await step1P();
    const b = await step2P(a);
    const c = await step3P(b);
    console.log("result", c);
  } catch (err) {
    console.log("error", err);
  }
}
run();

Closures in Industry

Stale closure pattern

Handlers created earlier may observe older snapshots of state.

let count = 0;

function makeHandler() {
  const snapshot = count;
  return () => console.log("snapshot", snapshot, "current", count);
}

const h = makeHandler();
count = 5;
h();

  • snapshot is chosen at handler creation

  • current is read at handler call time

Practice: diagnose stale state

let state = 0;

function register(handler: () => void): void {
  setTimeout(handler, 0);
}

function render() {
  const snapshot = state;
  register(() => console.log("snapshot", snapshot, "state", state));
}

render();
state = 10;

  • What prints?

  • Give one fix that avoids relying on a stale snapshot

Practice answers

  • It prints: snapshot 0 state 10

  • Fix idea: do not capture snapshot; read state inside the callback when needed

function renderFixed() {
  register(() => console.log("state", state));
}

Retention and accidental memory growth

  • Long-lived callbacks can keep captured objects alive

  • If an event system stores your handler, your captures may live “forever”

  • Mitigation: capture only needed data, avoid capturing large objects

function makeHandler(big: number[]) {
  return () => console.log(big.length);
}

const big = new Array(1_000_000).fill(0);
const handler = makeHandler(big);

// If handler is stored globally, big stays alive too.

Pattern: memoization

function memoize1<A, R>(f: (a: A) => R): (a: A) => R {
  const cache = new Map<A, R>();
  return (a: A) => {
    if (cache.has(a)) return cache.get(a)!;
    const r = f(a);
    cache.set(a, r);
    return r;
  };
}

const slow = (x: number) => x * x;
const fast = memoize1(slow);
console.log(fast(10));
console.log(fast(10));

Pattern: debounce

function debounce(fn: () => void, delayMs: number): () => void {
  let timer: ReturnType<typeof setTimeout> | undefined;
  return () => {
    if (timer !== undefined) clearTimeout(timer);
    timer = setTimeout(() => fn(), delayMs);
  };
}

let fired = 0;
const h = debounce(() => { fired++; console.log("fired", fired); }, 200);

h(); h(); h();

Pattern: dependency injection

Capture dependencies once instead of using globals everywhere.

type Logger = { log: (msg: string) => void };

function makeGreeter(logger: Logger): (name: string) => void {
  return (name: string) => logger.log("hello " + name);
}

const consoleLogger: Logger = { log: (msg) => console.log(msg) };
const greet = makeGreeter(consoleLogger);
greet("Ada");

Rule of thumb

Use closures for

  • Configuration fixed at creation time

  • Private state (cache, counter)

  • Dependency injection

Avoid closures that capture

  • Large objects unnecessarily

  • Rapidly changing values when you need the latest state

  • Hidden state that makes debugging history-dependent
