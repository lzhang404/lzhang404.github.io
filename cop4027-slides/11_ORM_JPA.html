From JDBC to ORM

What JDBC Made Us Do

JDBC gives direct control over SQL, but our Repository still has repeated mapping work.

  • Write SQL strings for each operation.

  • Bind Java values into a PreparedStatement.

  • Read columns from a ResultSet.

  • Build Java objects from database rows.

  • Repeat similar code in many repository methods.

Manual Row Mapping

The Repository translates between database rows and Java domain objects.

private TaskItem mapTaskItem(ResultSet rows) throws SQLException {
    return new TaskItem(
            rows.getLong("id"),
            rows.getString("title"),
            rows.getBoolean("done"));
}

  • The database stores rows and columns.

  • The Java application works with TaskItem objects.

  • Mapping code connects those two representations.

The Object-Relational Gap

Java and relational databases organize data differently.

  • Java uses objects, fields, references, and methods.

  • Relational databases use tables, columns, rows, and keys.

  • An application often needs to move data between these two models.

  • Manual JDBC mapping makes that movement explicit.

  • Mapping frameworks can reduce repeated object-row translation code.

What ORM Means

ORM means object-relational mapping.

  • A Java class maps to a database table.

  • An object maps to one row in that table.

  • A field maps to a column.

  • An object ID maps to a primary key.

  • The ORM provider handles much of the object-row translation.

JPA, Hibernate, and Spring Data JPA

These names are related, but they are not the same thing.

  • JPA: the Java/Jakarta standard API for object-relational mapping.

  • Hibernate: a common implementation of JPA.

  • Spring Data JPA: Spring repository support built on top of JPA.

JPA defines the mapping model.
Hibernate performs the mapping work.
Spring Data JPA reduces repository code.

Where This Fits in Three-Tier

JPA and Spring Data JPA change the data tier. The rest of the application should stay separated from persistence details.

  • The presentation tier should not know how data is stored.

  • The application tier should call persistence operations through a boundary.

  • The data tier maps entities and communicates with the database.

Presentation -> Application -> Repository -> JPA -> Database

Mapping a TaskItem Entity

Entity, Table, Column, Row

JPA uses the word entity for a Java object that can be stored in a database.

  • An entity class maps to a table.

  • Each entity object maps to a row.

  • Each persistent field maps to a column.

  • Each entity has an identity value, usually mapped to a primary key.

TaskItem as a JPA Entity

TaskItem is the persistent object that JPA stores and loads.

@Entity
@Table(name = "task_items")
public class TaskItem {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private boolean done;
}

  • @Entity marks this class as persistent.

  • @Table connects the class to the task_items table.

  • @Id identifies the primary-key field.

  • @GeneratedValue marks the ID as generated when the entity is saved.

JPA Entity Requirements

A JPA entity has requirements that are different from a simple data record.

  • The entity class needs a no-argument constructor.

  • The entity class should not be final.

  • Persistent fields should not be final.

  • JPA providers need to create and manage entity objects.

  • A Java record is not used as a JPA entity.

Constructors

JPA needs a no-argument constructor, while application code can use a clearer constructor.

protected TaskItem() {
    // Used by JPA
}

public TaskItem(String title) {
    this.title = title;
    this.done = false;
}

  • The no-argument constructor can be protected.

  • The application constructor expresses how a new task item is created.

  • JPA can still create entity objects when it loads rows.

Identity: @Id and @GeneratedValue

Each entity needs an identity value.

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

  • @Id marks the entity identifier.

  • The identifier usually maps to the table primary key.

  • With GenerationType.IDENTITY, the database generates the ID.

  • New objects usually have no ID until they are saved.

Column Mapping

Fields can use default column names, or we can give JPA more detail.

@Column(nullable = false, length = 100)
private String title;

@Column(nullable = false)
private boolean done;

  • @Column customizes how a field maps to a column.

  • nullable = false means the column should not accept null values.

  • length = 100 limits the text column size.

  • The database still enforces constraints when data is written.

Entity Methods

An entity can contain simple state-changing methods.

public void setDone(boolean done) {
    this.done = done;
}

public void rename(String title) {
    if (title == null || title.isBlank()) {
        throw new IllegalArgumentException("Title required");
    }
    this.title = title.trim();
}

  • Entity methods can protect simple object state.

  • Larger application operations still belong in the service layer.

What JPA Persists

JPA persists entity objects, even when the application also uses collection objects.

  • TaskItem is an entity and maps to one row.

  • TaskList is an application collection of task items.

  • TaskRepository loads and saves TaskItem entities.

  • TaskList does not become a database table simply because the application uses it.

Working with Entities

JPA Works Through an Entity Manager

The lower-level JPA API uses an EntityManager to work with entities.

  • persist(...) stores a new entity.

  • find(...) loads an entity by its ID.

  • remove(...) deletes an entity.

  • Queries can load entities that match a condition.

  • Spring Data JPA will hide much of this direct API.

Basic Entity Operations

JPA operations work with entity objects rather than raw rows.

TaskItem item = new TaskItem("Review ORM");

entityManager.persist(item);

TaskItem saved = entityManager.find(TaskItem.class, item.getId());

saved.setDone(true);     // JPA can track this change

entityManager.remove(saved);

  • The application works with TaskItem objects.

  • JPA translates object operations into database work.

  • Repository code can use JPA instead of manual JDBC mapping.

Persistence Context

The persistence context is the set of entity objects currently managed by JPA.

  • A managed entity is being tracked by JPA.

  • JPA knows which object represents which database row.

  • Changes to managed entities can be written to the database.

  • The persistence context usually works within a transaction.

database row <-> managed TaskItem object

Entity States

An entity object can be in different states.

  • New: a new object not yet managed by JPA.

  • Managed: an object currently tracked by the persistence context.

  • Detached: an object that was managed before but is no longer tracked.

  • Removed: an object marked for deletion.

Dirty Checking

JPA can detect changes to managed entities.

TaskItem item = entityManager.find(TaskItem.class, id);

item.setDone(true);

  • If item is managed, JPA tracks the change.

  • The update can be written when the transaction is flushed or committed.

  • This is different from JDBC, where we write the UPDATE ourselves.

Transactions Still Matter

ORM does not remove the need for transactions.

  • A transaction groups database work into one unit.

  • Writes should happen inside a transaction.

  • Commit makes the changes permanent.

  • Rollback cancels changes if something fails.

  • Spring usually manages transactions with @Transactional.

Queries with JPQL

JPA can query entities using JPQL, which talks about entities instead of tables.

List<TaskItem> items = entityManager
        .createQuery(
                "select item from TaskItem item where item.done = false",
                TaskItem.class)
        .getResultList();

  • TaskItem is the entity class name.

  • item.done is an entity field.

  • The result is a list of TaskItem objects.

Manual JPA Repository Idea

A manual JPA Repository can use EntityManager instead of JDBC.

public List<TaskItem> findAll() {
    return entityManager
            .createQuery("select item from TaskItem item", TaskItem.class)
            .getResultList();
}

public void add(String title) {
    entityManager.persist(new TaskItem(title));
}

  • The Repository still exposes application-level operations.

  • JPA handles much of the row-to-object mapping.

  • Spring Data JPA will reduce this code further.

Spring Data JPA

What Spring Data JPA Adds

Spring Data JPA builds Repository support on top of JPA.

  • JPA gives us entity mapping and persistence APIs.

  • Hibernate commonly performs the actual mapping work.

  • Spring Data JPA creates repository implementations from interfaces.

  • We still design the entity, repository interface, and application structure.

Spring Data JPA with Maven

A Spring Boot project usually uses the Spring Data JPA starter.

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>

  • The JPA starter brings Spring Data JPA and a JPA provider.

  • H2 gives us a small database for development and testing.

Basic JPA Configuration

Spring Boot can configure JPA from application properties.

spring.datasource.url=jdbc:h2:file:./data/tasksdb
spring.datasource.username=sa
spring.datasource.password=

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true

  • The datasource properties tell Spring how to connect to the database.

  • ddl-auto=update lets Hibernate update the schema during development.

  • show-sql=true prints generated SQL so we can inspect the ORM behavior.

Spring Data Repository Interface

Spring Data JPA can create the repository implementation from an interface.

public interface TaskRepository
        extends JpaRepository<TaskItem, Long> {
}

  • TaskItem is the entity type.

  • Long is the ID type.

  • Spring Data JPA supplies the implementation at runtime.

What JpaRepository Gives Us

The repository already has common persistence methods.

  • findAll() loads all entities.

  • findById(id) loads one entity by ID.

  • save(entity) inserts or updates an entity.

  • deleteById(id) deletes by ID.

  • existsById(id) checks whether an ID exists.

Reading with a Repository

Repository read methods return entity objects instead of database rows.

List<TaskItem> items = repository.findAll();

Optional<TaskItem> item =
        repository.findById(id);

  • findAll() returns a list of entities.

  • findById(...) returns an Optional because the ID may not exist.

  • The caller does not handle ResultSet or row-mapping code.

Changing Persistent Data

Repository write methods hide common insert, update, and delete work.

TaskItem saved =
        repository.save(new TaskItem("Review JPA"));

TaskItem item = repository.findById(id)
        .orElseThrow(() -> new IllegalArgumentException("Task item not found"));

item.setDone(true);
repository.save(item);

repository.deleteById(id);

  • save(...) stores a new entity or an updated entity.

  • deleteById(...) deletes by primary key.

  • The application does not write SQL for these common operations.

Derived Query Methods

Spring Data JPA can create some queries from method names.

public interface TaskRepository
        extends JpaRepository<TaskItem, Long> {

    List<TaskItem> findByDone(boolean done);

    List<TaskItem> findByTitleContainingIgnoreCase(String text);
}

  • The method name describes the query.

  • Spring Data JPA creates the query implementation.

  • Use simple derived queries for simple search needs.

Sorting Results

Spring Data repositories can support sorted results.

List<TaskItem> items = repository.findAll(
        Sort.by("id").ascending());

  • The sort uses an entity property name.

  • Sorting belongs near the data request.

  • The View should not sort by directly querying the database.

From Manual Repository Code to Spring Data JPA

The goal is still a persistence boundary, but Spring Data JPA removes much repeated implementation code.

  • Manual JDBC Repository: write SQL, bind parameters, read rows, and map objects.

  • Manual JPA Repository: use EntityManager and entities.

  • Spring Data JPA Repository: define an interface and let Spring supply common implementations.

  • Common save, find, and delete methods no longer need hand-written repository code.

What Code Remains?

Spring Data JPA does not remove application design work.

  • Entity classes still need correct mappings.

  • Service methods still need application rules.

  • Transactions still need clear boundaries.

  • Custom queries still need careful design.

  • Controllers still should not become persistence code.

Custom Query with @Query

When a derived method name is not clear enough, we can write a query.

@Query("""
       select item from TaskItem item
       where lower(item.title) like lower(concat('%', :text, '%'))
       """)
List<TaskItem> searchByTitle(@Param("text") String text);

  • The query uses entity names and fields.

  • The method still belongs in the Repository interface.

  • Use custom queries when method names become hard to read.

Service Layer with Spring Data JPA

Why Add a Service Layer?

Spring applications often place application operations in a service class.

  • The Controller handles user or request input.

  • The Service handles application rules and operations.

  • The Repository handles persistence.

  • The entity represents persistent data.

  • This keeps the three-tier responsibilities clear.

TaskService

The service coordinates task item operations.

@Service
public class TaskService {
    private final TaskRepository repository;

    public TaskService(TaskRepository repository) {
        this.repository = repository;
    }
}

  • @Service marks application logic.

  • The service depends on the Repository interface.

  • Constructor injection supplies the Repository.

Add Task Item Operation

The service owns the application rule for adding a task item.

public TaskItem addTaskItem(String title) {
    if (title == null || title.isBlank()) {
        throw new IllegalArgumentException("Title required");
    }

    return repository.save(new TaskItem(title.trim()));
}

  • The Service checks the application rule.

  • The Repository performs persistence.

  • The Controller should not duplicate this rule.

Mark Task Item Done

The service can load an entity, change it, and save it.

public TaskItem setDone(Long id, boolean done) {
    TaskItem item = repository.findById(id)
            .orElseThrow(() -> new IllegalArgumentException("Task item not found"));

    item.setDone(done);
    return repository.save(item);
}

  • The service decides what the operation means.

  • The Repository provides database access.

  • The error message stays near the application operation.

@Transactional

A transaction groups database work into one unit.

@Transactional
public TaskItem setDone(Long id, boolean done) {
    TaskItem item = repository.findById(id)
            .orElseThrow(() -> new IllegalArgumentException("Task item not found"));

    item.setDone(done);  // tracked because item is managed
    return item;
}

  • The entity is managed inside the transaction.

  • JPA can detect the changed field.

  • The change is written when the transaction commits.

Read-Only Service Methods

Read operations can be marked as read-only transactions.

@Transactional(readOnly = true)
public TaskList findAllTaskItems() {
    List<TaskItem> items =
            repository.findAll(Sort.by("id").ascending());

    return new TaskList(items);
}

  • The method loads task items but does not intentionally change them.

  • TaskList gives the application a collection object.

  • The service gives the Controller a simple operation to call.

Add Task Item Flow

The same three-tier flow still applies.

Controller receives input
    -> Service checks rule and starts operation
    -> Repository saves the TaskItem
    -> JPA maps the entity to a database row
    -> Database stores the row

  • The Controller handles interaction.

  • The Service handles application behavior.

  • The Repository and JPA handle persistence.

Controller Uses the Service

The Controller should call application operations, not own persistence rules.

public void addClicked() {
    try {
        service.addTaskItem(view.getEnteredTitle());
        view.refresh();
        view.setStatus("Task item saved");
    } catch (IllegalArgumentException exception) {
        view.setStatus(exception.getMessage());
    }
}

  • The Controller handles the event and feedback.

  • The Service performs the task item operation.

  • The Repository is not used directly by the View.

Testing and Development

Using H2 for Development

H2 is useful for small examples and development testing.

  • It can run without installing a separate database server.

  • It works well for small applications, examples, and tests.

  • It lets us inspect generated tables and SQL.

  • It should not hide the need to understand transactions and mappings.

Testing a Service

A service test can use a Repository connected to a test database.

@Test
void addTaskItemSavesEntity() {
    TaskItem saved = service.addTaskItem("Review Spring Data JPA");

    assertNotNull(saved.getId());
    assertEquals("Review Spring Data JPA", saved.getTitle());
}

  • The test checks the application operation.

  • The generated ID shows that persistence happened.

  • More focused unit tests can still test rules separately.

Testing Repository Queries

Repository tests should focus on persistence behavior.

  • Does the entity save correctly?

  • Does the query return the expected rows?

  • Does sorting or filtering work?

  • Does the test database start with known data?

  • Focus repository tests on mappings and custom query behavior.

Common Mistakes

Common JPA Mistakes

  • Forgetting the entity ID field.

  • Using a Java record as an entity.

  • Making the entity class or persistent fields final.

  • Forgetting the no-argument constructor.

  • Assuming @Entity by itself saves an object.

  • Expecting detached objects to update the database automatically.

  • Ignoring transaction boundaries.

Common Spring Data Mistakes

  • Putting application rules directly inside the Controller.

  • Calling the Repository from the View.

  • Writing very long derived query method names.

  • Forgetting that findById returns Optional.

  • Assuming Spring Data removes the need for transactions.

  • Letting database annotations replace application validation.

Design Mistakes to Avoid

  • Mixing UI code into entity classes.

  • Treating entities as View objects.

  • Putting all application behavior inside Repository methods.

  • Letting Controller, Service, and Repository all repeat the same rule.

  • Forgetting that three-tier responsibilities still apply.

JPA changes how objects are stored.
It does not remove the need for good application structure.

Summary

Key Takeaways

  • TaskItem is the persistent to-do item; TaskList is the collection.

  • ORM maps Java objects to relational database rows.

  • JPA defines the standard mapping model and API.

  • Hibernate is a common JPA implementation.

  • An entity class maps to a table.

  • Managed entities are tracked in a persistence context.

  • Spring Data JPA supplies repository implementations from interfaces.

  • The Service layer keeps application operations separate from persistence details.

Where We Are Now

The persistence tier has changed, but the architecture remains familiar.

Before:
Controller -> TaskModel -> JDBC Repository -> Database

Now:
Controller -> TaskService -> Spring Data Repository -> JPA -> Database

  • The Controller handles interaction.

  • The Service handles application operations.

  • The Repository handles persistence access.

JavaFX:
button click -> Controller -> Service -> Repository

Spring Web:
HTTP request -> Web Controller -> Service -> Repository

The input mechanism changes, but the three-tier structure still guides where code belongs.
