Why Types?

Type errors and type safety

Type error:

  • Program uses a value in a way that does not match its type.

  • Examples: add integer to string, call something that is not a function.

Type safety (informal):

  • A language is type-safe if well-typed programs do not cause certain type errors at runtime.

  • Static type systems try to catch type errors before execution.

  • Dynamic checks catch type errors when that code path runs.

Reality check:

  • C is not type-safe (casts/pointers can break abstractions).

  • Java/C#/Rust aim for stronger safety guarantees.

  • TypeScript increases safety on top of JavaScript.

Type errors in practice

Compile-time type error (C / TypeScript):

// C: compile-time error
int n = 10;
n = "hello";   // incompatible types

Runtime type error (Python):

# Python: runtime error
x = 10
y = "20"
z = x + y  # TypeError happens when this line runs

Undefined behavior (C):

// C: undefined behavior, not a well-defined type error
int *p = NULL;
*p = 42;   // may crash or do anything

Files: py_runtime_type_error.py, c_undefined_behavior.c

Takeaway

  • Types are a tool for preventing entire categories of bugs.

  • Different languages enforce types at different times (before run vs during run).

  • Some languages allow “escape hatches” that reduce safety (casts, any, unchecked reflection).

Typing Dimensions

Static vs dynamic typing

Static typing:

  • Many checks happen before the program runs.

  • Examples: C, C++, Java, C#, Rust, Go, TypeScript.

Dynamic typing:

  • Types are checked at runtime when the code path runs.

  • Examples: Python, Ruby, JavaScript, Lua, PHP.

Mixed world:

  • TypeScript adds static checking on top of JavaScript.

  • Some languages add optional type hints + external checkers.

Static vs dynamic: examples

// C: static typing
int n = 10;
n = "hello";   // compile-time error
# Python: dynamic typing
n = 10
n = "hello"    # allowed, type changes at runtime
// TypeScript: static checking
let n: number = 10;
n = "hello";   // type error from TypeScript checker

Static vs dynamic: trade-offs

Static typing:

  • Catch many mistakes earlier.

  • Better refactoring and tooling.

  • Types document intent.

  • May add up-front design/boilerplate.

Static vs dynamic: trade-offs (cont.)

Dynamic typing:

  • Flexible and concise.

  • Great for scripts and experiments.

  • Some errors appear only in rarely executed paths.

  • Large systems can drift without strong interfaces/contracts.

Many teams mix both:

  • TypeScript + JavaScript.

  • Python + optional type hints + checkers.

Strong vs weak typing

Strong typing (informal):

  • Fewer implicit conversions between “unrelated” types.

  • Mixing incompatible types tends to error out.

Weak typing (informal):

  • More implicit conversions/coercions.

  • Can “make something work” but also create surprises.

Note:

  • Strong/weak are not precise definitions; usage varies.

  • Use these terms as a rough description of coercion behavior.

Strong vs weak vs static vs dynamic

Two mostly independent axes:

  • When are checks done? (static vs dynamic)

  • How much coercion is allowed? (strong vs weak)

Rough examples:

  • Static and relatively strong: Java, C#, Rust, Haskell.

  • Static and weaker: C (casts, pointer tricks).

  • Dynamic and strong-ish: Python, Ruby.

  • Dynamic and weaker: JavaScript coercions.

Takeaway:

  • Static vs dynamic is about timing.

  • Strong vs weak is about coercions/strictness.

Weak typing example: JavaScript

// JavaScript implicit conversions
1 + "2"        // "12"   (number + string -> string)
"3" * "4"      // 12     (strings converted to numbers)
true + 1       // 2
false == 0     // true
"0" == 0       // true

Python behaves differently:

1 + "2"     # TypeError in Python
"3" * "4"   # TypeError
True + 1    # result is 2, but bool is a subclass of int

Example: node js_coercions.js

TypeScript Basics

What is TypeScript?

  • Superset of JavaScript with static checking.

  • Compiles down to plain JavaScript.

  • Designed for large applications and teams.

  • Can be gradually added to existing JavaScript code.

Big picture:

  • Same runtime as JavaScript.

  • Better tooling: autocomplete, refactoring, safer renaming.

  • Helps catch bugs before shipping.

Why industry adopts TypeScript

  • Better editor support and refactoring tools.

  • Fewer runtime type errors in production.

  • Clear contracts between modules and services.

  • Easier onboarding for new team members.

  • Works well with modern frameworks (React, Angular, Vue).

Typed languages are common across stacks:

  • Backend: Java, C#, Go, Rust.

  • Systems: C, C++, Rust.

  • Front end: TypeScript.

TypeScript: basic annotations

// variable annotations
let count: number = 0;
let name: string = "Alice";
let done: boolean = false;

// function annotations
function add(a: number, b: number): number {
  return a + b;
}

// arrays
let nums: number[] = [1, 2, 3];
let names: Array<string> = ["a", "b"];

TypeScript checks that you use these values in a safe way.

Type inference in TypeScript

TypeScript often infers types without explicit annotations.

let x = 10;         // inferred as number
let message = "hi"; // inferred as string

function square(n: number) {
  return n * n;     // inferred return type: number
}

let result = square(5); // number
result = "oops";        // error

any vs unknown in TypeScript

any:

  • Opt-out of checking.

  • Use sparingly (especially in public APIs).

let value: any = 42;
value = "hello";
value.toUpperCase();   // allowed, no error
value.nonExisting();   // still allowed

unknown:

  • For “I don’t know yet,” but forces narrowing before use.

let value: unknown = 42;

if (typeof value === "number") {
  let double = value * 2;    // ok
}

// value.toUpperCase(); // error: unknown is not string

Example: ts_any_unknown.ts

Practice: any or unknown?

You are parsing JSON from the network. Which type is safer for the first step?

const raw = JSON.parse(text);
// choose: any or unknown?
const data: ??? = raw;

  • Answer: unknown is safer because it forces checks before use.

Primitive Types

Primitive types across languages

Common primitive types:

  • Numeric: int, float, double

  • Boolean: true or false

  • Character: single Unicode or byte char

  • String: sequence of characters

How some languages handle them:

  • C: int, double, char, no built-in string type (char arrays)

  • Java/C#: int, double, boolean, char, String class

  • JavaScript: number, boolean, string (no separate int vs float)

  • Python: int, float, bool, str

  • Rust/Go: many numeric sizes (i32, u64, f32, etc.)

Numeric types and overflow

Fixed-size integers (C, C++, Java, C#, Rust):

  • int32, int64, etc. have a maximum and minimum value.

  • Overflow behavior depends on the language.

Unbounded integers (Python, Java BigInteger, Haskell Integer):

  • Integers can grow arbitrarily large (limited by memory).

  • No overflow, but arithmetic can be slower.

JavaScript and TypeScript:

  • number is usually 64-bit floating point.

  • BigInt exists for integers that cannot fit in number.

Numeric types and overflow: examples

// C: signed overflow is undefined behavior (not guaranteed wrap)
int x = 2147483647; // INT_MAX (typical 32-bit)
x = x + 1;          // undefined behavior in C for signed int overflow
# Python: big integers, no overflow
x = 2 ** 100
print(x)  # very large integer

Primitive types: examples

// C
int count = 10;
double price = 19.99;
char letter = 'A';
# Python
count = 10           # int
price = 19.99        # float
letter = "A"         # string of length 1
flag = True          # bool
// JavaScript
let count = 10;      // number
let price = 19.99;   // number
let name = "Alice";  // string
let done = false;    // boolean

Strings and characters across languages

Characters:

  • C: char is usually one byte.

  • Java/C#: char is a Unicode code unit.

  • Python/JavaScript: no separate char type (strings of length 1).

Strings:

  • C: char arrays with '\0' terminator.

  • Java/C#: immutable String objects.

  • Python: immutable str, Unicode.

  • JavaScript/TypeScript: immutable string.

// C string: char array with terminator
char msg[] = "hi";     // 'h', 'i', '\0'
# Python string
msg = "hi"
ch = msg[0]   # "h"

Composite Types

Composite types: arrays and records

Arrays and lists:

  • Ordered sequence of elements.

  • Often all elements have the same type.

Records and objects:

  • Group fields under one name.

  • Fields can have different types.

Examples:

  • C: arrays, structs.

  • Java/C#: arrays, classes.

  • Python: list, dict, dataclass.

  • JavaScript/TypeScript: arrays, plain objects.

Arrays and records: examples

// C
int nums[3] = {1, 2, 3};
struct Point {
  int x;
  int y;
};
struct Point p = { .x = 10, .y = 20 };
// TypeScript
let nums: number[] = [1, 2, 3];
type Point = {
  x: number;
  y: number;
};
let p: Point = { x: 10, y: 20 };

Maps and dictionaries

Associative collections:

  • Store key-value pairs.

  • Often called maps, dictionaries, hash tables.

Common forms:

  • C++: map, unordered_map.

  • Java/C#: Map, Dictionary.

  • Python: dict.

  • JavaScript: objects and Map.

  • TypeScript: Record types and Map.

# Python dict
ages = {"Alice": 30, "Bob": 25}
print(ages["Alice"])   # 30
// TypeScript Record
type Ages = Record<string, number>;
const ages: Ages = { Alice: 30, Bob: 25 };

Unions and enums

Unions:

  • A value that may be one of several variants.

  • C has union (unsafe if you read the wrong field).

  • TypeScript has union types and safe narrowing.

Enums:

  • Fixed set of named constants (states/modes).

Union example in C (unsafe if misused)

// C union: unsafe if misused
union IntOrFloat {
  int i;
  float f;
};

int main(void) {
  union IntOrFloat x;
  x.i = 42;           // store an int
  // reading as float is not a safe “type conversion”
  printf("%f\n", x.f);
  return 0;
}

Tagged unions pattern in C

Safer pattern in C:

  • Combine an enum tag with a union.

  • The tag says which union member is valid.

enum Kind { IS_INT, IS_FLOAT };

struct Value {
  enum Kind tag;
  union {
    int i;
    float f;
  } u;
};

void print_value(struct Value v) {
  if (v.tag == IS_INT) {
    printf("int: %d\n", v.u.i);
  } else {
    printf("float: %f\n", v.u.f);
  }
}

This idea is similar to TypeScript unions with a kind field.

Example: c_tagged_union.c

Unions and enums in TypeScript

enum Direction {
  North,
  South,
  East,
  West
}

type Result =
  | { kind: "ok"; value: number }
  | { kind: "error"; message: string };

Example: ts_discriminate_union.ts

Practice 2: Narrow a union

Given this type:

type Result =
  | { kind: "ok"; value: number }
  | { kind: "error"; message: string };

Write the missing code so it returns a number in the ok case, and throws an error in the error case:

function unwrap(r: Result): number {
  // TODO
}

Practice 2: Answer

function unwrap(r: Result): number {
  if (r.kind === "ok") {
    return r.value;
  } else {
    throw new Error(r.message);
  }
}

TypeScript uses the kind field to narrow the union safely.

ADTs and Polymorphism

Algebraic data types (informal idea)

  • Built from simpler types using sum and product.

  • Product type: combine fields (records/tuples).

  • Sum type: choose one of several variants (unions).

Haskell style:

data Result = Ok Int
            | Error String

data Point = Point Int Int

TypeScript can mimic this:

type Result =
  | { kind: "ok"; value: number }
  | { kind: "error"; message: string };

Generics and parametric polymorphism

  • Write code once, reuse for many types (type parameters).

  • Industry term: generics (or templates in C++).

Examples across languages:

  • Java: List<T>, Map<K, V>

  • Rust: Vec<T>, Option<T>

  • TypeScript: Array<T>, Promise<T>

Polymorphism

Polymorphism = “many forms”. Common kinds:

Ad-hoc polymorphism:

  • Overloading, operator overloading.

Parametric polymorphism:

  • Generics: same code works for any type parameter.

Subtype polymorphism:

  • Code works for a base type and can be called with subtypes.

Generics in TypeScript

function first<T>(items: T[]): T | undefined {
  return items[0];
}

let nums = [1, 2, 3];
let names = ["a", "b", "c"];

let n = first(nums);   // number | undefined
let s = first(names);  // string | undefined

Generic interface:

interface Box<T> {
  value: T;
}

let intBox: Box<number> = { value: 42 };
let strBox: Box<string> = { value: "hello" };

Example: ts_generics.ts

Subtyping and Structural Typing

Subtyping and inheritance

Subtyping:

  • If S is a subtype of T, values of S can be used where T is expected.

Inheritance:

  • Class B extends class A and inherits fields and methods.

  • Often introduces a subtype relation: B is a subtype of A.

Examples:

  • Java: class Circle extends Shape

  • C#: class SqlConnection extends DbConnection

Nominal vs structural typing

Nominal typing:

  • Types match by name/declared identity.

  • Common in Java/C#/C++ classes.

Structural typing:

  • Types are compatible if their structures match.

  • TypeScript (and Go) use structural typing for many types.

TypeScript example:

interface Point {
  x: number;
  y: number;
}
interface Pixel {
  x: number;
  y: number;
}
let p: Point = { x: 1, y: 2 };
let px: Pixel = p;  // ok: structure matches

Example: ts_structural.ts

Interfaces and structural typing in TypeScript

interface Person {
  name: string;
  age: number;
}

function greet(p: Person) {
  console.log("Hello, " + p.name);
}

const user = {
  name: "Alice",
  age: 30,
  email: "a@example.com"
};

greet(user); // ok: user has at least name and age

Only the needed fields and types must match.

Union and intersection types in TypeScript

Union types:

type Id = number | string;

function printId(id: Id) {
  if (typeof id === "string") {
    console.log(id.toUpperCase());
  } else {
    console.log(id.toFixed(2));
  }
}

Intersection types:

type HasId = { id: number };
type HasName = { name: string };
type User = HasId & HasName;

const u: User = { id: 1, name: "Bob" };

Designing Types for APIs

Designing robust API types

  • Use interfaces/type aliases to describe data shapes.

  • Use enums or string unions for finite choices.

  • Use generics to keep APIs reusable.

  • Avoid any in public APIs when possible.

  • Use union/result types for success vs error.

Example result type in TypeScript:

type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string };

This pattern also appears in Rust (Result<T, E>) and Haskell (Either e a).

Example: ts_api_result.ts

Wrap-up

Summary

  • Types help prevent bugs by restricting how values can be used.

  • Static vs dynamic is about when checks happen; strong vs weak is about coercions.

  • TypeScript adds static checking while keeping JavaScript’s runtime.

  • Primitives and composites are the building blocks of data modeling.

  • Unions + tags lead naturally to ADTs and safe case analysis.

  • Generics support reuse; structural typing affects how APIs accept values.
