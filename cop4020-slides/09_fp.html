Foundations of functional programming

The main viewpoint

  • Imperative programming often focuses on commands that change program state

  • Functional programming focuses on computing values from other values

  • Instead of asking what state changes next, we ask what result should be produced from the inputs

  • This often makes programs easier to test, explain, and reorganize

Expressions and effects

  • An expression computes a value

  • An effect changes something outside the local computation, such as output, input, time, randomness, or mutable state

  • Functional programming tries to keep most computation expression-centered and to control where effects occur

Referential transparency

  • An expression is referentially transparent if it can be replaced by its value without changing program behavior

  • This matters because it allows local reasoning about code

  • Effects such as printing, mutation, reading time, or randomness break referential transparency

Pure function

  • A pure function returns the same result for the same inputs

  • A pure function does not mutate shared state or perform observable effects

  • Its behavior is determined only by its arguments

Immutability

  • Immutability means values are not updated in place after they are created

  • Instead of changing an existing value, a program computes a new value

  • This reduces hidden interactions caused by shared mutable state

Immutable update does not mean copying everything

  • Many immutable data structures are persistent

  • A persistent structure allows new versions to share most of the old structure

  • This is called structural sharing

  • So new value does not automatically mean full deep copy

Effects at the boundary

  • Functional programming does not eliminate effects

  • It tries to keep the core logic pure and place I/O or mutation in a smaller outer layer

  • A common design is a pure core surrounded by an effectful shell

Practice: identify the effects

Which lines cause effects, and how would you separate pure computation from logging and mutation?

type Cart = { items: number[]; total: number };

function addItem(cart: Cart, price: number): void {
  cart.items.push(price);
  cart.total = cart.total + price;
  console.log("added", price);
}

const c: Cart = { items: [], total: 0 };
addItem(c, 10);
addItem(c, 5);
console.log(c.total);

One refactoring

type Cart = { items: number[]; total: number };

function addItemPure(cart: Cart, price: number): Cart {
  return { items: [...cart.items, price], total: cart.total + price };
}

function logAdded(price: number): void {
  console.log("added", price);
}

let c: Cart = { items: [], total: 0 };
c = addItemPure(c, 10); logAdded(10);
c = addItemPure(c, 5);  logAdded(5);
console.log(c.total);

  • The update logic is now pure

  • Logging remains effectful, but it is outside the core update

Functions as values

First-class functions

  • A value is first-class if it can be stored in variables, passed as an argument, and returned from a function

  • In functional programming, functions are treated as first-class values

  • This allows programs to abstract over behavior as well as over data

Anonymous functions

  • TypeScript: (x) => x + 1

  • Python: lambda x: x + 1

  • Haskell: \x -> x + 1

The syntax differs, but the idea is the same: create behavior inline and pass it where needed.

Higher-order functions

  • A higher-order function takes a function as input, returns a function, or both

  • This lets us separate control structure from the specific operation performed at each step

  • A library can handle traversal while the programmer supplies the transformation rule

Why higher-order functions matter

  • The mechanism tells us how to traverse or repeat

  • The policy tells us what to do at each step

  • Higher-order functions separate these two concerns cleanly

Common FP toolkit for lists

  • Functional programming often processes collections by applying small functions to each element, keeping some elements, or combining all elements into one result

  • Three especially common operations are map, filter, and fold

  • These are higher-order functions because they take behavior as input

  • They let us describe what transformation we want without writing low-level traversal each time

map: transform every element

  • map applies a function to each element of a collection

  • The shape of the collection stays the same, but each value is transformed

  • This is useful when we want to describe a value-by-value computation cleanly

const xs = [1, 2, 3, 4];
const ys = xs.map(x => x * 2);

// ys is [2, 4, 6, 8]

filter: keep the elements that match a rule

  • filter keeps only the elements that satisfy a predicate

  • A predicate is a function that returns true or false

  • This is useful when we want to separate the selection rule from the traversal itself

const xs = [1, 2, 3, 4, 5, 6];
const evens = xs.filter(x => x % 2 === 0);

// evens is [2, 4, 6]

fold: combine many values into one

  • A fold reduces a collection to a single result

  • We provide a starting value and a rule for combining one element with the accumulated result

  • Sums, products, counts, and many aggregations follow this pattern

const xs = [1, 2, 3, 4];
const total = xs.reduce((acc, x) => acc + x, 0);

// total is 10

Pipeline example: transform, select, combine

const xs = [1, 2, 3, 4, 5, 6];

const result =
  xs
    .map(x => x * 2)
    .filter(x => x > 5)
    .reduce((acc, x) => acc + x, 0);

// doubled: [2, 4, 6, 8, 10, 12]
// kept:    [6, 8, 10, 12]
// result:  36

  • This style emphasizes a flow of values through transformations

  • Each step has one clear job

Function composition

  • Composition combines small functions into a larger transformation

  • If one function produces the kind of value that the next function expects, they can be chained together

  • This is especially useful when functions are pure and focused

Composition example

const trim = (s: string) => s.trim();
const lower = (s: string) => s.toLowerCase();
const normalize = (s: string) => lower(trim(s));

normalize("  Hello  ");

  • Each function has one clear job

  • The larger behavior is built by chaining them together

Currying and partial application

  • Currying represents a multi-argument function as a sequence of one-argument functions

  • Partial application means supplying some arguments now and receiving a more specialized function back

  • These ideas support reuse because one general function can generate many specialized ones

Currying example in TypeScript

const add = (x: number) => (y: number) => x + y;
const add10 = add(10);

add10(5);

  • add takes one argument and returns another function

  • add10 is a specialized function created by partial application

Data and control in FP

Recursive data

  • Functional programming often works with recursive data such as lists and trees

  • A recursive data structure is defined in terms of smaller instances of itself

  • This is why recursion becomes a natural control pattern in FP

Recursion as a control pattern

  • In FP, recursion often replaces loops

  • For recursive data, recursive programs naturally follow the structure of the data

  • This is called structural recursion

Structural recursion example

function product(xs: number[]): number {
  if (xs.length === 0) return 1;
  const [h, ...t] = xs;
  return h * product(t);
}

  • The base case handles the empty list

  • The recursive case combines the head with the result on the tail

Reusable recursion patterns

  • Many list programs follow recurring patterns

  • Some programs transform every element

  • Some select only the elements that pass a test

  • Some combine the whole list into one answer

  • Instead of rewriting the recursion each time, FP libraries package these patterns as reusable functions

Why map, filter, and fold matter

  • They capture very common recursion patterns over lists

  • They reduce boilerplate and make intent easier to see

  • They separate traversal from the operation performed at each step

  • They are central to functional style in Haskell and also common in TypeScript, Python, and many other languages

Folds

  • A fold captures a common recursion pattern over a recursive structure

  • Instead of writing the recursion by hand each time, we provide a base case and a combining rule

  • This makes programs more abstract and reusable

From recursion to reduce

function product(xs: number[]): number {
  return xs.reduce((acc, x) => acc * x, 1);
}

  • The base value is 1

  • The combining rule is multiplication

  • The traversal is handled by the library

Algebraic data types

  • An algebraic data type builds a type out of simpler pieces

  • A product type combines data together

  • A sum type represents a choice among different cases

  • ADTs help make valid program cases explicit

Pattern matching

  • Pattern matching is a structured way to inspect which case of a value we have

  • It lets a program branch on data shape and extract the parts needed in each case

  • This is clearer than manually inspecting tags with nested conditionals

Maybe and Result style types

  • A Maybe or Option value represents either a present value or no value

  • A Result or Either value represents either success or failure with information

  • These types make missing values and errors explicit in the program design

TypeScript: a Result type

type Result<T> =
  | { tag: "ok"; value: T }
  | { tag: "err"; message: string };

function safeDiv(x: number, y: number): Result<number> {
  return y === 0
    ? { tag: "err", message: "divide by zero" }
    : { tag: "ok", value: x / y };
}

The tag field tells us which case we are handling.

Python: matching on structure

def head_or(defval, xs):
    match xs:
        case []:
            return defval
        case [y, *rest]:
            return y

This expresses the same general idea of branching on data shape.

Evaluation strategy

Strict evaluation

  • Strict evaluation computes function arguments before the function body uses them

  • Most mainstream languages are strict, including JavaScript, TypeScript, Python, Java, and C

  • This often makes cost easier to predict because work happens immediately

Lazy evaluation

  • Lazy evaluation delays computation until the value is needed

  • This can avoid unnecessary work and allow demand-driven data structures

  • It also changes the way we reason about performance and termination

Demand-driven sequences in mainstream languages

def squares():
    n = 1
    while True:
        yield n * n
        n += 1
function* squares(): Generator<number> {
  let n = 1;
  while (true) {
    yield n * n;
    n++;
  }
}

These are not fully lazy languages, but generators show the idea of producing values only when asked.

Practice: think about what must be evaluated

  • If a computation needs only the first few results, does the rest need to be computed?

  • What kinds of programs benefit from delaying work?

  • What kinds of programs become harder to reason about when work is delayed?

Functional style in mainstream languages

Functional style in TypeScript and Python

  • Write core logic as pure transformations when possible

  • Represent state changes as new values instead of in-place mutation

  • Use map, filter, reduce, comprehensions, and pipelines to express data flow clearly

Reducer pattern

A reducer is a pure function that takes the current state and an action, then returns the next state.

type State = { count: number };
type Action =
  | { tag: "inc"; by: number }
  | { tag: "reset" };

function reducer(s: State, a: Action): State {
  switch (a.tag) {
    case "inc":   return { count: s.count + a.by };
    case "reset": return { count: 0 };
  }
}

const actions: Action[] = [{ tag: "inc", by: 2 }, { tag: "inc", by: 3 }];
const final = actions.reduce(reducer, { count: 0 });

Python pipeline example

def normalize(s):
    return s.strip().lower()

def keep_alpha(s):
    return "".join(ch for ch in s if ch.isalpha())

raw = ["  Hello! ", " CS 4020 ", "  FP  "]
clean = [keep_alpha(normalize(s)) for s in raw]

Each function has one purpose, and the pipeline shows the order of transformations clearly.

Where this style appears in real systems

  • Data processing often uses transform, filter, group, and reduce patterns

  • State management libraries often use reducer-style updates

  • Log processing and streaming systems often look like pipelines of transformations

  • Pure logic in these systems is easier to test than code mixed with I/O and mutation

Haskell as a pure functional language

Characteristics of Haskell

  • Pure functions are the default

  • Immutable values are the normal model

  • Functions are first-class and higher-order functions are common

  • Algebraic data types and pattern matching are built into the language

  • Evaluation is lazy by default

  • Types communicate what functions can do and where effects appear

Why learn Haskell?

  • It makes FP ideas easier to see because the language is organized around them

  • It helps us reason more carefully about purity, types, and effects

  • It strengthens our understanding of abstraction, recursion, and program design

  • Even if we do not use Haskell in industry, the ideas transfer to many other languages

Haskell: hello world

main :: IO ()
main = putStrLn "Hello, world!"

  • main is the entry point

  • IO () tells us this action may perform effects

  • putStrLn prints a string to the screen

How to read Haskell type signatures

  • Int -> Int means a function from Int to Int

  • [Int] means a list of integers

  • (a -> b) -> [a] -> [b] means: first a function from a to b, then a list of a, then a list of b

  • Lowercase type variables such as a and b mean the function is generic

Haskell: pure function example

square :: Int -> Int
square x = x * x

  • This function depends only on its input

  • It has no printing, mutation, input, or randomness

  • So square 5 can always be replaced with 25

Haskell: higher-order function example

applyTwice :: (a -> a) -> a -> a
applyTwice f x = f (f x)

inc :: Int -> Int
inc x = x + 1

result = applyTwice inc 5

  • applyTwice takes a function as an argument

  • That makes it a higher-order function

  • result becomes 7

Haskell: partial application is ordinary

add :: Int -> Int -> Int
add x y = x + y

add10 :: Int -> Int
add10 = add 10

nums :: [Int]
nums = [1, 2, 3]

result :: [Int]
result = map add10 nums

  • Giving add only one argument produces a new function

  • This makes partial application feel natural in Haskell

Haskell: function composition

double :: Int -> Int
double x = x * 2

inc :: Int -> Int
inc x = x + 1

doubleThenInc :: Int -> Int
doubleThenInc = inc . double

  • . is the composition operator

  • doubleThenInc 5 means inc (double 5)

  • This builds larger behavior from small functions

Haskell: map

map :: (a -> b) -> [a] -> [b]

double :: Int -> Int
double x = x * 2

nums :: [Int]
nums = [1, 2, 3, 4]

doubled :: [Int]
doubled = map double nums

  • map applies the given function to every element of the list

  • The traversal is handled by the library; we provide only the transformation rule

Haskell: filter

filter :: (a -> Bool) -> [a] -> [a]

nums :: [Int]
nums = [1, 2, 3, 4, 5, 6]

evens :: [Int]
evens = filter even nums

  • filter keeps only the values that satisfy the predicate

  • Here the predicate is even

Haskell: building a list-processing pipeline

nums :: [Int]
nums = [1, 2, 3, 4, 5, 6]

result :: [Int]
result = filter (> 5) (map (*2) nums)

  • map (*2) doubles every element

  • filter (> 5) keeps only values greater than 5

  • This shows how small pure functions can be combined into a processing pipeline

Haskell: structural recursion on lists

sumList :: [Int] -> Int
sumList xs =
  case xs of
    []     -> 0
    (y:ys) -> y + sumList ys

  • The base case handles the empty list

  • The recursive case processes the head and tail

Haskell: fold example

sumList :: [Int] -> Int
sumList xs = foldr (+) 0 xs

  • foldr captures a common recursion pattern over lists

  • The base value is 0

  • The combining rule is (+)

  • So this means: combine all list elements using addition, starting from 0

Haskell: practical view of foldr

foldr :: (a -> b -> b) -> b -> [a] -> b

sumList :: [Int] -> Int
sumList = foldr (+) 0

countEvens :: [Int] -> Int
countEvens = foldr step 0
  where
    step x acc =
      if even x then acc + 1 else acc

  • foldr replaces explicit recursion with a reusable combining pattern

  • For a sum, the base value is 0 and the combining rule is (+)

Haskell: tail recursion example

sumTail :: [Int] -> Int
sumTail xs = go xs 0
  where
    go [] acc = acc
    go (y:ys) acc = go ys (acc + y)

  • The helper function carries an accumulator

  • The recursive call is the last thing the function does

  • This is the basic tail-recursive pattern

Haskell: algebraic data type example

data Shape
  = Circle Double
  | Rect Double Double

area :: Shape -> Double
area sh =
  case sh of
    Circle r -> pi * r * r
    Rect w h -> w * h

  • Shape is a sum type with two cases

  • area uses pattern matching to handle each case clearly

Haskell: Maybe example

safeDiv :: Int -> Int -> Maybe Int
safeDiv x y =
  if y == 0 then Nothing else Just (x `div` y)

  • Maybe Int means the result may be missing

  • This avoids using null for ordinary failure cases

Haskell: Either example

parseInt :: String -> Either String Int
parseInt s =
  if all (`elem` "0123456789") s
    then Right (read s)
    else Left "not a number"

  • Either String Int means failure carries an error message

  • This is useful when the caller should know why an operation failed

Haskell: lazy evaluation example

nums :: [Int]
nums = [1..]

firstFive :: [Int]
firstFive = take 5 nums

  • nums is an infinite list

  • take 5 only asks for five elements

  • This works because Haskell evaluates values only when needed

Haskell: laziness and list processing

nums :: [Int]
nums = [1..]

firstThreeEvenSquares :: [Int]
firstThreeEvenSquares =
  take 3 (map (^2) (filter even nums))

  • The list nums is infinite

  • Because Haskell is lazy, only the part needed by take 3 is computed

  • This is one place where higher-order functions and lazy evaluation work together naturally

What to notice in the Haskell examples

  • Pure functions and effectful actions are clearly separated

  • Functions are passed around as values naturally

  • Composition and recursion are ordinary programming tools

  • Types make program structure and effect boundaries easier to see

  • Lazy evaluation changes how we think about data and control

Preview: FP and concurrency

Why immutability helps concurrency

  • If values are not changed in place, many shared-state bugs disappear

  • Pure functions are easier to run in parallel because they depend only on their inputs

  • This is one reason FP ideas matter beyond Haskell itself

What we save for the concurrency module

  • Parallel execution patterns

  • Race conditions and synchronization

  • Performance tradeoffs in concurrent systems

For now, the main point is that FP improves reasoning before it improves parallel execution.

Review

Tradeoffs in practice

  • There is a learning curve because FP introduces new vocabulary and new design patterns

  • Performance can be excellent, but evaluation strategy and data structures matter

  • Functional code often interacts with effectful libraries, so boundaries must be designed carefully

  • Functional programming is a set of tools that improves some problems more than others

Key ideas to remember

  • Functional programming starts with a value-centered way of thinking about programs

  • Purity, immutability, and referential transparency improve reasoning and testing

  • Higher-order functions, composition, currying, partial application, and list transformations support reuse and abstraction

  • ADTs, pattern matching, recursion, and folds make data processing more explicit

  • Evaluation strategy affects termination and performance

  • Haskell is useful because it gathers these ideas into one clear language model
