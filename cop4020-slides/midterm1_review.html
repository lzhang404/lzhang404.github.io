Module 1: Lexical Structure

Token, lexeme, attribute

  • Lexeme: the exact character sequence in the source.

  • Token: a category (token-name) plus an optional attribute.

  • Typical representation: ⟨token-name, attribute⟩.

"123"  → ⟨NUMBER, 123⟩
"sum"  → ⟨IDENT, "sum"⟩
"+"    → ⟨OP, "+"⟩

What a lexer/scanner does

  • Input: raw source characters.

  • Output: a stream of tokens (with positions).

  • Skips: whitespace and comments (but updates line/column/index).

  • Goal: turn characters into a structured sequence for the parser.

Two rules that decide most lexer outputs

  • Longest match: consume the longest prefix that forms a valid token.

  • Rule priority: if two token rules match the same length, choose the higher-priority rule.

  • Shared-prefix operators: recognize the longer one first (== before =).

  • Keywords: often scan as IDENT, then upgrade using a keyword table.

Regex in lexing

  • A regex describes the set of lexemes a rule matches (a regular language).

  • Lexers apply regex-like rules repeatedly to form tokens.

  • Anchors (^, $) matter when you want to match the whole lexeme.

Regex mini-cheatsheet (JS/TS)

  • ^ start, $ end

  • [0-9] digit, [a-fA-F0-9] hex digit

  • + 1+, * 0+, ? optional

  • () group, | alternative

decimal integer:   ^[0-9]+$
identifier:        ^[A-Za-z_][A-Za-z0-9_]*$
whitespace:        ^[ \t\r\n]+$

Hex integer literals (token rule)

  • Syntax: starts with 0x or 0X, then 1+ hex digits.

  • No underscores, no suffixes.

  • Whole lexeme must match (anchors).

hex integer (only): ^0[xX][0-9a-fA-F]+$

Scanner stopping point (intuition)

Assume NUMBER is [0-9]+ and IDENT begins with a letter/_.

Input: 123x

  • The NUMBER rule matches 123, then stops at x.

  • The scanner emits NUMBER(123) and leaves x for the next token.

Module 2: DFAs and Scanning

Definition: DFA

  • A DFA (deterministic finite automaton) is a 5-tuple:

  • Q (finite set of states), Σ (input alphabet), δ (transition function), q0 (start state), F (accepting states).

  • Deterministic means: for each state and input character, there is at most one next state.

δ: Q × Σ → Q
(transition function maps (state, char) to the next state)

How DFAs relate to scanning

  • Token patterns like identifiers and numbers are regular languages.

  • A DFA can recognize each pattern by reading characters left-to-right.

  • Lexers simulate these DFAs to decide how many characters to consume.

  • Longest match: keep going while transitions exist; remember the last accepting state.

Integer DFA intuition for [0-9]+

  • Start → on digit → in “number” state (accepting)

  • Keep consuming digits while possible

  • Stop when next char is not a digit

Input: 123x
Read 1,2,3  → still accepting NUMBER
Read x      → no transition → stop, emit NUMBER(123)

Shared-prefix operators

  • When multiple operators share a prefix, longest-match is essential.

  • Example: language includes = and ==.

  • Scanner should prefer == when the input begins with ==.

Lexer errors (what to include)

  • Unexpected character and its position (index/line/column)

  • Context snippet if you provide it (helpful)

Unexpected character '@' at line 3, col 12

Module 3: Grammars, Parsing, ASTs

Grammar basics

  • A context-free grammar defines how tokens form valid programs.

  • Nonterminals (like Expr) expand using productions.

  • Terminals are token kinds (NUM, IDENT, "+", etc.).

BNF vs EBNF (the * operator)

  • BNF uses only productions; EBNF adds repetition operators.

  • In EBNF, (X)* means “repeat X zero or more times”.

  • So Term (("+" Term)*) means: a Term, then zero or more + Term groups.

Expr ::= Term (("+"|"-") Term)*

Ambiguity

  • A grammar is ambiguous if a string has more than one parse tree.

  • Ambiguity often appears when precedence/associativity is not encoded.

Expr ::= Expr "+" Expr | Expr "*" Expr | NUM

Precedence and associativity (how grammar encodes it)

  • Precedence: put higher-precedence nonterminal “lower” (nested) in the grammar.

  • Associativity: loops like (...)* usually build left-associative trees in recursive descent.

Expr   ::= Term (("+"|"-") Term)*
Term   ::= Factor (("*"|"/") Factor)*
Factor ::= "(" Expr ")" | NUM

Recursive descent parsing (implementation strategy)

  • Typical strategy: one function per nonterminal.

  • Each function consumes tokens and returns an AST node.

  • Errors happen when the next token cannot satisfy what the grammar requires.

AST: what it keeps vs drops

  • AST keeps the essential structure for evaluation and analysis.

  • AST drops syntax-only details (like parentheses nodes).

  • Operator precedence is reflected by tree shape.

AST example (JSON style)

Expression:

5 + 2 * (4 - 1)

AST (JSON style, parentheses removed):

{
  "type": "BinaryExpr",
  "op": "+",
  "left": { "type": "NumberLiteral", "value": 5 },
  "right": {
    "type": "BinaryExpr",
    "op": "*",
    "left": { "type": "NumberLiteral", "value": 2 },
    "right": {
      "type": "BinaryExpr",
      "op": "-",
      "left": { "type": "NumberLiteral", "value": 4 },
      "right": { "type": "NumberLiteral", "value": 1 }
    }
  }
}

Parser errors: what you should report

  • Expected token(s)

  • Actual token found (type and lexeme)

  • Position

Expected ")" after expression, got IDENT("as") at index 42

Module 4: Names, Bindings, Scope, Lifetime

Definitions (must-know)

  • Name: identifier text in the program (x, f).

  • Binding: association from a name to an entity (value/location/function).

  • Scope: region of program text where a binding is visible.

  • Lifetime: how long storage exists during execution.

Static (lexical) scoping

  • Free variables in a function refer to bindings in the environment where the function was defined.

  • Not based on who calls the function (that would be dynamic scoping).

Shadowing

  • An inner scope can introduce a new binding with the same name.

  • References resolve to the nearest binding in scope.

let x = 1;
function g() {
  let x = 2;
  return x;
}

Hoisting and TDZ

  • var is function-scoped and hoisted; read-before-assign yields undefined.

  • let/const are block-scoped; access before initialization throws ReferenceError (TDZ).

function demoVar() {
  console.log(msg); // undefined
  var msg = "hello";
}

function demoLet() {
  // console.log(msg); // ReferenceError (TDZ)
  let msg = "hello";
}

Closures

  • A closure is a function + the environment of captured variables.

  • Closures make free variables keep working after the outer function returns.

  • Captures bindings, not “snapshots” of values.

Closure + loop binding

  • var: one shared binding across iterations.

  • let: a fresh binding each iteration.

const fs1: (() => number)[] = [];
for (var i = 0; i < 3; i++) fs1.push(() => i);
console.log(fs1[0](), fs1[1](), fs1[2]());

Module 5: Data Types & Type Systems

Why types?

  • Types restrict how values can be used (prevent categories of bugs).

  • Type systems aim to detect invalid uses early or at runtime.

  • Type error: using a value in a way that does not match its type.

Static vs dynamic typing

  • Static vs dynamic differs mainly in when type checks happen.

  • Static: many checks before running.

  • Dynamic: checks happen when the code path runs.

  • TypeScript: static checking, JavaScript runtime behavior.

Strong vs weak typing (coercion)

  • Strong/weak is about implicit conversions between unrelated types.

  • JavaScript allows many coercions (surprising results).

1 + "2"        // "12"
"3" * "4"      // 12
false == 0     // true

Unions and narrowing

  • Union: a value may be one of several variants.

  • Narrowing: refine the union to a specific variant using checks.

  • Discriminated union: a shared tag field (like kind) drives narrowing.

type Result =
  | { kind: "ok"; value: number }
  | { kind: "error"; message: string };

any vs unknown

  • any: opt out of checking; unsafe operations allowed.

  • unknown: forces narrowing/validation before use.

  • Safer default for “data from outside” (network, JSON, user input).

Tagged unions vs raw C unions

  • Raw union: you can read the wrong field with no built-in protection.

  • Tagged union: tag indicates which variant is valid before reading data.

  • This is the same idea as TypeScript discriminated unions.

Generics (parametric polymorphism)

  • Enable reuse: write code once that works for many types using type parameters.

function first<T>(items: T[]): T | undefined {
  return items[0];
}

Structural typing

  • Compatibility is based on matching required fields/types (shape).

  • Extra fields are allowed if the required structure matches.

interface Person { name: string; age: number; }
function greet(p: Person) { console.log(p.name); }

const user = { name: "Alice", age: 30, email: "a@example.com" };
greet(user);
