What is a Programming Language? (Informal)

  • A system of rules for telling a computer what to do

  • Consists of

    • Syntax: what programs look like

    • Semantic: what programs mean / what they do

  • Similar to human language:

    • Vocabulary, grammar, meaning

  • but with stricter rules: computers don’t guess what we meant

Why Not Just Use English?

  • Natural languages are

    • Ambiguous: "Put the glasses on the table"

    • Context-dependent: meaning changes with situation

    • Vague: "Do it quickly" - How quick?

  • Computers need:

    • Precise instructions

    • Repeatable behavior

    • No guessing / interpretation

  • Programming languages = controlled, precise languages for computers

Programming Languages as Contracts

  • A program is an agreement between:

    • Programmer: what they think will happen

    • Language definition / compiler (what really happens)

    • Computer (how it actually runs)

  • Languages define:

    • What is legal to write

    • What a legal program must do

The Hardware Reality

  • At the lowest level

    • Computers work with voltages, bits, and machine instructions

  • Machine code:

    • Sequences of binary numbers (e.g., 100110000)

    • Directly control CPU operations

  • Writing large programs in pure machine code:

    • Extremely error-prone

    • Hard to read, hard to change

  • We need something more human-friendly

Example: Machine vs High-Level Languages

  • Task: add 2 and 3, store the result

  • Machine-level idea:

    • Load value 2 into a register

    • Add 3

    • Store result in memory

  • High-level (e.g., python-like)

        x = 2 + 3

  • Programming languages:

    • Let us think at a higher level

    • Hide a lot of hardware detail

How High-Level Code Becomes Machine Code

  • A compiler: translates your program once into machine code

    • e.g., C, Rust, many others

  • An interpreter:

    • Reads your program and executes it step by step

    • e.g., Python, JavaScript (simplified picture)

  • Languages exist partly to make this translation possible and reliable

Layers of Abstraction

  • Abstraction: ignoring details that don’t matter right now

  • Programming languages give you:

    • Variables instead of registers

    • Functions instead of jump instructions

    • Data structures instead of raw memory addresses

  • This lets programmer:

    • Focus on problem solving

    • Not on micro-managing hardware

Core Purposes of Programming Languages

  • Communication:

    • Between humans and computers

    • Between humans (reading each other’s code)

  • Abstraction

    • Hiding unnecessary detail

    • Organizing large systems

  • Safety & reliability: preventing certain classes of bugs

  • Performance & efficiency: Allowing good use of hardware resources

  • Expressivness: Letting us describe complex ideas concisely

Languages as Human-Human Communication

  • Most code is red more often than written

  • Language are designed for :

    • Readability: how easy to understand?

    • Maintainability: how easy to change safely?

  • Style guidelines, idioms, and tooling: make languages more usable for teams

  • Question: would you rather debug:

    • a clear but slow program?

    • a fast but unreadable one?

Languages as Abstraction Tools

  • Languages give new building blocks:

    • Functions, classes, modules, packages

    • Types, intefraces, generics, traits

  • Examples:

    • Instead of thinking in bytes, think in strings

    • Instead of loops and indices, think in map/filter/reduce

  • Languages help align code structure with how we think about problems

Safety and Guarantees

  • Languages can forbid dangerous actions:

    • Reading past the end of an array

    • Using unitialized variables

  • Type systems: Check consistency of data usage before running

  • Memory safety, concurrency safety, null safety, etc.

  • The more work the language does for us, the fewer hidden landmines in our code

Performance and Control

  • Some languages aim for:

    • High performance (close to machine speed)

    • Fine-grained control over memory / CPU

  • Others aim for:

    • Productivity: fast to write, easier to change

    • Automatic memory management (garbage collection)

  • Trade-off: Control vs convenience

  • Different domains have different priorities

Language Roles in Practice

  • Embedded systems: tight performance and memory constraints

  • Web backends: serving requests, talking to databases

  • Front-end / UI: running in browsers or mobile apps

  • Data / ML: cleaning, analyzing, training models

  • DevOps / scripting: automating repetitive tasks

  • Different roles emphasize different language features

Domain-Specific Languages

  • Shader languages (graphics / GPUD):

    • GLSL - OpenSL shading language

    • HLSL – High Level Shading Language (DirectX)

    • MSL – Metal Shading Language (Apple platforms)

    • Used to program how pixels/vertices are drawn on screen

  • Configuration languages:

    • YAML, JSON, TOML - app & service config files

    • Focus on declaring setting, not computation

  • Scripting languages:

    • Bash / shell scripts – automating command-line tasks

    • Python, Ruby, Perl – glue code, automation, tools

    • JavaScript – scripting in browsers and many tools

    • Often used to automate or “glue together” other systems

  • Other domian-specific examples:

    • SQL – querying and updating relational databases

    • HTML/CSS – describing structure and style of web pages

  • Why create a new language?

    • Make certain tasks easier, safer, less repetitive

    • Capture expert patterns in the language itself

Paradigms: Different Ways of Thinking

  • A paradigm is a style / philosophy of programming

    • Imperative: change state step by step

    • Object-Oriented: organize code around objects & methods

    • Functional: emphasize functions, immutability

    • Logic/Declarative: state what should be true, not how

  • Many languages support multiple paradigms

  • Paradigms influence:

    • How we decompose problems

    • The kinds of bugs we’re likely to make

Same Problem, Different Styles

  • Example: Sum of a list

  • Imperative style:

        total = 0
    for x in nums:
      total += x

  • Functional style:

        total = sum(nums)

  • Declarative (SQL-ish idea)

        SELECT SUM(value) FROM numbers;

Languages Shape How We Think

  • Languages encourage some patterns, discourage others

    • Easy recursion? \(\rightarrow\) You think recursively more often

    • Easy objects? \(\rightarrow\) You think in terms of entties & messages

  • Learning new languages:

    • Expands your mental toolbox

    • Changes what feels "natural" when solving problems

Summary: What Are Languages Really For?

  • Bridging humans and machines. Making it possible to express intent precisely

  • Managing complexity: abstractions, modularity, organization

  • Enforcing constraints: catching errors early, improving reliability

  • Optimizing for resources: time, memory, energy

  • Shaping thought: Providing concepts that guide how we solve problems
