Core idea: structure code around responsibilities

OOP and modules are about managing complexity:

  • Encapsulation: hide representation details behind methods

  • Stable interfaces: depend on contracts, not implementations

  • Separation of concerns: split features into modules/packages

  • Evolution: add features without rewriting everything

API Signatures

Why signatures matter in OOP and modules

  • Most users of your code only see signatures, not implementations.

  • Signature design affects readability at call sites and how easily APIs evolve.

  • Common goals: fewer mistakes, clearer intent, stable evolution.

Association mechanisms across languages

  • Positional arguments: C/C++, Java, JS/TS default

  • Keyword arguments: Python (and many others)

  • Named options via records/objects: common in JS/TS

Defaults

Defaults reduce call-site noise when most callers use the same value.

function greet(name: string, punctuation: string = "!"): string {
  return "Hello, " + name + punctuation;
}
console.log(greet("Ada"));
console.log(greet("Ada", "!!"));
// C++ default argument
#include <iostream>
std::string greet(std::string name, std::string punctuation = "!") {
  return "Hello, " + name + punctuation;
}
int main() {
  std::cout << greet("Ada") << "\n";
}

Java often uses overloads instead of default arguments.

class Util {
  // Overloads often simulate defaults:
  static String greet(String name) { return greet(name, "!"); }
  static String greet(String name, String punct) { return "Hello, " + name + punct; }
}

Named options (options object / record parameter)

Use when you expect parameters to evolve over time.

type RequestOptions = { timeoutMs?: number; retries?: number; cache?: boolean; };

function request(url: string, opts: RequestOptions = {}): void {
  const timeoutMs = opts.timeoutMs ?? 2000;
  const retries = opts.retries ?? 2;
  const cache = opts.cache ?? true;
  console.log(url, timeoutMs, retries, cache);
}

request("/api/users");
request("/api/users", { retries: 3, cache: false });

  • Call sites document intent: { retries: 3 } is self-explanatory.

  • New fields can be added without breaking most call sites.

Keyword arguments (Python)

def request(url: str, timeout_ms: int = 2000, retries: int = 2, cache: bool = True) -> None:
    print(url, timeout_ms, retries, cache)

request("/api/users")
request("/api/users", retries=3, cache=False)

Keyword arguments make call sites readable without a separate options object.

Varargs (variable number of arguments)

  • JS/TS: rest parameters

  • Java: varargs become arrays

  • C: varargs are flexible but unsafe (printf-style)

  • C++: can do varargs, and also type-safe variadic templates

function sum(...xs: number[]): number {
  return xs.reduce((acc, x) => acc + x, 0);
}
console.log(sum(1, 2, 3));

Java varargs

class Util {
  static int sum(int... xs) {
    int acc = 0;
    for (int x : xs) acc += x;
    return acc;
  }
}

Design checklist for signatures

  • Are call sites readable without comments?

  • Will adding a new optional setting break existing callers?

  • Is the “common case” concise?

  • Are error/timing expectations visible (return type or result type)?

Objects and Classes

Objects and classes

Object

  • A runtime entity that bundles state and behavior

  • State stored in fields, behavior provided by methods

Class

  • A blueprint for creating objects

  • Defines fields and methods

  • Often defines invariants that should always hold

Encapsulation connects these: interact through methods, not raw fields.

Java: class and object basics

class BankAccount {
  private int balanceCents; // encapsulated state

  BankAccount(int initialCents) {
    if (initialCents < 0) throw new IllegalArgumentException();
    balanceCents = initialCents;
  }

  void deposit(int cents) {
    if (cents <= 0) throw new IllegalArgumentException();
    balanceCents += cents;
  }

  boolean withdraw(int cents) {
    if (cents <= 0) throw new IllegalArgumentException();
    if (cents > balanceCents) return false;
    balanceCents -= cents;
    return true;
  }

  int getBalanceCents() { return balanceCents; }
}

class Demo {
  public static void main(String[] args) {
    BankAccount a = new BankAccount(1000);
    a.deposit(250);
    System.out.println(a.getBalanceCents());
  }
}

TypeScript: class basics

TypeScript compiles to JavaScript; access modifiers are checked by TypeScript.

class BankAccount {
  private balanceCents: number;

  constructor(initialCents: number) {
    if (initialCents < 0) throw new Error("bad init");
    this.balanceCents = initialCents;
  }

  deposit(cents: number): void {
    if (cents <= 0) throw new Error("bad deposit");
    this.balanceCents += cents;
  }

  getBalanceCents(): number {
    return this.balanceCents;
  }
}

const a = new BankAccount(1000);
a.deposit(250);
console.log(a.getBalanceCents());

Python: class basics

Python uses classes and objects with a different visibility culture.

class BankAccount:
  def __init__(self, initial_cents: int):
    if initial_cents < 0:
      raise ValueError("bad init")
    self._balance_cents = initial_cents  # convention: internal

  def deposit(self, cents: int) -> None:
    if cents <= 0:
      raise ValueError("bad deposit")
    self._balance_cents += cents

  def balance_cents(self) -> int:
    return self._balance_cents

a = BankAccount(1000)
a.deposit(250)
print(a.balance_cents())

Underscore naming signals intended privacy; it is a convention, not enforcement.

C++: class basics 

#include <iostream>
#include <stdexcept>

class BankAccount {
  int balanceCents_;                 // private by default in 'class'
public:
  explicit BankAccount(int initialCents) {
    if (initialCents < 0) throw std::invalid_argument("bad init");
    balanceCents_ = initialCents;
  }

  void deposit(int cents) {
    if (cents <= 0) throw std::invalid_argument("bad deposit");
    balanceCents_ += cents;
  }

  int balanceCents() const {         // const method: doesn't modify object
    return balanceCents_;
  }
};

int main() {
  BankAccount a(1000);
  a.deposit(250);
  std::cout << a.balanceCents() << "\n";
}

  • private state enforces invariants via methods (same goal as Java/TS).

  • const methods advertise “no mutation” in the contract.

C++ angle: RAII (resource safety via object lifetime)

  • In C++, objects often manage resources (files, locks, memory) in constructors/destructors.

  • This is a major reason encapsulation matters: correct cleanup is “built into” object lifetime.

#include <mutex>

void safe_update(std::mutex& m, int& x) {
  std::lock_guard<std::mutex> guard(m); // locks now, unlocks automatically on return
  x += 1;
}

Encapsulation: representation and invariants

Encapsulation is not only about hiding fields:

  • Protect invariants by controlling updates

  • Reduce coupling by exposing a stable interface

  • Allow internal representation to change without breaking callers

Examples of invariants:

  • Balance never negative

  • Collection contains no duplicates

  • State transitions follow allowed rules

Practice 1: fix an encapsulation leak (Java)

Identify what breaks the invariant and propose a fix.

class Account {
  public int balanceCents;  // intended invariant: non-negative
  public Account(int initial) { balanceCents = initial; }
  public void deposit(int cents) { balanceCents += cents; }
}

class Demo {
  public static void main(String[] args) {
    Account a = new Account(100);
    a.balanceCents = -999;
    System.out.println(a.balanceCents);
  }
}

  • What went wrong?

  • What change enforces the invariant?

Practice 1 Answer

  • balanceCents is public, so callers can violate invariants.

  • Fix: make state private; validate updates in methods.

class Account {
  private int balanceCents;
  public Account(int initial) {
    if (initial < 0) throw new IllegalArgumentException();
    balanceCents = initial;
  }
  public void deposit(int cents) {
    if (cents <= 0) throw new IllegalArgumentException();
    balanceCents += cents;
  }
  public int getBalanceCents() { return balanceCents; }
}

Inheritance, Composition, and Dynamic Dispatch

Inheritance (is-a)

Inheritance models an is-a relationship:

  • FileSource is a DataSource

  • ApiSource is a DataSource

  • We can write code that accepts DataSource and works for all subclasses

Next: how does ds.read() choose which body runs?

Java: Inheritance

abstract class DataSource {
  abstract String read();
}

class FileSource extends DataSource {
  @Override String read() { return "file data"; }
}

class ApiSource extends DataSource {
  @Override String read() { return "api data"; }
}

We have one base class (DataSource) and many concrete subclasses.

Dynamic dispatch

Dynamic dispatch means the method body is chosen at runtime based on the receiver object’s class.

  • Call site chooses the method name: read

  • Runtime chooses which override runs: File vs API

  • Enables polymorphism: one call works for many types

Static type vs dynamic type

  • Static type: what the compiler uses for type checking (e.g., DataSource)

  • Dynamic type: what the object really is at runtime (e.g., FileSource)

  • Compile time: “is read() allowed?”

  • Runtime: “which read() body runs?”

Java: dispatch happens at the call site

class Demo {
  static void load(DataSource ds) {
    System.out.println(ds.read()); // dynamic dispatch happens here
  }

  public static void main(String[] args) {
    DataSource a = new FileSource(); // static: DataSource, dynamic: FileSource
    DataSource b = new ApiSource();  // static: DataSource, dynamic: ApiSource
    load(a); // prints "file data"
    load(b); // prints "api data"
  }
}

C++: dynamic dispatch requires virtual

#include <iostream>
#include <string>

struct DataSource {
  virtual ~DataSource() = default;
  virtual std::string read() const = 0;
};

struct FileSource : DataSource {
  std::string read() const override { return "file data"; }
};

struct ApiSource : DataSource {
  std::string read() const override { return "api data"; }
};

void load(const DataSource& ds) {
  std::cout << ds.read() << "\n"; // virtual dispatch happens here
}

  • virtual enables runtime dispatch; override checks intent.

  • virtual ~DataSource() matters for safe deletion via base pointers.

C++ pitfall: no virtual means no dynamic dispatch

#include <iostream>
#include <string>

struct DataSource {
  std::string read() const { return "base data"; } // NOT virtual
};

struct FileSource : DataSource {
  std::string read() const { return "file data"; } // looks like override, but isn't virtual dispatch
};

void load(const DataSource& ds) {
  std::cout << ds.read() << "\n"; // static binding
}

int main() {
  FileSource f;
  load(f); // prints "base data"
}

Method lookup intuition

  • Runtime starts at the receiver’s dynamic type (actual class).

  • Find the most specific override; if not found, walk up the base-type chain.

  • Runtimes optimize this (e.g., vtables), but the mental model is the same.

Composition (has-a)

Composition models a has-a relationship:

  • Build objects from other objects (components)

  • Delegate work to a contained component

  • Great for add-on features (logging, caching, retry)

TypeScript: composition by delegation

type Logger = { log(msg: string): void };

class Service {
  constructor(private logger: Logger) {}

  handle(id: string) {
    // delegate the logging work to the logger object
    this.logger.log("handling " + id);
  }
}

const consoleLogger: Logger = {
  log(msg) { console.log(msg); }
};

const s = new Service(consoleLogger);
s.handle("r1");

Practice: caching with inheritance vs composition

You have many sources: File, DB, API… You want caching.

  • Option A (Inheritance): CachedFile, CachedDb, CachedApi, ...

  • Option B (Composition): one CachedDataSource that wraps any DataSource

Question: Which option scales better and why?

Practice answer

  • Composition typically scales better for add-on features.

  • Inheritance tends to explode into subclasses (CachedFile, CachedDb, CachedApi, ...).

  • Composition supports stacking features (caching + logging + retry) using wrappers.

Liskov Substitution Principle

  • If B is a subtype of A, code written for A should still behave correctly with a B.

  • Subclasses should not break assumptions callers rely on (invariants + method contracts).

This is why inheritance is more than “reuse”: it commits you to a behavioral promise.

Polymorphism in APIs

Three “one name, many behaviors” mechanisms

  • Overriding (runtime): subclass replaces method body; dynamic dispatch picks the body.

  • Overloading (compile time): same name, different parameter lists; compiler picks which one.

  • Generics (compile time typing): one implementation works for many types.

Always ask: when is the decision made? compile time vs runtime.

Overriding vs overloading (don’t confuse them)

// Overriding: chosen at runtime (dynamic dispatch)
abstract class DataSource { abstract String read(); }
class FileSource extends DataSource { @Override String read() { return "file"; } }
class ApiSource  extends DataSource { @Override String read() { return "api"; } }

class Demo {
  static void load(DataSource ds) { System.out.println(ds.read()); } // runtime picks body
}

// Overloading: chosen at compile time (parameter types)
class Util {
  static int max(int a, int b) { return a > b ? a : b; }
  static double max(double a, double b) { return a > b ? a : b; }
}

  • Overriding changes behavior across subtypes (runtime choice).

  • Overloading changes which function is selected based on argument types (compile-time choice).

C++: templates (parametric polymorphism)

#include <vector>
#include <optional>

template <class T>
std::optional<T> first(const std::vector<T>& xs) {
  if (xs.empty()) return std::nullopt;
  return xs[0];
}

// Overloading still exists too:
int max(int a, int b) { return a > b ? a : b; }
double max(double a, double b) { return a > b ? a : b; }

  • Templates are parametric polymorphism (compile-time).

  • Typical effect: specialized code per type (instantiation).

Generics (parametric polymorphism)

One definition works across many types.

function first(xs: T[]): T | undefined {
  return xs.length === 0 ? undefined : xs[0];
}

console.log(first([1, 2, 3]));
console.log(first(["a", "b"]));

Typing benefit: callers get the “right” type back without casts.

Practice 4: classify the mechanism

For each scenario: overriding, overloading, or generics/templates?

  • A subclass changes toString() / f() behavior

  • print(int) and print(String) share the same name

  • List<T> (Java/TS) or vector<T> (C++) works for many element types

Practice 4 Answer

  • Subclass changes behavior: overriding (runtime dispatch)

  • Same name, different params: overloading (compile-time selection)

  • Type-parameterized containers: generics (Java/TS) / templates (C++)

Interfaces vs Abstract Classes

Interfaces

Interface

  • A contract: method signatures implementers must provide

  • Supports polymorphism without inheriting implementation

  • Encourages “program to an interface”

Typical uses:

  • Plug-in points and dependency injection

  • Multiple implementations behind a stable API

  • Test doubles: fake implementations for testing

Abstract classes

Abstract class

  • A partial implementation plus an abstract contract

  • Can define shared fields, constructors, and helper methods

  • Often used for a family of closely related classes

Tradeoff:

  • Abstract class provides reuse

  • Interface provides decoupling and flexibility

Java: interface vs abstract class

Interface example:

interface PaymentProcessor {
  boolean charge(int cents);
}

class StripeProcessor implements PaymentProcessor {
  public boolean charge(int cents) { return cents > 0; }
}

Abstract class example:

abstract class BaseProcessor {
  protected int attempts = 0;

  public boolean chargeWithRetry(int cents) {
    attempts++;
    return charge(cents);
  }

  protected abstract boolean charge(int cents);
}

C++: “interface” is a pure abstract base class

struct Logger {
  virtual ~Logger() = default;
  virtual void log(const char* msg) = 0;
};

struct ConsoleLogger : Logger {
  void log(const char* msg) override;
};

C++ uses abstract base classes for interface-like design; multiple inheritance is often used to combine interfaces.

TypeScript: interfaces and classes

TypeScript uses structural typing: if it has the right shape, it matches the interface.

interface PaymentProcessor {
  charge(cents: number): boolean;
}

class StripeProcessor implements PaymentProcessor {
  charge(cents: number): boolean { return cents > 0; }
}

function checkout(p: PaymentProcessor): void {
  console.log(p.charge(250));
}

checkout(new StripeProcessor());

Practice 5: choose interface or abstract class

Scenario A: many unrelated implementations; minimal coupling.

Scenario B: closely related family; shared state and helper methods.

  • For A: interface or abstract class? Why?

  • For B: interface or abstract class? Why?

Practice 5 Answer

  • Scenario A: interface (pure contract, easy substitution and testing)

  • Scenario B: abstract class (shared state/constructors/helpers reduce duplication)

Guideline: default to interface for public extension points; use abstract classes when shared implementation is central.

Mixins and Traits

Mixins and traits (conceptual) across languages

Mixin

  • A reusable bundle of methods combined into many classes

  • Share behavior without deep inheritance

Trait

  • Similar goal: compose behavior from pieces

  • Often includes conflict rules for name collisions

Where you see it:

  • TypeScript: mixin patterns (functions that extend classes)

  • Python: multiple inheritance used mixin-style

  • Java: interfaces with default methods (limited form)

  • C++: multiple inheritance for “interface mixins”; template/CRTP mixins are common for reuse without deep hierarchies

TypeScript: simple mixin pattern

type Ctor = new (...args: any[]) => T;

function Timestamped>(Base: TBase) {
  return class extends Base {
    createdAt = new Date();
    ageMs(): number { return Date.now() - this.createdAt.getTime(); }
  };
}

class User {
  constructor(public name: string) {}
}

const TimestampedUser = Timestamped(User);
const u = new TimestampedUser("Ada");
console.log(u.name);
console.log(u.ageMs());

Python: mixin-style multiple inheritance

class JsonMixin:
  def to_json(self) -> str:
    import json
    return json.dumps(self.__dict__)

class User(JsonMixin):
  def __init__(self, name: str):
    self.name = name

u = User("Ada")
print(u.to_json())

Multiple inheritance can complicate method resolution; use carefully.

Practice 6: mixin tradeoffs

Consider using mixins to add logging and caching behaviors.

  • What problem do mixins solve compared to inheritance?

  • What new problem can mixins introduce?

Practice 6 Answer

  • Mixins reuse behavior across unrelated classes without deep inheritance.

  • They can introduce name conflicts and confusing method resolution.

  • Safer alternative: composition/wrappers/delegation.

Modules and Packages

Modules connect to earlier scope ideas

  • Earlier: scope answers “what does this name refer to?” inside a program.

  • Modules/packages scale that idea across files: namespaces + visibility.

  • Goal: small public API; many private helpers.

Modules and namespaces

Module

  • A unit of code organization (file or compilation unit)

  • Defines what is exported and what stays internal

  • Prevents name collisions by using imports rather than globals

Package

  • A collection of related modules under a namespace

  • Defines visibility and dependency boundaries

C++ note: “module boundaries” are traditionally header/source + namespaces; C++20 modules exist but headers remain common.

Visibility and access control across languages

Java

  • public, protected, package-private (default), private

  • package-private is a strong tool for internal APIs

TypeScript

  • public/protected/private checked by compiler

  • module exports control public API

Python

  • underscore conventions: _internal, name mangling __x

  • relies on discipline + documentation

C++

  • public/protected/private inside classes; friend can grant access

  • namespaces avoid collisions; headers expose public API; static/anonymous namespaces give internal linkage

  • const-correctness communicates “read-only” operations (int f() const)

C++: namespaces + headers are the boundary tools

  • namespace prevents name collisions (like packages/modules).

  • Headers expose the public API; source files hide implementation details.

// math.h (public API)
#pragma once
namespace math {
  int add(int a, int b);
}

// math.cpp (implementation)
#include "math.h"
namespace math {
  int add(int a, int b) { return a + b; }
}

TypeScript modules: export and import

File math.ts:

export function add(a: number, b: number): number {
  return a + b;
}

function helper(x: number): number {
  return x * 2;
}

export function addThenDouble(a: number, b: number): number {
  return helper(add(a, b));
}

File main.ts:

import { addThenDouble } from "./math";
console.log(addThenDouble(2, 3));

helper is not exported, so it stays internal.

Java packages: organization and visibility

File src/com/example/app/User.java:

package com.example.app;

class UserRepo { // package-private: internal to com.example.app
  User find(String id) { return new User(id); }

Package-private is a practical internal-API boundary.

Industry Code Organization

Typical layering in services and libraries

A common service structure:

  • API layer: controllers/handlers, request parsing

  • Domain layer: core business rules

  • Data layer: repositories, persistence, external APIs

  • Infrastructure: logging, metrics, configuration

Goal: dependencies point inward (domain is least coupled).

Package structure strategies

Two common approaches:

Package by layer

  • controllers/, services/, repositories/, models/

  • Easy to find technical concerns; can scatter feature code

Package by feature

  • users/, orders/, billing/ each contains controller/service/repo

  • Easier to work on a feature end-to-end; can duplicate patterns

Consistency matters more than the choice.

  • Name one technique in TypeScript to keep helpers internal

  • Name one technique in Python to signal internal helpers

Practice 9 Answer

  • Java: package-private classes/methods; expose only selected public types

  • TypeScript: don’t export helpers; export only the public surface from the module

  • Python: underscore naming + document the public API; keep helpers in internal modules

  • C++: keep helpers in .cpp (not headers); use anonymous namespace or static for internal linkage; expose only declarations in headers

Review

Summary: what to remember

  • Encapsulation protects invariants and reduces coupling

  • Inheritance enables subtype polymorphism but increases coupling risk

  • Composition scales well for feature combinations

  • Dynamic dispatch chooses method bodies at runtime based on receiver class (C++ needs virtual)

  • Overriding (runtime) vs overloading (compile-time) vs generics/templates (parametric)

  • Interfaces define contracts; abstract classes combine contracts with reuse (C++ uses abstract base classes)

  • Modules/packages/namespaces define boundaries for visibility and evolution (C++: namespaces + headers)
