Hashing Basics

Hash function and hash code

We want to store the student entry (22, "Vera").

  1. Start with the key: 22.

  2. Use the rule h(x) = x. This rule is our hash function.

  3. Apply it: h(22) = 22. The numeric result is the hash code.

Our table has only 11 slots. Hash code 22 still needs to become a valid array index.

Compression and table index

Continue with hash code 22 and a table of m = 11 slots.

  1. Valid indices run from 0 through m - 1, so here they are 0 through 10.

  2. Use compression to fit the code into that range: index = hashCode % m.

  3. Compute 22 % 11 = 0. The result, 0, is the table index.

Chaining trade-offs

Our search for 33 scanned the linked list in bucket 0.

  • Search work: search and removal scan one bucket. More entries in that bucket mean more key comparisons.

  • Worst case: if all n keys share that bucket, a search can examine all n entries: O(n).

  • Storage: each bucket can grow, so entries may outnumber array slots. Linked-list nodes require extra pointer memory.

Open addressing

  • One entry per occupied array slot.

  • Entry: key and associated value.

  • After a collision, check another slot.

  • A probe checks one candidate slot.

  • Insertion and search follow the same probe sequence.

Linear probing

  • Compute h(k) % m.

  • After a collision, check the next slot.

  • After index m − 1, continue at index 0.

  • index(k, i) = (h(k) + i) % m

Double hashing

  • h1(k): hash code for the first index.

  • h2(k): distance between successive probe indices.

  • i: probe number, 0, 1, 2, …

  • index(k, i) = (h1(k) + i * h2(k)) % m

  • First probe: i = 0, so index(k, 0) = h1(k) % m.

Prime table size

  • A prime number is an integer greater than 1 and D\divisible only by 1 and itself.

  • Examples: 2, 3, 5, 7, 11, 23.

  • Prime table size: the number of slots is prime.

  • Example: m = 11.

h2(k) and table size

  • h2(k) must be nonzero.

  • h2(k) and m share no factor except 1.

  • This allows probes to reach every slot.

  • Prime m: choose 1 <= h2(k) <= m - 1.

  • With h1(k) = 0: index(k, i) = (0 + i * h2(k)) % m.

Load factor

  • Load factor α: how full the table is.

  • n: number of stored keys.

  • m: number of array slots.

  • α = n / m

Live entries nTable size mLoad factor α
3113 / 11 ≈ 0.27
8118 / 11 ≈ 0.73

  • Open addressing: α ≈ 0.27 means about 27% occupied.

  • Chaining: α may exceed 1.

Fullness and search cost

  • More occupied slots: more probing.

  • Longer buckets: more key comparisons.

  • Deleted slots cannot stop a search.

  • Many deletions can leave long search paths.

  • Rebuilding removes Deleted markers.

Across the first 32 insertions, rebuilding reinserts 4 + 8 + 16 = 28 entries.

Doubling creates a longer interval before the next rebuild.

Resize cost

The previous example spread 28 reinsertions across 32 insertions.

  1. One rebuild reinserts n live entries: O(n) expected time.

  2. Growing by a constant factor keeps the total rebuilding work proportional to the number of insertions.

  3. Spread across those insertions, the cost is O(1) expected amortized per insertion.

An individual insertion that triggers resizing can still take O(n) expected time.

Hash Function Design

Hash function correctness

Search recomputes an index from the key. It must be able to find the entry inserted earlier.

  • The same key must keep the same hash code.

  • Keys that compare equal must have equal hash codes.

  • Different keys may share a hash code. Compare actual keys to identify an entry.

Sources: Open Data Structures: hash codes

Hash function efficiency

  • Distribution: spread typical inputs across the table slots. Fewer collisions mean shorter buckets or probe sequences.

  • Computation: produce the code quickly. String hashing must process the characters.

An O(1) hashing assumption requires bounded-size keys or cached hash codes.

  • Square the key.

  • Use four digits, including leading zeros.

  • Take the middle two digits.

  • Compress to a valid index.

Extension: password hashing

Two accounts choose the password "summer123". An attacker obtains their stored password hashes.

  1. With the same unsalted scheme, hashing one guess lets the attacker test it against both accounts.

  2. A unique random salt for each stored password forces the attacker to recompute the guess for each salt.

  3. A dedicated password-hashing scheme uses deliberately expensive computation, making repeated guesses costly.

A generic fast hash alone is insufficient.

Sources: OWASP: password storage

Wrap-up

Key takeaways

  • Map: unique keys with associated values.

  • Hash function: key to hash code.

  • Compression: hash code to table index.

  • Collisions: chaining or probing.

  • Deletion: preserve the search path.

  • Load factor and resizing affect performance.

Concept check

  • Different keys, same index: replace or keep both? → Keep both.

  • Empty versus Deleted: when does search stop? → Empty: stop. Deleted: continue.

  • Prime size: does square-offset probing reach every slot? → No.

  • Larger table: can entries keep their old positions? → No. Reinsert entries.
