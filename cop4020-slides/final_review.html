The Compiler Pipeline

Modules 1, 2, 3

What Is a Programming Language?

  • A programming language defines two things:

    • Syntax: what programs look like (rules for valid text)

    • Semantics: what programs mean (what they do when run)

  • A program is a contract between programmer, language, and machine

    • The language promises what a legal program must do

    • The programmer relies on those promises

  • Languages cluster into paradigms: imperative, object-oriented, functional, logic

    • Most real languages blend multiple paradigms

    • Paradigms shape how you decompose and reason about problems

Lexical Analysis: Characters to Tokens

  • The lexer (scanner) is the first phase of a compiler or interpreter

    • Input: raw stream of characters

    • Output: stream of tokens (keyword, identifier, literal, operator, separator)

    • Whitespace and comments are recognized and discarded

  • Regular expressions specify token patterns; finite automata (DFA) implement them

    • Every regex has an equivalent DFA; a DFA can be executed in linear time

    • Scanners can be hand-written or generated from regex specifications

  • Key vocabulary: character, lexeme, token type, attribute

    • Token: a pair <token-type, attribute>

let total = a + 10;
  →  [LET_KW,"let"]  [IDENT,"total"]  [ASSIGN,"="]
     [IDENT,"a"]     [PLUS,"+"]       [INT_LIT,10]  [SEMI,";"]

Grammars and Parsing

  • A context-free grammar (CFG) describes valid token sequences

    • Terminals: tokens from the lexer

    • Nonterminals: syntactic categories (e.g., Expr, Stmt)

    • Productions: rules that expand nonterminals

    • Start symbol: represents a complete program

  • Ambiguity is a problem: one token sequence has two parse trees

    • Fixed by stratifying the grammar (precedence levels) or rewriting rules

    • Classic example: the dangling else problem

  • Parsers build an Abstract Syntax Tree (AST)

    • AST removes grammar bookkeeping; keeps semantic structure

    • Later passes (type checking, code generation) operate on the AST

<expr>   ::= <expr> "+" <term> | <term>
<term>   ::= <term> "*" <factor> | <factor>
<factor> ::= "(" <expr> ")" | NUM

The Full Pipeline

  • Every language implementation follows essentially the same pipeline:

    • Source text → Lexer → token stream

    • Token stream → Parser → AST

    • AST → Type checker / semantic analysis

    • AST → Code generation or interpreter

  • Connections to later modules:

    • The type checker builds a symbol table (Module 4) and checks type rules (Module 5)

    • Evaluation order in the interpreter relates to expression semantics (Module 6)

    • Module 13 shows how this exact pipeline is reused for DSLs

Names, Bindings, Scope, and Lifetime

Module 4

Names, Locations, and Binding Times

  • A name in source code refers to a location that holds a value

    • A binding connects a name to a type, a storage location, or a value

    • The environment is the set of active bindings at a point in execution

  • Binding time: when a binding is established

    • Language design time: keywords and built-in types

    • Compile time: many type decisions, stack layout

    • Link/load time: addresses of globals

    • Runtime: parameter values, heap objects, dynamic dispatch

  • Earlier binding → more optimization and safety checks

  • Later binding → more flexibility and dynamism

Scope: Where Names Are Visible

  • Lexical (static) scope: a name is resolved based on where it appears in the source text

    • Used by C, Java, Python, JavaScript/TypeScript

    • Python uses the LEGB rule: Local → Enclosing → Global → Built-in

  • Dynamic scope: a name is resolved based on the call stack at runtime

    • Easier to implement; harder to reason about

  • Closures: a function that captures bindings from its enclosing lexical scope

    • The captured environment is retained as long as the closure lives

    • Classic bug: var in a loop captures the same binding; let creates a fresh one per iteration

    • Closures reappear in Module 7 (callbacks), Module 9 (functional style), and Module 11 (async/await)

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);  // prints: 3 3 3
}
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);  // prints: 0 1 2
}

Lifetime and Storage Duration

  • Scope is a source-level concept (where a name is visible)

  • Lifetime is a runtime concept (how long storage exists)

  • Storage duration categories:

    • Static: exists for the entire program run (global variables, static locals in C)

    • Stack (automatic): allocated on entry to a scope, freed on exit

    • Heap (dynamic): explicitly allocated; freed manually, by GC, or by ownership rules

  • Closures extend lifetime: a captured variable on the heap outlives the frame that created it

  • This distinction is central to Module 12 (memory management) and Module 11 (task lifetimes)

Types and Type Systems

Module 5

Why Types? Two Axes of Classification

  • A type system prevents programs from using values in ways they were not intended for

  • First axis: when checks happen

    • Static typing: checks at compile time (C, Java, Rust, TypeScript)

    • Dynamic typing: checks at runtime when the path executes (Python, JavaScript)

  • Second axis: how strict coercions are

    • Strong typing: few implicit conversions; type mismatches tend to error (Python, Java)

    • Weak typing: more implicit coercions; mixing types can "succeed" but surprise (JavaScript, C)

  • These axes are independent: Python is dynamic and strong; C is static and weaker

  • TypeScript adds a static layer on top of JavaScript without changing the runtime

// TypeScript (static): caught before the program runs
let n: number = 10;
n = "hello";      // type error from the TypeScript checker

// JavaScript implicit coercion (weak): no error, surprising result
1 + "2"    // "12"  (number coerced to string)
"3" * "4"  // 12    (strings coerced to numbers)

Primitive and Composite Types

  • Primitive types: integers, floats, booleans, characters

    • Overflow is silent in many languages (C, Java integers wrap); Rust panics in debug mode

  • Composite types combine simpler types:

    • Arrays / tuples: ordered, positionally accessed

    • Records / structs / objects: named fields

    • Maps / dictionaries: key-value associations

    • Unions: a value is one of several alternatives

  • Tagged unions (discriminated unions) associate a tag with each variant

    • Pattern matching over tags is safe: the tag tells you which fields exist

    • TypeScript union types + narrowing implement this pattern

    • In Module 9, algebraic data types formalize the same idea

type Result =
  | { kind: "ok";    value: number  }
  | { kind: "error"; message: string };

function unwrap(r: Result): number {
  if (r.kind === "ok") {
    return r.value;           // TypeScript knows r.value exists here
  } else {
    throw new Error(r.message);
  }
}

Subtyping and Structural vs Nominal Typing

  • Nominal typing: two types are compatible only if they have the same name or an explicit relationship

    • Java and C++ use nominal typing: you must declare implements or extends

  • Structural typing: two types are compatible if they have the same shape (same fields and methods)

    • TypeScript and Go use structural typing

    • A type automatically satisfies an interface if it has the right members

  • Subtyping underpins the Liskov Substitution Principle in Module 8

  • TypeScript's any bypasses all type checking; unknown forces you to narrow before use

Expressions, Control Flow, and Subprograms

Modules 6, 7

Expressions: Precedence vs Evaluation Order

  • Operator precedence: a parse-time concept that determines grouping

    • 1 + 2 * 3 groups as 1 + (2 * 3) due to precedence rules

  • Evaluation order: a runtime concept that determines what executes first

    • TypeScript and Python specify left-to-right evaluation of arguments

    • C often does not specify subexpression evaluation order

    • Order matters only when subexpressions have side effects

  • Short-circuit evaluation: && and || skip the right operand when the answer is known

    • Used as a safety guard: obj != null && obj.value > 0

    • In JS/TS and Python, || and && return an operand, not a boolean

  • Pattern matching (Rust match, Python match/case) makes control flow over types exhaustive and explicit

type User = { name: string } | null;

function greet(u: User) {
  if (u !== null && u.name.length > 0) {
    console.log("Hello,", u.name);  // safe: u is not null here
  }
}

Subprograms and Contracts

  • A contract is the behavior a caller can rely on without reading the body

    • Inputs (parameter types), outputs (return type), effects (mutation, I/O), errors, and timing

    • A signature only specifies types; a contract includes effects and guarantees

  • At runtime, each call creates an activation record (stack frame)

    • Frame holds: parameters, local variables, return address, saved registers

    • Recursion works because each call gets fresh bindings on a fresh frame

  • Frames are allocated on call and popped on return; exceptions may unwind multiple frames (Module 12)

Parameter Passing

  • Call-by-value: a copy of the argument is passed; the callee cannot affect the caller's variable

  • Call-by-reference: the callee gets an alias for the caller's variable; assignments in the callee change it

  • Call-by-sharing (most OO and scripting languages): the reference is passed by value

    • Reassigning the parameter does not affect the caller

    • Mutating the object the parameter points to does affect the caller

  • Aliasing: two different names refer to the same location; a write through one name affects the other

  • First-class functions and higher-order functions connect directly to Module 9 (functional programming)

function rebind(obj: { v: number }) { obj = { v: 99 }; }  // local only
function mutate(obj: { v: number }) { obj.v = 99; }       // shared object

const a = { v: 1 };
rebind(a);  console.log(a.v); // 1  -- caller's variable unchanged
mutate(a);  console.log(a.v); // 99 -- shared object was mutated

Object-Oriented Programming

Module 8

Encapsulation, Inheritance, and Composition

  • Encapsulation: bundle state and behavior; expose only a stable interface

    • Protects class invariants by preventing external code from writing raw fields

    • Access modifiers (private, protected, public) enforce boundaries at compile time

  • Inheritance (is-a): a subclass inherits fields and methods from a superclass

    • Enables code reuse but creates tight coupling

    • C++ requires virtual to opt in to dynamic dispatch; Java uses it by default

  • Composition (has-a): an object holds references to other objects and delegates

    • Looser coupling; behavior can be changed at runtime by swapping the delegate

    • Prefer composition over inheritance when the relationship is not a true is-a

class Account {
  private int balanceCents;         // hidden; enforces invariant
  public Account(int initial) {
    if (initial < 0) throw new IllegalArgumentException();
    balanceCents = initial;
  }
  public void deposit(int cents) {
    if (cents <= 0) throw new IllegalArgumentException();
    balanceCents += cents;
  }
  public int getBalanceCents() { return balanceCents; }
}

Dynamic Dispatch and Polymorphism

  • Dynamic dispatch: the method body executed is selected at runtime based on the receiver object's actual class

    • The static type determines which methods exist; the dynamic type determines which body runs

    • Implemented via virtual method tables (vtables) in C++ and Java

  • Three "one name, many behaviors" mechanisms:

    • Overriding (subtype polymorphism): subclass replaces a superclass method; dispatch is dynamic

    • Overloading (ad-hoc polymorphism): same name, different parameter types; resolved at compile time

    • Generics / templates (parametric polymorphism): code written for a type parameter, instantiated per type

  • Liskov Substitution Principle: a subtype must honor every contract of its supertype

    • Subtypes must not strengthen preconditions or weaken postconditions

DataSource a = new FileSource(); // static: DataSource, dynamic: FileSource
DataSource b = new ApiSource();  // static: DataSource, dynamic: ApiSource
load(a);  // prints "file data" -- FileSource.read() called
load(b);  // prints "api data"  -- ApiSource.read() called

RAII: Resource Safety via Object Lifetime

  • RAII (Resource Acquisition Is Initialization): a C++ pattern that ties resource lifetimes to object lifetimes

    • Acquire the resource in the constructor; release it in the destructor

    • The destructor runs deterministically when the object leaves scope

    • File handles, mutex locks, and network connections are common examples

  • The same idea appears throughout the course:

    • Python with statement and Java try-with-resources (Module 12)

    • Rust ownership model: the borrow checker enforces RAII-like guarantees statically (Module 12)

    • Structured concurrency: task lifetimes tied to a scope (Module 11)

#include <mutex>

void safe_update(std::mutex& m, int& x) {
  std::lock_guard<std::mutex> guard(m); // acquires lock
  x += 1;
} // destructor releases lock -- even if an exception is thrown

Functional Programming

Module 9

Purity, Immutability, and Referential Transparency

  • Functional programming focuses on computing values rather than changing state

  • Pure function: returns the same result for the same inputs; no observable side effects

  • Referential transparency: an expression can be replaced by its value without changing program behavior

    • Enables equational reasoning and confident refactoring

    • Mutation, I/O, and time all break referential transparency

  • Immutability: values are not updated in place; new values are computed

    • Persistent data structures share structure across versions (not full copies)

    • Immutability eliminates one major source of concurrency bugs: shared mutable state (Module 11)

  • FP does not eliminate effects; it keeps the core pure and pushes effects to the boundary

// Impure: mutates shared state
function addItem(cart: Cart, price: number): void {
  cart.items.push(price);
  cart.total += price;         // side effect on caller's object
}

// Pure: returns a new value
function addItemPure(cart: Cart, price: number): Cart {
  return { items: [...cart.items, price], total: cart.total + price };
}

Higher-Order Functions and Composition

  • Functions are first-class values: they can be stored, passed as arguments, and returned

  • Higher-order functions take or return other functions

    • map: apply a function to every element of a list

    • filter: keep elements satisfying a predicate

    • reduce / fold: combine a list into a single value using an accumulator

  • Function composition: build complex behavior by chaining small pure functions

  • Currying: transform a function of N arguments into a chain of N single-argument functions

  • Partial application: fix some arguments and return a function expecting the rest

  • These ideas connect back to closures (Module 4 and 7) and forward to async callbacks (Module 11)

const xs = [1, 2, 3, 4, 5, 6];
const result = xs.map(x => x * 2).filter(x => x > 5).reduce((acc, x) => acc + x, 0);
// map: [2,4,6,8,10,12]  filter: [6,8,10,12]  reduce: 36

const add = (x: number) => (y: number) => x + y;  // curried
const add10 = add(10);    // partial application
add10(5);                 // 15

Algebraic Data Types, Pattern Matching, and Folds

  • Algebraic data types (ADTs): a type that is either a product (record-like) or a sum (union-like)

    • Example: a tree is either a Leaf or a Node(value, left, right)

  • Pattern matching over ADTs is exhaustive: the compiler can verify all cases are handled

    • More powerful and safer than a chain of instanceof checks

  • Structural recursion: recurse on the structure of the data type

    • Base case: the constructor with no recursive fields

    • Inductive case: reduce to a smaller structure

  • A fold captures the recursion pattern itself as a higher-order function

  • Lazy evaluation: expressions are not evaluated until their value is needed

    • Enables infinite sequences; Haskell uses lazy evaluation by default

    • JavaScript/TypeScript generators model demand-driven computation

type Result<T> =
  | { tag: "ok";  value: T }
  | { tag: "err"; message: string };

function safeDiv(x: number, y: number): Result<number> {
  return y === 0 ? { tag: "err", message: "divide by zero" }
                 : { tag: "ok",  value: x / y };
}

Logic Programming and Declarative Paradigms

Module 10

Declarative vs Imperative Thinking

  • Imperative: describe the steps; order matters; you manage control flow

  • Declarative: describe what must be true of the answer; a solver chooses strategy

    • SQL, regular expressions, build systems, policy engines, and constraint solvers all use declarative ideas

  • Logic programming is the most fully declarative mainstream paradigm

    • You write facts (ground truths) and rules (implications)

    • A query asks whether something can be made true

    • The runtime searches for a proof via resolution and backtracking

  • Declarative does not mean "no control": clause order, goal order, and cut all affect search behavior

Prolog: Unification and Resolution

  • Prolog programs are sets of Horn clauses: facts and rules of the form head :- body

  • Unification: matching terms by finding substitutions for variables

    • Two terms unify if they can be made identical by binding variables

    • Unification is the engine that drives both argument passing and pattern matching in Prolog

  • Resolution: prove a goal by finding a clause whose head unifies with it, then proving the body

  • Prolog uses depth-first search with backtracking

    • Choice points are created when multiple clauses could match

    • On failure, control returns to the most recent choice point

    • Left-recursive rules cause infinite loops; clause order matters

parent(alice, bob).
parent(bob,   carol).
grandparent(X, Z) :- parent(X, Y), parent(Y, Z).

?- grandparent(alice, Z).
% Prolog unifies X=alice, finds Y=bob, then finds Z=carol
% Z = carol.

Negation as Failure and the Cut

  • Negation as failure (\+): \+ Goal succeeds if Prolog cannot prove Goal

    • Based on the closed-world assumption: anything not provable is false

    • This is not classical logical negation; it is an operational notion

  • Groundness before negation: all variables in a negated goal must be bound first

    • Applying \+ to an unbound variable gives unsafe, counterintuitive results

    • Always ground variables using positive goals before calling \+

  • Cut (!): commits to the current clause; removes remaining choice points up to the enclosing predicate

    • Used for determinism and to implement if-then-else-like control

    • Overuse of cut makes programs harder to reason about declaratively

bird(tweety).
penguin(pingu).
bird(X) :- penguin(X).          % every penguin is also a bird

% X can fly if X is a bird AND X is not provably a penguin
can_fly(X) :- bird(X), \+ penguin(X).

?- can_fly(tweety).  % true  (bird, not a penguin)
?- can_fly(pingu).   % false (penguin, \+ fails)

Concurrency Models

Module 11

Shared Memory Threads and Race Conditions

  • Concurrency: structuring a program to handle multiple tasks in progress (possible on one core)

  • Parallelism: tasks execute at the same time on multiple cores

  • Race condition: behavior depends on the interleaving of threads accessing shared state

    • Lost update: two threads read, modify, and write the same variable; one write is overwritten

    • Hard to reproduce because timing varies across runs

  • Synchronization primitives:

    • Mutex / lock: one thread at a time in the critical section

    • Semaphore: limit how many threads may proceed (generalized counter)

    • Monitor / condition variable: lock plus a way to wait for a predicate; always check the predicate in a while loop

// Unsynchronized: two threads calling inc() lose updates
class Counter { int value = 0; void inc() { value = value + 1; } }
// Expected: 2,000,000.  Actual: often less.

// Fix: synchronized makes the critical section mutually exclusive
class Counter { int value = 0; synchronized void inc() { value = value + 1; } }

Deadlocks and Avoidance

  • The four Coffman conditions for deadlock (all must hold simultaneously):

    • Mutual exclusion: at least one resource is non-shareable

    • Hold and wait: a thread holds at least one resource and waits for more

    • No preemption: resources cannot be taken away; a thread must release voluntarily

    • Circular wait: a cycle exists in the resource-dependency graph

  • Breaking any one condition prevents deadlock

    • Most practical strategy: impose a global lock ordering (always acquire A before B)

  • Related hazards: livelock (threads keep changing state but make no progress) and starvation (a thread is perpetually denied access)

Message Passing: Go Goroutines and Channels

  • Go's model: "Do not communicate by sharing memory; share memory by communicating"

  • Goroutines: lightweight threads managed by the Go runtime; cheap to create

  • Channels: typed conduits for goroutines to send and receive values

    • Unbuffered: sender blocks until receiver is ready (synchronous rendezvous)

    • Buffered: sender only blocks when the buffer is full

  • Sending on a channel with no receiver (and no buffer space) causes a goroutine to block forever

  • The actor model generalizes message passing: each actor has a mailbox and processes one message at a time

ch := make(chan int)   // unbuffered

go func() { ch <- 42 }()  // goroutine 1: blocks until goroutine 2 receives
x := <-ch                 // goroutine 2: both sync at this rendezvous point

ch2 := make(chan int, 3)   // buffered: sender can run ahead by up to 3

Async/Await, Futures, and Structured Concurrency

  • Futures / Promises: represent a value that will be available later

    • States: pending, fulfilled, rejected

    • Promise.all, Promise.race, Promise.allSettled are combinators for multiple futures

  • Async/await: syntax sugar over Promises that makes asynchronous code look sequential

    • await suspends the function and yields the event loop; execution resumes when the Promise settles

    • An async function always returns a Promise; errors propagate as rejections

  • Event loop model: a single thread processes one callback at a time from a queue; no blocking I/O

  • Structured concurrency: tasks are scoped to a block; the block does not complete until all child tasks finish

    • Prevents orphaned background tasks and leaked work

  • Rust: the ownership and borrow checker prevents data races at compile time; no shared mutable state by default

// Promise chain
fetchUser(id).then(user => fetchOrders(user))
             .then(orders => fetchInvoice(orders[0]))
             .catch(err  => console.error(err));

// Async/await equivalent -- same semantics, sequential-looking
async function load(id: string) {
  const user    = await fetchUser(id);
  const orders  = await fetchOrders(user);
  const invoice = await fetchInvoice(orders[0]);
}

Runtime Systems and Memory Management

Module 12

Error Handling Models

  • Three common models for recoverable failures:

    • Error codes: caller checks a return value; explicit but easy to ignore; boilerplate-heavy

    • Exceptions: automatic propagation; hides control flow; cleanup must be structured

    • Typed results (Result<T, E>): encode failure in the return type; compiler forces handling

  • Java distinguishes checked (must handle or declare) from unchecked (runtime) exceptions

  • Stack unwinding: when an exception propagates, frames are popped and cleanup code runs

    • finally in Java/TypeScript always runs on both normal and exceptional exit

    • C++ uses RAII (destructors) for cleanup; no finally

    • Python uses with; Java uses try-with-resources

  • In async code, exceptions surface as rejected Promises; try/catch inside async functions handles them

// TypeScript: throw on invalid input; caller decides how to handle
function parsePort(s: string): number {
  const n = Number(s);
  if (!Number.isInteger(n) || n <= 0) throw new Error("invalid port: " + s);
  return n;
}
// Java: try-with-resources guarantees cleanup on all exit paths
static String readFirstLine(String path) throws IOException {
  try (BufferedReader br = new BufferedReader(new FileReader(path))) {
    return br.readLine();  // br.close() called on normal exit AND on exception
  }
}

Memory Management Strategies

  • Manual (C/C++): programmer calls malloc/free or new/delete

    • Full control; risks: use-after-free, double-free, memory leaks

  • Reference counting (Python, Swift, Rust Rc): each object tracks how many references point to it; freed when count reaches zero

    • Problem: cycles prevent the count from reaching zero; requires weak references to break cycles

  • Tracing GC (Java, Go, JavaScript): a collector periodically finds all live objects and reclaims the rest

    • GC does not prevent all leaks: a live reference that is never cleared keeps an object alive

    • Generational GC: most objects die young; optimize collection for the young generation

  • Rust ownership: one owner at a time; borrows are checked at compile time; no GC needed

    • Result<T, E> and ? operator for propagating errors without exceptions

fn main() {
  let s = String::from("hi");
  let t = s;           // ownership moved to t
  // println!("{}", s); // compile error: value moved
  println!("{}", t);
}

fn read_all(path: &str) -> Result<String, io::Error> {
  let mut f = File::open(path)?;   // ? propagates the error on failure
  let mut s = String::new();
  f.read_to_string(&mut s)?;
  Ok(s)
}

Language Design and DSLs

Module 13

Language Decisions Are Product Decisions

  • Every language embodies answers to three questions:

    • What mistakes do we want to make impossible?

    • What do we want to make easy and frequent?

    • What do we want to make hard or forbidden?

  • Constraints that actually drive design: runtime performance, safety guarantees, team size, hiring pool, migration cost, build speed

  • Case study contrasts:

    • Go: simplicity first; goroutines built-in; GC accepted; no inheritance

    • TypeScript: gradual typing; structural types; layered over JavaScript ecosystem

    • Rust: ownership eliminates data races and GC pauses; steep learning curve accepted

    • Java: checked exceptions; nominal types; strong tooling; enterprise stability

DSLs: When and Why

  • A domain-specific language targets a narrow domain; the common case is easy, the dangerous case is hard

  • Two forms:

    • External DSL: its own syntax (SQL, HCL, policy languages)

    • Embedded DSL: fluent API inside a host language; gains tooling, loses readability for non-engineers

  • DSLs succeed when the domain is stable, static validation is valuable, and tooling is invested in

  • DSLs fail when: error messages are poor, versioning is neglected, or feature creep turns them into weak general-purpose languages

  • Building a DSL reuses the full compiler pipeline: parse → type-check → evaluate (Module 3)

// External DSL: its own syntax; readable by non-engineers
policy "admin_access" when user.role == "admin" and resource.sensitivity <= 2 {
  allow;
}
// Embedded DSL: fluent API; gains TypeScript types and tooling
rule("free_shipping")
  .when(and(eq(varOf("tier"), str("gold")), gte(varOf("total"), num(50))))
  .do(setVar("shipping", num(0)))

Cross-Cutting Themes

How the modules connect

Binding Time: The Earliest-Is-Safest Principle

  • The earlier a decision is bound, the more the language can verify and optimize it:

    • Static types (Module 5): type errors caught before execution, not at an unlikely runtime path

    • Lexical scope (Module 4): name resolution at compile time enables closures and dead-code analysis

    • Ownership (Module 12): memory and aliasing rules enforced at compile time in Rust

    • Data-race freedom (Module 11): Rust catches concurrent aliasing at compile time

  • Later binding gives flexibility at a cost:

    • Dynamic dispatch (Module 8): body chosen at runtime; enables polymorphism but precludes some inlining

    • Dynamic typing (Module 5): errors surface only on executed paths

    • Lazy evaluation (Module 9): work deferred until demanded; harder to reason about space/time

Immutability as a Unifying Thread

  • Module 4: const prevents rebinding; closures over immutable values are safe to share

  • Module 6: aliasing bugs require mutable state; immutable values cannot alias dangerously

  • Module 9: functional programming uses immutability to achieve referential transparency and safe composition

  • Module 11: immutable values can be freely shared across threads with no synchronization needed

  • Module 12: Rust's borrow checker enforces that mutable references are exclusive; no simultaneous mutable aliasing

  • Takeaway: immutability is not just a style preference; it is a correctness guarantee that the type system can enforce

Closures Across the Course

  • A closure = a function + captured bindings from its lexical environment

  • Module 4: closures are introduced; var vs let in loops; closure bug with hoisting

  • Module 7: closures implement callbacks; timing of capture matters for async code

  • Module 9: closures enable partial application, currying, and reusable higher-order functions

  • Module 11: async functions are suspended closures; each await point is a resumption boundary

  • Module 12: closures on the heap extend variable lifetime beyond the creating stack frame

// count lives on the heap; the returned function closes over it
function makeCounter() {
  let count = 0;
  return () => { count += 1; return count; };
}
const c = makeCounter();
c();  // 1 -- count is captured; it outlives makeCounter's frame
c();  // 2 -- same binding, incremented again

Type Systems Across the Paradigms

  • Module 5: foundational concepts (static/dynamic, strong/weak, unions, inference)

  • Module 8: subtype polymorphism; nominal vs structural typing; LSP

  • Module 9: algebraic data types; pattern matching enforced by type; Option/Result encode absence and error

The Declarative Spectrum

  • The course traces a spectrum from fully imperative to fully declarative:

    • Module 6: imperative control flow; every step specified by the programmer

    • Module 8: OOP encapsulates state behind interfaces; caller sees a contract, not steps

    • Module 9: functional programming replaces loops and mutation with transformations and recursion

    • Module 10: logic programming; the programmer writes only what is true; the engine finds how

    • Module 13: DSLs capture the declarative endpoint for a specific domain

  • No paradigm is universally best; good engineers choose the right tool for the problem

// Imperative (M6): explicit steps
const out = [];
for (const x of xs) { if (x % 2 === 0) out.push(x * 2); }

// Functional (M9): describe the transformation
const out = xs.filter(x => x % 2 === 0).map(x => x * 2);
% Logic (M10): declare what is true; engine searches
doubled_even(X, D) :- member(X, Xs), 0 is X mod 2, D is X * 2.

Resource Safety: A Recurring Problem

  • "Resources" include memory, file handles, network connections, mutex locks, and spawned tasks

  • The same fundamental pattern appears in different forms across the course:

    • Module 8 (RAII): constructors acquire; destructors release; scope drives lifetime in C++

    • Module 12 (cleanup): finally, try-with-resources, and with ensure cleanup on all exit paths

    • Module 12 (memory): manual, reference counting, tracing GC, and Rust ownership are four answers to "who frees this?"

    • Module 11 (structured concurrency): tasks as resources; scope-bounded lifetimes prevent orphaned work

  • Rust unifies all of these: the ownership model is one mechanism that handles memory, locks, file handles, and tasks uniformly

# Python with (M12): cleanup guaranteed on all exit paths
with open("data.txt") as f:
    contents = f.read()
# f.close() called here, even if an exception was raised
// Structured concurrency (M11): tasks scoped like resources

  return { user, orders };

Summary: The Big Picture

  • Languages are designed artifacts, not natural facts

    • Every design choice trades off expressiveness, safety, performance, and usability

  • The compiler pipeline (Modules 1–3) explains how text becomes meaning

  • Names, types, scope, and lifetime (Modules 4–5) explain how programs refer to values safely

  • Expressions, subprograms, OOP, FP, and logic (Modules 6–10) are different answers to "how do we organize computation?"
