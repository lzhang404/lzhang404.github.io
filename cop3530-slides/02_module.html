Modular Development

What Is Modular Development?

  • Split code into focused parts.

  • Give each part one main responsibility.

  • Keep the public interface separate from the internal code.

  • Reuse the same module in more than one program.

  • Test one module without running the full program.

Why Split Code Into Modules?

  • Avoid one giant source file.

  • Make each file easier to read.

  • Change one module with fewer side effects.

  • Recompile only the files affected by the change.

  • Let different people work on different modules.

Header File: The Interface

#ifndef THREE_INTS_HPP
#define THREE_INTS_HPP

class ThreeInts {
public:
  ThreeInts(int a, int b, int c);
  int sum() const;

private:
  int x_, y_, z_;
};

#endif

  • The header tells other files what exists.

  • It declares the class name.

  • It declares public methods.

  • It declares private fields.

  • It does not need to show method bodies here.

Source File: The Implementation

#include "three-ints.hpp"

ThreeInts::ThreeInts(int a, int b, int c)
  : x_(a), y_(b), z_(c) {
}

int ThreeInts::sum() const {
  return x_ + y_ + z_;
}

  • The source file includes the header.

  • The constructor body is defined here.

  • The sum() method body is defined here.

  • ThreeInts:: says the method belongs to the class.

Driver File: Uses the Module

#include "three-ints.hpp"
#include <iostream>

int main() {
  ThreeInts nums(1, 2, 3);
  std::cout << nums.sum() << "
";
  return 0;
}

  • The driver includes the module header.

  • The driver creates an object.

  • The driver calls public methods.

  • The driver does not need to know private fields.

Header Guards: Why They Matter

#ifndef THREE_INTS_HPP
#define THREE_INTS_HPP

// declarations go here

#endif

  • A header may be included more than once.

  • Repeated declarations can confuse the compiler.

  • The guard allows the header content only once per source file.

  • #ifndef checks whether the name is not defined yet.

  • #define marks the header as already included.

  • Build means translate code into a runnable program.

  • Preprocessing handles #include and macros.

  • Compiling checks each .cpp file.

  • Compiling creates one .o file per source file.

  • Linking combines object files.

  • Linking creates the final executable.

  • A compile error usually points to one source file.

  • A link error usually means a needed object file is missing.

One-Step Build

g++ -std=c++14 -Wall -Wextra -I include   -o main main.cpp src/three-ints.cpp

  • This command compiles and links together.

  • It is simple for small projects.

  • It recompiles every listed source file.

  • It becomes repetitive as the project grows.

Step-Wise Build: Compile First

g++ -std=c++14 -Wall -Wextra -I include -c main.cpp -o main.o

g++ -std=c++14 -Wall -Wextra -I include -c src/three-ints.cpp -o three-ints.o

  • -c creates object files.

  • No executable is created yet.

  • Each source file becomes one object file.

  • The object files contain compiled code.

Step-Wise Build: Link Second

g++ -o main main.o three-ints.o

  • The linker combines object files.

  • The output is the executable named main.

  • All needed method definitions must be present.

  • Missing object files cause link errors.

Why Step-Wise Builds Are Faster

Change madeNeeds recompilingNeeds relinking
Only main.cppmain.oYes
Only three-ints.cppthree-ints.oYes
Header used by both filesBoth object filesYes
No source changedNothingNo

  • Unchanged source files can keep their old object files.

  • The build still relinks when an object file changes.

g++ -o main main.cpp grade-book.cpp grades.hpp

Practice 2 Answer

  • This is a one-step build.

  • Headers are included by source files.

  • Better command: g++ -o main main.cpp grade-book.cpp.

Practice 3: Object File Mistake

g++ -o main.o main.cpp

  • Question 1: What does this likely produce?

  • Question 2: What option is missing?

  • Question 3: How do you correctly create main.o?

Practice 3 Answer

  • Without -c, g++ tries to link.

  • The output may be an executable named main.o.

  • Correct command:

g++ -std=c++14 -Wall -Wextra -c main.cpp -o main.o

Practice 4: -c With Multiple Inputs

g++ -c -o main.o main.cpp grade-book.cpp

  • Question 1: Why is this incorrect?

  • Question 2: How many object files should be created?

  • Question 3: Show one correct fix.

Practice 4 Answer

  • -c compiles source files separately.

  • Two source files should create two object files.

  • -o main.o gives only one output name.

  • Compile each source file separately:

g++ -c main.cpp -o main.o
g++ -c grade-book.cpp -o grade-book.o
g++ -o main main.o grade-book.o

Make

Why Use make?

  • Step-wise builds require many commands.

  • Repeated commands are easy to mistype.

  • make stores the build rules.

  • make checks which files changed.

  • make rebuilds only what is needed.

  • make can build both the program and tests.

Make Rule Vocabulary

PartMeaningExample
TargetOutput to buildmain
DependenciesFiles needed by the targetmain.o three-ints.o
RecipeCommand that builds the targetg++ -o main ...

  • A rule says how to build one target.

  • A recipe line must start with a tab.

Automatic Variables

VariableMeaningCommon use
$@The target nameName the output
$^All dependenciesLink all object files
$<The first dependencyCompile one source file

  • Automatic variables reduce repeated file names.

  • They also reduce copy-paste mistakes.

Makefile: Shared Settings

CXX := g++
CXXFLAGS := -std=c++14 -Wall -Wextra -I include

  • CXX stores the compiler command.

  • CXXFLAGS stores common compile options.

  • Changing the flags in one place updates all compile rules.

Makefile: Build Executables

all: main test

main: main.o three-ints.o
	$(CXX) -o $@ $^

test: test.o three-ints.o
	$(CXX) -o $@ $^

  • all builds both executables.

  • main links the main driver and module object file.

  • test links the test driver and module object file.

  • $@ becomes main or test.

  • $^ becomes the object-file list.

Makefile: Build Object Files

main.o: main.cpp include/three-ints.hpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

test.o: test.cpp include/three-ints.hpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

three-ints.o: src/three-ints.cpp include/three-ints.hpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

  • Each object file depends on one source file.

  • Each object file also depends on the header it includes.

  • Changing the header can force recompilation.

  • $< is the first dependency.

Makefile: Run Tests and Clean

.PHONY: test-run clean

test-run: test
	./test

clean:
	rm -rf main test *.o *.gc* *.dSYM

  • test-run first builds test if needed.

  • ./test runs the test executable.

  • clean removes generated files.

  • .PHONY marks targets that are commands, not real files.

Complete Makefile Example

CXX := g++
CXXFLAGS := -std=c++14 -Wall -Wextra -I include

all: main test

main: main.o three-ints.o
	$(CXX) -o $@ $^

test: test.o three-ints.o
	$(CXX) -o $@ $^

main.o: main.cpp include/three-ints.hpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

test.o: test.cpp include/three-ints.hpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

three-ints.o: src/three-ints.cpp include/three-ints.hpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

.PHONY: test-run clean

test-run: test
	./test

clean:
	rm -rf main test *.o *.gc* *.dSYM

Common make Commands

CommandWhat it does
makeBuilds the first target, usually all
make mainBuilds only the main executable
make testBuilds only the test executable
make test-runBuilds and runs tests
make cleanRemoves generated files

How make Decides What to Rebuild

Target missing or older than dependencies -> run recipe

Target exists and is newer than dependencies -> skip recipe

  • Make compares file timestamps.

  • A changed .cpp makes its .o outdated.

  • A changed header can make several .o files outdated.

  • After object files change, the executable is linked again.

Testing

Why Testing Matters

  • Manual testing is slow.

  • Manual testing is easy to forget.

  • Tests record expected behavior.

  • Tests catch regressions after changes.

  • Modules are easier to test than one large program.

Types of Tests

Test typeWhat it checksExample
Unit testOne function or classThreeInts::sum()
Integration testMultiple modules togetherParser plus gradebook
System testWhole program behaviorInput file to output file

  • Start with unit tests when possible.

  • Add larger tests after small pieces work.

Simple Test Driver

#include "three-ints.hpp"
#include <iostream>

int main() {
  ThreeInts t(1, 2, 3);
  std::cout << "sum=" << t.sum() << "
";
  return 0;
}

  • This driver uses the module without the main program.

  • The expected output is sum=6.

  • This is useful for quick checking.

  • It still requires a human to inspect the output.

Tests With assert

#include "three-ints.hpp"
#include <cassert>

void testSum() {
  ThreeInts t(1, 2, 3);
  assert(t.sum() == 6);
}

int main() {
  testSum();
  return 0;
}

  • assert checks a condition.

  • If the condition is true, the program continues.

  • If the condition is false, the program stops with an error.

  • No output usually means the test passed.

Framework Style: Catch2-Like Tests

#include "catch.hpp"
#include "three-ints.hpp"

TEST_CASE("ThreeInts computes a sum", "[three-ints]") {
  ThreeInts t(1, 2, 3);
  CHECK(t.sum() == 6);
}

  • A framework gives named test cases.

  • CHECK reports a failed check.

  • The test report is easier to read.

  • This style scales better than one large test driver.

What Should We Test?

  • Normal cases: expected common input.

  • Boundary cases: smallest or largest valid values.

  • Error cases: invalid input, if the program handles it.

  • Repeated calls: make sure object state stays correct.

  • Bug cases: add a test when you fix a bug.

Run Tests From make

test-run: test
	./test
make test-run

  • make test-run first checks whether test is current.

  • If needed, make rebuilds the test executable.

  • Then make runs ./test.

  • This gives one command for build and test.

  • Example: run make test-run

Build-and-Test Workflow

Edit code -> Run make test-run -> Fix failures -> Run make -> Submit

  • Edit one module at a time when possible.

  • Run tests before trusting the executable.

  • Use make clean when generated files seem stale.

  • Read compiler errors before changing many files.
