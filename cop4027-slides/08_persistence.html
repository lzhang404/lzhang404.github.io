From Runtime State to Persistent Data

Objects in Memory Are Temporary

A desktop application usually keeps its current state in Java objects.

  • A drawing app may store strokes, selected color, and brush size.

  • A text editor may store current text, file path, and dirty state.

  • A signup app may store events, students, and registrations.

Program is running
    -> objects exist in memory
Program exits
    -> memory is released
Program opens again
    -> data must be loaded from storage

Persistence means saving data so it can be used after the program ends.

Running Example: Task List

The same task data can be stored as a serialized object graph or as database rows.

  • TaskItem stores an ID, title, and completion status.

  • TaskList stores a collection of tasks.

  • Serialization saves the whole task list to one file.

  • JDBC stores each task as one row in a database table.

Object file approach:
    TaskList -> tasks.bin

Database approach:
    tasks table -> rows with id, title, done

Persistence Choices

Different storage choices solve different problems.

ChoiceUseful whenLimitation
Java object serializationSave and restore a simple Java object graphJava-specific and hard to query
JSON or XML fileData should be readable or shared across toolsSearching and updating records can become manual work
Relational databaseData needs search, filtering, updates, and relationshipsRequires SQL and connection handling

The right choice depends on how the application will use the saved data.

Java Object Serialization

Serializable Task List

Java serialization saves a reachable object graph as bytes.

public final class TaskList implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;

    private final String name;
    private final List<TaskItem> tasks;
    private transient int completedCount;
}

  • writeObject(taskList) also reaches its serializable TaskItem objects.

  • serialVersionUID is checked when loading to verify class compatibility.

  • transient fields are skipped; they return with default values and may need rebuilding.

Save and Load

Path file = Path.of("data/tasks.bin");

try (ObjectOutputStream out = new ObjectOutputStream(
        Files.newOutputStream(file))) {
    out.writeObject(taskList);
}

TaskList restored;
try (ObjectInputStream in = new ObjectInputStream(
        Files.newInputStream(file))) {
    restored = (TaskList) in.readObject();
}

ObjectOutputStream writes the graph; ObjectInputStream reads it. readObject() returns Object, and try-with-resources closes both files.

Run: basics/TaskSerializationDemo.java

Serialization vs Database

Serialization is useful for a small, trusted, Java-only snapshot.

  • The program normally loads the whole object graph before searching it.

  • Updating one task usually means writing the whole graph again.

  • The saved bytes depend on Java classes and their compatible versions.

  • Never deserialize data from an untrusted source.

A database is a better fit when the application must search, update, or relate individual records.

What JDBC Is

JDBC is the standard Java API for working with relational databases.

  • Java code calls JDBC interfaces such as Connection and PreparedStatement.

  • A JDBC driver translates those calls for a specific database.

  • The database executes SQL and returns results.

Java application
    -> JDBC API
    -> JDBC driver
    -> database

Important JDBC Pieces

  • DriverManager: creates a connection from a JDBC URL.

  • Connection: represents an open database connection.

  • PreparedStatement: represents a SQL command with safe value placeholders.

  • ResultSet: represents rows returned by a SELECT query.

  • SQLException: reports database connection and SQL errors.

Connection opens the door.
PreparedStatement sends a command.
ResultSet reads returned rows.

JDBC Driver with Maven

The code uses the JDBC API, but the project also needs a database driver.

<dependencies>
    <dependency>
        <groupId>com.h2database</groupId>
        <artifactId>h2</artifactId>
        <version>2.5.250</version>
    </dependency>
</dependencies>

  • JDBC API: standard Java types such as Connection.

  • H2 driver: library that knows how to open an H2 database.

  • Maven: downloads the driver and adds it to the project build.

JDBC in module-info.java

A modular Java project must declare the modules it reads.

module cop4027.persistence.basics {
    requires java.sql;
    requires com.h2database;
}

  • requires java.sql lets the code use JDBC types such as Connection, PreparedStatement, and ResultSet.

  • requires com.h2database makes the H2 driver module available to the application.

  • The module name for a library comes from that library, not from the Maven artifact name in general.

Configuration and Connection

Connection settings can stay outside the Java source code.

jdbc.url=jdbc:h2:file:./data/tasksdb
jdbc.username=sa
jdbc.password=
DatabaseConfig config =
        DatabaseConfig.load("/database.properties");

try (Connection conn = config.openConnection()) {
    // use the database
}

  • The properties file keeps connection settings outside Java code.

  • openConnection() returns a JDBC Connection.

  • Closing the connection does not delete the rows stored in the database.

Database Table Setup

The tasks table stores one task in each row.

CREATE TABLE IF NOT EXISTS tasks (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title VARCHAR(100) NOT NULL,
    done BOOLEAN NOT NULL
)

  • id uniquely identifies each task.

  • title and done store the task data.

  • Java code writes values to this table and reads rows through JDBC.

PreparedStatement and Safe SQL

Statement vs PreparedStatement

JDBC has more than one way to send SQL to the database.

ToolHow it worksMain use
StatementSends one complete SQL stringFixed SQL with no outside values
PreparedStatementUses a SQL template with ? placeholdersSQL with values from variables, forms, or files

In application code, prefer PreparedStatement whenever values come from outside the SQL string.

The Risk: Building SQL with String Concatenation

A common mistake is to paste user input directly into a SQL string.

String sql = "SELECT id, title, done FROM tasks "
        + "WHERE title = '" + userTitle + "'";

  • This mixes the SQL command and the user's value into one string.

  • If the value contains quotes or SQL syntax, the final command can change meaning.

  • The program becomes easier to break and easier to attack.

SQL Injection Example

Suppose the program expects a task title, but the input is this:

' OR '1'='1

String concatenation can turn the query into:

SELECT id, title, done FROM tasks
WHERE title = '' OR '1'='1';

  • '1'='1' is always true.

  • The query may return rows that the user did not actually search for.

  • In other contexts, injection can modify or delete data.

How PreparedStatement Helps

PreparedStatement keeps the SQL structure separate from the values supplied to it.

String sql =
        "SELECT id, title, done FROM tasks WHERE title = ?";

PreparedStatement stmt = conn.prepareStatement(sql);
stmt.setString(1, userTitle);

ResultSet rs = stmt.executeQuery();

  • The ? marks where a value will be supplied.

  • setString(1, userTitle) sends the title as data, not SQL code.

  • The SQL structure stays separate from the user value.

Placeholders Are for Values

A placeholder can replace a value, but not a table name or column name.

// Good: the title pattern is a value.
String sql = "SELECT id, title FROM tasks WHERE title LIKE ?";
stmt.setString(1, "%exam%");

// Not the right use: table names and column names are SQL structure.
String badSql = "SELECT ? FROM ?";

  • Use placeholders for user values such as names, IDs, prices, and search text.

  • Do not build SQL structure from raw user input.

  • If the user chooses a sort field, map the choice to a fixed allowed column name.

Parameter Indexes Start at 1

String sql =
        "INSERT INTO tasks (title, done) VALUES (?, ?)";

PreparedStatement stmt = conn.prepareStatement(sql);

stmt.setString(1, title);    // first ?
stmt.setBoolean(2, false);   // second ?

stmt.executeUpdate();

  • JDBC parameter indexes start at 1, not 0.

  • Each setter corresponds to one placeholder.

  • Use a setter that matches the value type.

executeUpdate and executeQuery

Use the method that matches the kind of SQL command.

MethodUse forReturns
executeUpdate()CREATE, INSERT, UPDATE, DELETENumber of rows changed, or 0 for some schema commands
executeQuery()SELECTA ResultSet containing returned rows
 
int changed = stmt.executeUpdate();
ResultSet rows = stmt.executeQuery();

How ResultSet Works

A ResultSet acts like a cursor over returned rows.

try (ResultSet rs = stmt.executeQuery()) {
    while (rs.next()) {
        long id = rs.getLong("id");
        String title = rs.getString("title");
        boolean done = rs.getBoolean("done");
        System.out.println(id + ": " + title + " - " + done);
    }
}

The cursor starts before the first row. rs.next() moves it forward, and getter methods read columns from the current row.

Resources and Errors

JDBC code must close resources and handle database failures.

try (PreparedStatement stmt = conn.prepareStatement(sql);
     ResultSet rs = stmt.executeQuery()) {

    while (rs.next()) {
        // read rows
    }
} catch (SQLException ex) {
    System.out.println("Database error: " + ex.getMessage());
}

  • try-with-resources closes the statement and result set automatically.

  • SQLException reports connection problems, invalid SQL, missing tables, or constraint violations.

  • The program should report or handle the failure instead of silently ignoring it.

Do Not Put JDBC Everywhere

JDBC code works, but it is low-level code.

@FXML
private void saveClicked() throws SQLException {
    String title = titleField.getText();

    try (Connection conn = DriverManager.getConnection(URL);
         PreparedStatement stmt = conn.prepareStatement(
                 "INSERT INTO tasks (title, done) VALUES (?, ?)")) {
        stmt.setString(1, title);
        stmt.setBoolean(2, false);
        stmt.executeUpdate();
    }

    statusLabel.setText("Saved");
}

This event handler now knows UI controls, SQL, database connections, and status display.

Design Takeaway

Good persistence code should have a clear home.

  • UI event handlers should not contain long SQL blocks.

  • Application rules should not depend on button fields or text areas.

  • Database code should be separated so it can be tested and changed more easily.

UI event
    -> application operation
    -> persistence code
    -> database

The important idea is separation of responsibilities, not just making the code run.

Why Persistence Needs a Boundary

What Goes Wrong When SQL Spreads

  • Harder to read: UI logic and database logic are mixed together.

  • Harder to test: saving a task requires a JavaFX event and a database.

  • Harder to change: switching from H2 to another storage choice affects many files.

  • Harder to protect: one forgotten string concatenation can create a SQL injection risk.

  • Harder to maintain: the same SQL patterns are copied into many event handlers.

A program is easier to grow when persistence has one clear home.

Persistence Boundary

A persistence boundary hides storage details from the rest of the application.

Outside code sees task operations. The Repository sees JDBC, SQL, and rows.

DAO and Repository

Data Access Layer

The data access layer is the part of the program that reads and writes persistent data.

  • It owns SQL strings, JDBC resource handling, and row-mapping code.

  • It maps database rows into Java objects.

  • It reports persistence failures in one consistent way.

  • It prevents the UI and controller from depending on JDBC URLs, SQL strings, table names, or JDBC types.

Outside the data access layer:
    TaskItem objects and repository method calls

Inside the data access layer:
    Connection, PreparedStatement, ResultSet, SQL

DAO and Repository in Practical Terms

Both patterns separate persistence code from the rest of the application.

NameMain ideaExample name
DAOObject that directly handles database access for a data type or tableTaskDao
RepositoryObject that looks like a collection of domain objectsTaskRepository

In many Java applications, the two ideas overlap. The important part is the boundary.

Designing a Task Repository

Domain Object: TaskItem

The Repository stores and returns application objects, not JDBC rows.

public record TaskItem(
        long id,
        String title,
        boolean done) {
}

  • TaskItem represents one task item used by the application.

  • It contains no SQL, JDBC types, or JavaFX controls.

  • The Repository converts between database rows and TaskItem objects.

Uses: TaskItem.java

Repository Interface

The interface describes the task operations the application needs.

public interface TaskRepository {
    List<TaskItem> findAll();

    void add(String title);

    void setDone(long id, boolean done);

    void delete(long id);
}

  • The method names describe task operations, not SQL commands.

  • The return and parameter types are ordinary Java types.

  • No Connection, PreparedStatement, or ResultSet appears in the interface.

Uses: repository/TaskRepository.java

Why Use an Interface?

An interface lets the rest of the application depend on behavior instead of storage details.

Hide JDBC Exceptions Behind the Boundary

Code outside the JDBC Repository should not need to handle SQLException.

public final class RepositoryException
        extends RuntimeException {

    public RepositoryException(String message, Throwable cause) {
        super(message, cause);
    }
}

  • SQLException stays inside the JDBC implementation.

  • RepositoryException reports that a persistence operation failed.

  • The original exception remains available as the cause.

Uses: repository/RepositoryException.java

Another Repository Implementation

The same Repository interface can use a completely different storage mechanism.

public final class InMemoryTaskRepository
        implements TaskRepository {

    private final List<TaskItem> tasks = new ArrayList<>();

    public List<TaskItem> findAll() {
        return List.copyOf(tasks);
    }

    public void add(String title) {
        // store the new TaskItem in the list
    }

    // setDone(...) and delete(...) use the same list
}

  • The interface stays the same.

  • This implementation stores tasks in memory instead of a database.

  • Application code can use either implementation through TaskRepository.

JDBC Repository Implementation

JdbcTaskRepository Structure

The JDBC repository implements the same operations promised by TaskRepository.

public final class JdbcTaskRepository implements TaskRepository {
    private final DatabaseConfig config;

    public JdbcTaskRepository(DatabaseConfig config) {
        this.config = Objects.requireNonNull(config, "config");
        createTableIfMissing();
    }

    private Connection connect() throws SQLException {
        return config.openConnection();
    }

    private void createTableIfMissing() { ... }
    private TaskItem mapTask(ResultSet rows) throws SQLException { ... }

    public List<TaskItem> findAll() { ... }
    public void add(String title) { ... }
    public void setDone(long id, boolean done) { ... }
    public void delete(long id) { ... }
}

  • Setup: receive the database configuration and make sure the table exists.

  • Helpers: open connections and convert rows into TaskItem objects.

  • Repository methods: implement the operations from TaskRepository.

Example: repository/JdbcTaskRepository.java

Repository Owns Database Setup

Database-specific setup stays inside the JDBC Repository.

private static final String CREATE_TABLE_SQL = """
    CREATE TABLE IF NOT EXISTS tasks (
        id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        title VARCHAR(100) NOT NULL,
        done BOOLEAN NOT NULL
    )
    """;

  • The Repository knows the table structure.

  • The Repository runs this setup when it is created.

  • The Controller and Model do not need this SQL.

JdbcTaskRepository: Mapping Rows to Tasks

mapTask(...) converts one database row into one TaskItem object.

private TaskItem mapTask(ResultSet rows) throws SQLException {
    long id = rows.getLong("id");
    String title = rows.getString("title");
    boolean done = rows.getBoolean("done");

    return new TaskItem(id, title, done);
}

  • This helper is the bridge from relational rows to Java objects.

  • Keeping it in one method avoids repeated column-reading code.

JdbcTaskRepository: findAll()

The caller asks for tasks. JDBC details stay inside this repository method.

public List<TaskItem> findAll() {
    String sql = "SELECT id, title, done FROM tasks ORDER BY id";
    List<TaskItem> tasks = new ArrayList<>();

    try (Connection connection = connect();
         PreparedStatement statement = connection.prepareStatement(sql);
         ResultSet rows = statement.executeQuery()) {

        while (rows.next()) {
            tasks.add(mapTask(rows));
        }
        return List.copyOf(tasks);
    } catch (SQLException exception) {
        throw new RepositoryException("Could not load tasks", exception);
    }
}

  • The repository uses the JDBC pattern internally.

  • The caller receives a List<TaskItem>, not a ResultSet.

Repository Write Operation

The application asks to add a task. The JDBC Repository translates that operation into SQL.

public void add(String title) {
    String sql =
            "INSERT INTO tasks (title, done) VALUES (?, ?)";

    try (Connection connection = connect();
         PreparedStatement statement =
                 connection.prepareStatement(sql)) {

        statement.setString(1, title);
        statement.setBoolean(2, false);
        statement.executeUpdate();
    } catch (SQLException exception) {
        throw new RepositoryException(
                "Could not add task", exception);
    }
}

  • The application operation is add(title).

  • The JDBC implementation decides which SQL performs that operation.

  • Other Repository methods follow the same pattern.

Repository Method Checklist

Each JDBC repository method should answer the same design questions.

  • What application operation does this method represent?

  • What fixed SQL template does it need?

  • Which values are bound to placeholders?

  • Does it use executeUpdate() or executeQuery()?

  • If rows are returned, where are they mapped into Java objects?

  • How does the method handle SQLException?

Repository Back in MVC

Where the Repository Fits

Each part of the application has a different responsibility.

  • View: displays the current state and collects user input.

  • Controller: handles user events and coordinates application operations.

  • Model: holds the application's current state in memory.

  • Repository: saves and loads domain objects.

  • Database: stores persistent data as rows.

The Controller coordinates the Model and Repository. The View displays the Model, and the Repository communicates with the database.

Application Startup

public void start(Stage stage) throws IOException {
    DatabaseConfig config =
            DatabaseConfig.load("/database.properties");
    TaskRepository repository =
            new JdbcTaskRepository(config);

    TaskModel model = new TaskModel(repository.findAll());
    TaskView view = new TaskView(model);
    TaskController controller =
            new TaskController(model, view, repository);

    controller.connectHandlers();
    stage.setScene(new Scene(view));
    stage.show();
}

  • The repository is created once and passed to the controller.

  • The model starts with tasks loaded from persistent storage.

  • The controller depends on the TaskRepository interface.

Run: repository/TaskRepositoryApp.java

Controller Uses the Repository

public final class TaskController {
    private final TaskModel model;
    private final TaskView view;
    private final TaskRepository repository;

    public void addClicked() {
        String title = view.getEnteredTitle();
        if (title.isBlank()) {
            view.setStatus("Title required");
            return;
        }

        repository.add(title);
        model.replaceTasks(repository.findAll());
        view.refresh();
        view.setStatus("Task saved");
    }
}

  • The controller coordinates the event.

  • The repository saves and loads persistent data.

  • The model holds the current task list used by the view.

Uses: repository/TaskController.java

Common Mistakes

  • Putting long SQL blocks directly inside JavaFX event handlers.

  • Returning ResultSet from repository methods.

  • Building SQL values with string concatenation instead of placeholders.

  • Hard-coding the JDBC URL instead of loading external configuration.

  • Letting the View decide database rules or table details.

  • Copying the same row-mapping code into many methods.

  • Ignoring persistence failures or hiding exceptions without a useful message.

Good repository code keeps database details local and application operations clear.

Practice: Refactor Direct JDBC

Start with an event handler that inserts a task using JDBC.

  • Create a TaskRepository interface.

  • Move the SQL into JdbcTaskRepository.add(...).

  • Keep PreparedStatement and placeholders inside the repository.

  • Make the controller call repository.add(title).

  • Reload the Model with repository.findAll(), then refresh the View.

Controller coordinates the event.
Model holds current state.
Repository handles persistence.

Summary

Key Takeaways

  • Persistence keeps application data available after the program ends.

  • Serialization is useful for saving a trusted Java object graph; databases are better for searchable and independently updated records.

  • JDBC connects Java applications to relational databases through APIs such as Connection, PreparedStatement, and ResultSet.

  • PreparedStatement keeps parameter values separate from SQL structure and helps prevent SQL injection.

  • Try-with-resources ensures JDBC resources are closed even when an operation fails.

  • A persistence boundary keeps SQL, JDBC types, connection details, and row mapping out of the rest of the application.

  • DAO and Repository both organize data access; a Repository exposes application-level operations instead of database details.

  • Depending on a TaskRepository interface allows storage implementations to change without rewriting the Controller.

  • In MVC, the Controller coordinates actions, domain objects represent application data, and the Repository handles persistence.
