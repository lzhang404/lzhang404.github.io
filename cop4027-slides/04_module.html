Maven: The Java Build Workflow

What Maven Does

  • Uses a standard project structure.

  • Downloads external libraries.

  • Compiles source code.

  • Runs tests as part of the build.

  • Packages the project into a .jar file.

  • Makes the build repeatable across machines.

pom.xml
  -> dependencies
  -> plugins
  -> compile
  -> test
  -> package

Maven Standard Directory Layout

maven-basics/
├── pom.xml
├── src/
│   ├── main/
│   │   ├── java/          application source code
│   │   └── resources/     files packaged with the app
│   └── test/
│       ├── java/          test source code
│       └── resources/     files used by tests
└── target/                generated build output

  • Do not manually edit files in target.

  • Maven can delete and recreate target.

  • Example: examples/maven-basics

The POM: Maven's Project File

<project>
  <modelVersion>4.0.0</modelVersion>

  <groupId>cop4027</groupId>
  <artifactId>maven-basics</artifactId>
  <version>1.0.0-SNAPSHOT</version>

  <properties>
    <maven.compiler.release>21</maven.compiler.release>
  </properties>
</project>

  • pom.xml describes project identity, dependencies, plugins, and build behavior.

  • Project coordinates are written as groupId:artifactId:version.

  • Example: examples/maven-basics/pom.xml

Dependencies: Libraries Your Project Uses

<dependencies>
  <dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>${commons-lang3.version}</version>
  </dependency>
</dependencies>

  • You declare the library in pom.xml.

  • Maven downloads it to the local .m2 repository.

  • Maven also downloads required transitive dependencies.

  • mvn dependency:tree shows the resolved dependency graph.

  • Example: examples/maven-basics/pom.xml

Dependencies vs Build Plugins

Dependency

<dependency>
  <artifactId>commons-lang3</artifactId>
</dependency>

GreetingApp imports and calls library code.

Build plugin

<plugin>
  <artifactId>maven-compiler-plugin</artifactId>
</plugin>

Maven invokes the plugin while building the project.

Example: examples/maven-basics/pom.xml

Maven Phases Run in Order

compile  ->  test  ->  package  ->  verify
   |          |          |           |
 main       tests       JAR       integration
 classes                file         checks

  • mvn package also compiles the code and runs unit tests.

  • mvn verify performs the complete check used by this example.

  • mvn clean uses a separate lifecycle to delete target.

  • Run combined lifecycles with mvn clean verify.

Maven Is Convention-Based

If you follow Maven conventions:

src/main/java
src/main/resources
src/test/java
src/test/resources

Maven already knows what to do.

If you use a custom layout:

source/
assets/
tests/
output/

You must configure more manually.

For this course, use the standard layout unless there is a strong reason not to.

Resources, Tests, and Build Output

Tests in Maven: Build Integration Only

<dependency>
  <groupId>org.junit.jupiter</groupId>
  <artifactId>junit-jupiter</artifactId>
  <version>${junit.version}</version>
  <scope>test</scope>
</dependency>

  • scope is test because JUnit is needed for test code, not main application code.

  • Test files belong under src/test/java.

  • Run tests with Run As > JUnit Test or Run As > Maven test.

  • Test design, integration testing, and contract testing are separate topics later.

  • Example: examples/maven-basics/src/test/java/cop4027/maven/GreetingAppTest.java

Test Folder Layout

src/
├── main/
│   └── java/
│       └── cop4027/maven/GreetingApp.java
└── test/
    └── java/
        └── cop4027/maven/GreetingAppTest.java

This topic focuses on Maven test folder structure; test design comes later.

Resources in Maven

src/main/resources/
└── application.properties

target/classes/
└── application.properties

  • Main resources are packaged with the application.

  • Test resources are available while tests run.

  • Use classpath resource loading for files that travel with the program.

  • Example: examples/maven-basics/src/main/resources/application.properties

Loading Packaged Resources

try (InputStream input = GreetingApp.class
        .getResourceAsStream("/application.properties")) {
    if (input == null) {
        throw new IllegalStateException("Missing resource");
    }

    properties.load(input);
}

  • Files in src/main/resources are packaged with the application.

  • Maven copies these files into target/classes during the build.

  • "/application.properties" looks for the resource from the root of the packaged resources.

  • getResourceAsStream() opens the resource as an input stream.

  • If the resource cannot be found, the method returns null.

Use this approach for files that should travel with the application, not for files chosen by the user at runtime.

What Maven Generates

target/
├── classes/              compiled main classes and resources
├── test-classes/         compiled test classes and test resources
├── surefire-reports/     test reports
├── lib/                  runtime dependency JARs
└── maven-basics-1.0.0-SNAPSHOT.jar

  • target is generated output.

  • It can be deleted and recreated.

  • Do not submit or manually edit generated files unless specifically asked.

Packages and Java Modules

Packages First

src/main/java/
└── cop4027/
    └── greeting/
        └── GreetingService.java
package cop4027.greeting;

public class GreetingService {
    public String greet(String name) {
        return "Hello, " + name + "!";
    }
}

  • Packages group related classes.

  • Packages provide a namespace for class names.

  • In Eclipse, you create packages inside a Java project.

What a Java Module Adds

course-greeting/
└── src/main/java/
    ├── module-info.java
    └── cop4027/greeting/
        └── GreetingService.java

  • A Java module groups one or more packages.

  • module-info.java defines the Java module.

  • The module can decide which packages are exported.

  • Packages that are not exported stay internal to the module.

A Java module is a Java language feature. It is not the same thing as a Maven project.

Java Module Descriptors

Library module:

module course.greeting {
    exports cop4027.greeting;
}

exports makes the public package available to other Java modules.

Application module:

module course.app {
    requires course.greeting;
}

requires lets this Java module read the exported API.

  • Module descriptors are written in module-info.java.

  • Every Java module implicitly requires java.base.

Public Is Not Enough Across Java Modules

course.app
  requires course.greeting
             |
             v
course.greeting
  exports cop4027.greeting
             |
             v
  public GreetingService

  • The class must be public.

  • Its package must be exported by its Java module.

  • The caller's Java module must require the provider module.

Summary

  • Maven gives Java projects a standard structure and repeatable build process.

  • pom.xml declares project identity, dependencies, plugins, and build settings.

  • Eclipse imports each topic from the folder containing its pom.xml.

  • Java packages organize related classes inside a project.

  • Java modules provide stronger boundaries through requires and exports.

  • A Java module is defined by module-info.java; Maven project structure and build behavior are defined by pom.xml.

  • For this course, always verify your project with Maven, not only the editor run button.
