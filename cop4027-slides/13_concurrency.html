Java Concurrency

Advanced Programming

Liting Zhang

Learning Goals

  • Distinguish concurrency from parallel execution.

  • Separate a task from the thread that runs it.

  • Explain why a shared update can fail.

  • Choose a coordination or execution tool for the problem.

  • Handle completion, failure, and cancellation.

Concurrency and Threads

Why Use Concurrency?

  • Keep an application responsive during slow work.

  • Handle several independent requests.

  • Use multiple CPU cores for suitable calculations.

  • Example: load a file while the user keeps working.

Processes, Threads, and Tasks

  • A process is a running program.

  • A thread is one path of execution inside a process.

    • Threads share the process heap but keep separate call stacks.

  • A task is work that a thread can execute.

    • One thread can execute several tasks over time.

Concurrency and Parallelism

  • Concurrency: tasks make progress during overlapping periods.

    • One CPU core can switch between concurrent tasks.

  • Parallelism: tasks execute at the same time.

    • Multiple CPU cores can run tasks in parallel.

CPU-Bound and I/O-Bound Work

  • CPU-bound work spends most of its time calculating.

    • Parallel speedup needs independent tasks and available cores.

  • I/O-bound work spends most of its time waiting.

    • Another task can use the CPU during that wait.

  • Concurrency has overhead.

    • Thread creation, switching, and coordination consume resources.

    • More threads do not guarantee faster execution.

Representing a Task with Runnable

  • A functional interface has one abstract method.

    • Runnable declares run().

  • A task can provide the Runnable implementation in two forms.

    • A lambda provides a compact implementation.

    • A named class supports reuse or extra structure.

class GreetingTask implements Runnable {
    @Override
    public void run() {
        System.out.println("Hello");
    }
}

Runnable named = new GreetingTask();
Runnable lambda = () -> System.out.println("Hello");

Creating and Starting a Thread

  • The main thread begins by executing main().

  • Runnable defines the worker's task.

  • new Thread(task) creates a thread object.

    • Creating the object does not run the task.

  • start() starts the new thread, which executes the task.

    • The current thread can continue while the worker runs.

  • Each Thread object can be started only once.

Runnable task = () -> System.out.println("Hello");
Thread worker = new Thread(task, "Thread A");
worker.start();

start() and run()

  • run() is an ordinary method call on the current thread.

  • start() starts a new thread, which calls run().

Runnable task = () ->
        System.out.println(Thread.currentThread().getName());
Thread worker = new Thread(task, "Thread A");

worker.run();   // main
worker.start(); // Thread A

Thread Scheduling

  • The scheduler decides which runnable thread executes.

  • Starting first does not guarantee finishing first.

  • The output order may change across runs.

  • A correct program must tolerate valid scheduling changes.

Waiting for Completion with join()

  • Both workers can make progress after their start() calls.

  • worker.join() waits until that worker terminates.

  • The final message appears after both join() calls return.

  • join() can throw InterruptedException.

static void runWorkers() throws InterruptedException {
    Thread first = new Thread(() -> System.out.println("Hello"));
    Thread second = new Thread(() -> System.out.println("Bye"));
    first.start();
    second.start();
    first.join();
    second.join();
    System.out.println("Both finished");
}

  • Example: threads/ThreadBasicsDemo.java

join() and sleep() Solve Different Problems

join()

  • Waits for another thread to finish.

  • Expresses a real completion dependency.

  • A timed join may return before completion.

static void startAndWait(Thread worker) throws InterruptedException {
    worker.start();
    worker.join();
}

sleep()

  • Pauses the current thread.

  • Does not know whether another task finished.

static void pause() throws InterruptedException {
    Thread.sleep(100);
}

Blocking and Non-Blocking Calls

  • A blocking call makes the calling thread wait.

    • worker.join() waits for completion.

    • Thread.sleep(100) waits for time to pass.

  • A non-blocking call lets the caller continue.

    • worker.start() returns before the worker finishes.

  • Asynchronous work proceeds separately from the caller.

    • It can still make blocking calls.

Interruption Requests Cooperation

  • worker.interrupt() requests interruption.

    • It does not forcibly kill the worker.

    • Interruptible waits can throw InterruptedException.

  • Task code decides how to respond to the request.

Interruption During a Wait

  • Interrupt status records an interruption request.

    • sleep() throws InterruptedException and clears the status.

    • Restore it when higher-level code should observe the request.

Runnable task = () -> {
    try {
        Thread.sleep(1000);
        System.out.println("Work finished");
    } catch (InterruptedException exception) {
        Thread.currentThread().interrupt();
        return;
    }
};
Thread worker = new Thread(task, "Thread A");
worker.start();
worker.interrupt();

  • Example: threads/InterruptionDemo.java

Interruption During Active Work

  • A calculation does not automatically throw InterruptedException when interrupted.

  • isInterrupted() checks the current interrupt status without clearing it.

  • Check between small units of work so the task can stop promptly.

Runnable task = () -> {
    long total = 0;
    for (long n = 1; n <= 1_000_000_000L; n++) {
        if (Thread.currentThread().isInterrupted()) {
            return;
        }
        total += n;
    }
    System.out.println(total);
};

Quick Check: Starting and Waiting

  • To run a task concurrently with the current thread, call worker.run() or worker.start()?

  • Answer: worker.start(). Calling run() directly stays on the current thread.

  • Is Thread.sleep(100) a reliable way to wait for a worker to finish?

  • Answer: No. Use worker.join().

  • If the main thread calls worker.interrupt(), must the worker terminate immediately?

  • Answer: No. The worker must handle the request cooperatively.

Shared State and Synchronization

Shared Object References

  • Shared mutable state can be changed by multiple threads.

    • Two threads can reference the same object.

    • A local reference may still point to that shared object.

class Counter {
    private int value;

    public void increment() {
        value++;
    }
}

Nonatomic Counter Updates

  • An atomic operation behaves as one indivisible action.

  • value++ is not atomic.

    • It performs a read, an addition, and a write.

    • Another thread can run between those steps.

Counter counter = new Counter();
Thread first = new Thread(counter::increment, "Thread A");
Thread second = new Thread(counter::increment, "Thread B");
first.start();
second.start();

Race Condition: A Lost Update

  • Both threads read 0, compute 1, and write 1.

  • A race condition makes correctness depend on thread timing.

  • Thread-safe code remains correct under concurrent execution.

  • One successful run does not prove thread safety.

  • Example: shared/LostUpdateDemo.java

Mutual Exclusion Protects a Critical Section

  • A critical section accesses shared state.

    • Protect the complete read-change-write sequence.

  • Mutual exclusion allows one thread at a time.

    • Every conflicting access must use the same lock.

  • Java objects have a monitor used by synchronized.

synchronized Methods

  • An instance synchronized method locks this.

  • Calls on the same object therefore use the same monitor.

  • Two different objects have different monitors.

  • A static synchronized method locks the class object.

  • The JVM releases the monitor automatically when the method exits.

class SafeCounter {
    private int value;
    public synchronized void increment() {
        value++;
    }
    public synchronized int value() {
        return value;
    }
}

synchronized Blocks

  • A block can protect only the operation that needs the lock.

  • Use a stable lock object.

  • Use that same lock for every conflicting access to the protected state.

class BlockCounter {
    private final Object lock = new Object();
    private int value;

    public void increment() {
        synchronized (lock) {
            value++;
        }
    }
}

  • Example: shared/CounterDemo.java

The Update with Synchronization

  • Thread B waits while Thread A holds the lock.

  • Thread B then reads the updated value.

  • Two increments now produce 2.

Compound Operations and Invariants

  • A compound operation combines several steps into one critical section.

    • The balance check and subtraction must stay together.

    • Two 80 withdrawals cannot both succeed from 100.

  • An invariant is a rule every operation must preserve.

    • For positive withdrawals, the balance stays nonnegative.

class Account {
    private int balance = 100;
    public synchronized boolean tryWithdraw(int amount) {
        if (balance < amount) {
            return false;
        }
        balance -= amount;
        return true;
    }
}

Java Thread States

  • NEW: created but not started.

  • RUNNABLE: executing or ready to execute.

  • BLOCKED: waiting to acquire a monitor used by synchronized.

  • WAITING: waiting without a timeout, as in join().

  • TIMED_WAITING: waiting with a time limit, as in sleep().

  • TERMINATED: execution has ended.

Java uses RUNNABLE, not a separate RUNNING state. BLOCKED specifically means waiting for a monitor.

Safety and Liveness

  • Safety: an incorrect state or result does not occur.

  • Liveness: useful work can eventually make progress.

  • Deadlock: threads wait permanently for resources held by one another.

  • Starvation: one thread repeatedly fails to obtain a needed resource.

  • Prevent deadlock by acquiring locks in a consistent order.

Atomicity and Visibility

  • Atomicity: an operation behaves as one indivisible update.

  • Visibility: other threads can reliably observe a write.

  • synchronized provides both mutual exclusion and visibility.

  • Releasing a monitor happens-before a later acquisition of the same monitor.

    • The acquiring thread observes earlier protected writes.

  • A successful join() also makes the completed worker's writes visible to the caller.

The volatile Keyword

  • volatile is a field modifier that makes updates visible across threads.

    • A write happens-before subsequent reads of the same field.

  • It provides no mutual exclusion.

    • Compound operations such as value++ still need a lock or an atomic operation.

  • Example: one thread sets a stop flag while another repeatedly checks it.

class StopFlag {
    private volatile boolean stopRequested;
    public void requestStop() {
        stopRequested = true;
    }
    public boolean shouldStop() {
        return stopRequested;
    }
}

  • Example: shared/VolatileStopDemo.java

Without volatile or another synchronization mechanism, the worker is not guaranteed to observe the flag change.

Sources: JLS 8.3.1.4: volatile Fields; JLS 17.4.5: Happens-before Order.

AtomicInteger Updates

  • incrementAndGet() performs one atomic update.

  • get() reads the current value.

  • Separate atomic calls do not automatically form one atomic transaction.

  • Use a lock when correctness depends on several fields or several steps.

AtomicInteger count = new AtomicInteger();

count.incrementAndGet();
System.out.println(count.get());

  • Example: shared/AtomicCounterDemo.java

ConcurrentHashMap: Atomic Updates

Goal: keep accurate job counts by type while several workers update one map.

  • ConcurrentHashMap makes individual map operations safe.

  • get() followed by put() is still two separate steps.

    • Two workers both read 5 and write 6. The total should be 7.

  • Use merge() to make the whole update atomic for one key.

ConcurrentHashMap<String, Integer> counts =
        new ConcurrentHashMap<>();

counts.merge("reports", 1, Integer::sum);

Insert 1 if the key is absent; otherwise add 1 to its count.

  • Example: shared/ConcurrentMapDemo.java

Learning goal: distinguish a collection that supports safe concurrent access from an atomic sequence of operations. The preceding AtomicInteger slide handled one counter; a map lets us keep one count per job type. Each worker records a completion under the matching key, and no completion should be lost.

For a reports count initially equal to 5, worker A can read 5, worker B can read 5, A can put 6, and B can put 6. This lost update is possible even with ConcurrentHashMap because two separate calls do not form one atomic action. An ordinary HashMap is also unsafe for unsynchronized concurrent writes. On ConcurrentHashMap, merge combines the lookup and update atomically for that key. If both workers use merge to add 1, the final count is 7. This does not make updates spanning several keys into a single transaction.

The map is created once and shared. Each worker calls merge after completing a job; Integer::sum adds the existing count and the supplied 1. Example: shared/ConcurrentMapDemo.java uses the same pattern with a single completed key.

Source: ConcurrentHashMap.merge API.

Reduce Shared Mutable State

  • Task confinement: keep mutable data owned by one task.

  • Each task builds its own report text.

  • Return an immutable String that other tasks cannot change.

  • final prevents reference reassignment.

  • final does not make an object immutable.

static String buildReport(String name) {
    StringBuilder text = new StringBuilder();
    text.append("Report for ").append(name);
    return text.toString();
}

Quick Check: Fix the Counter

  • Two threads share a counter. Each increments its int field value once using value++.

  • Would Thread.sleep(100) before each increment prevent a lost update?

  • Answer: No. Sleep provides no protection.

  • Would volatile int value make value++ atomic?

  • Answer: No. Volatile provides visibility, not an atomic increment.

  • Would making the shared counter's increment() method synchronized protect both updates?

  • Answer: Yes. Both calls acquire the same counter's monitor.

Waiting and Thread Coordination

Lock Acquisition and Condition Waiting

  • Lock acquisition: wait for exclusive access to shared state.

    • Another thread may currently own the lock.

  • Condition waiting: wait until shared state allows an operation.

    • Owning the lock does not make the condition true.

  • Release the lock while waiting so another thread can change the state.

Example: a withdrawal owns the account's monitor, but the balance is only 20. Withdrawing 50 must wait for a deposit.

Holding the monitor protects the balance; it does not guarantee enough funds. Sleeping while holding the monitor keeps it locked, preventing the deposit that could make progress possible.

Source: Object.wait().

Condition Waiting with wait()

  • A thread must own an object's monitor before calling its wait().

  • wait() suspends the caller and releases that monitor.

    • The thread reacquires the monitor before returning.

    • Thread.sleep() keeps any monitors the thread holds.

  • Always recheck the condition in a while loop.

    • Another thread may change the state before this thread resumes.

    • A spurious wakeup can occur without notification.

class MonitorBankAccount {
    private int balance = 20;
    public synchronized void withdraw(int amount)
            throws InterruptedException {
        while (balance < amount) {
            wait();
        }
        balance -= amount;
    }
}

Monitor Notification with notifyAll()

  • After changing shared state, notify threads that may now proceed.

    • Own the same object's monitor when updating and notifying.

    • notifyAll() wakes all its waiters. notify() selects one.

  • A notification means the condition may have changed.

    • The caller keeps the monitor until it releases it.

    • Awakened threads must reacquire the monitor and recheck their condition.

public synchronized void deposit(int amount) {
    balance += amount;
    notifyAll();
}

  • Example: coordination/MonitorBankAccountDemo.java

A notification is not saved for a future waiter. Checking the condition and calling wait while owning the same monitor prevents an update from slipping between the check and the wait.

Source: Object.notifyAll().

Explicit Locking with ReentrantLock

  • ReentrantLock adds timed and interruptible acquisition to mutual exclusion.

  • lock() waits for ownership.

  • A reentrant lock may be acquired again by its owner.

  • Release with unlock() in finally, even if an exception occurs.

class LockingBankAccount {
    private int balance = 20;
    private final ReentrantLock lock = new ReentrantLock();
    public void deposit(int amount) {
        lock.lock();
        try {
            balance += amount;
        } finally {
            lock.unlock();
        }
    }
}

Timed and Interruptible Lock Acquisition

  • tryLock() supports bounded acquisition attempts.

    • The basic form returns immediately with success or failure.

    • The timed form waits for a limit and can be interrupted.

  • lockInterruptibly() waits for ownership but can be interrupted.

  • Unlock only after successful acquisition.

public boolean tryDeposit(int amount) throws InterruptedException {
    if (!lock.tryLock(100, TimeUnit.MILLISECONDS)) {
        return false;
    }
    try {
        balance += amount;
        return true;
    } finally {
        lock.unlock();
    }
}

  • Example: coordination/LockingBankAccount.java

Condition Waiting with await()

  • A Condition provides a wait set associated with a lock.

    • Separate conditions can group waiters for different state changes.

    • The program still checks a Boolean condition, such as sufficient funds.

  • Call await() while owning the associated lock.

    • It releases that lock while waiting and reacquires it before returning.

  • Use a while loop to recheck the condition after every wakeup.

private final ReentrantLock lock = new ReentrantLock();
private final Condition funds = lock.newCondition();

public void withdraw(int amount) throws InterruptedException {
    lock.lock();
    try {
        while (balance < amount) {
            funds.await();
        }
        balance -= amount;
    } finally {
        lock.unlock();
    }
}

Condition Signaling with signalAll()

  • After changing shared state, signal the relevant Condition.

    • With ReentrantLock, hold the associated lock while updating and signaling.

    • signalAll() wakes all its waiters. signal() selects one.

  • Signaling lets waiters recheck. It does not guarantee they can proceed.

    • The caller keeps the lock until it unlocks.

    • Each awakened thread reacquires the lock before testing its condition.

public void deposit(int amount) {
    lock.lock();
    try {
        balance += amount;
        funds.signalAll();
    } finally {
        lock.unlock();
    }
}

  • Example: coordination/LockingBankAccountDemo.java

Here, funds identifies the wait set, while balance >= amount is the Boolean condition. Each operation that can enable a waiting withdrawal must arrange an appropriate signal. With different withdrawal amounts, signalAll lets every waiter recheck.

Source: Condition API.

Monitor and Condition APIs

Operation Object monitor Lock + Condition
Wait and release the associated lock wait() await()
Wake one waiter notify() signal()
Wake all waiters notifyAll() signalAll()

  • Own the matching monitor or lock when calling these methods.

  • Keep monitor waiters and Condition waiters separate. Use the matching notification methods.

synchronized or ReentrantLock?

  • For straightforward mutual exclusion, synchronized handles locking and unlocking automatically.

  • For timed or interruptible acquisition, use ReentrantLock.

  • For separate wait sets on one lock, create multiple Condition objects.

  • Both approaches support waiting for state to change. Waiting alone does not require ReentrantLock.

Quick Check: Which Waiter Can Proceed?

The balance is 0. Thread A is waiting to withdraw 100. Thread B is waiting to withdraw 20.

A deposit adds 20 and calls notify() once.

Could Thread B remain waiting even though enough funds are available for it?

Answer: Yes. notify() may wake Thread A, which must wait again. notifyAll() lets both recheck, allowing Thread B to withdraw.

BlockingQueue

Problem: a file scanner finds files faster than a worker processes them.

  • The queue holds pending work and handles safe access and waiting.

  • Producer: put() adds a filename, waiting if the queue is full.

  • Consumer: take() removes one, waiting if the queue is empty.

BlockingQueue<String> jobs = new ArrayBlockingQueue<>(2);

jobs.put("report.csv");    // Scanner thread
String job = jobs.take();   // Worker thread

  • Example: coordination/BlockingQueueDemo.java

Use one motive: hand work between threads that run at different speeds. The scanner can enqueue another filename while the worker processes an earlier file. The queue stores pending work; it does not make the worker faster. This ArrayBlockingQueue is bounded: the scanner eventually waits if the worker cannot keep up. Connect this to the preceding slides: BlockingQueue provides the locking, condition checks, waiting, and wakeups for this handoff.

The code shows separate excerpts, not one sequential task. Both threads receive the same queue. put and take can throw InterruptedException; thread setup, interruption handling, and joining are in coordination/BlockingQueueDemo.java. Callers do not write their own wait/notifyAll loop for these operations. Each successful take removes one queue entry atomically; processing the file afterward is the consumer's responsibility. Capacity 2 limits pending filenames, not files already being processed. A longer-running pipeline also needs a completion policy.

Source: BlockingQueue API.

Organizing Concurrent Work and Results

A Report Is Several Tasks

A user clicks Generate Report. The interface must stay responsive while data loads.

  • A task describes a piece of work. A thread executes it.

  • Dependencies determine which tasks can run together.

Report taskWhen it can run
Load the sales totalCan start independently
Load the expense totalCan start independently
Calculate and format the summaryAfter both totals are ready
Display the reportAfter the summary is ready

The report is the running example for this section. Its two data sources can be loaded independently. The summary needs both results, and the interface can display it only afterward. Loading may involve file, database, or network I/O. The user should still be able to move the window or interact with other controls while those loads run.

A task is a unit of work, not a promise of a dedicated thread. Later stages may reuse a thread that ran earlier work. Ask students to identify the independent tasks before choosing any Java API. The code excerpts use loadSalesTotal() and loadExpenseTotal() as application helpers returning long totals in the same units. The helpers stand for the data-loading work.

Assign Work to Available Workers

  • A thread pool reuses workers across report requests.

    • ExecutorService manages execution of the tasks we submit.

  • Limit active workers and pending work separately.

    • newFixedThreadPool(2) limits workers but uses an unbounded queue.

    • A bounded queue also needs a policy for handling a full queue.

As report requests accumulate, creating a new platform thread for every piece of work can consume too many resources. A pool separates how much work is requested from how many worker threads execute it at once. In the diagram, imagine A and B are the two loads for one report and C through E are work from later requests. An available worker takes queued work.

The fixed pool used in the short examples is a simple execution mechanism, not a complete overload policy. Its worker limit does not bound queued tasks or memory use. For sustained request traffic, a bounded executor queue and a rejection or backpressure policy are separate design decisions. Blocking the UI thread to apply backpressure would make it unresponsive, so the application might disable repeated submissions or report that it is busy.

Sources: ExecutorService and Executors.newFixedThreadPool.

Work Starts Before Results Exist

  • Submission schedules work. Completion produces an outcome.

  • A Future<T> lets the caller track that outcome while continuing other work.

  • A Callable<T> describes a task that returns a value.

    • Use Runnable for a task with no returned value.

// Create one pool owned by the application
ExecutorService pool = Executors.newFixedThreadPool(2);

Callable<Long> loadSales = () -> loadSalesTotal();
Future<Long> sales = pool.submit(loadSales);

Submission does not wait for the data-loading result. The worker might start promptly, or the task might queue until a worker is available. A future is the caller's handle to the eventual outcome, which could be a value, a failure, or cancellation. The task may even finish before the caller next examines the future.

The declaration of loadSales describes work without running the helper yet. submit hands that work to the pool. Callable.call can declare checked exceptions, while Runnable.run cannot. Keep that signature detail secondary to whether the task returns a value. The pool is shared across requests, and its owner is responsible for shutdown.

Sources: ExecutorService and Future.

Wait Only When You Need the Result

Sales and expenses are independent. Submit both loads before waiting.

Future<Long> sales = pool.submit(() -> loadSalesTotal());
Future<Long> expenses = pool.submit(() -> loadExpenseTotal());

// Later, on a background coordinator thread
long profit = sales.get() - expenses.get();

  • get() blocks the calling thread if the result is not ready.

  • Waiting before submitting the expense task would prevent the loads from overlapping.

  • A waiting UI thread cannot handle input or repaint the interface.

  • Example: executors/ExecutorFutureDemo.java

Open executors/ExecutorFutureDemo.java and run main here. Point out that both loads are submitted before either get call. The main thread is the console coordinator, and the final result is Profit: 400. Open executors/ReportDataSource.java only if students need to see how the sample data and loading delay are supplied.

This is a background coordination option, not code to run inside a UI event handler. The coordinator must not occupy a worker needed by the tasks it waits for. Here it runs outside the two-worker loading pool. The alternative on the next slide registers dependencies without a coordinator blocking on get.

Both tasks are submitted before either result is retrieved. Waiting for sales first does not prevent the already-submitted expense load from running. If the caller instead submitted sales, immediately waited for it, and only then submitted expenses, it would serialize the two loads. Overlap is possible, not a guarantee that their start times are identical.

These excerpts omit surrounding exception handling. get may report a failed task with ExecutionException, cancellation with CancellationException, or interruption of the waiting caller with InterruptedException. The latter does not by itself cancel the worker task.

Source: Future.

Dependencies Determine What Runs Next

  • A stage is one step in a computation.

  • CompletableFuture connects stages that run after their inputs succeed.

var sales = CompletableFuture.supplyAsync(
        () -> loadSalesTotal(), pool);
var expenses = CompletableFuture.supplyAsync(
        () -> loadExpenseTotal(), pool);

CompletableFuture<String> report = sales
        .thenCombine(expenses, (s, e) -> s - e)
        .thenApply(profit -> "Profit: " + profit);

Combine both totals, then format the report. The caller does not wait for the loads.

  • Example: executors/CompletableFutureDemo.java

Open executors/CompletableFutureDemo.java, trace generateReport, and run main here. It first prints Profit: 400, then reports a failed sales load. Use that second outcome to lead into the next slide. The console main may join, while generateReport returns the future without waiting for its inputs.

This is an alternative implementation of the same report workflow. Each supplyAsync schedules an independent load on the application-owned pool. A stage is one computation in the dependency chain. thenCombine calculates profit after both loads succeed. thenApply formats that profit after the calculation succeeds. Registering the chain does not wait for an unfinished input.

Dependencies determine when a stage is eligible to run, not which thread must run it. Non-Async continuations can run on a thread completing an input or inline when attached to an already-completed stage. Keep these calculation and formatting steps brief. No new thread is promised for each stage, and no UI control is changed here. Calling join or get afterward would introduce a blocking wait, which is why the UI handoff uses a completion action later.

Sources: CompletableFuture and CompletionStage.

Plan for Missing Results

A data load may fail, take too long, or become unnecessary.

SituationMeaning for the reportApplication decision
FailureA required load failedShow an error or offer a retry
TimeoutThe caller's wait limit expiredStop waiting and decide whether to cancel
CancellationThe result is no longer wantedRequest a stop and handle unfinished work

  • A timeout does not automatically stop the task.

  • Stopping running work requires cooperation.

    • Cancelling a CompletableFuture does not interrupt its computation.

  • Example: executors/FutureTimeoutDemo.java

After discussing the failed load from CompletableFutureDemo, open executors/FutureTimeoutDemo.java and run main. Identify the expired wait, the separate cancellation request, and the final executor-termination message. The loader cooperates with interruption, so accepting cancellation and actually finishing the worker remain distinct events.

For this report, a failed required load means there is no valid summary to display. Success-only dependent functions such as thenCombine and thenApply are skipped on the failed path. Handle the failure at an appropriate boundary, such as the final UI delivery, rather than silently replacing missing data with zero.

Timed Future.get bounds one wait and can throw TimeoutException while work continues. A failed task is reported through ExecutionException by get or CompletionException by CompletableFuture.join, with the original failure available as a cause. An interrupted caller is a separate event from task failure.

For a task submitted to an executor, Future.cancel(true) attempts cancellation and may request interruption of its worker. Code must cooperate with interruption. A successful cancellation causes subsequent get calls to report CancellationException, but it does not prove the running code has already stopped. CompletableFuture.cancel marks the future cancelled without interrupting the computation. Cancelling a dependent report stage does not automatically stop the sales and expense loads. Actual work cancellation needs its own design.

Sources: Future and CompletableFuture.cancel.

Complete the Request Responsibly

  • Deliver the finished report or an error to the UI.

    • JavaFX control updates belong on the JavaFX Application Thread.

  • The application owns the pool across report requests.

    • At shutdown, stop accepting work and finish or cancel pending tasks.

report.whenComplete((text, failure) ->
    Platform.runLater(() -> {
        if (failure == null) showReport(text);
        else showError("Report could not be loaded");
    }));

Keep task waits and blocking shutdown waits off the UI thread.

whenComplete observes either success or failure. The callback can run outside the UI thread, so runLater posts a short interface update to the JavaFX Application Thread. showReport and showError stand for application methods that update controls. Loading and report calculation have already happened before this UI action. runLater posts work and returns without waiting for the UI action to execute.

The pool should have an explicit owner and lifetime. For this application it is created once and reused across report requests. shutdown rejects new tasks while allowing submitted work to finish, and it does not wait for termination. Java 21 close initiates shutdown and waits for termination. A try-with-resources block invokes close when leaving its scope, so a pool scoped to a UI event handler could block that handler while work finishes. Any termination wait belongs off the UI thread. Cancellation is cooperative, and outstanding work must be accounted for during application shutdown.

Sources: Platform.runLater, CompletableFuture.whenComplete, and ExecutorService.close.

Virtual Threads

Why Virtual Threads?

  • A platform thread is tied to an OS thread.

  • A virtual thread is a lightweight JVM-managed thread.

    • When it waits, the platform thread can run other work.

    • This benefits workloads with many I/O waits.

One Virtual Thread per Task

  • Each submitted task receives a virtual thread.

  • Tasks can use ordinary blocking code.

  • get() waits when we need the result.

static void runVirtualTask()
        throws InterruptedException, ExecutionException {
    try (ExecutorService executor =
            Executors.newVirtualThreadPerTaskExecutor()) {
        Future<String> report = executor.submit(() -> {
            Thread.sleep(100);  // simulate waiting for I/O
            return "Report ready";
        });
        System.out.println(report.get());
    }
}

What Virtual Threads Do Not Solve

  • Virtual threads improve waiting scalability, not every concurrency concern.

    • Shared mutable state still needs synchronization.

    • CPU-heavy work does not become faster.

    • Scarce resources still need limits.

  • Blocking inside synchronized can reduce Java 21 scalability.

  • Example: executors/VirtualThreadDemo.java

Summary

Choose a Tool for the Job

  • Simple shared state: synchronized.

  • Waiting on an object: wait() and notifyAll() under synchronized.

  • One shared counter: AtomicInteger.

  • Extra lock control and separate wait sets: ReentrantLock and Condition.

  • Producer-consumer handoff: BlockingQueue.

  • Task execution and results: ExecutorService and Future.

  • Dependent result stages: CompletableFuture.

  • Many blocking tasks: virtual threads.

Key Takeaways

  • A task describes work. A thread executes work.

  • start() starts a new thread. Calling run() directly does not.

  • Shared mutable state may require both atomicity and visibility.

  • Mutual exclusion prevents conflicting critical sections from overlapping.

  • Correctness requires both safety and liveness.

  • wait() and await() reacquire their lock before returning. Recheck shared state in a while loop.

  • Completion, failure, interruption, timeout, and cancellation are part of task design.
