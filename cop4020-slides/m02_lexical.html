Lexical Basics

What Is Lexical Analysis?

  • Lexical analysis (scanning) is the first phase of a compiler or interpreter.

  • It takes in:

    • a stream of characters from the source file

  • It produces:

    • a stream of tokens such as

    • keywords (let, if, while)

    • identifiers (variable and function names)

    • literals (numbers, strings)

    • operators and punctuation

  • Main job:

    • group characters into meaningful pieces (lexemes)

    • give each lexeme a token type

    • skip whitespace and comments

Where Does Lexical Analysis Fit?

  • A very simple view of a compiler or interpreter:

    • Source program (characters)

    • → scanner or lexer (tokens)

    • → parser (syntax trees)

    • → later phases (semantic checks, code generation, and so on)

  • Lexical analysis answers questions like:

    • Where does each identifier, number, or operator start and end?

    • What kind of token is each piece of the input?

  • In practice, a scanner can be:

    • hand-written, or

    • generated from regular expressions and finite automata

Basic Vocabulary

  • Character: one position in the file, for example a, +, 7, ;

  • Lexeme: a finite sequence of characters from the source program that matches the pattern for a token

  • Token: a pair <token-name, attribute> produced by the lexical analyzer to represent a lexeme.

  • Example line: int x = 42;

  • Lexemes in that line:

    • int

    • x

    • =

    • 42

    • ;

  • Tokens for those lexemes:

    • int → token type INT_KEYWORD

    • x → token type IDENT

    • = → token type ASSIGN

    • 42 → token type INT_LIT (value 42)

    • ; → token type SEMICOLON

  • Lexical structure: the rules that say how characters form valid tokens

Example: Token Stream

Consider the JavaScript statement:

let sum = a + 10;

One possible sequence of tokens:

  • token type LET_KW, lexeme let

  • token type IDENT, lexeme sum

  • token type ASSIGN, lexeme =

  • token type IDENT, lexeme a

  • token type PLUS, lexeme +

  • token type INT_LIT, value 10

  • token type SEMICOLON, lexeme ;

Whitespace is usually skipped by the scanner and does not become tokens.

Token Categories in Industry Languages

Common categories in Java, C++, and JavaScript:

  • Keywords (reserved words that are not allowed as identifiers)

  • Identifiers (names of variables, functions, classes, and so on)

  • Literals (integers, floats, strings, chars, booleans)

  • Operators (for example, + - * / == && || !)

  • Separators and punctuation (for example, ; , ( ) { } [ ])

  • Comments and whitespace (usually recognized, then ignored)

Regular Expressions

Why Use Regular Expressions?

  • Many token types follow simple text patterns.

  • Examples:

    • Identifier: letter or underscore, followed by letters, digits, or underscores

    • Integer literal: one or more digits in a row

    • Whitespace: one or more spaces, tabs, or newlines

  • Regular expressions are a compact way to write these patterns.

  • Later, we can turn these patterns into finite automata and then into code.

Regular Languages and Regex (Informal)

A regular language is a set of strings built from simpler pieces using:

  • Union (choice): \(L_1 \cup L_2\)

    • strings from \(L_1\) or from \(L_2\)

  • Concatenation: \(L_1 L_2\)

    • strings from \(L_1\) followed by strings from \(L_2\)

  • Kleene star: \(L^*\)

    • zero or more repetitions of strings from \(L\)

Regular expressions give us a way to write these ideas:

  • (a|b) means either a or b

  • ab means a followed by b

  • a* means any number of a, including zero

  • Common shorthands: [0-9], [A-Za-z], \d, +, ?, and so on

  • Identifier (simple version): [A-Za-z_][A-Za-z0-9_]*

  • Integer literal (non-negative): [0-9]+

  • Whitespace: [\t ]+

  • Line comment (C++/Java/JS style): //.*

Real languages add more details (hex, floats, Unicode, and so on), but the basic idea is the same.

Finite Automata

Finite Automata: Intuition

  • A finite automaton (FA) is a very simple machine with:

    • a small set of states

    • a start state

    • one or more accepting (final) states

    • rules that say how to move between states based on the next character

  • How it works:

    • start in the initial state

    • read characters one at a time and follow the transitions

    • if you end in an accepting state, the input string is accepted

  • Regular expressions and finite automata describe the same class of languages.

Deterministic vs Non-deterministic Automata

  • In a deterministic finite automaton (DFA):

    • for each state and each input character, there is at most one next state

  • In a non-deterministic finite automaton (NFA):

    • there may be several possible next states

    • there may be moves on empty input (epsilon transitions)

  • The important fact for us:

    • every NFA can be converted into an equivalent DFA

    • scanners are usually implemented as DFAs for speed

Deterministic Finite Automation for Integer Literals

Target language: non-empty sequences of digits, described by [0-9]+.

States (informal):

  • \(q_0\): start, no digits seen yet

  • \(q_1\): have seen at least one digit (accepting)

  • \(q_{\text{dead}}\): anything invalid

Behavior:

  • From \(q_0\):

    • digit goes to \(q_1\)

    • non-digit goes to \(q_{\text{dead}}\)

  • From \(q_1\):

    • digit stays in \(q_1\)

    • non-digit means we stop and accept the digits we saw as one token

This is the basic idea of how a scanner finds where an integer literal ends.

Example: Running the Integer DFA

Target pattern: sequences of digits [0-9]+.

Example 1: input "42"

  • Start in \(q_0\)

  • Read '4' (digit): \(q_0 \rightarrow q_1\)

  • Read '2' (digit): \(q_1 \rightarrow q_1\)

  • End of input in accepting state \(q_1\)

  • Result: one integer token with lexeme "42"

Example 2: input "123x"

  • Start in \(q_0\)

  • Read '1', '2', '3' (digits): \(q_0 \rightarrow q_1 \rightarrow q_1 \rightarrow q_1\)

  • Next character is 'x' (not a digit)

  • DFA says: stop token before 'x'

  • Result: integer token "123", remaining input "x" for the next token

DFA Sketch for Identifiers

Simple identifier rule: first character is a letter or underscore, rest are letters, digits, or underscores.

States:

  • \(q_0\) start, seen nothing yet

  • \(q_{\text{id}}\) seen a valid first character (accepting)

  • \(q_{\text{dead}}\) for anything that can not start an identifier

Behavior:

  • From \(q_0\):

    • letter or underscore goes to \(q_{\text{id}}\)

    • anything else goes to \(q_{\text{dead}}\)

  • From \(q_{\text{id}}\):

    • letter, digit, or underscore stays in \(q_{\text{id}}\)

    • other character means end of identifier token

Example: Running the Identifier DFA 1

Simple identifier rule:

  • first character: letter or underscore

  • rest: letters, digits, or underscores

Example 1: input "x1y"

  • Start in \(q_0\)

  • Read 'x' (letter): \(q_0 \rightarrow q_{\text{id}}\)

  • Read '1' (digit): stay in \(q_{\text{id}}\)

  • Read 'y' (letter): stay in \(q_{\text{id}}\)

  • End of input in accepting state \(q_{\text{id}}\)

  • Result: identifier token with lexeme "x1y"

Example: Running the Identifier DFA 2

Simple identifier rule:

  • first character: letter or underscore

  • rest: letters, digits, or underscores

Example 2: input "_main3"

  • Start in \(q_0\)

  • Read '_': \(q_0 \rightarrow q_{\text{id}}\)

  • Read 'm', 'a', 'i', 'n', '3': stay in \(q_{\text{id}}\) each time

  • End of input in \(q_{\text{id}}\)

  • Result: identifier token with lexeme "_main3"

From Regex to a Scanner

From Regex to Scanner (High Level)

  • For each token type:

    • write a regular expression

    • turn that regular expression into an automaton

  • Combine the automata for all token types into one machine.

  • Use that machine to scan the input:

    • find the longest prefix that matches some token

    • output that token

    • then continue with the rest of the input

  • Tools like lex, flex, and JLex can do this automatically.

Manual Lexing Walkthrough

Consider the line:

let total = a + 10;

Walk through as a scanner would:

  • Read l e t → matches keyword pattern, token LET_KW

  • Skip the space

  • Read t o t a l → matches identifier pattern, token IDENT

  • Skip the space

  • Read = → matches assign pattern, token ASSIGN

  • Skip the space

  • Read a → token IDENT

  • Skip the space

  • Read + → token PLUS

  • Skip the space

  • Read 1 0 → token INT_LIT

  • Read ; → token SEMICOLON

Implementation in JavaScript

Scanner Responsibilities

  • Read input characters from a source file or string.

  • Group characters into tokens using lexical rules.

  • Return a sequence (or stream) of tokens to the parser.

  • Skip over things that should not become tokens:

    • whitespace

    • comments

  • Keep track of:

    • line numbers and columns, for error messages

    • the original lexeme for identifiers, literals, and so on

Design Choices

  • How to write the scanner:

    • a table-driven DFA, or

    • hand-written if and else or switch code

  • Lookahead:

    • sometimes we must peek at the next character

    • examples: = versus ==, + versus ++

  • Error handling:

    • what should we do with unexpected characters?

    • one simple strategy: report the error and maybe skip one character

A Tiny Token Definition (TypeScript)

const TokenType = {
  LET: "LET",
  IDENT: "IDENT",
  NUMBER: "NUMBER",
  OP: "OP",
  ASSIGN: "ASSIGN",
  SEMI: "SEMI"
} as const;
class Token {
  public type: TokenType;
  public lexeme: string;
  constructor(type: TokenType, lexeme: string) {
    this.type = type;
    this.lexeme = lexeme;
  }
  toString(): string {
    return `${this.type}(${this.lexeme})`;
  }
}

Regex Specification for Tokens (TypeScript)

const tokenSpecs: [RegExp, TokenType | null][] = [
  // Whitespace (skip)
  [/^\\s+/, null],
  // Single-line comments (skip)
  [/^\\/\\/.*/, null],
  // Keywords
  [/^let\\b/, TokenType.LET],
  // Identifiers and numbers
  [/^[A-Za-z_][A-Za-z0-9_]*/, TokenType.IDENT],
  [/^[0-9]+/, TokenType.NUMBER],
  // Operators and punctuation
  [/^[+\\-*\\/]/, TokenType.OP],
  [/^=/, TokenType.ASSIGN],
  [/^;/, TokenType.SEMI]
];

  • Each entry is a pair: a regular expression and a token type.

  • If the token type is null, the scanner skips that text.

Tiny Lexer in TypeScript

function lex(input: string): Token[] {
  const tokens: Token[] = [];
  let str: string = input;
  while (str.length > 0) {
    let match: RegExpExecArray | null = null;
    let matchedType: TokenType | null = null;
    for (const [regex, type] of tokenSpecs) {
      match = regex.exec(str);
      if (match) {
        matchedType = type;
        break;
      }
    }
    if (!match) {
      throw new Error(`Unexpected character: '${str[0]}'`);
    }
    const lexeme = match[0];
    if (matchedType !== null) {
      tokens.push(new Token(matchedType, lexeme));
    }
    str = str.slice(lexeme.length);
  }
  return tokens;
}

Running the Tiny Lexer

const src = "let sum = a + 10;";

const tokens = lex(src);
for (const t of tokens) {
  console.log(t.toString());
}

Expected output (in words):

  • a LET token with lexeme let

  • an IDENT token with lexeme sum

  • an ASSIGN token with lexeme =

  • an IDENT token with lexeme a

  • an OP token with lexeme +

  • a NUMBER token with lexeme 10

  • a SEMI token with lexeme ;

Handling Whitespace and Comments

  • What counts as whitespace in most languages?

    • space character, tab character, newline, carriage return

  • Typical scanner rule:

    • recognize one or more whitespace characters

    • consume them (advance the input position)

    • do not return a token for them

  • Why we still care about whitespace:

    • we must update line and column numbers

    • newlines affect error messages and sometimes layout

  • Comments are handled the same way:

    • recognize the comment pattern (for example, //... or /* ... */)

    • consume everything up to the end of the comment

    • return no token, but still update line and column if there are newlines

  • Exception examples:

    • Python: indentation (leading spaces) is part of the syntax

    • some languages treat end of line as a special token

Wrap-up

Error Reporting in Scanners

  • Real source code will contain mistakes.

  • Your scanner should detect bad input such as:

    • characters that are not allowed in the language

    • badly formed tokens, if you choose to support more complex tokens

  • When an error is found:

    • print a clear message with the line and column

    • show the unexpected character or lexeme

Connecting Back to Java/C++ Token Categories

  • Java and C++ use the same basic ideas:

    • keywords: int, class, if, while, and so on

    • identifiers: names that follow the language rules

    • literals: integers, floats, chars, strings, booleans

    • operators: arithmetic, comparison, logical, bitwise

    • separators: punctuation and delimiters

  • Industrial compilers have many more token types and details.

  • The small scanners you build in this course use the same core ideas, just on a smaller scale.
