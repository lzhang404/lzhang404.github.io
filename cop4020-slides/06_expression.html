Expressions: What They Are

  • An expression is a syntactic form that can be evaluated to produce a value.

  • Key properties that differ across languages:

    • Evaluation order: which subexpression runs first

    • Side effects: whether evaluation changes program state

    • Definedness: whether the language specifies behavior for all cases

    • Type rules: whether expression types are inferred or annotated

  • Common sources of confusion:

    • Operator precedence vs evaluation order are different concepts

    • A program can be type-correct but still have unspecified behavior in some languages

Operator Precedence vs Evaluation Order

  • Operator precedence decides how an expression is grouped (its parse tree).

  • Evaluation order decides when the grouped pieces are executed.

  • Example grouping:

    • \(1 + 2 * 3\) groups as \(1 + (2 * 3)\) due to precedence

  • Evaluation order matters when:

    • function calls have side effects

    • operands update shared state

    • short-circuit logic can skip work

Evaluation order: left to right example

TypeScript evaluates function arguments from left to right:

function log(label: string, value: number): number {
  console.log(label, value);
  return value;
}
let x = 1;
let y = log("first", x++)
      + log("second", x++);
// Output:
// first 1
// second 2
// After expression: x is 3, y is 3

Evaluation order: C can be tricky

In C, order of evaluation of subexpressions is often not specified:

#include <stdio.h>
int inc(const char *label, int *p) {
  printf("%s %d\n", label, *p);
  return (*p)++;
}

int main(void) {
  int x = 1;
  int y = inc("first", &x) + inc("second", &x);
  printf("x = %d, y = %d\n", x, y);
}

  • The language specification does not guarantee which inc call happens first

  • Compilers may choose different orders

  • Code that depends on a particular order is fragile and may be incorrect

Side effects

  • A side effect is any observable change in program state besides returning a value

    • Modifying a variable or object field

    • Writing to a file or network

    • Printing to the console

  • Expressions with side effects can be harder to reason about

    • Value depends on when and how many times the expression is evaluated

  • Many languages allow side effects almost anywhere

    • Assignment as an expression in C, C++

    • Function calls with side effects in any language

  • Some styles and languages try to limit side effects

    • Pure functions, functional programming, immutable data

Side effects inside expressions

TypeScript example combining value and side effect:

let arr = [1, 2];

function pushAndSum(value: number): number {
  arr.push(value);        // side effect
  return arr.reduce((a, b) => a + b, 0);
}

let total = pushAndSum(3) + pushAndSum(4);

// After expression:
// arr is [1, 2, 3, 4]
// total is 6 + 10 = 16

  • The result depends on the order and number of calls

  • Avoid hidden side effects inside complex expressions when possible

Short-circuit boolean evaluation

  • Boolean operators and and or in many languages are short-circuiting

    • In a and b, if a is false, b is not evaluated

    • In a or b, if a is true, b is not evaluated

  • This is useful for

    • Avoiding unnecessary work

    • Avoiding errors when later expressions would be unsafe

  • It also means that boolean expressions can control side effects

    • Second expression may or may not run

Short-Circuit as a Safety Guard (TypeScript)

type User = { name: string } | null;

function greet(u: User) {
  if (u !== null && u.name.length > 0) {
    console.log("hello", u.name);
  } else {
    console.log("no user");
  }
}

  • The second condition is only evaluated when u is not null

  • This is one of the most common and safe uses of short-circuit

ts_short_circuit.ts

Short-Circuit as a Safety Guard (Python)

def greet(u):
    # u is either None or a dict with "name"
    if u is not None and len(u["name"]) > 0:
        print("hello", u["name"])
    else:
        print("no user")

  • The and operator short-circuits like &&

  • This avoids exceptions when u is None

Short-Circuit with Side Effects: Pitfall

Short-circuit can hide control flow inside expressions.

// typescript
let connected = false;
function connect(): boolean {
  console.log("connecting...");
  connected = true;
  return connected;
}
// works, but the intent is not obvious
connected || connect();

Guideline:

  • Prefer an explicit if statement when the right side has side effects

Short-Circuit Return Values

In TypeScript / JavaScript:

  • A && B returns either A or B (not necessarily a boolean)

  • A || B returns either A or B

In Python:

  • and and or also return one of the operands

Consequence:

  • This enables idioms like default values

  • It can also cause bugs when you expected a boolean

Default Values with Short-Circuit (TypeScript)

function label(name: string | undefined) {
  let shown1 = name || "anonymous";
  let shown2 = name ?? "anonymous"; // nullish coalescing

  console.log({ shown1, shown2 });
}

label(undefined);
label("");

  • || treats empty string as falsey

  • ?? only replaces null or undefined

Default Values with Short-Circuit (Python)

def label(name):
    shown = name or "anonymous"
    print(shown)

label(None)
label("")

Note:

  • Empty string behaves like false in Python

  • If empty string is a valid value, use an explicit check instead

Assignment Models

Assignment connects a name to a value (or updates a storage location).

Key questions:

  • Is assignment a statement, an expression, or both

  • Does assignment copy a value or copy a reference

  • What is the type behavior (implicit conversions, coercions)

  • Are there compound assignments and destructuring forms

Assignment as an Expression (C, TypeScript)

In C and JavaScript, assignment produces a value.

#include <stdio.h>

int main(void) {
  int x = 0;
  int y = (x = 5);  // assignment yields 5
  printf("x=%d y=%d\n", x, y);
  return 0;
}

Implication:

  • compact code is possible

  • bugs happen when = is confused with ==

Assignment is a Statement (Python)

In Python, assignment is a statement, not a general expression.

x = 5
# y = (x = 5)   # syntax error in Python
y = x
print(x, y)

Benefit:

  • fewer accidental assignments inside conditions

Related feature:

  • Python has a dedicated assignment expression operator := for limited cases

Compound Assignment

Compound assignment updates a location using an operator.

let x = 10;
x += 5;   // x = x + 5
x *= 2;   // x = x * 2
console.log(x);

Notes:

  • C and TypeScript support many compound operators

  • Python also supports them (+=, *=, etc.)

  • With objects, += may mutate or allocate depending on language and type

Chained Assignment: Readability vs Risk

// typescript
let a: number, b: number, c: number;
a = b = c = 0;
console.log(a, b, c);
# python
a = b = c = 0
print(a, b, c)

  • Works well for immutable values (numbers, strings)

  • Can be surprising for mutable objects if all names reference the same object

Chained Assignment with Mutability (Python)

a = b = []
a.append(1)
print(a)  # [1]
print(b)  # [1]

  • a and b refer to the same list object

  • mutation through one name is observed through the other

Safer pattern:

  • a = [] ; b = []

Destructuring and Multiple Assignment

TypeScript destructuring:

let pair: [number, string] = [7, "seven"];
let [n, s] = pair;

let obj = { x: 1, y: 2 };
let { x, y } = obj;

console.log(n, s, x, y);

Python tuple unpacking:

n, s = (7, "seven")
x, y = [1, 2]
print(n, s, x, y)

Sequences and Blocks

  • A sequence is a way to express multiple computations in order.

  • A block groups statements into a single syntactic unit:

    • often introduces a scope

    • often controls lifetime of locals

    • often used after if/while/for

  • Different languages emphasize different mechanisms:

    • C, TypeScript: braces define blocks; semicolons separate statements

    • Python: indentation defines blocks; newline separates statements

Blocks and scope

//typescript
let x = 1;
{
  let x = 2;        // inner x shadows outer x
  console.log(x);   // prints 2
}
console.log(x);     // prints 1
# python
x = 1
if True:
  x = 2          # modifies same x
print(x)           # prints 2

  • In TypeScript, block scope with let and const

  • In Python, if and while blocks do not introduce a new local scope

Selection Constructs

Selection chooses a control-flow path based on conditions or patterns.

Common forms:

  • if / else if / else

  • switch (C, TypeScript) with cases

  • match (Rust), match/case (Python) with pattern matching

Design choices:

  • fall-through vs no fall-through

  • exhaustiveness checking (compile-time guarantees)

  • pattern matching richness (values, types, structure)

Selection: if statements

  • if statements choose between blocks based on a boolean condition

  • General forms

    • Single branch if (condition) block

    • Two-way if (condition) block else block

    • Multi-way if, else if, else chains

  • Conditions are often expressions that evaluate to boolean

    • Some languages allow non-boolean values used as truthy or falsy

  • Nesting ifs leads to many possible paths, which can be a source of bugs

If / Else: Basic Pattern (TypeScript)

function category(score: number): string {
  if (score >= 90) {
    return "A";
  } else if (score >= 80) {
    return "B";
  } else if (score >= 70) {
    return "C";
  } else {
    return "F";
  }
}

  • ordered conditions implement a priority

  • readability improves when conditions are simple and side-effect free

If / Else: Common Bug Pattern

Confusing assignment with equality is a classic error in languages where assignment is an expression.

// C
int ok = 0;
/* bug: assigns 1 to ok, condition becomes true */
if (ok = 1) {
  /* ... */
}

Safer patterns:

  • enable compiler warnings

  • prefer explicit comparisons: ok == 1

  • keep assignments out of conditions

Multi-way selection: switch and match

  • When there are many discrete cases, if chains become verbose

  • switch in C, C++, Java, TypeScript

    • Compares a value against several constant cases

    • Typically allows fallthrough unless break is used

  • match expressions in some languages, for example Rust

    • Use pattern matching

    • Usually are expressions that produce a value

    • Often must be exhaustive: every case handled

Switch in C

int day = 3;
switch (day) {
  case 1:
    printf("Monday\n");
    break;
  case 2:
    printf("Tuesday\n");
    break;
  case 3:
  case 4:
    printf("Midweek\n");
    break;
  default:
    printf("Other day\n");
    break;
}

  • Without break, execution would fall through to the next case

  • fallthrough can be useful but is also a common source of bugs

Switch in TypeScript: Similar Shape, Different Use

function httpMessage(code: number): string {
  switch (code) {
    case 200: return "OK";
    case 404: return "Not Found";
    case 500: return "Server Error";
    default:  return "Unknown";
  }

Notes:

  • returning directly avoids forgetting break

  • for complex logic, match-like patterns can be clearer

Pattern Matching: Motivation

Pattern matching lets you select branches by structure, not only by boolean conditions.

Benefits:

  • often more readable than chained if/else

  • encourages explicit handling of all cases

  • can destructure data while branching

Languages:

  • Rust: match is central and exhaustiveness-checked

  • Python: match/case supports structural patterns (3.10+)

  • TypeScript: common alternative is discriminated unions plus switch

Rust match as an expression

fn classify_score(score: i32) -> &'static str {
    match score {
        0..=59 => "fail",
        60..=79 => "pass",
        80..=89 => "good",
        90..=100 => "excellent",
        _ => "invalid",
    }
}

  • match must handle all possible patterns, or use a catch all pattern

  • match returns a value, so it is an expression, not just a statement

  • Range patterns and other pattern forms make multi-way selection concise

Python match/case: Structural Patterns

def handle(m):
    match m:
        case ("move", x, y):
            return x + y
        case ("write", s):
            return len(s)
        case ("quit",):
            return 0
        case _:
            return -1

Notes:

  • patterns can match shapes such as tuples and literals

  • the wildcard case \(\_\) acts like default

Iteration Constructs

Iteration repeats a computation.

Common forms:

  • while: repeat while condition holds

  • for: counting loop or general loop with explicit control

  • foreach: iterate over elements of a collection

  • iterators: abstract the notion of producing next elements

Typical design choices:

  • where the loop variable is scoped

  • whether the language exposes iterators directly

  • how termination is represented (condition, StopIteration, option type)

while Loop: Basic Form (TypeScript)

let n = 5;
let acc = 1;

while (n > 1) {
  acc *= n;
  n--;
}

console.log(acc);

  • ensure the loop makes progress toward termination

  • keep mutation localized and easy to see

For loops with counters

C style:

int sum = 0;

for (int i = 1; i <= 10; i++) {
  sum += i;
}

TypeScript style:

let sum = 0;

for (let i = 1; i <= 10; i++) {
  sum += i;
}

  • Initialization, condition, and update are bundled together

  • Helps avoid forgetting to update the loop variable

foreach: Iterating Collections (Python)

nums = [1, 2, 3, 4]
total = 0

for x in nums:
    total += x

print(total)

Notes:

  • for in Python is a foreach over an iterator

  • loop variable remains in scope after the loop

foreach: Iterating Collections (TypeScript)

let nums = [1, 2, 3, 4];
let total = 0;

for (const x of nums) {
  total += x;
}

console.log(total);

Notes:

  • for..of iterates values from an iterable

  • for..in iterates property names (different meaning)

Iterators conceptually

  • An iterator is an abstraction that produces a sequence of values

    • Has an internal state

    • Each call to next gives the next value or signals the end

  • Many languages define iterator protocols

    • for loops can work with any object that implements the protocol

  • Iterators separate how to produce values from how to consume them

    • Makes code more modular and testable

Iterator Protocol in TypeScript

JavaScript defines an iterator protocol using Symbol.iterator. 

function range(n: number) {
  return {
    [Symbol.iterator]() {
      let i = 0;
      return {
        next() {
          if (i < n) return { value: i++, done: false };
          return { value: undefined, done: true };
        }
      };
    }
  };
}
for (const x of range(4)) {
  console.log(x);
}

  • iterators separate producing values from consuming them. done signals termination

Generators in TypeScript

Generators provide a compact way to write iterators.

function* range(n: number) {
  for (let i = 0; i < n; i++) {
    yield i;
  }
}

for (const x of range(4)) {
  console.log(x);
}

Notes:

  • yield produces values one at a time

  • control resumes after yield on the next iteration step

Iterators in Python

Python uses iter() and next() under the hood for for-loops.

it = iter([10, 20, 30])
print(next(it))
print(next(it))
print(next(it))

Notes:

  • when exhausted, next raises StopIteration

  • for handles StopIteration automatically

Guarded Commands (Dijkstra): Motivation

Guarded commands are a control model designed to emphasize correctness.

Core idea:

  • replace single-condition branching with a set of guarded alternatives

  • if multiple guards are true, any may be chosen

  • if no guard is true, the command is blocked (or fails)

Why it is interesting in a programming languages course:

  • it separates the notion of enabling conditions from chosen actions

  • it connects well to reasoning about programs (preconditions and invariants)

Guarded Commands: Syntax (Pseudo-Code)

Selection (if-like):

  • if

    • G1 \(\rightarrow\) S1

    • G2 \(\rightarrow\) S2

    • ...

    • Gn \(\rightarrow\) Sn

  • fi

Iteration (while-like):

  • do

    • G1 \(\rightarrow\) S1

    • G2 \(\rightarrow\) S2

    • ...

    • Gn \(\rightarrow\) Sn

  • od

Meaning:

  • Gi is a boolean guard

  • Si is a statement sequence

Guarded Selection: Semantics

For guarded if:

  • Evaluate which guards are true

  • If at least one guard is true, choose one true guard and execute its statement

  • If no guards are true, the command has no enabled action

Why this matters:

  • it avoids committing to an arbitrary priority order

  • it forces you to consider completeness: do you cover all cases

How languages simulate this:

  • explicit if/else chains with carefully designed conditions

  • match with guards (Rust) or case guards (Python) in structured forms

Guarded commands example: Absolute Value

Pseudo code :

if x < 0  -> x := -x
[] x == 0 -> skip
[] x > 0  -> x := x
fi

  • exactly one guard is true for any integer x

  • completeness is easy to argue

Guarded Iteration: Semantics

For guarded do:

  • While at least one guard is true, choose one true guard and execute its statement

  • Stop when all guards are false

Reasoning style:

  • pick an invariant that remains true after any enabled action

  • prove termination by showing progress toward a state where all guards are false

This viewpoint connects to concurrency:

  • multiple guards can represent different enabled actions in a system

Guarded commands vs mainstream control flow

  • Guarded commands emphasize correctness reasoning

    • Loop invariants and termination arguments

  • Mainstream languages use deterministic if, switch, while, for

  • Conceptually, guarded commands can be compiled into standard control flow

    • Choose one true guard in some fixed order

    • Use usual if and while constructs

  • Studying guarded commands helps understand the structure of control flow

Industry angle: controlling side effects

  • Side effects in expressions can make code hard to understand

    • Hidden mutations, unexpected I/O, global state changes

  • Common practices

    • Keep expressions mostly pure, side effects in clearly marked statements

    • Avoid assignment inside conditions when possible

    • Limit the scope of variables and mutable state

  • Functional style in TypeScript, Python, and other languages

    • Use map, filter, reduce instead of manual loops when appropriate

  • Tests and code review often focus on surprising side effects

Avoiding subtle branch bugs

Problematic C code:

if (x = 0) {
  printf("zero\n");
}

Intended:

if (x == 0) {
  printf("zero\n");
}

  • In C, x = 0 is an expression that evaluates to 0

  • The condition is always false, and x is modified

Safer styles:

  • Use comparisons in conditions, not assignments

  • In languages where assignment is only a statement, this bug cannot occur

  • Use linters and compiler warnings to catch suspicious constructs

Summary

  • Evaluation order and side effects strongly influence program behavior

  • Short-circuit boolean operators control both work and safety

  • Assignments, sequences, and blocks are the foundation of imperative code

  • Selection and iteration constructs shape control flow

  • Iterators provide a higher level view of looping

  • Guarded commands offer an abstract model to reason about programs

  • In practice, careful handling of side effects and branches reduces bugs
