Why MVC Exists

Why Architectural Patterns Matter

Codebases grow, so programs need structure.

  • Separation of concerns leads to cleaner code.

  • A clear structure makes behavior easier to test.

  • Teams can work on UI, data, and request handling in parallel.

  • MVC is one of the most enduring patterns for interactive applications.

Where MVC Comes From

  • MVC was created by Trygve Reenskaug in the 1970s in the Smalltalk community.

  • It became common in desktop GUI programming, including Swing and JavaFX-style applications.

  • It later influenced server-side web frameworks, mobile apps, and client-side UI frameworks.

  • The exact flow changes by platform, but the responsibility split remains useful.

What Is MVC?

MVC divides an application into three interconnected parts.

PartPrimary responsibility
ModelApplication data, state, and business rules.
ViewUI representation of data for the user.
ControllerUser input, coordination, and request flow.

The goal is to separate internal representations of information from the ways information is presented to, and accepted from, the user.

The Basic MVC Flow

User action
    -> Controller receives input
    -> Controller asks Model to read or change state
    -> Model applies data rules
    -> View renders the current state
    -> User sees the result

Different MVC variants disagree about how directly the View talks to the Model.

MVC Responsibilities

Model

The Model corresponds to the data-related logic that the user works with.

  • Managing data: CRUD operations.

  • Enforcing business rules.

  • Representing application state.

  • Notifying other parts of state changes in active-model designs.

  • Responding to instructions from the Controller to update itself.

View

The View handles the UI representation of the application.

  • Rendering data to the user in a specific format.

  • Displaying interface elements such as forms, tables, buttons, or drawings.

  • Updating the display when the model changes or when the controller supplies new data.

  • Keeping markup and UI code logic-light.

A View should not enforce business rules.

Controller

The Controller connects user input to the Model and the View.

  • Receiving user input and interpreting it.

  • Validating request or form data at the boundary.

  • Updating the Model based on user actions.

  • Selecting and displaying the appropriate View.

  • Coordinating workflow without becoming the whole application.

What Each Part Should Avoid

PartAvoidWhy
ModelUI controls and display codeThe same data rules should work without a screen.
ViewBusiness decisionsThe interface should render data, not own the rules.
ControllerDuplicating domain logicControllers become hard to test and reuse when they get too large.

MVC is not just three class names. It is a rule for where responsibilities belong.

The Model Is Not Just the Database

The Model may use a database, but it is not limited to database access.

Model concernExample
StateCurrent drawing color, list of points, selected student.
RulesClamp brush size, reject invalid input, assign unique IDs.
PersistenceLoad and save data through files, repositories, or databases.

In larger applications, services and repositories often support the Model.

Desktop MVC and Web MVC

GUI MVC

GUI MVC is the classic desktop style used in applications such as Smalltalk, Swing, and JavaFX.

  • The Model is active: it can notify the View when state changes.

  • The View listens to model changes and redraws.

  • Interaction is continuous: mouse moves, drags, key presses, and clicks keep the event loop running.

  • The session is stateful: the app holds state in memory across interactions.

  • The Controller translates UI events into model operations.

GUI MVC Flow

User drags mouse
    -> Controller handles the event
    -> Controller calls model.addPoint(...)
    -> Model stores the point
    -> Model notifies observers or bound properties change
    -> View redraws from the Model

The application usually stays alive with state in memory until the user exits.

Server-Side/Web MVC

Server-side/web MVC is common in frameworks such as Spring MVC.

  • The Model is usually passive during a single request.

  • The Controller queries the Model and passes data to the View for one response.

  • The View does not observe the Model directly.

  • Interaction is discrete: one HTTP request in, one response out.

  • Server-side requests are stateless by default unless the app adds session state.

Web MVC Request Flow

Browser sends HTTP request
    -> Router maps URL to controller method
    -> Controller validates input
    -> Controller calls services, repositories, or model objects
    -> Controller returns a template name or JSON response
    -> Server sends response to browser

After the response, the server should not assume it still owns the same in-memory interaction state.

Stateful vs Stateless

FeatureStatelessStateful
Information storageDoes not store client or session information between requests.Stores client or session information on the server.
ScalabilityAny server can handle a request when all needed context is included.May require session management or server affinity.
Fault toleranceMore resilient because one server does not own critical session state.Session data may be lost or must be replicated if a server fails.
ComplexitySimpler architecture; no session synchronization.More complex; session data must be managed carefully.
ExamplesREST APIs, webhooks, stateless firewalls.Shopping carts, login sessions, multi-step workflows.

MVC Variants

Observer / Active-Model MVC

This style is common in desktop GUI MVC with explicit Observer links.

  • Model: active; publishes changes.

  • View: subscribes or binds and pulls state on redraw.

  • Interaction: continuous events such as drag, resize, and key press.

  • State: long-lived in memory; many views can observe one model.

  • Controller: maps gestures to model operations and chooses the view.

Controller-Centric MVC

This style is common in server MVC and client-server demos.

  • Model: passive during the interaction; reached through the controller.

  • View: receives data from the controller and formats it.

  • Interaction: discrete steps.

  • State: often stateless per call; sessions are explicit and scoped.

  • Controller: validates, invokes domain operations, and prepares a view or JSON.

Example: Drawing App

A small JavaFX app records points and renders them on a canvas using MVC.

PartDrawing responsibility
ModelStores points and the current color.
ViewReads the model and renders through Canvas and ListView.
ControllerHandles mouse drags and color changes, updates the model, and triggers redraw.

The model stays testable and the view stays replaceable.

Drawing App Class Responsibilities

ClassStateOperations
DrawModelpoints, selectedColoraddPoint(...), addBreak(), clear(), setSelectedColor(...)
DrawViewcanvas, colorList, status, clearButtongetCanvas(), getColorList(), setStatus(...), redraw()
DrawControllermodel, viewConnects handlers, updates the model, and commands redraw.

Drawing Event Flow

Mouse pressed or dragged on Canvas
    -> DrawController event handler runs
    -> DrawController calls model.addPoint(x, y)
    -> DrawController calls view.redraw()
    -> DrawView reads model.getPoints()
    -> Canvas shows the updated drawing

The controller handles the event. The model stores the data. The view draws the result.

Practice: Add Brush Size

Lab Goal

Modify the drawing app to support brush size.

  • Add a way for the user to choose the brush size.

  • Store the selected size in the correct layer.

  • Use the selected size when the drawing is rendered.

  • Keep mouse press and drag handlers focused on adding points.

Question: how does this feature map to MVC layers?

Model: State and Rules

  • Add state: private int brushSize;

  • Add accessors: getBrushSize() and setBrushSize(int).

  • Apply a business rule: clamp to a sane range, such as >= 1.

  • Do not store new drawing history for this version.

  • Points can remain List<double[]>; brush size is global at render time.

View: UI and Rendering

  • Add a UI control, such as a slider or radio buttons for small, medium, and large.

  • Keep the control as an input. It should not own the rule for valid brush sizes.

  • In redraw(), set the line width from the model.

g.setLineWidth(model.getBrushSize());

for (double[] point : model.getPoints()) {
    // Draw lines exactly as before.
}

Controller: Input to Model, Then Refresh

  • Listen to the slider or radio-button choice.

  • Call model.setBrushSize(...) when the input changes.

  • Call view.redraw() if the current drawing should immediately update.

  • Leave press and drag handlers focused on adding points and redrawing.

sizeSlider.valueProperty().addListener(
    (obs, oldValue, newValue) -> {
        model.setBrushSize(newValue.intValue());
        view.redraw();
    }
);

Benefits and Pitfalls

Why MVC Helps

  • Code is easier to maintain and extend.

  • The Model can be tested separately.

  • View and domain work can happen in parallel.

  • Complexity is reduced by dividing the application into Model, View, and Controller responsibilities.

  • The structure supports test-driven development.

  • It works well for larger apps with many UI changes and data rules.

Pitfalls to Avoid

  • Fat controllers that duplicate business logic.

  • Views that compute business rules.

  • Models that leak persistence details into every layer.

  • Too many layers for a very small one-off program.

  • Confusing MVC with three-tier deployment architecture.

Testing by Layer

LayerWhat to testExample assertion
ModelBusiness rules and state changes.Invalid brush size is clamped.
ControllerInput handling and coordination.A drag event adds a point and redraws.
ViewRendering and UI wiring.The color list exposes the selected color.

The Model should be the easiest layer to test without launching the UI.

When to Use MVC

Use MVC when...Avoid MVC when...
The app has many features and interactions.The app is very small or one-off.
The UI changes often and should evolve independently.UI and business logic are tightly intertwined by nature.
You want reusable parts and multiple views.Hard real-time or game-like interaction dominates.
Testing and team parallelism matter.The team or timeline cannot absorb the layering overhead.

Summary

Key Takeaways

  • The Model owns data, state, and business rules.

  • The View renders data and collects UI input without owning business rules.

  • The Controller receives input, coordinates workflow, and chooses the next response.

  • Desktop MVC is usually stateful and event-driven; web MVC is usually stateless and request-driven.

  • Good MVC design keeps each new feature in the layer that naturally owns it.

Check Your Design

QuestionLayer that should answer it
What data do we store, and what rules make it valid?Model
How should the current state appear to the user?View
What should happen after this click, drag, route, or form submission?Controller

If a class answers all three questions, it is probably doing too much.
