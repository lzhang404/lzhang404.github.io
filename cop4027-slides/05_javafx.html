Mental Model

JavaFX Overview

JavaFX is a Java library for building desktop graphical user interfaces.

  • It provides windows, buttons, labels, text fields, menus, dialogs, charts, images, and drawing tools.

  • It uses a scene graph: a tree of UI objects.

  • It supports CSS styling and FXML layout files.

  • It is useful for desktop apps, teaching GUI design, and visualizing algorithms.

In this course, JavaFX is not just about buttons. It is also a way to practice event-driven programming.

JavaFX vs Swing

TopicSwingJavaFX
UI modelComponent hierarchyScene graph
StylingLook and Feel / UIManagerCSS-like stylesheets
View separationMostly Java codeJava code or FXML
GraphicsCustom paintingNodes, Canvas, animation APIs
Thread ruleSwing EDTJavaFX Application Thread

Shared rule: UI updates must happen on the toolkit's UI thread.

Mental Model

A JavaFX window is built as a hierarchy.

LevelMeaningExample
StageTop-level windowThe app window
SceneContent area inside the windowScene with width and height
Root layoutContainer at the top of the scene graphVBox, BorderPane, GridPane
NodesVisible UI objectsButton, Label, TextField

Scene Graph

The scene graph is a tree of UI nodes.

Stage
└── Scene
    └── BorderPane
        ├── top: MenuBar
        ├── center: GridPane
        │   ├── Label
        │   ├── TextField
        │   └── Button
        └── bottom: Label

  • Layouts are parent nodes that hold other nodes.

  • Controls such as buttons and text fields are usually leaf nodes.

  • Changing the scene graph changes what the user sees.

First Application

Lifecycle

JavaFX controls when the application starts and when the window is created.

Application Structure

Every JavaFX app starts from an Application subclass.

public class HelloWorld extends Application {
    public static void main(String[] args) {
        // Start JavaFX; the runtime will call start(...).
        launch(args);
    }

    @Override
    public void start(Stage primaryStage) {
        // Build the scene graph.
        Button btn = new Button("Say 'Hello World'");
        StackPane root = new StackPane();
        root.getChildren().add(btn);
        Scene scene = new Scene(root, 300, 250);

        // Put the scene in the window and show it.
        primaryStage.setScene(scene);
        primaryStage.show();
    }
}

Event-Driven Code

GUI programs wait for user actions.

  • The program does not run from top to bottom once and finish.

  • It creates the UI, shows the window, and waits.

  • When the user clicks, types, or selects something, an event is created.

  • An event handler is code that responds to that event.

btn.setOnAction(new EventHandler<ActionEvent>() {
    @Override
    public void handle(ActionEvent event) {
        System.out.println("Hello World: " + count++);
    }
});

This example shows the basic event pattern.

        System.out.println("Hello World: " + count++);

Layouts and Forms

Layout Managers

A layout manager decides where child nodes go.

  • Do not manually set every x and y position for normal forms.

  • Use a layout that matches the structure of the screen.

  • Layouts help the UI adapt when the window size changes.

  • Layouts can be nested inside other layouts.

Good JavaFX design usually starts with choosing the root layout.

Common Layouts

LayoutBest use
VBoxStack items vertically.
HBoxPlace items in one horizontal row.
BorderPaneTop, bottom, left, right, center structure.
GridPaneForms with rows and columns.
StackPaneCenter one item or overlay nodes.
FlowPaneWrap items like words in a paragraph.

Input and Validation

Form Workflow

A form event should follow a predictable sequence.

User enters values
        ↓
Button event handler reads the controls
        ↓
Validator checks data rules
        ↓
ValidationResult describes success or failure
        ↓
GUI displays feedback

The controls collect and display data. They should not own every validation rule.

GUI and Validation

GUI classValidator class
Reads TextField valuesReceives ordinary Java strings
Handles button eventsApplies reusable rules
Shows messages and stylesReturns a result
Requires JavaFX to runCan be tested without opening a window

Form Input

Most form programs follow a simple pattern: read, validate, respond.

TextField nameField = new TextField();
TextField emailField = new TextField();
Label feedback = new Label();
Button submitButton = new Button("Validate Details");

submitButton.setOnAction(event -> {
    ValidationResult result = validator.validate(
        nameField.getText(), emailField.getText()
    );

    feedback.setText(result.valid()
        ? "Student details are valid."
        : result.message());
});

Validation Result

The validator returns data that the UI can display.

package cop4027.javafx.validation;

public record ValidationResult(
        boolean valid, String message) {
    public static ValidationResult validResult() {
        return new ValidationResult(true, "");
    }

    public static ValidationResult invalid(String message) {
        return new ValidationResult(false, message);
    }
}

Design benefit: this class has no JavaFX imports, so it is easy to test.

Testable Validation

Keep validation rules separate from JavaFX controls.

public ValidationResult validate(String name, String email) {
    if (name == null || name.isBlank()) {
        return ValidationResult.invalid("Name is required.");
    }

    if (email == null ||
            !EMAIL_PATTERN.matcher(email.trim()).matches()) {
        return ValidationResult.invalid(
            "Enter a valid email address."
        );
    }

    return ValidationResult.validResult();
}

State and Commands

Core Idea

A GUI command is not just a click. It is an action that depends on the current application state.

User actionApplication questionResult
Click SaveIs there anything to save?Save or stay disabled
Click OpenWill current edits be lost?Ask first, then open
Click ExitAre there unsaved changes?Confirm before closing

Correct GUI behavior comes from combining commands with state.

Application State

Application state is information the program remembers between events.

currentFileWhich file is currently open?

Without state, commands cannot make safe decisions.

Use the mechanism that matches the kind of change you are handling.

Listeners

A listener is useful when the application should respond immediately to a changed value.

User edits TextArea
        ↓
textProperty changes
        ↓
listener marks document dirty
        ↓
title, status, and commands update

Example uses: live validation, character count, selected text count, unsaved-change tracking.

Listener Example

This listener turns text editing into an application-state update.

editor.textProperty().addListener(
    (observable, oldText, newText) -> {
        setDirty(true);
        updateTextStatus(newText);
    }
);

The detailed helper methods can be shown during the code demo.

State Updates

When one state value affects several UI elements, update them through one helper method.

State changeUI elements affected
dirty = trueTitle shows *, Save becomes enabled, status changes.
dirty = falseTitle removes *, Save becomes disabled, status changes.
currentFile changesWindow title shows the new file name.

Centralized updates prevent different handlers from updating the interface inconsistently.

Binding

Binding is useful when one UI property should continuously follow another value.

saveItem.disableProperty().bind(dirty.not());
dirty = false  ->  Save disabled
dirty = true   ->  Save enabled

Binding removes the need to manually enable or disable Save in every handler.

Event Flow

SituationBest mechanismReason
User chooses OpenEvent handlerA command starts.
User types in the editorListenerA property changed.
Save should match dirty stateBindingA relationship must stay synchronized.

Do not use binding for everything. File reading, saving, and dialogs are still command methods.

Dialogs

A dialog can pause a command and ask the user how to continue.

A dialog is part of the command workflow, not just a visual popup.

Responsive Apps

FX Thread Rule

JavaFX uses one special thread for UI work.

  • The JavaFX Application Thread renders the UI and handles user events.

  • UI controls should only be changed from this thread.

  • Long-running work should not run on this thread.

  • If a button handler runs a slow loop, the window may freeze.

Rule: background work can compute, but UI updates must return to the JavaFX Application Thread.

Frozen UI

This code runs a slow task directly inside the button handler.

startButton.setOnAction(event -> {
    for (int i = 1; i <= 100; i++) {
        progressLabel.setText("Step " + i);

        try {
            Thread.sleep(100);
        } catch (InterruptedException ex) {
            return;
        }
    }
});

Result: rendering and input handling pause until the loop finishes.

Platform.runLater

Platform.runLater schedules a UI update on the JavaFX Application Thread.

@Override
public void run() {
    final double reportedProgress = progress;

    Platform.runLater(new Runnable() {
        @Override
        public void run() {
            progressBar.setProgress(reportedProgress);
        }
    });
}

Example: cop4027.javafx.advanced.ConcurrencyExample

Background Task

Task.call() runs off the JavaFX Application Thread.

Task<Void> task = new Task<>() {
    @Override
    protected Void call() throws Exception {
        for (int step = 1; step <= 100; step++) {
            Thread.sleep(40); // Simulate slow work.
            updateProgress(step, 100);
            updateMessage("Step " + step + " of 100");
        }
        return null;
    }
};

Task Binding

Task exposes observable progress and message properties.

// JavaFX updates these controls when Task reports new values.
progressBar.progressProperty().bind(
    task.progressProperty()
);
statusLabel.textProperty().bind(
    task.messageProperty()
);

Thread worker = new Thread(task);
worker.setDaemon(true);
worker.start();

Example: cop4027.javafx.advanced.TaskProgressDemo

Threading Choices

ToolUse it when
Event handler onlyThe work is short and updates the UI immediately.
Background ThreadYou need general background execution.
Platform.runLaterA background thread needs to schedule a small UI update.
TaskBackground work needs progress, messages, completion, or cancellation state.

Task does not remove the thread rule; it provides JavaFX-aware state for following it.

Threading Check

Use this checklist when a JavaFX app freezes or crashes.

  • Is a long loop, file read, network request, or database query running on the UI thread?

  • Is a background thread directly calling label.setText(...) or changing a control?

  • Should the slow work be placed on a background thread?

  • Should UI updates use Platform.runLater or Task properties?

  • Can the operation be cancelled cleanly?

FXML and Controllers

FXML Overview

FXML is an XML-based file format for describing JavaFX UI layout.

  • FXML describes the view.

  • A controller class handles user events and application logic.

  • The main application loads the FXML file.

  • CSS can still style the UI.

FileRole
fxml_example.fxmlLayout and controls
FXMLExampleController.javaEvent handlers and UI logic
FXMLExample.javaStarts JavaFX and loads FXML

FXML Anatomy

FXML connects UI nodes to controller fields and methods.

<GridPane
    fx:controller="cop4027.javafx.fxml.FXMLExampleController"
    xmlns:fx="http://javafx.com/fxml">

    <Button text="Sign In"
        onAction="#handleSubmitButtonAction" />

    <Text fx:id="actiontarget" />
</GridPane>

Controller Basics

The controller uses @FXML to access nodes declared in FXML.

package cop4027.javafx.fxml;

public class FXMLExampleController {
    @FXML private Text actiontarget;

    @FXML
    protected void handleSubmitButtonAction(ActionEvent event) {
        actiontarget.setText("Sign in button pressed");
    }
}

Loading FXML

The main application no longer builds every control manually.

public class FXMLExample extends Application {
    @Override
    public void start(Stage stage) throws Exception {
        Parent root = FXMLLoader.load(
            getClass().getResource("/fxml_example.fxml")
        );

        stage.setTitle("FXML Welcome");
        stage.setScene(new Scene(root, 300, 275));
        stage.show();
    }
}

FXML Mistakes

Most FXML errors come from broken connections.

  • Wrong resource path: getResource(...) returns null.

  • Wrong controller package: fx:controller does not match the Java class.

  • Wrong fx:id: the FXML id does not match the controller field name.

  • Missing @FXML: private fields or methods are not visible to the loader.

  • Wrong method signature: onAction points to a method that does not exist.

Scene Builder

Scene Builder is a visual editor for FXML files.

  1. Create or open an FXML file.

  2. Drag controls from the library panel.

  3. Set layout positions and properties.

  4. Assign fx:id values for controls the controller needs.

  5. Assign event handler names such as #handleSubmitButtonAction.

  6. Save the FXML and run the JavaFX application.

Scene Builder changes the FXML file. It does not replace the controller logic.

Summary

Key Takeaways

  • Stage, Scene, layouts, and controls form a scene graph.

  • Events handle commands; listeners observe changes; binding maintains relationships.

  • Application state determines what menu commands should do.

  • Background work must not block or directly modify the UI.

  • FXML separates view construction, but its controller is not the entire MVC architecture.

Correct Patterns and Mistakes to Avoid

  • Use layouts instead of hardcoded positions.

  • Keep validation rules separate from JavaFX controls.

  • Use events, listeners, and binding for their distinct jobs.

  • Centralize application-state updates.

  • Do not block the JavaFX Application Thread.

  • Do not make the FXML controller the entire application.
