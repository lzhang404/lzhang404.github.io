Core idea: subprograms as reusable behavior

A subprogram is a named unit of executable code that can be invoked.

Common reasons to use subprograms

  • Abstraction: hide details behind a simple interface

  • Reuse: call the same logic from many places

  • Testability: isolate logic to test it independently

  • Composition: build larger behavior from smaller pieces

In practice, subprograms include functions, procedures, methods, constructors, lambdas, and callbacks.

Procedures and Functions

Procedures and Functions

Procedures vs functions

Procedure

  • Emphasizes performing an action

  • May not return a meaningful value

  • Often used for I/O, logging, mutation of state

Function

  • Emphasizes computing and returning a value

  • Ideally depends only on inputs (pure), but real code may still have side effects

In many modern languages, the syntax does not enforce a strict separation, so the distinction is about design intent.

function logUserLogin(userId: string): void {
  console.log("login", userId); // procedure-like
}

function computeDiscount(price: number, rate: number): number {
  return price * (1 - rate); // function-like
}

npx ts-node ts_procedure_vs_function.ts

Why the difference matters in practice

When you mix side effects into computations, you make code harder to test and reason about.

Typical symptoms

  • A function sometimes returns a value, sometimes prints or mutates global state

  • Hidden dependencies (reads global variables, reads time, reads random)

  • Unclear call order changes results

A common refactor is to separate computation from effects.

function computeTotal(items: number[]): number {
  return items.reduce((sum, x) => sum + x, 0);
}
function printReceipt(total: number): void {
  console.log("Total:", total);
}
const total = computeTotal([10, 20, 5]);
printReceipt(total);

Java viewpoint: methods that return vs void methods

Java uses methods for both procedure-like and function-like behavior.

class Cart {
  private int totalCents = 0;

  void addItem(int priceCents) {   // procedure-like
    totalCents += priceCents;
  }

  int getTotalCents() {            // function-like
    return totalCents;
  }
}

Design guideline

  • Use void methods for state change and I/O

  • Use returning methods for query-like operations

Python viewpoint: everything is an object, but intent still matters

Python does not require a separate procedure construct. Returning None is common for procedure-like functions.

def add_item(cart, price_cents):
  cart["total"] += price_cents  # procedure-like mutation
    # implicit return None

def total_cents(cart):
  return cart["total"]          # function-like query

cart = {"total": 0}
add_item(cart, 199)
print(total_cents(cart))

First-Class Functions

First-Class Functions

First-class vs second-class functions

  • First-class function means a function can be used like a value.

  • Typical capabilities

    • Assign to variables

    • Pass as arguments

    • Return from other functions

    • Store in data structures

  • Second-class function usually means some of those are restricted, or require special wrappers.

  • This matters because many patterns in modern software rely on passing behavior around: callbacks, middleware, event handlers, and functional pipelines.

lambda

Lambda

  • An anonymous function written inline without a name

  • Used when a function is needed as a value (pass it, store it, return it)

  • Often short; can capture variables from surrounding scope (closure)

Same idea in three languages:

TypeScript: (x) => x * 2
Python:     lambda x: x * 2
Java:       x -> x * 2

Compare to a named function:

function twice(x: number): number { return x * 2; }
const twice2 = (x: number) => x * 2;

Both represent a function value; the lambda is just the unnamed form.

TypeScript: functions are first-class

In TypeScript, functions are values with types.

type Combiner = (a: number, b: number) => number;

const add: Combiner = (a, b) => a + b;
const mul: Combiner = (a, b) => a * b;

function apply(a: number, b: number, op: Combiner): number {
  return op(a, b);
}

console.log(apply(2, 3, add));
console.log(apply(2, 3, mul));

Java: functions via interfaces and lambdas

Java historically emphasized methods, but modern Java supports lambdas targeting functional interfaces.

import java.util.function.IntBinaryOperator;
class Demo {
  static int apply(int a, int b, IntBinaryOperator op) {
    return op.applyAsInt(a, b);
  }
  public static void main(String[] args) {
    IntBinaryOperator add = (x, y) -> x + y;
    IntBinaryOperator mul = (x, y) -> x * y;

    System.out.println(apply(2, 3, add));
    System.out.println(apply(2, 3, mul));
  }
}

The function value is represented through an object that implements an interface.

Cost model: why some languages needed wrappers

  • In languages designed before first-class functions were common, subprograms were not naturally values.

  • A common workaround pattern

    • Define an interface with one method

    • Pass objects implementing that interface

    • Later add lambda syntax as shorthand

  • Consequence

    • Extra types and boilerplate compared to languages that treat functions as direct values

Parameters and Argument Passing

Parameters and Argument Passing

Parameter passing models

  • Parameter passing describes how the arguments at the call site relate to the parameters in the callee.

  • Common models (conceptual)

    • Pass-by-value: copy the value into the parameter

    • Pass-by-reference: parameter aliases the caller’s variable

    • Pass-by-result (out): parameter writes back to caller on return

    • Pass-by-value-result (inout): copy in on call, copy back on return

  • Real languages often implement combinations, and object references complicate intuition.

TypeScript: primitives vs objects at the call boundary

  • TypeScript (JavaScript runtime) passes argument values.

  • Key detail

    • For primitives, the value is the primitive itself

    • For objects, the value is a reference to the object

function bump(n: number): void {
  n = n + 1;
}
function rename(user: { name: string }): void {
  user.name = "new";
}
let x = 10;
bump(x);
console.log(x); // still 10
let u = { name: "old" };
rename(u);
console.log(u.name); // "new"

npx ts-node ts_param.ts

How to describe this precisely

  • A precise explanation that avoids confusion

    • The argument expression is evaluated to a value

    • That value is assigned to the parameter variable

    • Reassigning the parameter does not affect the caller variable

    • Mutating through an object reference affects the shared object

  • Many programmers call this pass-by-sharing or call-by-object-sharing to highlight that references are shared, but variables are not aliased.

function change(n: number, obj: { v: number }): void {
  n = n + 100;
  obj.v = obj.v + 100;
}
let a = 1; let b = { v: 1 };
change(a, b);

console.log(b.v); // 101

  • n = n + 100 is local only because n is a local parameter variable; it does not alias the caller variable a.

  • obj.v = obj.v + 100 affects shared state because obj refers to the same object as b; it mutates that object in place.

Refactor to avoid mutation (return new values instead of mutating)

function changePure(n: number, obj: { v: number }): { n2: number; obj2: { v: number } } {
  return { n2: n + 100, obj2: { v: obj.v + 100 } };
}
let a = 1; let b = { v: 1 };
const { n2, obj2 } = changePure(a, b);
console.log(a);     // 1
console.log(b.v);   // 1
console.log(n2);    // 101
console.log(obj2.v);// 101

Java passes argument values.

  • Primitive arguments behave like pass-by-value

  • Object arguments pass a reference value; mutation affects shared object

  • Reassigning the parameter does not update the caller variable

class User {
  String name;
  User(String n) { name = n; }
}
class Demo {
  static void reassign(User u) {
    u = new User("new"); // only local parameter changes
  }
  static void mutate(User u) {
    u.name = "mutated";
  }
  public static void main(String[] args) {
    User a = new User("old");
    reassign(a);
    System.out.println(a.name); // "old"
    mutate(a);
    System.out.println(a.name); // "mutated"
  }
}

Python: references and mutation

Python also binds names to objects. Calling a function binds parameter names to argument objects.

def reassign(lst):
    lst = [99]     # local name now points elsewhere

def mutate(lst):
    lst.append(99) # mutates the shared object

a = [1, 2]
reassign(a)
print(a)           # [1, 2]
mutate(a)
print(a)           # [1, 2, 99]

Practical rule: reassignment is local; mutation is shared.

Pass-by-reference

  • In pass-by-reference, the callee parameter is an alias for the caller variable.

  • Consequences

    • Reassigning the parameter updates the caller variable

    • The callee can replace what the caller variable refers to

  • Many mainstream languages avoid general pass-by-reference for safety and reasoning, but they may offer it in limited forms:

    • C++ references

    • C# ref and out

    • Rust borrowing rules

Simulating out parameters in TypeScript

TypeScript does not have out parameters, but you can use objects to carry results.

type ParseResult = 
  { ok: boolean; value?: number; error?: string };

function parseIntSafe(s: string): ParseResult {
  const n = Number.parseInt(s, 10);
  if (Number.isNaN(n)) {
    return {ok: false, error: "not an int" };
  }
  return { ok: true, value: n };
}

const r = parseIntSafe("123");
if (r.ok) console.log(r.value);

Industry pattern: return a value object instead of mutating multiple outputs.

Multiple results: tuples in Python

Python commonly returns multiple values as a tuple.

def divmod_like(a, b):
    q = a // b
    r = a % b
    return q, r

q, r = divmod_like(17, 5)
print(q, r)

Returning structured results often replaces out parameters in practice.

Multiple results: records in TypeScript

TypeScript commonly returns an object with named fields.

function divmodLike(a: number, b: number): { q: number; r: number } {
  return { q: Math.floor(a / b), r: a % b };
}

const { q, r } = divmodLike(17, 5);
console.log(q, r);

Named fields make call sites self-documenting.

Defaults, Named Arguments, and Varargs

Defaults, Named Arguments, and Varargs

Default parameters in TypeScript

Default parameters apply when the argument is missing or undefined.

function greet(name: string, punctuation: string = "!"): string {
  return "Hello, " + name + punctuation;
}

console.log(greet("Ada"));
console.log(greet("Ada", "!!"));

Common use: small configuration knobs without forcing the caller to pass every argument.

Named arguments pattern in TypeScript

TypeScript does not have true named arguments at call sites, but an options object provides similar readability.

type FetchOptions = { timeoutMs?: number; retries?: number; cache?: boolean };

function fetchWithOptions(url: string, options: FetchOptions = {}): void {
  const timeoutMs = options.timeoutMs ?? 2000;
  const retries = options.retries ?? 2;
  const cache = options.cache ?? true;
  console.log(url, timeoutMs, retries, cache);
}

fetchWithOptions("https://example.com", { retries: 5, cache: false });

Benefit: callers can specify only what they need, in any order.

Python: default and named arguments

Python supports default values and keyword arguments directly.

def connect(host, port=5432, timeout_s=2.0):
    return (host, port, timeout_s)

print(connect("db.local"))
print(connect("db.local", timeout_s=5.0))
print(connect(host="db.local", port=6000))

Keyword arguments significantly improve readability for functions with many parameters.

Python pitfall: mutable default arguments

Default values are evaluated once when the function is defined, not each call.

def add_item(x, lst=[]):
    lst.append(x)
    return lst

print(add_item(1))  # [1]
print(add_item(2))  # [1, 2] surprising for many learners

Safe pattern uses None and creates a new list inside.

def add_item_safe(x, lst=None):
    if lst is None:
        lst = []
    lst.append(x)
    return lst

Java: default arguments via overloading

Java does not have default arguments; common substitutes are overloaded methods or builders.

class Connector {
  static String connect(String host) {
    return connect(host, 5432, 2.0);
  }
  static String connect(String host, int port) {
    return connect(host, port, 2.0);
  }

  static String connect(String host, int port, double timeoutS) {
    return host + ":" + port + " timeout=" + timeoutS;
  }
}

Overloads can grow quickly; builders are often preferred for many optional fields.

Variadic parameters: rest args

Variadic functions accept a variable number of arguments.

function sum(...xs: number[]): number {
  return xs.reduce((acc, x) => acc + x, 0);
}

console.log(sum(1, 2, 3));
console.log(sum(10));

Similar features exist in Java and Python, but the call syntax and typing differ.

Variadic parameters: Python and Java

Python uses star args.

def sum_all(*xs):
    total = 0
    for x in xs:
        total += x
    return total

print(sum_all(1, 2, 3))

Java uses varargs.

class Demo {
  static int sumAll(int... xs) {
    int total = 0;
    for (int x : xs) total += x;
    return total;
  }
}

Closures and Capturing

Closures and Capturing

Closures and lexical environments

Closure

  • A function together with the environment of variables it captures

  • The captured variables are free variables in the function body (not parameters, not locals)

Lexical environment

  • The set of bindings visible due to where the function is defined in source code

  • Lexical scoping means the structure of the code determines variable resolution

Closures allow behavior to depend on values that existed when the function was created, even if the outer function has returned.

TypeScript closure: function returning function

This example returns a function that remembers a captured variable.

function makeAdder(k: number): (x: number) => number {
  return (x: number) => x + k; // captures k
}

const add10 = makeAdder(10);
const add3 = makeAdder(3);

console.log(add10(5)); // 15
console.log(add3(5));  // 8

k remains available because the returned function closes over it.

Practice 3: function factory and capture (TypeScript)

function makeLimiter(max: number): (x: number) => number {
  // return a function that clamps x into [0, max]
  return (x: number) => {
    if (x < 0) return 0;
    if (x > max) return max;
    return x;
  };
}
const limit10 = makeLimiter(10);
console.log(limit10(-3));
console.log(limit10(7));
console.log(limit10(100));

Practice 3: function factory and capture (TypeScript)

function makeLimiter(max: number): (x: number) => number {
  return (x: number) => {
    if (x < 0) return 0;
    if (x > max) return max;
    return x;
  };
}
const limit10 = makeLimiter(10);
console.log(limit10(-3));  // 0
console.log(limit10(7));   // 7
console.log(limit10(100)); // 10

What variable is captured, and how does it affect behavior

  • The returned function closes over max.

  • max is fixed when makeLimiter is called; for limit10 it is 10.

  • Each call to limit10 uses the same captured max value to clamp the input.

  • A different call makeLimiter(5) would create a different returned function with a different captured max.

Python closure: nested function capturing outer variable

Python closures behave similarly.

def make_adder(k):
    def add(x):
        return x + k  # captures k
    return add

add10 = make_adder(10)
print(add10(5))

Nested definitions are a common way to build specialized behavior.

Java closure-like behavior with lambdas

Java lambdas can capture variables, with a restriction.

Captured local variables must be effectively final (not reassigned).

import java.util.function.IntUnaryOperator;

class Demo {
  static IntUnaryOperator makeAdder(int k) {
    return (int x) -> x + k; // captures k
  }

  public static void main(String[] args) {
    IntUnaryOperator add10 = makeAdder(10);
    System.out.println(add10.applyAsInt(5));
  }
}

The restriction simplifies reasoning about captured locals and threading.

What gets captured: value vs variable

  • A key subtlety: closures capture variables (bindings), not just values.

  • Consequences

    • If the variable changes later, the closure observes the updated value

    • Captured variables can extend lifetimes of data beyond the original scope

  • This is powerful but can cause surprising bugs, especially with loops and asynchronous callbacks.

TypeScript: capturing and mutation

The closure observes changes to captured variables.

function makeCounter(): () => number {
  let count = 0;
  return () => {
    count = count + 1;
    return count;
  };
}

const c = makeCounter();
console.log(c()); // 1
console.log(c()); // 2

This pattern implements private state without a class.

Python: closure with nonlocal for reassignment

Python requires nonlocal to rebind a captured variable.

def make_counter():
    count = 0
    def inc():
        nonlocal count
        count += 1
        return count
    return inc

c = make_counter()
print(c())
print(c())

Without nonlocal, count would be treated as a new local inside inc.

npx ts-node ts_closure_counter.ts

Closure lifetime and memory

When an inner function outlives the outer function call, captured variables must remain alive.

Practical implications

  • Closures can keep large objects alive longer than intended

  • Event handlers can accidentally retain DOM nodes and leak memory

  • Long-lived closures should capture only what they need

A useful habit: avoid capturing entire objects when a small primitive value is enough.

Closure Pitfalls

Closure Pitfalls

Classic bug: loop variable capture in JavaScript-style code

The bug often appears when callbacks run later, after the loop finishes.

const callbacks: Array<() => void> = [];

for (var i = 0; i < 3; i++) {
  callbacks.push(() => console.log(i));
}

callbacks[0]();
callbacks[1]();
callbacks[2]();

With var, i is function-scoped, so all callbacks share the same i.

Fix: use block scope with let

let creates a new binding per iteration in a for loop, so each closure captures a distinct variable.

const callbacks: Array<() => void> = [];

for (let i = 0; i < 3; i++) {
  callbacks.push(() => console.log(i));
}

callbacks[0](); // 0
callbacks[1](); // 1
callbacks[2](); // 2

Rule: prefer let and const over var in modern TypeScript.

npx ts-node ts_closure_loop_capture.ts

Python: late binding in closures inside loops

Python closures in loops can surprise you similarly.

funcs = []
for i in range(3):
    funcs.append(lambda: i)

print(funcs[0]()) #2
print(funcs[1]()) #2
print(funcs[2]()) #2

Many learners expect 0, 1, 2, but all lambdas refer to the same i binding.

Python fix: capture current value using a default argument

Default arguments are evaluated at function creation time, capturing the current loop value.

funcs = []
for i in range(3):
    funcs.append(lambda i=i: i)

print(funcs[0]())  # 0
print(funcs[1]())  # 1
print(funcs[2]())  # 2

This is a widely used idiom for loop capture in Python.

Higher-Order Functions and Callbacks

Higher-Order Functions and Callbacks

Higher-order functions

A higher-order function is a function that

  • takes a function as an argument, or

  • returns a function as a result

Benefits

  • Code reuse through generic control patterns (map, filter, retry, debounce)

  • Separation of policy from mechanism (algorithm vs decision rule)

  • Composition: build behavior by combining functions

Costs

  • Debugging can be harder due to indirect control flow

  • Types and error handling need careful design

Callback

  • A function you pass into another function so the other function can call it

  • Inversion of control: the library controls when/how many times it calls your function

  • Can be called immediately (synchronous) or later (asynchronous)

Synchronous callback example (array processing):

const nums = [1, 2, 3];
const squares = nums.map(x => x * x); // callback is x => x * x

Asynchronous callback example (event-style):

function onClick(handler: () => void): void {
  // real UI code would call handler later
  handler();
}
onClick(() => console.log("clicked")); // callback is () => ...

A callback API should document when it runs, how often, and how errors are reported.

TypeScript: map, filter, reduce as higher-order functions

Arrays provide higher-order functions that accept callbacks.

const nums = [1, 2, 3, 4, 5];

const squares = nums.map(x => x * x);
const evens = nums.filter(x => x % 2 === 0);
const sum = nums.reduce((acc, x) => acc + x, 0);

console.log(squares);
console.log(evens);
console.log(sum);

The callback provides the custom behavior; the loop mechanism is reused.

Python: list processing with functions

Python offers functional tools and comprehensions.

nums = [1, 2, 3, 4, 5]

squares = list(map(lambda x: x * x, nums))
evens = list(filter(lambda x: x % 2 == 0, nums))
total = sum(nums)

print(squares)
print(evens)
print(total)

In Python, comprehensions are often preferred for readability, but callbacks remain important for libraries.

Java: higher-order style with streams

Java streams accept lambdas and functional interfaces.

import java.util.List;

class Demo {
  public static void main(String[] args) {
    List<Integer> nums = List.of(1, 2, 3, 4, 5);

    int sum = nums.stream()
      .filter(x -> x % 2 == 0)
      .map(x -> x * x)
      .reduce(0, (acc, x) -> acc + x);

    System.out.println(sum);
  }
}

Streams encourage a pipeline model where each step is a small function.

Callbacks: event handler example

UI and server frameworks often use callbacks because they invert control.

function onClick(handler: () => void): void {
  // imagine this registers handler with a UI system
  handler(); // demo call
}

let clicks = 0;

onClick(() => {
  clicks = clicks + 1;
  console.log("clicks", clicks);
});

The callback closes over clicks, so it can update private state across events.

Callback design considerations

When you expose callbacks in an API, callers need to know:

  • When the callback is invoked (immediately, later, possibly multiple times)

  • Which thread or event loop invokes it

  • Error signaling model (throw, return value, error parameter, promise rejection)

  • Cancellation mechanism

Many production issues happen because the callback contract is unclear, not because the syntax is hard.

Async Patterns in Industry

Async Patterns in Industry

Industry angle: why callback hell happens

Callback hell is deeply nested callbacks that appear when:

  • Each async step depends on the previous step result

  • Errors are handled separately at each nesting level

  • Multiple branches and retries are needed

Symptoms

  • Hard to read control flow

  • Duplication of error handling

  • Difficult to compose and test

Modern JavaScript ecosystems introduced Promises and async/await to make async flow look like sequential code.

TypeScript: callback-based async style

This style is still common in older Node.js APIs and some libraries.

type Callback<T> = (err: Error | null, value?: T) => void;
function readUser(id: string, cb: Callback<{ id: string; name: string }>): void {
  setTimeout(() => cb(null, { id, name: "Ada" }), 10);
}
function readOrders(userId: string, cb: Callback<string[]>): void {
  setTimeout(() => cb(null, ["A1", "B2"]), 10);
}
readUser("u1", (err, user) => {
  if (err || !user) return console.log("error", err);
  readOrders(user.id, (err2, orders) => {
    if (err2 || !orders) return console.log("error", err2);
    console.log(user.name, orders);
  });
});

Nesting grows as you add more steps, branching, and retries.

TypeScript: Promises reduce nesting

Promises represent a value that may be available later.

function readUserP(id: string): Promise<{ id: string; name: string }> {
  return new Promise(resolve => setTimeout(() => resolve({ id, name: "Ada" }), 10));
}

function readOrdersP(userId: string): Promise<string[]> {
  return new Promise(resolve => setTimeout(() => resolve(["A1", "B2"]), 10));
}

readUserP("u1")
  .then(user => readOrdersP(user.id).then(orders => [user, orders] as const))
  .then(([user, orders]) => console.log(user.name, orders))
  .catch(err => console.log("error", err));

Control flow is flatter, but chains can still become complex.

TypeScript: async/await for sequential readability

async/await is syntax over Promises that improves readability.

async function workflow(): Promise<void> {
  try {
    const user = await readUserP("u1");
    const orders = await readOrdersP(user.id);
    console.log(user.name, orders);
  } catch (err) {
    console.log("error", err);
  }
}
workflow();

try/catch works for awaited promise rejections, which simplifies error handling.

Async closures: what is captured

In async code, closures often capture variables whose values change over time.

Typical bugs

  • Capturing a loop variable and using it when the async task resolves

  • Capturing a mutable object and seeing later changes unexpectedly

Typical fixes

  • Use block scope variables for each iteration

  • Capture immutable snapshots (copy the needed values)

  • Prefer pure functions and explicit parameters for async callbacks

Closures in UI and React

Closures in UI and React

Closures in UI: event handlers

UI systems store callback functions and invoke them later.

That means:

  • The handler must keep access to needed state

  • Closures provide that access

  • Captured state may become stale if the UI updates but the handler closes over an old snapshot

This is a common source of bugs in React and other event-driven frameworks.

React hook idea: stale closure pattern (conceptual TypeScript)

This is a simplified illustration of a stale capture issue.

let count = 0;

function makeHandler() {
  const captured = count;
  return () => console.log("captured", captured, "current", count);
}

const h1 = makeHandler();
count = 5;
h1(); // captured 0, current 5

In React, handlers created during a render capture that render’s state values.

React-style fix: functional update pattern (conceptual TypeScript)

A common fix is to compute next state from previous state, avoiding dependence on a captured stale value.

function updateCount(prev: number): number {
  return prev + 1;
}

let state = 0;
state = updateCount(state);
state = updateCount(state);
console.log(state);

React provides a setState form that takes a function prev \(\rightarrow\) next to address stale closure issues.

Rule of thumb for closures in production code

Prefer explicit parameters for data that varies per call.

Use closures for

  • Configuration fixed at creation time

  • Encapsulated private state (counters, memoization caches)

  • Dependency injection (passing services without globals)

Avoid closures that capture

  • Large objects unnecessarily

  • Variables that change frequently when you need the latest value

  • Loop indices used later in async callbacks without proper scoping

Argument evaluation order and side effects

When a call has multiple argument expressions, the language defines an order.

Why this matters

  • If argument expressions have side effects, order changes behavior

  • Code becomes fragile and hard to refactor

Practical guidance

  • Avoid side effects inside arguments

  • Compute intermediate values in separate statements for clarity

TypeScript: make side effects explicit

Instead of embedding state changes into call arguments, separate them.

let i = 0;

function f(a: number, b: number): void {
  console.log("a", a, "b", b);
}

i = i + 1;
const a = i;
i = i + 1;
const b = i;

f(a, b);

This style is easier to read and debug than relying on tricky evaluation order.

Closure Design Patterns

Closure Design Patterns

Closure pattern: memoization

Memoization caches results based on inputs to speed up repeated calls.

function memoize1<A, R>(f: (a: A) => R): (a: A) => R {
  const cache = new Map<A, R>();
  return (a: A) => {
    if (cache.has(a)) return cache.get(a)!;
    const r = f(a);
    cache.set(a, r);
    return r;
  };
}

const slowSquare = (x: number) => x * x;
const fastSquare = memoize1(slowSquare);
console.log(fastSquare(10));
console.log(fastSquare(10));

The cache is private state captured by the returned function.

Closure pattern: debounce for event handlers

Debounce delays execution until events stop firing for a period.

function debounce(fn: () => void, delayMs: number): () => void {
  let timer: ReturnType<typeof setTimeout> | undefined;
  return () => {
    if (timer !== undefined) clearTimeout(timer);
    timer = setTimeout(() => fn(), delayMs);
  };
}
let fired = 0;
const handler = debounce(() => {
  fired = fired + 1;
  console.log("fired", fired);
}, 200);
handler();
handler();
handler(); // only one execution after the last call settles

timer is captured state that persists across invocations.

Closure pattern: dependency injection

Instead of reading globals, create a function that closes over dependencies.

Example concept

  • Provide a logger, configuration, or database client once

  • Return a handler that uses those dependencies without passing them every time

Benefits

  • Easier testing with fake dependencies

  • Fewer hidden global dependencies

  • Better modularity

Dependency injection with closures in TypeScript

Create a specialized function by capturing a service.

type Logger = { log: (msg: string) => void };

function makeGreeter(logger: Logger): (name: string) => void {
  return (name: string) => logger.log("hello " + name);
}

const consoleLogger: Logger = {log: (msg) => console.log(msg)};
const greet = makeGreeter(consoleLogger);

greet("Ada");

The returned function depends on logger without using a global variable.

Java: capturing effectively final variables

In Java, a lambda is allowed to capture a local variable only if that variable is final or effectively final.

import java.util.function.IntUnaryOperator;
class Demo {
  static IntUnaryOperator makeScaler(int factor) {
    return x -> x * factor;//factor is effectivly final
  }
  public static void main(String[] args) {
    IntUnaryOperator times3 = makeScaler(3);
    System.out.println(times3.applyAsInt(7));
  }
}

If factor were reassigned later in the same scope, the code would not compile.

static IntUnaryOperator makeScaler(int factor) {
  factor = factor + 1;          // reassignment
  return x -> x * factor;       // compile error
}

Python: capturing configuration for callbacks

Capturing configuration is a common pattern for callbacks.

def make_prefix_logger(prefix):
    def log(msg):
        print(prefix + ": " + msg)
    return log

info = make_prefix_logger("INFO")
warn = make_prefix_logger("WARN")

warn("disk almost full")

Each returned function retains its own prefix.

Summary: what to remember

Key takeaways

  • Procedures emphasize actions and effects; functions emphasize computed results

  • TypeScript and Python have first-class functions directly; Java uses functional interfaces and lambdas

  • Many languages pass argument values; references can make mutation visible across call boundaries

  • Default parameters and named arguments improve call-site readability (Python directly, TypeScript via defaults and options objects, Java via overloads/builders)

  • A closure is a function plus captured lexical environment; capture can extend lifetimes and cause subtle bugs

  • Callback-heavy async code can become hard to manage; Promises and async/await improve structure
