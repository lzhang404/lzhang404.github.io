Operator precedence vs evaluation order

  • Precedence decides grouping (parse tree)

  • Evaluation order decides what runs first

  • Order matters when evaluation has side effects

  • Example grouping: \(1 + 2 * 3\) groups as \(1 + (2 * 3)\)

Evaluation order: TypeScript is left-to-right

TypeScript evaluates function arguments from left to right:

function log(label: string, value: number): number {
  console.log(label, value);
  return value;
}
let x = 1;
let y = log("first", x++)
      + log("second", x++);
// Output:
// first 1
// second 2
// After expression: x is 3, y is 3

Evaluation order: C can be tricky

In C, order of evaluation of subexpressions is often not specified:

#include <stdio.h>
int inc(const char *label, int *p) {
  printf("%s %d\n", label, *p);
  return (*p)++;
}

int main(void) {
  int x = 1;
  int y = inc("first", &x) + inc("second", &x);
  printf("x = %d, y = %d\n", x, y);
}

  • Spec does not guarantee which call happens first

  • Different compilers/flags may behave differently

  • Depending on a particular order is fragile

c_eval_order.c

Definedness: what does the language guarantee?

  • Some languages specify evaluation order (TypeScript, Python)

  • Some leave more freedom to compilers (C)

  • When order is not guaranteed, expressions with side effects can become unreliable

  • Guideline: avoid writing expressions that “need” a specific order to be correct

Short-circuit boolean evaluation

  • Many languages short-circuit:

    • A && B: if A is false, B is not evaluated

    • A || B: if A is true, B is not evaluated

  • Useful for safety guards and avoiding unnecessary work

  • But it can hide control flow inside expressions

ts_sideeffect.ts

Short-circuit as a safety guard (TypeScript)

type User = { name: string } | null;

function greet(u: User) {
  if (u !== null && u.name.length > 0) {
    console.log("hello", u.name);
  } else {
    console.log("no user");
  }
}

  • Second condition only runs when u !== null

ts_short_circuit.ts

Short-circuit as a safety guard (Python)

def greet(u):
    # u is either None or a dict with "name"
    if u is not None and len(u["name"]) > 0:
        print("hello", u["name"])
    else:
        print("no user")

  • and short-circuits like &&

Short-circuit with side effects: pitfall

Works, but intent is not obvious:

let connected = false;
function connect(): boolean {
  console.log("connecting...");
  connected = true;
  return connected;
}
connected || connect();

  • Prefer an explicit if when the right side has side effects

ts_short_circuit_pitfall.ts

Short-circuit return values

  • In TypeScript / JavaScript: && and || return one operand (not necessarily boolean)

  • In Python: and and or also return one operand

  • This enables defaults, but can surprise you if you expected a boolean

Default values with short-circuit (TypeScript)

function label(name: string | undefined) {
  let shown1 = name || "anonymous";
  let shown2 = name ?? "anonymous"; // nullish coalescing
  console.log({ shown1, shown2 });
}
label(undefined);
label("");

  • || treats empty string as falsey

  • ?? only replaces null or undefined

ts_default_val.ts

Default values with short-circuit (Python)

def label(name):
    shown = name or "anonymous"
    print(shown)

label(None)
label("")

  • If empty string is a valid value, use an explicit check instead

Assignment as an expression (C, TypeScript)

In C and JavaScript, assignment produces a value.

#include <stdio.h>

int main(void) {
  int x = 0;
  int y = (x = 5);  // assignment yields 5
  printf("x=%d y=%d\n", x, y);
  return 0;
}

  • Compact code is possible

  • Also enables classic bugs when = is confused with ==

c_assign_expr.c

Assignment is a statement (Python)

x = 5
# y = (x = 5)   # syntax error
y = x
print(x, y)

  • Fewer accidental assignments inside conditions

  • Related: Python has := for limited assignment-expression cases

Compound assignment

let x = 10;
x += 5;   // x = x + 5
x *= 2;   // x = x * 2
console.log(x);

  • With objects, += may mutate or allocate depending on language/type

Chained assignment: readability vs risk

let a: number, b: number, c: number;
a = b = c = 0;
console.log(a, b, c);
a = b = c = 0
print(a, b, c)

  • Safer for immutable values than for mutable objects

Chained assignment with mutability (Python)

a = b = []
a.append(1)
print(a)  # [1]
print(b)  # [1]

  • a and b refer to the same list object

  • Safer pattern: a = [] ; b = []

Destructuring and multiple assignment

TypeScript destructuring:

let pair: [number, string] = [7, "seven"];
let [n, s] = pair;

let obj = { x: 1, y: 2 };
let { x, y } = obj;

console.log(n, s, x, y);

Python tuple unpacking:

n, s = (7, "seven")
x, y = [1, 2]
print(n, s, x, y)

Assignment in conditions: what happens?

C code:

int x = 5;
if (x = 0) {
  printf("x is zero\n");
} else {
  printf("x is nonzero\n");
}

  • x = 0 changes x and evaluates to 0

  • Condition is false, so the else branch runs

  • Intended: x == 0

Compare with Python (not allowed as a condition expression).

Sequences and blocks

  • A sequence expresses multiple computations in order

  • A block groups statements into a unit

    • often introduces a scope

    • often controls lifetime of locals

    • often used after if/while/for

  • C/TypeScript: braces; Python: indentation

Blocks and scope

let x = 1;
{
  let x = 2;        // inner x shadows outer x
  console.log(x);   // prints 2
}
console.log(x);     // prints 1
x = 1
if True:
  x = 2          # modifies same x
print(x)         # prints 2

  • TypeScript: block scope with let/const

  • Python: if/while blocks do not introduce a new local scope

Selection constructs

  • if / else: general-purpose branching

  • switch: discrete cases (sometimes fall-through)

  • match / pattern matching: branch by structure, often exhaustive

If / else: basic pattern (TypeScript)

function category(score: number): string {
  if (score >= 90) {
    return "A";
  } else if (score >= 80) {
    return "B";
  } else if (score >= 70) {
    return "C";
  } else {
    return "F";
  }
}

  • Order matters: you are encoding a priority

Switch in C

int day = 3;
switch (day) {
  case 1:
    printf("Monday\n");
    break;
  case 2:
    printf("Tuesday\n");
    break;
  case 3:
  case 4:
    printf("Midweek\n");
    break;
  default:
    printf("Other day\n");
    break;
}

  • Without break, execution can fall through

c_switch.c

Switch in TypeScript

function httpMessage(code: number): string {
  switch (code) {
    case 200: return "OK";
    case 404: return "Not Found";
    case 500: return "Server Error";
    default:  return "Unknown";
  }
}

  • Returning directly avoids forgetting break

Pattern matching: motivation

  • Branch by structure, not only by boolean conditions

  • Encourages explicit handling of all cases

  • Often pairs naturally with destructuring

  • Rust: match is central and exhaustiveness-checked

  • Python: match/case supports structural patterns (3.10+)

Rust match as an expression

fn classify_score(score: i32) -> &'static str {
    match score {
        0..=59 => "fail",
        60..=79 => "pass",
        80..=89 => "good",
        90..=100 => "excellent",
        _ => "invalid",
    }
}

  • match returns a value

  • Typically must be exhaustive

Python match/case: structural patterns

def handle(m):
    match m:
        case ("move", x, y):
            return x + y
        case ("write", s):
            return len(s)
        case ("quit",):
            return 0
        case _:
            return -1

Iteration constructs

  • while: repeat while a condition holds

  • for: counting loop (init/condition/update bundled)

  • foreach: iterate over elements of a collection

  • Iterators and generators: abstract “produce next element”

while loop: basic form (TypeScript)

let n = 5;
let acc = 1;

while (n > 1) {
  acc *= n;
  n--;
}

console.log(acc);

  • Make progress toward termination

  • Keep mutation localized and visible

for loops with counters

C style:

int sum = 0;

for (int i = 1; i <= 10; i++) {
  sum += i;
}

TypeScript style:

let sum = 0;

for (let i = 1; i <= 10; i++) {
  sum += i;
}

foreach: Python

nums = [1, 2, 3, 4]
total = 0

for x in nums:
    total += x

print(total)

  • Python for is a foreach over an iterator

  • Loop variable remains in scope after the loop

foreach: TypeScript

let nums = [1, 2, 3, 4];
let total = 0;

for (const x of nums) {
  total += x;
}

console.log(total);

  • for..of iterates values; for..in iterates property names

Iterators conceptually

  • An iterator produces a sequence of values over time

  • It has internal state; each next() advances

  • Iterator protocols let loops work with many data sources uniformly

Iterator protocol in TypeScript

JavaScript defines an iterator protocol using Symbol.iterator.

function range(n: number) {
  return {
    [Symbol.iterator]() {
      let i = 0;
      return {
        next() {
          if (i < n) return { value: i++, done: false };
          return { value: undefined, done: true };
        }
      };
    }
  };
}
for (const x of range(4)) {
  console.log(x);
}

Generators in TypeScript

Generators provide a compact way to write iterators.

function* range(n: number) {
  for (let i = 0; i < n; i++) {
    yield i;
  }
}
for (const x of range(4)) {
  console.log(x);
}

  • yield produces one value at a time

Iterators in Python

Python uses iter() and next() under the hood for for-loops.

it = iter([10, 20, 30])
print(next(it))
print(next(it))
print(next(it))

  • When exhausted, next raises StopIteration

Guarded commands (Dijkstra): motivation

  • Replace single-condition branching with a set of guarded alternatives

  • If multiple guards are true, any may be chosen

  • If no guard is true, the command is blocked (or fails)

  • PL angle: connects directly to reasoning with invariants and completeness

Guarded commands: syntax (pseudo-code)

Selection (if-like):

  • if

    • G1 \(\rightarrow\) S1

    • G2 \(\rightarrow\) S2

    • ...

    • Gn \(\rightarrow\) Sn

  • fi

Iteration (while-like):

  • do

    • G1 \(\rightarrow\) S1

    • G2 \(\rightarrow\) S2

    • ...

    • Gn \(\rightarrow\) Sn

  • od

Guarded selection: semantics

  • Evaluate which guards are true

  • If at least one is true, choose one true guard and execute its statement

  • If none are true, there is no enabled action

  • For reasoning: forces you to think about completeness (“did we cover all cases?”)

Guarded commands example: absolute value

Pseudo code:

if x < 0  -> x := -x
[] x == 0 -> skip
[] x > 0  -> x := x
fi

  • Exactly one guard is true for any integer x

Guarded iteration: semantics

  • While at least one guard is true, choose one true guard and execute its statement

  • Stop when all guards are false

  • Reasoning style: invariants + termination arguments

Guarded commands vs mainstream control flow

  • Guarded commands emphasize correctness reasoning

  • Mainstream languages use deterministic if/switch/while/for

  • Guarded commands can be compiled into standard control flow

Industry angle: controlling side effects

  • Hidden mutation inside complex expressions hurts readability

  • Prefer explicit control flow when side effects occur

  • Limit scope of mutable state

  • Use tests, linters, and compiler warnings to catch suspicious constructs

Summary

  • Precedence groups expressions; evaluation order runs them

  • Short-circuit is control flow inside expressions

  • Assignment differs across languages and causes classic bugs

  • Blocks, selection, and iteration shape imperative programs

  • Iterators and generators unify looping across data sources

  • Guarded commands provide a reasoning-first model of control flow
