Introduction to Serialization

Object Lifetime and Persistent State

TaskList object                    No Java objects remain
  name = "Week 6"         ---->   Only an external representation can survive

  • Objects and their fields live in memory while the program is running.

  • To keep that state, the program must convert it into data that can be stored or transmitted.

Serialization and Deserialization

  • Serialization encodes object state into a representation.

  • Deserialization reconstructs objects from that representation.

  • The restored objects contain the saved state, but they are newly created objects in memory.

What Is an Object Graph?

TaskList
  |-- name ----------> String
  `-- tasks ---------> ArrayList
                        |-- Task
                        `-- Task

  • The object passed to writeObject is the root.

  • Its fields may reference other objects, which may reference more objects.

  • Together, the reachable objects form an object graph.

Saving and Loading Java Objects

The Serializable Interface

import java.io.Serializable;

public final class Task implements Serializable {
    // Serializable is a marker interface: no methods are required here.
    private final String title;
    private boolean done;

    public Task(String title) {
        this.title = title;
    }
}

  • Serializable tells Java that instances of the class are eligible for object serialization.

  • Instance fields are candidates for the saved object state.

[Sources] https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/Serializable.html

Serializable Objects with Referenced Fields

public final class TaskList implements Serializable {
    private final String name;
    private final List<Task> tasks = new ArrayList<>();

    public TaskList(String name) {
        this.name = name;
    }

    public void add(Task task) {
        tasks.add(task);
    }
}

A TaskList contains its own fields and references to other objects.

Serializing an Object with ObjectOutputStream

static void save(Path file, TaskList taskList) throws IOException {
    try (ObjectOutputStream out = new ObjectOutputStream(
            Files.newOutputStream(file))) {
        // writeObject starts at this root and follows reachable objects.
        out.writeObject(taskList);
    } // Closing ObjectOutputStream also flushes the object-stream data.
}

  • ObjectOutputStream converts a Java object graph into object-stream data.

  • The object passed to writeObject is the root of that graph.

Deserializing an Object with ObjectInputStream

static TaskList load(Path file) throws IOException, ClassNotFoundException {
    try (ObjectInputStream in = new ObjectInputStream(
            Files.newInputStream(file))) {
        // readObject returns Object because the stream stores type metadata.
        Object value = in.readObject();
        if (!(value instanceof TaskList taskList)) {
            throw new InvalidObjectException("Expected TaskList");
        }
        return taskList;
    }
}

  • readObject() reconstructs the next object from the stream.

  • The required classes must be available while the stream is read.

Saving and Loading an Object

TaskList original = new TaskList("Week 6");

What Java Serialization Saves

Serialization of Referenced Objects

TaskList
  |-- name --------------------> String
  `-- tasks -------------------> ArrayList
                                  |-- Task
                                  |     `--> String
                                  `-- Task
                                        `--> String

  • writeObject(taskList) does not save only the fields physically declared in TaskList.

  • It follows reachable object references through the graph.

  • Default serialization therefore works across nested object structures.

Serializable Requirements for an Object Graph

public final class TaskList implements Serializable {
    private final List<Task> tasks = new ArrayList<>();
    private AuditLogger logger;  // not Serializable
}
java.io.NotSerializableException: example.AuditLogger

  • A non-serializable object anywhere in the reached graph can cause the write to fail.

  • Possible fixes: make it serializable, exclude the field, or save a serializable representation instead.

Instance, Static, and Transient State

public final class TaskList implements Serializable {
    private static int createdCount;        // class state: not saved with one object

    private final String name;              // instance state: saved
    private final List<Task> tasks = new ArrayList<>();

    private transient Path sourceFile;      // runtime context: excluded
    private transient int completedCount;   // derived cache: rebuild after loading
}

  • Normal instance fields such as name and tasks are part of the saved object state.

  • static fields belong to the class, not to one serialized instance.

  • transient fields are intentionally excluded from default serialization.

Field Values After Deserialization

class Example implements Serializable {
    static int total = 10;

Excluded primitive fields similarly receive their normal default values such as 0 or false.

Using transient Fields

  • Runtime resource: a file handle, socket, or environment-specific object should be reopened or recreated.

  • Derived value: a cache can be recomputed from authoritative saved state.

  • Runtime collaborator: a logger or service can be injected again after loading.

  • Data that should not be stored: exclude the field from this serialized representation.

  • transient changes what is serialized; it is not an encryption or access-control mechanism.

  • Example: examples/serialization/src/main/java/cop4027/serialization/TransientFieldsExample.java

Object Identity and Cyclic References

Shared reference                         Cycle

Task -----> SharedNote <--- Task          Object A ------> Object B
                                              ^              |
                                              |              |
                                              +--------------+

  • Object streams track objects that have already been written.

  • If two fields refer to the same object before saving, the restored fields refer to the same restored object.

  • Back-references also allow cyclic graphs without infinite recursion.

  • All reached state must still satisfy serialization requirements.

  • Example: examples/serialization/src/main/java/cop4027/serialization/SharedReferenceExample.java

Serialization and Inheritance

class Item implements Serializable { /* ... */ }
final class Task extends Item { /* also serializable */ }

class SessionContext {
    SessionContext() { /* runs while loading */ }
}

final class SavedWork extends SessionContext
        implements Serializable {
    private String documentName;
}

  • A subclass of a serializable class is also serializable.

  • If a serializable class extends a non-serializable superclass, the superclass state is initialized through its accessible no-argument constructor.

[Sources] https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/Serializable.html

Checking a Serializable Object Graph

  1. What is the root object passed to writeObject?

  2. Which non-static, non-transient fields are reachable from it?

  3. Does every reached object implement Serializable?

  4. Which references are shared or cyclic?

  5. Which excluded values must be reconstructed after loading?

Versioning and Deserialization

Deserializing Data After a Class Changes

Monday                     Friday

TaskList v1                TaskList v2
save tasks.bin   ---->     load tasks.bin

fields and rules           fields and rules changed

  • A serialized file may outlive the exact class version that created it.

  • Class evolution asks whether old bytes still describe a valid object under the current code.

serialVersionUID

import java.io.Serial;

@Serial
private static final long serialVersionUID = 1L;

  • The serialized stream records the class's version identifier.

  • During loading, Java compares the saved identifier with the current class.

  • Keeping the same UID states that the versions are intended to be compatible.

  • @Serial lets the compiler check serialization-specific declarations.

[Sources] https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/Serializable.html https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/Serial.html

Compatible and Incompatible Changes

ChangeTypical effect
Add a fieldOld streams provide its default value
Remove a fieldThe old saved value is ignored
Add methodsSerialized field data is unaffected
Change a field to an incompatible typeCompatibility can fail
Change the class hierarchy or serialization formMay require migration or rejection
Change UID from 1L to 2LInvalidClassException

The UID is a compatibility declaration; it does not migrate data by itself.

Constructor Behavior During Deserialization

public TaskList(String name) {
    System.out.println("constructor");
    this.name = Objects.requireNonNull(name);
}

  • Normal deserialization restores serializable fields without calling this constructor.

  • Therefore, constructor checks do not guarantee that restored data satisfies current rules.

  • Serialized data should be treated as input that must satisfy object invariants.

Validate Restored State

@Serial
private void readObject(ObjectInputStream in)
        throws IOException, ClassNotFoundException {
    in.defaultReadObject();

    if (name == null || name.isBlank()) {
        throw new InvalidObjectException(
            "Task list name must not be blank");
    }
    if (tasks == null) {
        throw new InvalidObjectException(
            "Task collection is required");
    }
}

Validation during deserialization enforces the same important invariants expected from normally constructed objects.

Restoring Transient and Derived State

private transient int completedCount;

@Serial
private void readObject(ObjectInputStream in)
        throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    validateState();

    completedCount = (int) tasks.stream()
        .filter(Task::isDone)
        .count();
}

  • defaultReadObject() restores the normal serialized fields.

  • Validation checks the restored authoritative state.

  • Derived transient values can then be recomputed.

Custom Serialization Hooks

@Serial
private void writeObject(ObjectOutputStream out)
        throws IOException {
    out.defaultWriteObject();
    out.writeInt(calculateCompletedCount());
}

@Serial
private void readObject(ObjectInputStream in)
        throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    int savedCount = in.readInt();
}

  • Custom hooks can add application-specific values to the default serialized fields.

  • Custom values must be read in the same order and with compatible types used when writing them.

  • Use custom hooks only when the default representation does not meet the object's needs.

Practice: Class Version Changes

  1. Save a TaskList using version 1 of the class.

  2. Add a description field while keeping UID 1L.

  3. Load the old file and observe the new field's value.

  4. Supply a valid default during deserialization if the application requires one.

  5. Change the UID to 2L and explain the resulting exception.

Compatibility Tests

  1. Keep a small serialized fixture written by each supported version.

  2. Load every fixture with the current code.

  3. Verify required defaults, reconstructed values, and invariants.

  4. Reject unsupported versions with a clear error.

A round trip using only the current class cannot prove backward compatibility.

Common Deserialization Errors

  • IOException: the bytes cannot be read or do not form the expected stream.

  • ClassNotFoundException: a class named in the stream is unavailable.

  • InvalidClassException: the saved class version is incompatible with the current class.

  • InvalidObjectException: restored data violates application validation rules.

  • Unexpected top-level type: the stream contains a different kind of object than the application expects.

These failures represent different problems and should not be hidden by an empty catch block.

Serialization Security and Alternatives

Security Risks of Deserialization

The bytes in an object stream influence which classes are created, their field values, and the shape of the reconstructed graph.

  • Deserialization can invoke class-specific restoration hooks.

  • A malicious graph can consume excessive memory, depth, references, or processing time.

  • Unexpected classes can introduce dangerous behavior during restoration.

Do not treat arbitrary network input or unknown files as safe Java object streams.

[Sources] https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/Serializable.html https://openjdk.org/jeps/415

ObjectInputFilter

ObjectInputFilter filter =
    ObjectInputFilter.Config.createFilter(
        "maxdepth=20;maxrefs=10000;maxbytes=1000000;" +
        "cop4027.serialization.TaskList;" +
        "cop4027.serialization.Task;" +
        "java.base/*;!*");

try (ObjectInputStream in = new ObjectInputStream(
        Files.newInputStream(file))) {
    // Apply the filter before readObject creates objects from the stream.
    in.setObjectInputFilter(filter);
    TaskList list = (TaskList) in.readObject();
}

  • Filters can limit graph depth, reference count, input size, and allowed classes.

  • A narrow allowlist reduces what the stream is permitted to reconstruct.

  • Example: examples/serialization/src/main/java/cop4027/serialization/FilteredDeserializationExample.java

[Sources] https://docs.oracle.com/en/java/javase/21/core/java-serialization-filters.html https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/ObjectInputFilter.html

Limitations of Deserialization Filters

  • Control or authenticate the source of serialized data.

  • Use realistic size and graph limits.

  • Validate restored fields and invariants.

  • Handle rejected input as a normal failure path.

  • Remember that binary data is not encrypted data.

Encryption, integrity protection, access control, filtering, and object validation solve different problems.

Serialization vs. Persistence

  • Serialization: converts state to and from a representation.

  • Persistence: keeps data beyond one program execution.

  • Transport: moves data between processes or machines.

  • Encoding: defines how information is represented as bytes or text.

A serialized representation may be stored in a file, sent over a network, or used in a cache, but serialization itself does not decide where the data goes.

Choosing a Data Representation

RepresentationUseful whenMain tradeoff
Java object streamOne Java application controls the object graphTightly coupled to Java classes

XMLStructured interchange, schemas, document-oriented dataMore verbose and requires mapping
Database modelQueryable, shared, durable application dataRequires a persistence schema/model

A Java object stream is a binary Java-specific representation, not a stable public data contract by default.

  • The boundary explicitly states which data crosses between systems.

  • Private implementation fields do not automatically become part of the external contract.

  • The stored or transmitted representation can evolve separately from internal object structure.

Example: JSON Instead of an Object Stream

ObjectMapper mapper = new ObjectMapper();

Enrollment enrollment = new Enrollment(
    "Grace", "COP4027-02", LocalDate.now()
);

// JSON stores named data fields, not Java object-stream metadata.
String json = mapper.writeValueAsString(enrollment);
Enrollment restored =
    mapper.readValue(json, Enrollment.class);

  • JSON stores a named data representation instead of Java's private object-stream format.

  • This is usually a better fit when data crosses application, language, or trust boundaries.

  • Example: examples/serialization/src/main/java/cop4027/serialization/JacksonMappingExamples.java

When to Use Java Object Serialization

  • A short-lived local cache controlled by one Java application.

  • Trusted data exchanged between closely matching Java code.

  • A quick object snapshot where class coupling is acceptable.

  • Learning how Java preserves object graphs, identity, and state.

Prefer another representation when data is long-lived, public, cross-language, or supplied by untrusted sources.

Design Checklist

  • Is Java object serialization appropriate for this boundary?

  • Is every intended object in the graph serializable?

  • Are runtime-only and sensitive fields excluded appropriately?

  • Are compatibility expectations and serialVersionUID explicit?

  • Are restored invariants validated and transient state rebuilt?

  • Is incoming data trusted, filtered, and size-limited?

  • Do tests cover both round trips and older serialized fixtures?

Summary and Review

Key Takeaways

  • Serialization converts object state into a representation that can survive outside the running JVM.

  • ObjectOutputStream and ObjectInputStream operate on reachable object graphs, not isolated fields.

  • Normal instance state is saved; static state is not part of the instance, and transient state is excluded.

  • Class evolution requires explicit compatibility decisions and validation of restored objects.

  • Untrusted object streams are risky; choose JSON, XML, or a database model when the boundary needs a clearer and safer data contract.
