Core idea: describe relations, let the engine search

Logic programming mental model:

  • You write relations (facts + rules)

  • A query asks: "Is there a way to make this true?"

  • The runtime finds values for variables (via unification) and explores possibilities (via backtracking)

Why it is different:

  • You specify what is true, not how to compute it step-by-step

  • Control flow emerges from search + rule application

  • Debugging often means reasoning about search order

Where logic/declarative ideas show up

Even if you never ship Prolog, the ideas are everywhere:

  • SQL: declare a set of rows you want

  • Regular expressions: declare patterns, engine searches for matches

  • Build systems: declare dependencies, tool figures out build order

  • Policy engines: declare rules, engine decides allow/deny

  • Constraint solvers: declare constraints, solver finds satisfying assignments

Declarative foundations

Imperative vs declarative

Imperative (typical C/Java/Python loops):

  • Describe steps: update variables, iterate, branch

  • Order matters: evaluation order is the program

Declarative (logic/SQL/constraints):

  • Describe a property of the solution

  • A solver/search engine chooses an execution strategy

Key question shift:

  • Imperative: "How do I compute this?"

  • Declarative: "What must be true of the answer?"

Declarative does not mean "no control"

Reality check:

  • Declarative code often has an underlying engine (optimizer, solver, search)

  • Performance can still depend on structure: indexes, rule order, constraints

  • In Prolog, clause order and goal order affect search

Practical skill:

  • Keep the program meaning declarative

  • Learn engine behavior to avoid accidental slow search

Logic programming in one slide

A Prolog program is a set of Horn clauses:

  • Facts: parent(alice, bob).

  • Rules: grandparent(X,Z) :- parent(X,Y), parent(Y,Z).

You ask queries:

  • ?- grandparent(alice, Z).

The engine:

  • Unifies terms to make goals match rule heads

  • Uses backtracking to explore alternatives

Predicates, terms, and variables

Building blocks of predicate logic:

  • Constant:alice , uwf , 3 — a specific named object in the domain

  • Variable:X , Y (capitalized in Prolog) — an unknown term, bound by unification

  • Function symbol (term constructor):pair(X,Y) , node(Left,Right) — builds compound structured terms

  • Predicate:parent(X,Y) , edge(U,V) — a named relation that is true or false

Read:

  • parent(alice, bob) is a ground proposition: either true or false in a model

  • parent(alice, X) is a formula with a free variable (a query pattern: "who are Alice's children?")

Quantifiers (conceptual)

Predicate logic often uses:

  • \(\forall x\)(for all): the property holds for every element

  • \(\exists x\)(there exists): there is at least one element satisfying the property

Example:

  • "Everyone has a parent":\(\forall x \exists y \; parent(y, x)\)

Prolog viewpoint (informal):

  • Variables in rules behave like\(\forall\)— the rule holds for all substitutions

  • Queries behave like\(\exists\)— ask "does there exist values that satisfy this?"

Implication and reading rules

Implication:

  • \(A \leftarrow B\)reads "A is true if B is true"

  • In Prolog: A :- B. (the :- is read as "if")

Example:

  • \(grandparent(X,Z) \leftarrow parent(X,Y) \wedge parent(Y,Z)\)

  • Read: X is grandparent of Z if X is parent of Y and Y is parent of Z

Note:

  • Rules define sufficient conditions, not necessarily necessary conditions

  • Multiple rules for the same predicate act as alternatives (logical OR)

From English to logic (tiny examples)

English:

  • If someone is a parent, they are an ancestor.

  • If someone is an ancestor of Y, and Y is an ancestor of Z, then they are an ancestor of Z.

Logic-style:

  • \(ancestor(X,Y) \leftarrow parent(X,Y)\)

  • \(ancestor(X,Z) \leftarrow ancestor(X,Y) \wedge ancestor(Y,Z)\)

This is a recursive definition expressing transitive closure — a fundamental pattern in logic programming.

Practice 1: translate to logic-style rules

Translate into rule form:

  • "If X is a sibling of Y, then Y is a sibling of X." (symmetry)

  • "If X is a parent of Y, and Y is a parent of Z, then X is a grandparent of Z."

  • "If X is a professor and teaches course C, then X is an instructor of C."

Use predicate names you like (e.g., sibling , parent , teaches ).

Practice 1 Answer: translate to logic-style rules

One possible set:

  • \(sibling(X,Y) \leftarrow sibling(Y,X)\)is not a good definition (it loops)

  • Better: treat sibling as given by facts, then add a derived predicate:

    • \(sibling2(X,Y) \leftarrow sibling(X,Y)\)

    • \(sibling2(X,Y) \leftarrow sibling(Y,X)\)

  • \(grandparent(X,Z) \leftarrow parent(X,Y) \wedge parent(Y,Z)\)

  • \(instructor(X,C) \leftarrow professor(X) \wedge teaches(X,C)\)

Key lesson: logic rules can accidentally create non-terminating recursion if used naively.

Prolog basics and unification

Horn clauses (why Prolog works)

A Horn clause is a logical clause with at most one positive (non-negated) head atom:

  • Shape: \(Head \leftarrow Body_1 \wedge \cdots \wedge Body_n\)

  • The head is what we conclude; the body is what must be proven first

Prolog programs are built entirely from Horn clauses:

  • Facts: \(Head \leftarrow true\)

    • written as head.

  • Rules: \(Head \leftarrow Body\)

    • written as head :- body.

  • Queries: a goal with no head

    • written as ?- goal.

Why this restriction matters:

  • Enables efficient proof search (SLD resolution)

  • Gives Prolog a clear, predictable operational semantics

Prolog syntax cheat sheet

  • Fact ends with a period .

  • Rule uses :- and ends with .

  • Variables start with capital letters or underscore

  • Atoms start with lowercase (or are quoted)

  • Query starts with ?-


parent(alice, bob).
parent(bob, carol).

grandparent(X, Z) :-
  parent(X, Y),
  parent(Y, Z).

?- grandparent(alice, Who).

Example knowledge base: family


% facts
parent(alice, bob).
parent(bob, carol).
parent(alice, dana).
parent(dana, eric).

female(alice).
female(dana).
male(bob).
male(eric).
female(carol).

% rules
grandparent(X, Z) :- parent(X, Y), parent(Y, Z).
mother(X, Y)      :- parent(X, Y), female(X).
father(X, Y)      :- parent(X, Y), male(X).

Reading:

  • mother(X,Y) is true if X is a parent of Y and X is female

Queries return substitutions

Query patterns:

  • ?- mother(X, bob). "who is Bob's mother?"

  • ?- mother(alice, Y). "who are Alice's children?"

Conceptually, Prolog answers by finding a substitution, a mapping from variables to terms that makes the query true:

  • X = alice

  • Y = bob or Y = dana (depending on query)

Multiple answers arise via backtracking.

Relational thinking: functions vs relations

In most languages, you write functions:

  • input\(\rightarrow\)output, one direction only

In Prolog, you write relations:

  • multiple arguments can be "unknown"

  • the same rule can be used in different directions

Example:

  • parent(alice, bob) can answer both:

    • "Who are Alice's children?": ?- parent(alice, Y).

    • "Who are Bob's parents?": ?- parent(X, bob).

Unification: the matching engine

Unification is the core mechanism behind all Prolog execution. It answers:

  • Can two terms be made equal by substituting variables?

  • If yes, what is the most general unifier (MGU), the substitution with fewest commitments?

Examples:

  • parent(alice, X) unifies with parent(alice, bob) giving X=bob

  • f(X, a) unifies with f(b, Y) giving X=b, Y=a

If unification fails, that search branch fails and Prolog backtracks.

Term structure matters

Unification compares structure recursively:

  • Constants unify only if identical: alice with alice , but not alice with bob

  • Compound terms unify if same functor and same arity, then arguments are unified pairwise:

    • edge(a,b) unifies with edge(X,Y) giving X=a, Y=b

    • edge(a,b) does not unify with edge(a,b,c), different arity

  • Variables unify with any term (subject to the occurs check)

Occurs check (conceptual)

The occurs check prevents a variable from unifying with a term that contains itself:

  • X = f(X) would create an infinite term which is not allowed in strict unification

  • Without the check, this could silently create circular structures

  • Many Prolog systems omit the full occurs check for performance; be aware this is a theoretical gap

What to remember for this course:

  • Unification is "structural matching with variable binding"

  • The occurs check is a correctness detail you may encounter in practice

Unification examples with lists

Prolog list syntax:

  • [] empty list

  • [a,b,c] list of three atoms (shorthand)

  • [H|T] head/tail form — head is first element, tail is the rest


% Unify [H|T] with [1,2,3]
% H = 1, T = [2,3]

% Unify [A,B|Rest] with [x,y,z]
% A = x, B = y, Rest = [z]

1) f(X, a)      with   f(b, Y)

Bridge: from unification to search

Unification answers: "Can these terms match?"

Next question: "How does Prolog explore multiple matching possibilities?"

  • Resolution chooses which rule body to expand

  • Backtracking revisits choice points after failure/success

  • Goal and clause order directly affect termination and performance

Execution model and search

Resolution (high-level)

Resolution is a proof rule for logic. In Prolog, it drives execution.

In Prolog terms (operational intuition):

  • You have a goal list (a conjunction to be proven): G1, G2, ...

  • Pick the leftmost goalG1

  • Find a clause whose head unifies with G1

  • Replace G1 with that clause's body (new subgoals) and continue

This is called SLD resolution (Selective Linear Definite clause resolution), the theoretical foundation of Prolog execution.

Prolog execution mantra

Prolog is often summarized as:

  • unification + search

More operational detail:

  • Depth-first search, which follows one branch fully before trying alternatives

  • Left-to-right goals in a rule body

  • Top-to-bottom clause order in the program

Consequence:

  • Program meaning is logical, but performance/termination depends on clause and goal order

A tiny proof trace (conceptual)

Program:


parent(alice, bob).
parent(bob, carol).
grandparent(X, Z) :- parent(X, Y), parent(Y, Z).

Query:

?- grandparent(alice, Z).

Goal reduction steps:

  • Match grandparent(alice,Z) with rule head grandparent(X,Z) → bind X=alice

  • New goal list: parent(alice,Y), parent(Y,Z)

  • Solve parent(alice,Y) : matches fact → Y=bob

  • Solve parent(bob,Z) : matches fact → Z=carol

  • Goal list is empty: success , answer is Z=carol

Choice points

A choice point is created whenever multiple clauses could satisfy a goal:

  • Prolog tries the first matching clause and records the others as alternatives

  • If later goals fail, it backtracks to the most recent choice point and tries the next alternative

  • If the user asks for more answers (e.g., ; in the REPL), backtracking is triggered from the last choice point

This is why one query can produce multiple answers.

Practice 4: predict a trace outcome

Consider:


p(a).
p(b).
q(b).
r(X) :- p(X), q(X).

Questions:

  • What does ?- r(X). return?

  • In what order are candidates tried?

Practice 4 Answer: predict a trace outcome

Evaluate r(X) :- p(X), q(X).

  • Try p(X) :

    • First fact p(a) gives X=a

    • Then q(a) fails (only q(b) exists)

  • Backtrack to p(X) :

    • Next fact p(b) gives X=b

    • q(b) succeeds

Result: one answer X=b .

Depth-first search: the good and the risky

Good:

  • Simple mental model

  • Produces answers incrementally

  • Often efficient for "find one solution" tasks

Risky:

  • Can get stuck exploring an infinite branch

  • May be exponential without pruning/constraints

Practical message:

  • Clause order and recursion structure matter for termination

Search tree intuition

Think of evaluation as exploring a tree:

  • Each goal can match multiple clauses\(\rightarrow\)branching

  • Each branch accumulates substitutions

  • Failure prunes a branch; success yields an answer

Depth-first:

  • Explore one branch to completion, then backtrack to the nearest choice point

Backtracking diagram (conceptual)

For the query ?- r(X). with p(a). p(b). q(b). r(X) :- p(X), q(X).

Goal Clause tried Binding Result
r(X) r(X):-p(X),q(X) — expand to p(X), q(X)
p(X) p(a) X=a try q(a) next
q(a) no match — FAIL → backtrack
p(X) p(b) X=b try q(b) next
q(b) q(b) — SUCCESS: X=b

Negation as failure

Prolog commonly uses \+ Goal (read: "not provable"):

  • Succeeds if Goal cannot be proven from the knowledge base

  • Fails if Goal can be proven

Example:


bird(tweety).
penguin(pingu).

bird(X) :- penguin(X).

can_fly(X) :- bird(X), \+ penguin(X).

Caution:

  • This is not classical logical negation

  • It depends on the closed-world assumption: "unprovable" is treated as "false"

The closed-world assumption

Many Prolog programs assume:

  • Anything not provable from the knowledge base is considered false

This is often practical for databases and rule systems:

  • If you didn't list it, we assume it doesn't exist

But it differs from open-world logic (e.g., knowledge graphs):

  • "unknown" is not the same as "false"

  • Example: not knowing Alice's age doesn't mean Alice has no age

Groundness and negation

This can be dangerous:


% "X is not a bird"
not_bird(X) :- \+ bird(X).

If you ask:

?- not_bird(X).

  • You are asking for all things that are not birds. It not well-defined in a finite KB.

  • Prolog will check "can I prove bird(X) for some X?" and, finding that it can, will make \+ bird(X) fail globally.

Safer pattern:

  • Use negation after variables are already bound (ground) by earlier goals

Practice 5: goal ordering for safety

Suppose:


bird(tweety).
bird(woody).
penguin(pingu).
bird(X) :- penguin(X).

Which is safer?

  • A: can_fly(X) :- \+ penguin(X), bird(X).

  • B: can_fly(X) :- bird(X), \+ penguin(X).

Explain in terms of variable binding and search.

Practice 5 Answer: goal ordering for safety

Safer is B:

  • bird(X) binds X to known birds/penguins first

  • Then \+ penguin(X) checks whether that bound X can be proven to be a penguin

A is risky:

  • \+ penguin(X) runs with X unbound; it asks "can I prove penguin(X) for some X?"

  • Since penguin(pingu) exists, the negation fails immediately, making can_fly(X) fail for all X

Why Prolog can feel "magical"

Beginners often experience:

  • "I wrote the correct rules, but it loops"

  • "I got an answer, but it took forever"

  • "Changing order changes behavior"

The missing concept:

  • Prolog is both logical and operational (search strategy matters)

Two lenses for reading a Prolog program:

  • Declarative meaning: what is true (the logical reading)

  • Procedural meaning: how the engine searches (the operational reading)

Common performance/termination tips

  • Put base cases before recursive cases

  • Avoid left-recursive rules — Prolog's depth-first search will loop

  • Avoid recursion patterns that never consume input

  • Add visited checks when traversing graphs

  • Use constraints to prune early (when available)

  • Be careful with \+ when variables are not grounded

Programming with Prolog

Prolog lists as relations (bridge from Module 9)

In classic Prolog, lists are central:

  • Recursion over lists is a core pattern (same structural idea as Module 9, but now expressed as relations )

  • Many problems become "generate candidates" + "filter constraints"

Two common tasks:

  • Define relations over lists: membership, append, length

  • Use lists as paths, schedules, parse results, etc.

member/2 and append/3 (classic)


member(X, [X|_]).
member(X, [_|T]) :- member(X, T).

append([], Ys, Ys).
append([H|T], Ys, [H|Zs]) :- append(T, Ys, Zs).

Notes:

  • member is relational: can ask "what is a member?" or "is this a member?"

  • append can be used to split lists too

Relational power: splitting with append/3

Query:

?- append(Front, Back, [a,b,c]).

Conceptual answers (via backtracking):

  • Front=[], Back=[a,b,c]

  • Front=[a], Back=[b,c]

  • Front=[a,b], Back=[c]

  • Front=[a,b,c], Back=[]

This is hard to express as a single function in imperative style without extra loops.

Recursion in Prolog relations (transfer from Module 9)

For lists:

  • Base case: empty list []

  • Recursive case: [H|T]

For trees:

  • Base case: leaf

  • Recursive case: node with subtrees

This aligns with inductive data definitions from Module 9 (algebraic data types and pattern matching).

Graph reachability: path/2

Facts (direct edges):


edge(a, b).
edge(b, c).
edge(c, d).
edge(a, d).

Rules (reachability via transitive closure):

path(X, Y) :- edge(X, Y).
          path(X, Y) :- edge(X, Z), path(Z, Y).

This expresses transitive closure, but may loop on cyclic graphs.

Cycles and termination

If you add:

  • edge(d, b). (a cycle)

Then naive path/2 can recurse forever — it will keep following the cycle.

Typical fix:

  • Carry a visited list and refuse to revisit nodes

Graph reachability with visited set


path(X, Y) :- path(X, Y, [X]).

path(X, Y, _) :-
edge(X, Y).

path(X, Y, Visited) :-
edge(X, Z),
\+ member(Z, Visited),
path(Z, Y, [Z|Visited]).

Now the recursion stops revisiting nodes.

Control: ordering goals and clauses

Two practical heuristics:

  • Put more restrictive goals earlier (fail fast — avoid exploring large spaces before a filter)

  • Avoid generating huge candidate spaces before filtering

Example pattern:

  • Bad: generate all lists, then test property

  • Better: generate only the needed structure, apply constraints early

The cut (!) (control feature)

The cut ! is a special goal that, when reached, commits to the choices made so far :

  • It prunes all remaining choice points created since the current predicate was called

  • Once past the cut, Prolog cannot backtrack into the current clause

Example: deterministic max:


max(X, Y, X) :- X >= Y, !.
max(_, Y, Y).

Caution:

  • Cut makes programs less purely declarative

  • Use it deliberately to control search, not as a patch for logic errors

Practice 8: where does cut change answers?

Consider:


p(1).
p(2).

q(2).

r(X) :- p(X), !, q(X).
r(X) :- p(X).

Question:

  • What are the answers to ?- r(X).

  • Explain the effect of the cut

Practice 8 Answer: where does cut change answers?

Evaluate first clause: r(X) :- p(X), !, q(X).

  • p(X) first gives X=1

  • Cut commits to this p(X) choice (no backtracking to p(2) )

  • Then q(1) fails

  • Because of the cut, Prolog will not retry p(X) with X=2 in that clause

Then Prolog tries the second clause: r(X) :- p(X).

  • This yields X=1 then X=2

Final answers: X=1 ; X=2 . The cut changed the search space of the first clause, not the second clause.

From pure relations to constraints

"Pure" Prolog:

  • Uses unification + backtracking search

  • Often does generate-and-test: enumerate candidates, then filter

  • Can be slow if the candidate space is large

Constraint Logic Programming (CLP) idea:

  • Add constraint domains (integers, finite domains, reals)

  • Propagate constraints to prune search early before generating candidates

Typical payoff:

  • Scheduling, timetabling, resource allocation become natural and efficient

CLP(FD) flavor (conceptual example)

Many Prolog systems support finite-domain constraints (often via a library).

Example goal (read conceptually):


% X and Y are integers in 1..5
% X #\= Y means X not equal Y (constraint)
% X + Y #= 6 means X+Y equals 6

solve(X, Y) :-
X in 1..5,
Y in 1..5,
X #\= Y,
X + Y #= 6.

The solver narrows possibilities before brute-force enumeration.

Constraint mindset

Instead of:

  • "Try all schedules and check conflicts"

You write:

  • Variables represent unknown decisions

  • Constraints express what must hold

  • Labeling/search assigns values consistent with constraints

This is a classic declarative paradigm: describe the problem, let the solver find a solution.

Prolog feels like querying a database

Facts resemble rows; predicates resemble tables:

  • parent(alice,bob). is like a row in a Parent table

A rule resembles a join:

  • grandparent(X,Z) :- parent(X,Y), parent(Y,Z).

  • This is equivalent to joining Parent with itself on the middle node

Conceptually:

  • Prolog search behaves like a nested-loop join (unless optimized)

  • SQL optimizers can reorder joins and use indexes automatically

Prolog "join" example


enrolled(alice, cop4020).
enrolled(alice, cda3100).
enrolled(bob, cop4020).

teaches(zhang, cop4020).
teaches(smith, cda3100).

student_of(Student, Prof) :-
enrolled(Student, Course),
teaches(Prof, Course).

Query:

?- student_of(alice, P).

SQL comparison (same idea)

SQL "student_of" query:


SELECT e.student, t.prof
FROM enrolled e
JOIN teaches t ON e.course = t.course
WHERE e.student = 'alice';

Compare:

  • Prolog rule looks like a logical join specification

  • SQL optimizer decides join strategy; Prolog uses a fixed search order by default

  • Both share the declarative idea: describe the result, not the retrieval steps

Datalog (conceptual comparison)

Datalog is like a restricted Prolog designed for database-style reasoning:

  • Forbids complex function symbols — all terms are flat, keeping the domain finite

  • Uses set semantics (no duplicates) and guarantees termination on finite databases

  • Common for program analysis, policy engines, and graph queries

Prolog is more general:

  • Can build arbitrary compound terms, supports deeper recursion

  • Turing-complete; termination is not guaranteed

Why query languages like restrictions

Restrictions enable:

  • Optimizations (indexes, join reordering)

  • Guaranteed termination (on finite input)

  • Clear complexity bounds

Tradeoff:

  • Less expressive for some computations

  • Prolog's generality comes at the cost of predictability

Logic as a foundation for configuration/policy

Many systems use a rule-based core modeled on Horn-clause logic:

  • Policies: allow/deny decisions based on user attributes

  • Compliance checks: must satisfy constraints (e.g., GDPR, access control)

  • Routing rules: choose target by conditions

Pattern:

  • Facts about the world (requests, attributes)

  • Rules derive conclusions (allowed, violations, actions)

Practice 11: write a policy as Horn-style rules

Write rules for:

  • "A request is allowed if the user is an admin."

  • "A request is allowed if the user owns the resource."

  • "Otherwise denied."

Use predicates like:

  • admin(User)

  • owns(User, Resource)

  • allow(User, Resource)

Discussion: how does "otherwise denied" relate to the closed-world assumption?

Practice 11 Answer: policy as rules

Rules:

  • allow(U,R) :- admin(U).

  • allow(U,R) :- owns(U,R).

"Otherwise denied":

  • In Prolog-style closed world, if allow(U,R) cannot be proven, treat it as denied.

  • This is a design choice; some systems want an explicit deny predicate for auditability.

Case study: course prerequisites

Model prerequisites as relations:

  • prereq(Course, PrereqCourse)

  • can_take(Student, Course)

Questions we want to ask:

  • Which prerequisites are required (directly or indirectly)?

  • What courses can a student take next?

This is graph reachability + set filtering by combining patterns we have already seen.

Prerequisites example (conceptual Prolog)

prereq(cop3530, cop2510).
prereq(cop4020, cop3530).
prereq(cda3100, cop2510).

passed(alice, cop2510).
passed(alice, cda3100).

needs(X, Y) :- prereq(X, Y).
needs(X, Y) :- prereq(X, Z), needs(Z, Y).

eligible(S, C) :-
\+ passed(S, C),
\+ (needs(C, P), \+ passed(S, P)).

Read eligible : student has not passed the course, and there is no prerequisite P that the student has not passed.

Discussion: what is declarative here?

  • needs/2 is a clean declarative transitive closure definition

  • eligible/2 mixes declarative intent with operational negation patterns

Reality in industry:

  • Many real rule systems blend declarative rules with evaluation strategy constraints

Industry and wrap-up

Rule engines

Rule engines in industry often look like:

  • Facts: events, attributes, measurements

  • Rules: if conditions then conclusions/actions

Use cases:

  • pricing/discount policies

  • fraud detection heuristics

  • access control decisions

  • alerting logic in observability

Why logic ideas help:

  • business rules change frequently

  • you want rules readable by domain experts

Query languages as declarative programming

SQL-like systems:

  • relational databases

  • distributed query engines

  • graph queries (paths, reachability)

Typical differences vs Prolog:

  • SQL has an optimizer and set semantics

  • Prolog has a fixed evaluation order and backtracking

Both share the declarative idea: describe the result set.

Constraint solvers

Constraint solvers appear in:

  • scheduling (airlines, exams, staff)

  • routing and resource allocation

  • verification (SAT/SMT solving)

  • configuration solving (packages, dependencies)

Declarative approach:

  • represent unknowns as variables

  • add constraints

  • solver finds assignments

When Prolog-style thinking is a good fit

Good fit:

  • exploring combinations with constraints

  • symbolic reasoning and relations (graphs, rules)

  • quickly prototyping inference logic

Less ideal fit:

  • heavy numeric computing

  • problems needing strict performance predictability without careful tuning

Common compromise:

  • write a small declarative core; integrate with imperative host code

Summary: what to remember

  • Declarative programming describes what, not step-by-step how

  • Prolog programs are Horn clauses: facts + rules

  • Execution is unification + backtracking search (depth-first, left-to-right)

  • Unification finds substitutions; failure triggers backtracking

  • Search order matters: clause order and goal order can affect termination/performance

  • Lists + recursion are core Prolog patterns (member, append, path)

  • Negation-as-failure assumes a closed world; use it carefully with variables

  • Constraints (CLP) prune search and shine in scheduling/allocation problems

  • SQL, rule engines, and constraint solvers are all declarative relatives
