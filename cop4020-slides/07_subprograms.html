Subprograms as Contracts

Contract

A contract is the behavior a caller can rely on without reading the body.

  • Inputs: parameter types and meaning

  • Outputs: return value and meaning

  • Effects: mutation, I/O, global state

  • Errors: how failures are reported (exceptions, codes, results)

  • Timing: sync/async, may run later, may run multiple times

Contract vs signature (definition)

  • Signature: parameter profile + return type (what the header states)

  • Contract: signature plus effects, errors, and timing rules

A “good” contract answers:
- What does this compute or do?
- What assumptions must hold at the call site?
- What can change in the outside world?
- How do I handle failure?
- When does the result become available?

Contract example (async + errors + effects)

type User = { id: string; name: string };

async function fetchUser(id: string): Promise<User> {
  const r = await fetch("/api/users/" + id);
  if (!r.ok) throw new Error("http " + r.status);
  return (await r.json()) as User;
}

  • Effects: network I/O

  • Errors: promise rejection (exception inside async)

  • Timing: completes later

Practice: contract reading

What important contract details are missing from this interface?

declare function writeFile(path: string, data: Uint8Array): void;

  • Overwrite vs append?

  • Possible errors and signaling mechanism?

  • Blocking vs non-blocking?

  • Atomicity: could it partially write?

  • Permissions / encoding / path rules?

Takeaway

  • When control flow or errors cross boundaries (callbacks/async), contracts must include timing + error rules.

  • When mutation is possible, contracts should state what can be modified.

Calls at Runtime

Abstract machine view of a call

  • Evaluate argument expressions (order may matter)

  • Bind parameter names to argument values/locations

  • Execute the body using those bindings

  • Return (or raise error)

Next: what “bindings you can use” means (environment), then how runtimes implement it (frames).

Local referencing environment (definition)

The referencing environment is the collection of all bindings a subprogram can use while it runs.

  • Formal parameters

  • Local variables

  • Nonlocals captured from surrounding scopes (if nested functions exist)

PL idea: this answers “what names are in scope with meaning at runtime?”

How is the environment represented at runtime?

  • Most local bindings live in the activation record for the call

  • The runtime also needs a way to find the caller and (sometimes) nonlocals

Common links (conceptual):
- Dynamic link: points to caller’s frame (return/unwind support)
- Static link or environment pointer: supports nonlocal access (nested scopes)
- Closure environment: heap-allocated captured bindings that outlive the call

Activation record (stack frame) intuition

An activation record (also called a stack frame) is the runtime data structure that represents one active call of a subprogram.

Typical frame contents (varies by runtime):
- return address
- parameters (values or references)
- locals and temporaries
- bookkeeping (saved registers, debug info)

  • Frames enable recursion: each call gets fresh locals/parameters.

  • Returning normally pops the frame; exceptions may unwind multiple frames.

Call stack model

Top of stack = most recent call.

Calling a function:
- push a new frame
- jump to callee code

Returning:
- restore caller context
- pop the frame

Lifetime of stack-allocated locals is “until return” unless a closure forces retention elsewhere.

Example: c_stack_frames.c

Nested calls create nested frames

function f(x: number): number { return g(x + 1) + 10; }
function g(y: number): number { return y * 2; }
console.log(f(3));
Conceptual call stack (top is most recent):
frame for g(y=4)
frame for f(x=3)
frame for main

Now the “environment” idea is concrete: each frame contributes bindings.

Recursion relies on fresh bindings per call

function fact(n: number): number {
  if (n === 0) return 1;
  return n * fact(n - 1);
}

  • Each call has its own n binding (different frame slot)

  • Space cost is maximum depth of frames (unless optimized)

Activation records across runtimes

  • C/C++: stack frames are central; pointers/references expose low-level effects

  • JVM/.NET: still have call stacks, but allocation/GC/exceptions are runtime-managed

  • Python/JS: frames exist conceptually; VM/runtime manages details

  • Functional languages: tail-call optimization (when supported) can change stack growth

PL takeaway: the abstract machine model stays the same even when implementations differ.

Parameters

Two separate issues (don’t mix them)

  • Association: how arguments match parameters (position, name, defaults, varargs)

  • Passing method: what is transmitted (value, reference, copy-in/out, etc.)

A third issue interacts with both: argument evaluation order (when side effects exist).

parameter, argument, arity, profile

  • Parameter (formal): named input in the subprogram definition

  • Argument (actual): expression/value provided at the call site

  • Arity: number of parameters a subprogram expects

  • Parameter profile: the full signature shape (types, order, count)

Parameter association mechanisms

  • Positional association: match by position (C/C++, Java, JS default)

  • Keyword association: match by name (Python, Swift, Kotlin; JS often uses options objects)

  • Defaults: omitted arguments get default values (Python, JS, C++; Java via overloads, etc.)

  • Variable parameters: varargs/rest (*args, params, ...)

JS/TS often simulates keyword arguments with a record (“options object”).

Parameter modes (intent)

  • In: data flows into the subprogram

  • Out: data is produced for the caller

  • InOut: bidirectional

Modes describe intent; concrete languages implement them with specific passing methods.

Out parameters (example idea)

void Fixer(out int x, out int y) {
  x = 17;
  y = 35;
}
// Fixer(out a, out b);

Caller provides locations; callee assigns outputs; values are “received” by the caller.

Four classic parameter passing modes (formal)

  • Pass-by-value: callee receives a copy of the argument value
  • Pass-by-result: callee writes an output; value copied back to caller at return
  • Pass-by-reference: callee parameter aliases the caller variable slot (assignment updates caller)
  • Pass-by-value-result (copy-in/copy-out): copy in at call, copy out at return (differs from reference when aliasing exists)

Key test: “Does the parameter name become an alias for the caller’s variable location?”

Note: Many modern OO languages are still pass-by-value, but the values are often object references. That produces the call-by-sharing effect.

Aliasing: two different things can be shared

  • Aliasing = two names can refer to the same thing
A) Variable aliasing: two names refer to the same VARIABLE location (slot)
B) Object aliasing: two names reach the same HEAP object
  • Pass-by-reference creates (A) (and often also (B) if the slot holds a reference)
  • Call-by-sharing creates (B) without (A)

Call-by-sharing (pass-by-sharing): what it really means

Call-by-sharing is an effect description: the callee receives a copy of a reference (handle) to an object.

  • Caller & callee can reach the same object (object aliasing)
  • But the callee parameter does not alias the caller’s variable slot (no variable aliasing)

Formally: this is usually pass-by-value, where the “value” is a reference.

Common in: JS/TS objects, Python objects, Java objects, Ruby objects, C# reference types.

Call-by-sharing: reassignment vs mutation

  • Reassigning the parameter changes only the callee’s local binding (caller variable unchanged)
  • Mutating the shared object is visible to the caller
function rebind(obj: { v: number }) { obj = { v: 99 }; }   // local only
function mutate(obj: { v: number }) { obj.v = 99; }        // shared object

const a = { v: 1 };
rebind(a);  console.log(a.v); // 1   (caller variable not changed)
mutate(a);  console.log(a.v); // 99  (shared object mutated)

Takeaway: Objects are shared; variable bindings are local.

Pass-by-reference vs call-by-sharing (one-line test)

  • Pass-by-reference: parameter aliases caller variable slot ⇒ assigning to parameter updates caller variable
  • Call-by-sharing: parameter gets a copied reference value ⇒ assigning to parameter does NOT update caller variable
Reference:   param is another NAME for caller slot  (variable aliasing)
Sharing:     param is a local copy of a handle       (object aliasing only)
  • Java / Python / JS: pass-by-value (values are often references) ⇒ call-by-sharing effect
  • C++ / C# (ref/out) / Pascal (var): can do true pass-by-reference (variable aliasing)

Practice: predict the output

Assume pass-by-sharing like JS/TS/Python objects.

function change(n: number, obj: { v: number }): void {
  n = n + 100;
  obj.v = obj.v + 100;
}
let a = 1;
let b = { v: 1 };
change(a, b);
console.log(a);
console.log(b.v);

Practice answer (with reasoning)

  • a stays 1 because numbers are passed as values (no shared object to mutate)

  • b.v becomes 101 because b and obj refer to the same object

Pass-by-reference (contrast)

If parameters alias caller variables, reassignment updates the caller’s variable.

void reassign(int& x) { x = 99; }  // caller changes

Reference passing is powerful, but increases aliasing risk.

example: cpp_param_passing.cpp

Implementation tradeoffs

  • Copying (by-value) is simple but expensive for large data

  • Referencing is efficient but increases aliasing risk

  • Mitigations: immutability, read-only types, const/ref qualifiers, defensive copying

Argument evaluation order (observable with side effects)

If argument expressions mutate state, order becomes part of the language spec (or unspecified behavior).

let i = 0;
function next(): number { i++; return i; }

function f(a: number, b: number) { console.log(a, b); }
f(next(), next());

  • Left-to-right prints 1 2

  • Right-to-left prints 2 1

Dynamic Invocation

Dynamic invocation (definition)

Dynamic invocation means selecting which subprogram to call at runtime.

  • Functions as values (JS/TS, Python)

  • Function pointers (C/C++)

  • Delegates (C#)

  • Interfaces + lambdas + method references (Java)

  • Reflection-based invocation (some Java/C# APIs)

“Call target chosen at runtime” changes typing and environment questions.

Dynamic invocation mechanisms across languages

  • C: function pointers

  • C++: function objects, lambdas, virtual dispatch (runtime method selection)

  • Java: interfaces + lambdas; reflection for late-bound calls

  • C#: delegates; reflection

  • Python/JS: first-class functions; closures; dictionaries/objects often store callbacks

Runtime-selected call targets force you to discuss typing and environment binding.

first-class and higher-order

  • First-class functions: functions can be treated like values

  • Store them, pass them, return them, and put them in data structures

  • Higher-order function: takes a function as input, or returns a function

const f = (x: number) => x + 1;        // store a function value
function apply(x: number, g: (n: number) => number) {
  return g(x);                          // g is a function parameter
}

Example: ts_first_class_apply.ts

Relationship

  • First-class is a language feature (what values are allowed to be)

  • Higher-order is a programming pattern enabled by that feature

  • Higher-order APIs move control flow into libraries (inversion of control)

First-class functions  =>  can pass behavior as data
Passing behavior        =>  callbacks, higher-order libraries, frameworks

Higher-order function example

type Predicate<T> = (x: T) => boolean;

function countWhere<T>(xs: T[], p: Predicate<T>): number {
  let c = 0;
  for (const x of xs) if (p(x)) c++;
  return c;
}

console.log(countWhere([1, 2, 3, 4], x => x % 2 === 0));

p is behavior supplied by the caller; the library controls when it runs.

Key terms: callback and inversion of control

  • Callback: a function you pass to someone else to be invoked later (or multiple times)

  • Inversion of control: the library/framework decides when your code runs

Timing + error signaling become part of the contract.

Practice: what runs, and when?

function register(handler: () => void): void {
  setTimeout(handler, 0);
}

console.log("A");
register(() => console.log("B"));
console.log("C");

  • What prints first?

  • Which line makes timing part of the contract?

Practice answers

  • Print order: A, C, then B

  • setTimeout schedules the callback to run later

Passing subprograms as parameters

  • This is a common form of dynamic invocation

  • Main challenges: type checking and referencing environments

Referencing environment choice (binding strategy)

  • Deep binding: uses environment at function creation time (closures; most common)

  • Shallow binding: uses environment at call time

  • Ad hoc binding: language-specific special rules

This is a runtime design choice about which environment a passed subprogram uses.

Example: java_effective_final.java, py_deep_vs_shallow.py

Mini example (why deep vs shallow matters)

function makeAdder(x: number) {
  return (y: number) => x + y; // closure captures x
}

const add10 = makeAdder(10);
console.log(add10(5));

  • Deep binding: x is 10 (captured at creation)

  • Shallow binding: x would come from caller’s environment (very different)

Errors and Timing Boundaries

Error signaling mechanisms (contract choices)

  • Throw/exception: non-local control transfer (caller must catch/handle)

  • Return code / sentinel value: caller checks explicitly

  • Result object: success/failure visible in the type

  • Async errors: delivered later (callback error parameter, or promise rejection)

Result object pattern (makes failure explicit)

type ParseResult =
  | { ok: true; value: number }
  | { ok: false; error: string };

function parseIntSafe(s: string): ParseResult {
  const n = Number.parseInt(s, 10);
  if (Number.isNaN(n)) return { ok: false, error: "not an int" };
  return { ok: true, value: n };
}

Contract: caller must handle both branches; failure is not “hidden”.

Async as a contract shape

  • If the return type is a Promise<T>, the result arrives later.

  • Errors arrive later too (promise rejection).

  • The caller’s job is to handle both success and failure.

type User = { id: string; name: string };

async function fetchUser(id: string): Promise<User> {
  const r = await fetch("/api/users/" + id);
  if (!r.ok) throw new Error("http " + r.status);
  return (await r.json()) as User;
}

We study how “later” is scheduled (event loop, tasks, etc.) in Module 11.

Coroutines (Preview)

  • Very untypical subprograms

  • Multiple entry points

  • Symmetric control transfer

  • Quasi-concurrent execution

Key idea: a coroutine can suspend and later resume without “returning for good”.

def counter():
  i = 0
  while True:
    yield i
    i += 1

c = counter()
print(next(c))  # 0
print(next(c))  # 1

Coroutines and generators across languages

  • Python: generators (yield) and async/await build on coroutine ideas

  • C#: iterators (yield return) and async state machines

  • Kotlin: coroutines are a first-class design feature

  • Lua: explicit coroutine primitives (coroutine.yield/resume)

  • Rust: async/await uses futures + an executor

“Suspend and resume” is the unifying control abstraction.

Closures in Practice

Bridge

  • Deep binding (closures) is the most common strategy for passed functions

  • Here we focus on real-world issues: timing and retention

  • Stale state: callback observes an older snapshot than intended

  • Retention: captured objects stay alive while the closure is reachable

Stale state: snapshot vs read-latest

Callbacks often run later. What state do they observe?

let state = 0;
function register(handler: () => void): void {
  setTimeout(handler, 0);
}
function render() {
  const snapshot = state;
  register(() => console.log("snapshot", snapshot, "state", state));
}
render();
state = 10;

Think: which variables are captured as a snapshot vs read at callback time?

Fix: read state at callback time

function renderFixed() {
  register(() => console.log("state", state));
}

  • Now the callback reads state when it runs, not when it was registered.

Retention: long-lived handlers keep data alive

  • If an event system stores your handler, captured objects can live a long time

  • Mitigation: capture only what you need; unregister handlers when done

function makeHandler(big: number[]) {
  return () => console.log(big.length);
}

const big = new Array(1_000_000).fill(0);
const handler = makeHandler(big);

// If handler is stored globally, big stays alive too.

Patterns enabled by closures

  • Memoization (private cache)

  • Debounce (private timer)

  • Dependency injection (capture dependencies)

Closures are a way to package behavior + private state.

Pattern: memoization

function memoize1<A, R>(f: (a: A) => R): (a: A) => R {
  const cache = new Map<A, R>();
  return (a: A) => {
    if (cache.has(a)) return cache.get(a)!;
    const r = f(a);
    cache.set(a, r);
    return r;
  };
}

Contract note: cache changes effects (memory) and timing (later calls faster).

Pattern: debounce

function debounce(fn: () => void, delayMs: number): () => void {
  let timer: ReturnType<typeof setTimeout> | undefined;
  return () => {
    if (timer !== undefined) clearTimeout(timer);
    timer = setTimeout(() => fn(), delayMs);
  };
}

Contract note: the callback runs later; multiple calls collapse into one execution.

Pattern: dependency injection

type Logger = { log: (msg: string) => void };

function makeGreeter(logger: Logger): (name: string) => void {
  return (name: string) => logger.log("hello " + name);
}

Passing dependencies as values makes behavior configurable and testable.

Rule of thumb

  • Use closures for configuration and private state

  • Be careful capturing large objects or stale snapshots

  • Unregister handlers to reduce retention
